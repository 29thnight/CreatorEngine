# 새 셰이더 GPU 준비 계측과 PSO 캐시 개선

## 결과

Debug 에디터를 재빌드하고 CreatorRobot과 Aria를 각각 빈 엔진 캐시 및 캐시 재실행 조건에서 실제 콘텐츠 브라우저에서 씬으로 드래그했다. 준비 중인 PSO의 반복 확인이 신규 접수 예산을 소모하는 문제를 수정하고, indexed·mesh·reconstruction 준비를 겹쳐 진행하도록 변경했다. 종료 시 저장되지 않던 네이티브 PSO 라이브러리도 저장하도록 연결했다.

**직전 새 셰이더 첫 실행의 추가 4~5초는 이번 수정 전 계측에서도 재현되지 않았다. 따라서 그 지연의 원인을 확정하거나 전부 해결했다고 판단할 수 없다.** 이번 수정 전 Aria의 CPU 적용 이후 원본 렌더 제출은 1.234초, 수정 후 0.897초였다. Robot은 별도 빈 캐시 반복 기준 1.216 → 1.253초로 줄지 않았다. 재실행에서 그래픽 PSO의 디스크 라이브러리 적중은 확인했지만 전체 로딩 시간 개선은 작다.

여기서 GPU 준비는 CPU 재질 적용부터 원본 재질 draw 제출까지의 벽시계 구간이다. GPU 실행 시간이나 최초 Present 시간을 의미하지 않는다.

## 계측 조건

직접 실행한 Debug 실행 파일에 디버거를 붙이지 않았다. DX12 Debug Layer 사용, GPU validation 미사용이다. UI 동작은 computer-use로 실제 모델 타일을 드래그하고 Hierarchy 선택 및 기즈모 이동을 수행했다. console은 로그 수집과 정상 종료에만 사용했다.

모델별 별도 디렉터리에 LOCALAPPDATA, MaterialPrograms, NativePSO 캐시를 격리했다. 수정 후 빈 캐시 시작 파일 수는 두 모델 모두 0, 재실행 시작 파일 수는 Robot 443개·Aria 389개다. 재실행은 새 프로세스가 첫 실행의 캐시를 읽는다. 기존 사용자 캐시, OS·드라이버 캐시와 모델 import 데이터는 보존했다. 따라서 여기서 빈 캐시는 엔진 캐시가 비었다는 뜻이며, 드라이버가 새 셰이더를 처음 접하는 상태를 보장하지 않는다.

## 네이티브 준비 병목

DX12 graphics PSO에 작업 큐 대기, 라이브러리 조회, CreateGraphicsPipelineState, StorePipeline, 작업 완료 후 owner publication 대기를 분리해서 계측했다. 수정 전 trace 전용 빌드는 기존 접수 정책을 유지했다.

| 수정 전 Aria 빈 캐시 계측 | 값 |
|---|---:|
| CPU 적용 → 원본 제출 | 1.234초 |
| CreateGraphicsPipelineState 최장 | 23.690ms |
| 작업 큐 대기 최장 | 20.263ms |
| 작업 완료 → publication 최장 | 192.395ms |
| graphics native 호출 합계 | 361.254ms |

이 graphics 집계는 시작 준비를 포함한 프로세스 전체다. native 호출 합계에는 병렬 실행이 있으므로 벽시계 지연으로 더해서 해석하지 않는다. 이 실행에서는 단일 graphics native 호출이 수 초 걸린 증거가 없다. mesh 생성도 최장 49.981ms였다. 이전 실행에서 4초 이상 걸린 indexed-ready 구간을 이번 데이터로 드라이버 내부 컴파일이라고 단정하지 않는다.

코드에서 확인한 접수 문제는 다음과 같다. 프레임당 8개 예산을 신규 작업뿐 아니라 이미 Pending인 작업을 다시 확인할 때도 소비했다. 앞선 8개가 계속 Pending이면 뒤의 pass나 다음 재질을 접수할 수 없다. 준비 객체마다 신규 접수 여부를 기억해 처음 접수할 때만 예산을 소비하고, 이미 접수한 작업은 예산이 소진돼도 완료를 확인한다. 동기 backend는 기존 호출 예산을 유지한다.

또한 모든 indexed PSO를 기다린 뒤 mesh를 시작하던 장벽을 없애, 준비된 indexed별로 mesh 및 reconstruction을 접수한다. mesh가 Pending이어도 reconstruction을 접수하고 이미 확보한 mesh handle을 반복 요청하지 않는다. 모든 필수 PSO가 준비돼야 원본 프로그램을 공개하는 조건은 유지한다. 거부·무효화 후 사라진 program에 접근하지 않도록 검사한다.

이 접수 결함은 통제된 회귀 검사에서 검증했지만, 과거 4~5초 전체를 설명하는 실측 증거는 아니다.

## PSO 캐시 저장과 재실행

실제 renderer의 기존 경로는 라이브러리를 읽었지만 종료 전에 SaveCache를 호출하지 않았다. Shutdown에서 접수를 중단하고 진행 중인 worker를 모두 회수한 뒤 라이브러리를 저장하도록 수정했다. 임시 파일을 완전히 쓴 후 원자적으로 교체하며, 저장 실패로 정상 종료를 실패시키지 않는다. CE_PSO_CACHE_ROOT로 검사용 네이티브 캐시 경로도 격리할 수 있다.

| 드롭 직후부터 집계한 graphics PSO | 빈 캐시 호출 / 적중 | 재실행 호출 / 적중 | 재실행 native 호출 시간 합계 |
|---|---:|---:|---:|
| CreatorRobot | 30 / 0 | 30 / 30 | 0ms |
| Aria | 49 / 0 | 49 / 49 | 0ms |

두 모델 모두 종료 로그 save success=1, 다음 프로세스에서 위 적중을 확인했다. 이 적중은 graphics 라이브러리 조회이며 mesh 적중 횟수까지 계측한 결과는 아니다. 재실행에서도 라이브러리 조회 최장 Robot 26.993ms·Aria 29.258ms 및 mesh 요청 시간이 남는다. PSO 캐시 적중이 전체 준비를 즉시 끝내지는 않는다.

## 실제 드롭 전후 비교

단위는 드롭 요청 이후 초다. 전은 직전 동일 셰이더 버전의 실제 UI 기록, 후는 이번 최종 재빌드 실행이다. 조건별 각 1회이며 통계적으로 안정된 평균 개선율을 주장하지 않는다.

| 조건 | 대체 제출 전 → 후 | CPU 적용 전 → 후 | 원본 제출 전 → 후 | CPU → 원본 전 → 후 |
|---|---:|---:|---:|---:|
| Robot 빈 캐시 | 2.574 → 1.975 | 22.375 → 23.007 | 27.573 → 24.260 | 5.198 → 1.253 |
| Robot 재실행 | 1.992 → 1.975 | 2.277 → 2.261 | 3.443 → 3.427 | 1.166 → 1.166 |
| Aria 빈 캐시 | 1.225 → 1.191 | 19.310 → 19.578 | 23.711 → 20.475 | 4.401 → 0.897 |
| Aria 재실행 | 1.204 → 1.158 | 1.421 → 1.329 | 2.526 → 2.365 | 1.105 → 1.037 |

위의 이전 첫 실행 값만으로는 인과관계를 입증할 수 없어, 같은 변경 전 코드의 별도 빈 엔진 캐시 반복도 함께 비교한다.

| 4~5초가 재현되지 않은 변경 전 비교 | CPU 적용 | 원본 제출 | CPU → 원본 |
|---|---:|---:|---:|
| 이전 Robot 별도 빈 캐시 반복 | 21.609 | 22.825 | 1.216 |
| 이전 Aria 별도 빈 캐시 반복 | 19.408 | 20.492 | 1.084 |
| 이번 수정 전 Aria trace 빌드 | 19.308 | 20.543 | 1.234 |

따라서 첫 표의 5.198 → 1.253초 및 4.401 → 0.897초 차이 전체를 이번 코드 효과로 설명할 수 없다. Robot의 빈 캐시 전체 완료는 이전 반복보다 오히려 느리며 CPU 컴파일 변동이 크다. Aria의 이번 수정 전후 비교는 CPU 이후 0.337초 감소, 전체 완료 0.067초 감소다. 공통 셰이더를 드롭 때 다시 컴파일하거나 품질 옵션을 낮추는 변경은 하지 않았다.

이번 빈 캐시 원본 셰이더 컴파일은 Robot 64개·Aria 48개, 재실행은 모두 0개다. 네 실행 모두 드롭 중 공통 컴파일 0개·공통 메모리 적중 48개, 대체 재질 컴파일 0개·패키지 적중 11단계다. 공통 준비는 시작 로딩에서 빈 캐시 약 10.89~10.94초, 재실행 약 0.49~0.53초였다. 빈 캐시의 주된 남은 시간은 여전히 CPU 원본 컴파일이다.
