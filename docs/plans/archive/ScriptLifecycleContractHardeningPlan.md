## 0. 판단과 범위

**Verse 유사 계약이나 DSL이 없어도 현행 구조를 안정적으로 운영할 수 있다.** 틱과 Task를
사용한다는 사실 자체는 결함이 아니다. 다만 실패한 단계의 상태, 취소 중 예외, 완료된 대기의
참조 유지와 재진입은 현재 구현의 문제이며, 미래 언어 도입으로 해결을 미룰 이유가 없다.

| 구분 | 이 문서에서 처리할 것 | 미래 PHASE 24로 남길 것 |
|---|---|---|
| 생명주기 | 성공/실패 단계, 한 번만 정리, disable·DDOL·파괴·리로드 회귀 | 새로운 cold 시작 및 취소 시 본문 비재개 모델로의 이행 |
| 대기·수명 | 현행 `Scope.Delay`의 등록 해제, 취소 예외 격리, 재진입 안전성 | 자체 awaiter·실행기, `Race`, 구조화된 루틴 트리 |
| 스레드·실패 | 게임 스레드 경계와 외부 Task 지원 범위, 실패 처리 일관성 | PrSM과 C# 분석기가 공유하는 효과·중단·수명 카탈로그 |
| 성능 | 기존 틱·스코프의 비용을 분리 측정하고 필요한 항목만 개선 | 생성 PrSM 콘텐츠까지 포함한 실행기·효과 기록 성능 비교 |
| 결정성·트랜잭션 | 현재 보장하지 않는 경계를 명시 | 효과 기록·재생, `Var<T>`와 네이티브 커밋, 언어 계약 검사 |

LC0~LC5와 LC7을 현행 안정화의 필수 검증 범위로 두고, LC6 성능 변경은 측정 결과에 따라
선택한다. 이미 다른 리팩토링에서 해결된 항목은 최신 소스와 회귀 증거로 닫는다. 같은 변경을
두 계획에서 다시 구현하거나, 모든 항목을 한 번에 바꾸지 않는다.

## 1. 현재 생명주기와 실행 순서

### 1.1 소유자와 호출 경로

| 경계 | 현재 구현과 근거 |
|---|---|
| 네이티브 생명주기 구동 | [Scene.cpp](../../../Engine/SceneRuntime/Scene.cpp)의 `DrainPendingLifecycle`(2543행)이 초기화·씬 진입·시뮬레이션 시작을 구동한다 |
| 관리 인스턴스 연결 | [ScriptComponent.cpp](../../../Engine/SceneRuntime/ScriptComponent.cpp)의 `EnsureInstance`, 단계별 훅, `OnUninitializing`이 인스턴스 생성·필드 적용·관리 통지·제거를 연결한다 |
| 관리 단계·틱 목록 | [ScriptRegistry.cs](../../../ScriptCore/ScriptRegistry.cs)의 `DispatchLifecycle`, `ApplyEnabled`, `StartSimulation`, `Flush`가 관리 상태와 틱 멤버십을 관리한다. `Flush`를 별도 초기화 드라이버로 되돌리지 않는다 |
| 프레임 실행 | [RuntimeFrame.cpp](../../../Engine/SceneRuntime/RuntimeFrame.cpp)의 `Runtime::TickSimulationFrame` 호출 순서는 초기화·입력 → 일시 정지 검사 → PrePhysics → 물리/GameLogic → 후처리 → PostPhysics다. 관리 Pre/Post와 `Scope.Delay`를 고정 시간 스텝이라고 간주하지 않는다 |
| 대기 | [SimulationScope.cs](../../../ScriptCore/SimulationScope.cs)의 `Delay`가 Task를 만들고, 관리 PrePhysics의 `Scope.Tick(dt)`가 완료한다 |
| 파괴·즉시 제거 | `Scene::FlushPendingDestroy`와 [PrefabUtility.cpp](../../../Engine/SceneRuntime/PrefabUtility.cpp)의 즉시 제거 경로가 End → Removing → Uninitializing을 전달한다 |
| 어셈블리 종료 | [ScriptAssemblyLoader.cs](../../../ScriptCore/ScriptAssemblyLoader.cs)의 `Unload`가 `ScriptRegistry.Clear` 이후 팩터리·BT를 정리하고 로드 문맥을 해제한다 |

메서드명과 행 번호는 조사 시점의 탐색 기준이다. 변경 후에는 실제 호출 경로를 기준으로 갱신한다.

### 1.2 보존할 정상 동작

1. 정상 최초 진입은 `OnInitialized` → `OnAddedToScene` → 조건부 `OnEnable` →
   활성 상태에서 `OnBeginSimulation` → `OnSimulate` 시작이다. 초기 비활성 등은 별도 축이다.
2. 현재 `Task OnSimulate()`는 호출 즉시 첫 미완료 await까지 실행한다. 이를 다음 Pump로
   미루는 변경은 이 문서의 결함 수정에 포함하지 않는다.
3. 비활성 컴포넌트는 Pre/Post 훅을 받지 않지만, 이미 시작한 `Scope.Delay`는 계속 흐른다.
   `PrePhysicsTick`에서 `Scope.Tick`이 `Enabled` 검사보다 앞에 있다. 재활성은 루틴 재시작이 아니다.
4. 일시 정지의 시간 진행은 현재 프레임 경계에 따른다. 기존 프레임의 dt 기반 대기를
   벽시계나 미래 fixed simulation clock으로 암묵적으로 바꾸지 않는다.
5. DDOL 이동은 씬 Removing/Added 통지를 주며 인스턴스와 시뮬레이션을 유지한다.
   detach를 파괴·취소로 취급하거나 Initialized/Begin을 다시 전달하지 않는다.
6. 정상 종료에서는 스코프 취소가 `OnEndSimulation`에 앞선다. 현재 Task 취소는 대기 중
   본문을 예외 경로로 풀어 `catch (OperationCanceledException)`와 `finally`가 실행될 수 있다.
7. 구독·자원·관리 인스턴스의 해제는 생명주기의 소유자가 책임진다. 재진입·실패에도 같은
   정리를 중복 호출하지 않고 다른 컴포넌트의 정리를 끝까지 진행한다.

6번은 현재 지원하는 `Scope.Delay` 경로의 보존 대상이다. 외부 Task까지 임의의 시점에
강제 종료하거나 모든 continuation의 완료를 보장한다는 뜻은 아니다(LC5).

## 2. 확인한 문제와 위험 수준

우선순위 P1은 정확성·수명 문제, P2는 성능 또는 후속 개선이다. 실제 콘텐츠에서 발생한
장애, 소스에서 확인한 결함, 강제로 만든 경계 재현을 구분한다.

| 항목 | 관측 근거 | 문제가 되는 조건·영향 | 처리 |
|---|---|---|---|
| 실패와 단계 완료가 섞임 | `DispatchLifecycle` 204행에서 `MarkInitialized` 후 훅 호출. `Invoke`는 예외를 잡지만 성공 여부를 반환하지 않음 — 다만 **잡으면서 `b.Enabled = false`로 그 인스턴스를 끈다**(375~386행) | 초기화가 실패해도 완료 상태가 남는다. 실측(아래 §2.2): 끄기 덕분에 Begin/Simulate는 막히지만 **`OnAddedToScene`과 축소 삼단은 그대로 전달된다** — 그 셋은 `Enabled`를 보지 않는다. 반쪽만 초기화된 인스턴스가 성공한 초기화를 전제한 정리를 받는다 | LC1 · P1 |
| Begin 실패 뒤 루틴 시작 | 272행 `Invoke(OnBeginSimulation)` 다음 273행 `StartSimulation`을 조건 재검사 없이 호출 | 훅 예외로 비활성화돼도, 훅이 스스로 비활성화해도 루틴이 시작된다. 실측에서 가장 날카로운 자리다 — **`Invoke`가 방금 그 인스턴스를 껐는데 바로 다음 줄이 그것을 무시한다** | LC1 · P1 |
| 정리 예외가 종료 절차를 중단 | `SimulationScope.Cancel`의 `_cts.Cancel()` 뒤에 목록 비우기·Dispose·새 토큰 생성이 있음 | 콜백 예외가 뒤 단계를 건너뛰게 함. `TearDown`/`Clear`를 빠져나가 관리 훅·다른 인스턴스·언로드 정리가 누락될 수 있음 | LC2 · P1 |
| 완료된 대기 등록을 유지 | `Delay`의 `token.Register(...)` 반환 등록을 보관/해제하지 않음 | 오래 사는 스코프가 대기를 반복하면 완료된 Task와 캡처가 스코프 취소까지 유지됨 | LC3 · P1 |
| 완료 콜백 중 목록 비우기 | `Tick`(88~99행)은 원본 목록을 **역순 순회**하며 `RemoveAt(i)` **뒤** `TrySetResult`를 부른다. 완료 중 추가되는 연쇄 `Delay`는 이 형태가 이미 막는다(코드 주석이 그 이유를 적고 있다) | 남는 경계는 inline continuation이 `Cancel()`을 불러 `_pending.Clear()`가 도는 경우다. 이후 인덱스 접근이 무효가 된다. 내부 Cancel을 호출한 격리 시험에서 `ArgumentOutOfRangeException`으로 재현 | LC4 · P1 |
| await 경계가 주석에 의존 | `OnSimulate`는 일반 Task이며 외부 await를 타입 수준에서 제한하지 않음 | 외부 완료가 워커에서 이어지면 엔진 API 접근 수명·스레드 규약을 벗어날 수 있음. 현재 게임 스크립트의 실제 오용은 확인하지 않음 | LC5 · P1 |
| 동기/Task 실패 정책 불일치 | 시작 호출의 throw는 disable, 반환 Task의 fault는 `ReportSimulationFault`에서 로그만 기록 | 같은 논리적 실패도 발생 형태에 따라 남는 활성 상태가 다름. 실패 후 틱 반복 등의 정책을 일관되게 정해야 함 | LC5 · P1 |
| 기본 틱·스코프 비용 | Pre/Post가 전체 목록을 순회하며 생존 검사. `Component.Scope`는 즉시 생성. dt 캡처 콜백 존재 | 빈 훅이 많은 콘텐츠·대량 인스턴스에서는 비용이 누적될 여지. 현재 수치만으로 엔진 병목이라고 확정할 수 없음 | LC6 · P2 |
| 관리 회귀의 증거 범위 | 네이티브 `lifecycle_baseline.tsv`에 `ScriptComponent` 행 0건 | 기존 200사건 비교만으로 관리 훅·Task 취소·리로드를 증명할 수 없음. 관리 전용 시험과 오류 주입이 필요 | LC0/LC7 |

LC1은 관리 플래그 한 줄을 이동하는 것만으로 끝나지 않는다. 네이티브 드레인도 호출 전에
초기화/시작 상태를 세우므로, 호출 중 재진입을 막는 상태와 성공한 상태를 구분하고 양쪽을
대조해야 한다. LC2 역시 `CancellationTokenSource.Cancel`이 다른 등록 콜백을 처리하는
것과 호출자 쪽 후속 생명주기가 끝까지 진행하는 것은 별개의 문제다.

### 2.1 조사 중 수행한 격리 시험

2026-09-05 분석 세션에서 실제 `ScriptRegistry.cs`/`SimulationScope.cs`를 연결한 별도
.NET 10.0.11 Release 시험을 사용했다. 레지스트리 주변 Component·Native 등은 대역이며
네이티브 엔진을 실행한 시험이 아니다. 재현 코드는 아직 저장소 회귀 도구로 편입하지 않았다.

**대역이 덮는 경로가 하나 있다.** 2026-09-05 활성 축 배선(`80db6b36`) 이후
`Component.Enabled` setter는 네이티브를 거친다 — `Native.ScriptSetEnabled`로 넘기고,
전달에 실패했을 때만 경고를 남기고 관리 측 국소 폴백(`ScriptRegistry.ApplyEnabled`)으로
내려간다. Native가 대역이면 이 setter는 **항상 폴백만** 타므로, LC5의 "동기 throw →
`b.Enabled = false`" 경로가 대역 시험에서는 실제 경계를 건너지 않는다. LC0에서 §2.1을
저장소 시험으로 옮길 때 이 분기는 대역이 아니라 실엔진 회귀 쪽에 남긴다. 폴백 경고
건수를 함께 세지 않으면 다리가 죽어도 훅·틱이 똑같이 보여 판별력이 0이다
(`verify-lifecycle-axis`의 판정 6이 그 형태다).

| 시험 | 관측 | 해석 범위 |
|---|---|---|
| Pre+Post 1,000프레임, 인스턴스 10/1,000/10,000개 | 각 조건 192,000 B, 합계 **192 B/프레임** | 해당 컴파일러의 프레임 호출당 캡처/델리게이트 비용. **컴포넌트당 192 B가 아니다.** 생존 검사·네이티브 호출·엔진 전체 할당 제외 |
| `Delay(0)` 후 `Tick(1)`, 10,000회 | 약 **304 B/대기 호출** | 해당 시험의 등록·Task·대기 비용. 비동기 본문이나 실제 엔진의 총비용 아님 |
| 완료 Task의 약한 참조, 외부 강한 참조 제거·GC | 스코프 유지 중 생존, Cancel 후 회수 | 완료된 등록이 붙잡는 참조 유지 재현. Task 자체를 모두 즉시 풀링해야 한다는 근거는 아님 |
| 정리 콜백 하나가 throw한 뒤 Cancel | `AggregateException`, 토큰이 취소 상태로 남음 | Cancel 뒤 정리/교체 경로를 건너뛰는 결함 재현 |
| 대기 2개, 완료 continuation에서 내부 Cancel 직접 호출 | `Tick`에서 `ArgumentOutOfRangeException` | 강제 재진입 시험. 실제 게임 스크립트가 이미 이 경로로 충돌했다는 증거는 아님 |

**이관 결과 (2026-09-05 · LC0).** 다섯 행이 어디까지 실엔진으로 옮겨졌는지 갈라
적는다. 옮겨졌다는 것은 **같은 결함을 실엔진 게이트가 붉힐 수 있다**는 뜻이지
같은 수치를 재현했다는 뜻이 아니다.

| 대역 시험 | 이관 상태 | 실엔진 근거 |
|---|---|---|
| 정리 콜백 throw 뒤 Cancel | **이관 완료** | `verify-lifecycle-failure` 판정 E(격리 + 원인 보존). LC2가 고쳤다 |
| 완료 continuation의 내부 Cancel → 순회 파손 | **이관했고 결론이 바뀌었다** | `verify-lifecycle-reentrancy` 판정 P. 저작 표면에서는 그 창이 열리지 않는다(LC4 절 참고) — 대역이 내부 메서드를 직접 불러 만든 조건이었다 |
| 완료 Task의 참조 유지 | **미이관** | 실엔진에서 재려면 유지 메모리 관측 축이 필요하다. LC3의 선행 과제다 |
| Pre+Post 프레임당 192 B | **미이관 · 성능 축** | LC6에서 잰다. 대역 수치는 컴파일러의 캡처 비용이지 엔진 총비용이 아니다 |
| `Delay` 호출당 304 B | **미이관 · 성능 축** | 같음 |

`Enabled` setter 경로는 계획대로 실엔진 쪽에만 남겼다 — 대역에서는 항상 폴백만
타므로 경계를 건너지 않는다. 그 판단이 옳았다는 것이 실측으로 드러났다:
LC5-c 후속에서 나온 결함(거부가 폴백으로 새는 자리)은 **정확히 그 폴백 분기**에
있었고, 대역으로는 원리적으로 볼 수 없었다.

### 2.2 실엔진 실패 픽스처 실측 (2026-09-05)

`verify-lifecycle-failure`가 실엔진에서 받아 적은 결과다. 대역이 아니라 에디터를
띄워 재생까지 몬 것이고, 정상 인스턴스(`Control`)를 같은 실행에 두어 대조했다.

| 픽스처 | 받은 훅 (순서대로) | 트랙 |
|---|---|---|
| 초기화가 던짐 | `OnInitialized` → **`OnDisable`** → `OnAddedToScene` → `OnEndSimulation` → `OnRemovingFromScene` → `OnUninitializing` | LC1 |
| 시작 훅이 던짐 | … `OnEnable` → `OnBeginSimulation` → **`OnDisable`** → **`OnSimulate`** → 축소 삼단 | LC1 |
| 시작 훅에서 자기 비활성화 | … `OnBeginSimulation` → `OnDisable` → **`OnSimulate`** → 축소 삼단 | LC1 |
| 정리 콜백이 던짐 | … `OnDisable` → `OnSimulateCancel` → `cleanup3` → `cleanup1` → **(`OnEndSimulation` 없음)** → `OnRemovingFromScene` → `OnUninitializing` | LC2 |
| 루틴이 첫 await 전 던짐 | … `OnSimulate` → `OnDisable` → **실패 후 틱 0회** → 축소 삼단 | LC5 |
| 루틴이 await 뒤 던짐 | … `OnSimulate` → `OnSimulateResume` → **실패 후 틱 13회** → 축소 삼단 | LC5 |
| 대조군(정상) | 11훅 전부 · 누락 0 | — |

위 표의 LC1 세 줄은 **고침 전** 관측이다. LC1 착지 뒤 같은 픽스처는 이렇게 바뀌었다:

| 픽스처 | 고침 후 |
|---|---|
| 초기화가 던짐 | `OnInitialized` **하나뿐** — 이후 어떤 단계도 오지 않는다 |
| 시작 훅이 던짐 | … `OnBeginSimulation` → `OnDisable` → `OnRemovingFromScene` → `OnUninitializing` (`OnSimulate` 없음, `OnEndSimulation` 없음) |
| 시작 훅에서 자기 비활성화 | … `OnBeginSimulation` → `OnDisable` → **축소 삼단 전부** (`OnSimulate`만 없음) |

뒤 두 줄의 차이가 이 트랙의 계약을 보여 준다 — 던진 시작 훅은 짝을 못 받고,
성공적으로 끝난 뒤 스스로 끈 것은 짝을 받는다.

**`Invoke`의 끄기는 이미 격리 장치다.** 그래서 초기화 실패는 Begin/Simulate까지
가지 못한다 — `OnBeginSimulation` 갈래의 `if (b.Enabled)`가 막는다. 남는 구멍은
그 검사를 하지 않는 자리들이다: `OnAddedToScene`, 그리고 축소 삼단.

**가장 날카로운 것은 시작 훅이다.** 예외든 자기 비활성화든 그 인스턴스는 확실히
꺼진 상태인데, `StartSimulation`이 바로 다음 줄에서 그것을 보지 않고 루틴을
시작한다. LC1의 고침은 여기서 **끄기를 새로 만드는 것이 아니라 이미 일어난 끄기를
읽는 것**이다.

**LC2는 §2의 예상대로 둘로 갈렸다.** 형제 콜백은 2/2 살아남았고(인자 없는
`Cancel()`이 `throwOnFirstException: false`라 전부 돌린 뒤 모아 던진다),
끊긴 것은 **호출자 쪽 후속 생명주기**다 — `Scope.Cancel()`이 `Invoke` 밖이라
그 다음 줄의 `Invoke(OnEndSimulation)`이 통째로 건너뛰어진다. `OnRemovingFromScene`과
`OnUninitializing`은 별개 단계로 오므로, 결과는 "축소 삼단 중 가운데만 빠진" 모양이다.
경계에서 죽지는 않는다 — `Bootstrap.DispatchLifecycle`이 잡아 -1을 돌려준다.

**LC5는 결과 축으로만 갈린다.** 처음에는 판정을 "`OnDisable`이 왔는가"로 짰는데
**두 픽스처가 나란히 초록**이었다. 축소가 `ApplyEnabled(b, false)`로 모든
인스턴스에 `OnDisable`을 주므로(2026-09-05 슬라이스 2), 재생 중에 꺼진 것과 정지가
끈 것이 그 축에서 구분되지 않는다. 훅의 유무가 아니라 **실패 후에도 틱을 받는가**로
바꾸자 동기 0회 · Task 13회로 갈렸다. 이 문서의 고침이 나중 판정의 축을 오염시킬 수
있다는 실례다.

대조군이 온전한 것도 함께 확인됐다 — 한 인스턴스의 예외가 이웃의 생명주기를 끊지
않는다.

미래 계획에 보존한 참조 구현의 **992 B는 루틴 코어·홀더·스코프·대기 1건을 합한 값**이다.
위 304 B와 측정 단위가 다르므로 두 값을 나눠 성능 개선/악화 배수로 쓰지 않는다. 평균 할당은
프레임 시간·GC 정지·유지 메모리의 대체 지표가 아니다.

### LC1 — 단계 성공과 실행 허용 상태 정리 (P1 · LC0 선행)

- `Invoke`의 결과를 호출자가 알 수 있게 하고, 전달 시도·진행 중·성공·실패 격리를 구분한다.
  재진입을 막는 표식을 없애고 단순히 성공 플래그를 뒤로 옮기는 수정은 피한다.
- 초기화 실패한 인스턴스는 이후 정상 단계로 진행하지 않게 한다. 부분 초기화에서 얻은
  자원을 해제하는 경로를 정하되, 성공한 초기화를 전제로 한 훅을 무조건 호출하지 않는다.
- `OnBeginSimulation` 이후 성공 여부·활성·생존 상태를 다시 확인하고 `OnSimulate` 시작을
  결정한다. 훅 안에서 비활성화·파괴를 요청하는 경우와 예외를 분리한다.
  §2.2 실측을 반영하면 이 항목의 최소 형태는 **끄기를 새로 만드는 것이 아니라 이미
  일어난 끄기를 읽는 것**이다 — `Invoke`가 예외에서 이미 `Enabled = false`를 하고,
  자기 비활성화도 같은 상태로 수렴한다. 다만 그 한 줄로 닫았다고 보고하지 않는다:
  예외로 꺼진 것과 스스로 끈 것은 이후 정책(재시도·격리)이 달라야 하므로 상태를
  구분해 남긴다.
- 실패 후 자동 재시도, 비활성 격리, 제거 중 어느 정책을 사용할지 단계별로 확정한다.
  기본 방향은 같은 인스턴스의 무한 재시도를 막는 격리이며 명시적 재생성 경계를 사용한다.
- `Scene::DrainPendingLifecycle`와 관리 상태를 함께 확인한다. 관리 목록에 두 번째
  초기화 스케줄러를 만들지 않는다.

**완료 조건**: 실패한 Initialized/Begin 이후 루틴이 시작되지 않고, 반복 프레임·활성 전환에도
실패 훅이 자동 반복되지 않는다. 부분 초기화 자원과 정상 인스턴스의 대칭 정리가 모두 검증된다.

**완료 (2026-09-05).** `verify-lifecycle-failure`의 판정 A·B·C가 RED에서 GREEN으로
넘어갔고, 기존 게이트 다섯(네이티브·관리 골든, 활성 축, DDOL, 부착 초기화 1회,
단계 미러)은 그대로 초록이다.

**고친 것은 축 하나다.** `Invoke`를 `bool` 반환으로 바꾸고, 여는 훅이 예외 없이
끝났을 때만 서는 표식 셋을 두었다 — `InitializeSucceeded`·`EnterSucceeded`·
`BeginSucceeded`. `IsInitialized`는 그대로 남기고 일을 **재진입 방지 하나로** 좁혔다
(그 값은 훅을 부르기 **전에** 서야 두 번 초기화하지 않는다). 계획서가 경계한
"성공 플래그를 뒤로 옮기는 수정"을 피한 형태다.

**계약: 성공한 훅의 짝만 부른다.**

| 여는 훅 | 닫는 짝 |
|---|---|
| `OnInitialized` | `OnUninitializing` |
| `OnAddedToScene` | `OnRemovingFromScene` |
| `OnBeginSimulation` | `OnEndSimulation` |

`Component.IsInitialized`의 주석이 원래 규정하던 "짝이 맞지 않으면 스크립트가
초기화하지 않은 것을 정리하려 든다"가 이 계약이다. 재던 축이 **불렸는가**여서
던진 초기화도 참이 됐고, 그래서 막으려던 바로 그 상황을 통과시키고 있었다.

**단계가 열리는 것과 루틴이 시작되는 것을 갈랐다.** 처음 구현에서 이 둘을 한
줄로 뭉갰더니 자기 비활성화한 인스턴스가 짝(`OnEndSimulation`)을 못 받았다 —
훅은 성공적으로 끝났는데도. 실패 픽스처 트레이스가 그것을 잡아 줬다. 지금은
`OnBeginSimulation`이 예외 없이 끝나면 `BeginSucceeded`를 세우고, 활성·생존은
`StartSimulation` 여부만 정한다. 실측 대조:

- 시작 훅이 **던진** 인스턴스 → `OnRemovingFromScene`·`OnUninitializing`만, `OnEndSimulation` 없음
- 시작 훅에서 **스스로 끈** 인스턴스 → 축소 삼단 전부, `OnSimulate`만 없음

**정책 결정 (계획서가 LC1에 위임한 것).** 실패한 단계는 **격리**한다 — 자동
재시도 없음. `Invoke`가 이미 인스턴스를 끄고, 성공 표식이 이후 단계를 막는다.
재시도는 명시적 재생성 경계로만 한다(인스펙터의 `RetryInstance`, `script.reload`).

**받아들인 잔여.** 초기화가 자원을 잡은 **뒤에** 던지면 그것을 놓을 엔진 제공
훅이 없다 — `OnUninitializing`을 부르지 않기로 했기 때문이다. 반쪽 상태에서 도는
정리 코드가 새 예외를 만드는 쪽(§2.2에서 LC2가 보여 준 모양)이 더 나쁘다고 판단했다.
스크립트는 `OnInitialized` 안에서 자기 자원을 스스로 다뤄야 한다. 이 판단을
뒤집으려면 "부분 초기화 전용 정리 훅"이 필요하고, 그것은 이 트랙의 범위 밖이다.

### LC2 — 취소·정리 예외 격리와 종료 보장 (P1 · LC0 선행)

- 취소 통지, 사용자 정리 콜백, 대기 목록 해제, 토큰 폐기/재사용 상태 전환을 분리한다.
  하나의 예외가 나머지 등록이나 인스턴스의 정리를 중단하지 않게 한다.
- 최초 원인과 정리 중 발생한 예외를 보존해 보고한다. 예외를 삼키고 성공으로 표시하지 않는다.
- `TearDown`, 네이티브 End 통지, `Clear`가 서로 같은 정리를 반복하지 않게 한다.
  일반 제거·즉시 제거·orphan·리로드 각각에서 사용 가능한 네이티브 핸들의 경계를 확인한다.
- 로드 문맥 해제까지 진행하되 아직 실행 중인 콜백을 안전하게 다룬다. 이미 무효한 핸들로
  엔진 자원을 정리하려는 코드는 해당 경계에서 검출한다.

**완료 조건**: 여러 정리 중 첫/중간/마지막 콜백이 실패해도 필요한 나머지 정리가 한 번씩
실행되고 목록·등록·로드 문맥 참조가 정리된다. 원래 오류와 추가 정리 오류를 구분해 확인한다.

**완료 (2026-09-05).** `verify-lifecycle-failure`의 판정 E가 RED에서 GREEN으로 넘어갔다.

`SimulationScope.Cancel`이 하던 네 가지 일을 갈랐다 — ① 취소 통지, ② 대기 목록
해제, ③ 토큰 폐기, ④ 새 토큰. 예전에는 넷이 한 줄씩 이어져 ①이 던지면 나머지
셋이 통째로 날아갔고, 더 나쁘게는 그 예외가 호출자 경계를 넘어
`Invoke(OnEndSimulation)`을 건너뛰게 했다.

**호출자 쪽에 try/catch를 덧대지 않았다.** `Cancel`이 던지지 않는 것을 계약으로
두고, 그 계약이 깨지면 게이트가 붉어지게 남긴다 — 감싸면 다음 회귀가 조용히
지나간다.

**격리와 삼킴을 갈랐다.** `AggregateException`의 내부 예외를 하나씩 로그로 남기고,
게이트가 **그 건수**를 함께 센다. 이 판정이 없으면 조용히 삼켜도 초록이다 —
변이로 확인했다(로그 줄을 지우니 `E(보고)`만 정확히 빨강, 나머지 E는 초록).

실측(§2.2 갱신): 정리 콜백 다섯 중 둘이 던져도 나머지 셋이 전부 돌고,
`OnEndSimulation`을 포함한 축소 삼단이 온전히 전달된다. 예외 둘은 각각 원인 줄
번호까지 보고된다. 콜백 실행 순서는 규약이 아니므로 판정이 그것에 기대지 않는다 —
양 끝과 가운데를 동시에 덮는 등록 배치를 쓴다.

### LC3 — 완료된 대기의 취소 등록 해제 (P1 · LC0 선행)

- 대기 레코드가 `CancellationTokenRegistration`을 소유하고 정상 완료·취소 경로에서 해제한다.
- 등록 중 즉시 취소, 완료와 취소가 만나는 경계, 콜백 안의 해제/재진입을 검증한다.
  콜백 실행을 기다리는 Dispose 때문에 서로 기다리는 구조를 만들지 않는다.
- 정상 완료된 대기 기록과 캡처는 스코프 전체가 종료될 때까지 붙잡지 않는다. 실제 진행 중인
  대기·정리 등록의 보유와 구분한다. 풀링은 정확성 수정의 선행 조건으로 두지 않는다.

**완료 조건**: 스코프를 살려 둔 채 완료 Task의 외부 참조를 제거하면 회수된다. 반복 대기의
유지 메모리가 누적 완료 횟수에 비례해 증가하지 않으며 완료/취소는 한 번만 관측된다.

**LC3 착지 (2026-09-05).** `verify-lifecycle-retention`의 판정 V가 RED에서 GREEN으로
넘어갔고 게이트를 `run-all.ps1`에 편입했다.

**실측: 완료된 대기 50개 중 50개가 살아 있었다 → 0개.**

`PendingDelay`가 `CancellationTokenRegistration`을 소유하게 하고 `Tick`이 완료
시점에 놓는다. 등록을 **완료보다 먼저** 놓는 것이 순서상 중요하다 — 완료가 먼저면
그 자리에서 이어지는 continuation이 도는 동안 등록이 아직 토큰에 매달려 있고, 그
사이에 취소가 오면 이미 결정된 대기에 `TrySetCanceled`가 한 번 더 날아간다.

계획서가 경고한 교착(`Dispose`가 콜백 실행을 기다린다)은 성립하지 않는다. 그것은
**다른 스레드**가 콜백을 실행 중일 때만 기다리는데, `_pending`은 게임 스레드
전용이고 LC5-b·c가 그것을 런타임 성질로 만들었다. 자기 콜백 안에서 부르는
`Dispose`도 즉시 반환한다.

**관측 축을 메모리 총량으로 잡지 않았다.** `GC.GetTotalMemory`는 엔진 전체의
잡음을 함께 재서 몇십 KB 차이가 묻히고, 묻히지 않게 규모를 키우면 시나리오가
길어진다. 대신 **도달 가능성**을 직접 센다 — 완료된 Task마다 약한 참조를 남기고
강한 참조를 버린 뒤 GC를 돌려 몇 개가 살아남는지 본다. 잡음이 0이고 살아남은
개수가 곧 누수 개수다. 계획서의 완료 조건 문장을 그대로 실행한 셈이다.

픽스처의 기술적 요점은 **강한 참조를 확실히 버리는 것**이다. 지역 변수에 담았다가
`null`을 대입하는 것으로는 부족하다 — Debug 빌드는 지역을 스코프 끝까지 살려 두고
비동기 본문이면 상태 기계 필드에 남는다. 생성과 약한 참조 만들기를 인라인하지
않는 별도 메서드에 넣었고, 같은 이유로 `await`하지 않는다(기다리면 그 Task가 상태
기계에 잡힌다 — `Scope.Tick`이 완료시키므로 재려는 것에는 영향이 없다).

**남는 것**: `RegisterCleanup`/`Subscribe`의 등록은 그대로 둔다. 그것들은 정의상
스코프가 끝날 때까지 살아야 하므로 같은 문제가 아니다 — "실제 진행 중인 대기·정리
등록의 보유와 구분한다"가 그 뜻이다. 풀링은 하지 않았다(정확성 수정의 선행 조건이
아니라고 계획서가 이미 정해 뒀다).

### LC4 — 대기 완료·취소·파괴 재진입 (P1 · LC0 선행, LC2/LC3와 통합 검증)

- 원본 목록에서 준비된 항목을 분리하는 단계와 사용자 continuation을 실행하는 단계를 나눈다.
  구체적인 자료구조는 기존 동작을 보존하는 최소 변경으로 정한다. 현재의 역순 순회와
  `RemoveAt` 선행이 이미 막고 있는 범위(완료 중 추가되는 연쇄 대기)를 다시 고치지 않는다 —
  닫을 것은 순회 중 목록이 **통째로 비워지는** 경우다.
- 정리 중 새 대기 등록, 완료 중 취소/제거, 중복 취소가 기존 순회 인덱스와 다음 세대를
  손상시키지 않게 한다. 완료 후보를 수집한 뒤에도 취소·소유자 상태를 재확인한다.
- 같은 프레임에 추가된 대기를 반복 소모하지 않고, 이미 취소된 세대의 완료 후보가 성공으로
  재개되지 않게 한다. 0초·음수·NaN·무한대 대기의 지원 의미도 명시해 시험한다.
- `RunContinuationsAsynchronously`만 추가해 해결했다고 하지 않는다. 게임 스레드 재개와
  기존 훅 순서를 바꿀 수 있으므로 LC5의 스레드 경계와 함께 판단한다.

**완료 조건**: §2.1 강제 재현이 통과하고, 실제 엔진의 완료→자기 제거/즉시 제거/리로드
경로에서 무효 접근·이중 완료·정리 누락이 없다. disable 중 대기 진행은 보존된다.

**전제 실측 (2026-09-05) — 창이 저작 표면에서 열리지 않는다. LC5-b가 닫았다.**
`verify-lifecycle-reentrancy`를 세워 실엔진에서 쟀다.

§2.1의 창이 열리려면 두 조건이 함께여야 한다. ① 재개가 `Tick` 루프 안에서, 게임
스레드에서 일어난다. ② 그 재개가 `_pending`을 통째로 비운다. **둘 다 지금은
성립하지 않는다.**

①에 대한 실측: 저작 표면에는 컨텍스트를 타거나(재개가 프레임 경계로 · LC5-b)
`ConfigureAwait(false)`로 나가거나(재개가 **스레드 풀**로) 두 길뿐이고, 어느 쪽도
`Tick` 안이 아니다. 게임 스레드 `tid=2`에 대해 재개는 `tid=4`·`6`이었다.

`ConfigureAwait(false)`가 인라인일 것이라 보고 픽스처를 짰는데 실측이 그것을
부정했다. **원인은 LC5-b가 세운 컨텍스트다** — `continueOnCapturedContext:false`인
재개는 현재 컨텍스트가 있으면 인라인될 수 없어 풀로 간다. 변이로 확인했다:
`GameThreadSynchronizationContext.Install()` 한 줄을 걷어내자 두 픽스처의 재개가
곧바로 `tid=2`(게임 스레드, 곧 `Tick` 루프 안)로 돌아왔다. **LC5-b 이전에는 이
창이 실제로 열려 있었다.**

②에 대한 실측: `_pending`을 비우는 것은 `Scope.Cancel()` 하나뿐이고 그 호출부는
`TearDown`과 `DispatchLifecycle(OnEndSimulation)` 둘이다. `ScriptRegistry.Remove`는
큐에 넣기만 하고, `Api_Entity_Destroy`는 엔진의 지연 파괴 규약을 따른다 — 저작
코드에서 동기적으로 닿는 길이 없다.

그러므로 **LC4에서 지금 고칠 것은 없다.** 대신 그 사실을 게이트로 고정했다 —
판정 P(창 부재)는 재개 스레드가 게임 스레드와 같아지면 붉어진다. 언젠가 컨텍스트
정책이 바뀌거나 런타임이 인라인으로 돌아서면 창이 다시 열리고, 그때 위의 "완료
후보 수집과 continuation 실행을 나눈다"를 실제로 해야 한다. 지금의 초록은 "결함이
없다"가 아니라 **"경로가 없다"**는 기록이다.

이 픽스처가 LC5-c의 결함 하나를 물어 왔다 — 아래 LC5 절에 적었다.

**LC7에서 이어받아 닫았다**(2026-09-05, `9b895107`): 0초·음수·NaN·무한대 대기의 지원
의미를 재고 계약으로 적었다. 여기서 넘긴 "무한 같은 프레임 재개 방지"는 그 게이트의
판정 DD가 재는데, 실측 결과 그것을 묶고 있는 것은 LC4가 예상한 대기열 구조가 아니라
**LC5-b의 컨텍스트 마샬링**이었다 — 재개가 Post 되어 다음 프레임 배수에서 돌므로
새 대기는 그 프레임의 Tick 이 이미 지난 뒤에 등록된다.

### LC5 — 외부 await·엔진 스레드·Task 실패 정책 (P1 · LC0 선행)

- 현재 지원하는 `Scope.Delay`와 외부 Task를 구분한다. 현재 게임 스크립트의 await 8곳은
  모두 `Scope.Delay`이므로 외부 I/O 실행기 전체를 이번 수정에 끼워 넣지 않는다.
- 게임 스레드 전용 API의 실제 진입 경계에 검사와 오류 위치를 제공한다. 훅 입구 검사만으로
  중간의 `Task.Run`이나 외부 await 이후 호출까지 보호했다고 하지 않는다.
- 외부 작업을 지원한다면 완료 결과를 엔진 프레임 경계로 넘기고 소유자·취소 세대를 검사한다.
  지원하지 않는 범위는 명시적으로 거부/진단한다. 단순 경고를 완전한 강제 계약이라고 부르지 않는다.
- 직접 throw, 즉시 faulted Task, await 이후 faulted Task의 격리·로그·종료 정책을 맞춘다.
  일반 `async Task`의 첫 await 전 예외도 faulted Task로 반환될 수 있음을 시험한다.
- `ContinueWith(ExecuteSynchronously, TaskScheduler.Default)`는 게임 스레드 보장이 아니다.
  외부 완료 시 워커에서 실행될 수 있으므로 실패 통지와 엔진 상태 변경을 올바른 경계로 보낸다.

**완료 조건**: 지원 경로에서는 스레드·소유자 규약이 유지되고, 금지한 외부 경로는 오류로
드러난다. 세 종류의 실패가 같은 정책을 따르며 취소와 fault를 혼동하지 않는다.

**부분 완료 (2026-09-05) — 실패 정책만.** `verify-lifecycle-failure`의 판정 F가
RED에서 GREEN으로 넘어갔고, 이로써 게이트 여섯 판정이 전부 초록이 되어
`run-all.ps1`에 편입됐다.

세 갈래를 `FaultSimulation` 하나로 모았다:

| 갈래 | 도착 지점 | 예전 정책 | 지금 |
|---|---|---|---|
| 동기 throw (`async` 없음) | `StartSimulation`의 try/catch | 끈다 | 끈다 |
| 즉시 faulted (`async`, 첫 await 전) | `task.IsCompleted` 갈래 | 로그만 | 끈다 |
| 나중 faulted (await 이후) | `ContinueWith` | 로그만 | 끈다 |

**방향은 격리다** — LC1과 같다. 반대(둘 다 로그만)는 본문이 죽은 것을 행동으로
알 수 없게 만들어 더 나쁘다. 되살리는 것은 명시적 재생성 경계로만 한다.

실측: 실패 후 틱이 셋 다 0회(고침 전 0·13·13). 취소는 여전히 정상 종료다 —
`ReportSimulationFault`의 `IsFaulted` 조기 반환이 그것을 지킨다.

게이트는 일관성만이 아니라 **방향**도 못 박는다. 셋이 같기만 하면 통과하게 두면
정책이 반대로 통일돼도 초록이기 때문이다.

**LC5-b 착지 (2026-09-05) — 프레임 경계 마셜링.** 재개 스레드를 닫았다.
`verify-lifecycle-thread`의 판정 H가 RED에서 GREEN으로 넘어갔고 게이트를
`run-all.ps1`에 편입했다.

원인은 관리 측에 `SynchronizationContext`가 **하나도 없었다**는 것이다(실측
`ScriptCore` 전체 0건). `await`의 재개 지점은 포착한 컨텍스트가 정하는데
포착할 것이 없으면 `TaskScheduler.Default` — 스레드 풀 — 로 이어진다.

| 표지 | 고침 전 | 고침 후 |
|---|---|---|
| `begin`(기준·게임 스레드) | tid 2 | tid 2 |
| `delay`(`Scope.Delay` 뒤) | tid 2 | tid 2 |
| `worker`(`Task.Run` 몸통) | tid 4 | tid 4 |
| `external`(`Task.Run` 뒤) | **tid 4** | **tid 2** |

`GameThreadSynchronizationContext`를 게임 스레드에 세우고(`Bootstrap.Initialize`)
`PrePhysicsTick`이 스코프 진행과 `PrePhysics` 배달 **사이**에서 배수한다.
그 자리인 이유는 "`await Scope.Delay`는 프레임의 일이 시작되기 전에 재개된다"가
지켜야 할 순서이기 때문이다. 대신 재개가 이제 **모든** `PrePhysics`보다 앞선다 —
예전에는 자기 인스턴스의 것보다만 앞섰다. 프레임과 스레드는 그대로다.

금지가 아니라 마셜링을 고른 이유: 외부 `await`를 타입으로 막는 것은 저작 표면을
바꾸는 일(PHASE 24의 방향)이고, 여기서 닫아야 하는 것은 지금 코드가 이미 할 수
있는 일의 안전성이다. 완료를 프레임 경계로 넘기면 무엇을 await하든 재개가 게임
스레드에서 일어난다 — 규약이 저작 규율이 아니라 런타임 성질이 된다.

`Send`는 워커에서 오면 **거부한다**(`NotSupportedException`). 규약대로 막으면
게임 스레드와 서로를 기다려 프레임이 멈추고, 조용히 비동기로 바꿔 치면 `Send`가
약속한 "돌아올 때는 끝나 있다"가 깨져 더 나쁜 자리에서 드러난다.

**변이 둘로 확인했다.**

- 판정 I(워커 실재)는 태어날 때부터 초록이라 존재 이유를 시험했다. 외부 경계를
  넘지 않게 픽스처를 바꾸자 **H는 초록인 채 I만 붉었다** — 정확히 그 거짓 초록을
  잡으라고 둔 판정이다.
- **판정 G의 근거는 틀렸다.** 게이트 주석에 "`RunContinuationsAsynchronously`를
  붙이면 G가 붉어진다"고 적었는데 실제로는 초록이었다. 컨텍스트가 재개를 어차피
  게임 스레드로 되돌리기 때문이다. 그 변이가 깨는 것은 스레드가 아니라 **시점**
  (재개가 그 프레임의 배수를 놓친다)이고, 붉어진 것은 `verify-lifecycle-baseline`의
  관리 축이었다(ScriptHostB의 `SimulateStart`·`SimulateResume` 소실). 주석을
  실측대로 고쳤다.

`ScriptRegistry.Clear`(어셈블리 리로드)는 남은 재개를 버리고 건수를 남긴다.
그 시점에는 스코프가 이미 취소됐으므로 이어 봐야 사라진 객체를 만진다. 다만
0이 아니면 그만큼의 `async` 상태 기계가 완료되지 않은 채 끊긴 것이고, 그것은
LC3(완료 대기의 참조 유지)에서 다시 볼 자리다.

**LC5-c 착지 (2026-09-05) — 진입 경계.** `verify-lifecycle-thread`의 판정 J·K가
RED에서 GREEN으로 넘어갔고, 정적 게이트 `check-native-thread-guard`를 새로 세워
`run-all.ps1`에 편입했다.

마셜링이 닫는 것은 `await` **뒤**다. `Task.Run`의 **몸통 안**은 재개가 아니라
워커 그 자체라 컨텍스트가 원리적으로 닿지 못한다. 실측:

| | `alive` | `name` |
|---|---|---|
| 게임 스레드(tid 2) | True | `WorkerCall` |
| 워커(tid 4) · 고침 전 | **True** | **`WorkerCall`** |
| 워커(tid 4) · 고침 후 | False | (빈 값) |

`Native`의 정적 메서드 **206개**가 실제 진입 경계다(계획서가 적어 둔 210은
`_api`를 만지지 않는 넷을 함께 센 값이다). 그 206개가 전부 `_ready`를 **정확히
한 번씩** 보고 있어 치환이 기계적이었다. `_ready` → `Entered()`, 원본 필드는
`_bound`로 이름을 바꿔 우회를 눈에 띄게 했다.

**거부를 골랐다.** 통과시키면 게임 스레드가 같은 순간에 고치는 씬 그래프를
워커가 읽고 쓴다 — 결과에 경계가 없다(운이 좋으면 낡은 값, 나쁘면 접근 위반).
거부는 결과가 정해져 있고 기록이 남는다. 결정적으로 **거부가 새 분기를 만들지
않는다** — 모든 메서드는 "표가 아직 없을 때"의 반환값을 이미 정의하고 있고,
거부는 그 길을 그대로 탄다.

거부와 기록을 판정 J·K로 갈랐다(실패 게이트의 판정 E와 같은 이유). 거부만
있고 기록이 없으면 저작자에게는 "왜 갑자기 빈 값이지"만 남는다. 보고는 **API
이름마다 한 번**이라 상한이 표 크기로 묶이면서도 어디가 새는지는 전부 드러난다 —
필요한 정보는 건수가 아니라 어디다. `Log`는 면제한다. 진단이 나가는 통로 자체를
막으면 거부가 조용해진다. `ScriptRegistry.Clear`(리로드)가 보고 기록을 비워
다음 회차에 같은 결함이 다시 드러나게 한다.

**드리프트는 정적 게이트로 막는다.** 206곳을 사람이 지키는 규약은 곧 무너진다 —
새 API에서 검사를 빠뜨려도 컴파일은 되고, 실행 게이트는 자기가 부르는 두 API만
본다. 변이 셋이 각각 자기 축만 붉혔다: ① `Entered()` 제거 → 판정 1, ②
`Entered()`를 부르되 결과를 버리고 `_bound`로 우회 → **판정 1은 초록이고 판정 2만
빨강**(이것이 판정 2의 존재 이유다), ③ `Entered` 안의 스레드 비교 삭제 → 판정 3.

**부수 확인**: 최근 실행 로그 8개(게이트 6종)에서 경계 밖 호출로 거부된 API는
픽스처가 부르는 `GetName`·`IsAlive` 둘뿐이었다. 엔진의 다른 어느 경로도 워커에서
관리 API를 부르고 있지 않다.

`FaultSimulation`의 게임 스레드 가드는 그대로 둔다. 마셜링 이후 지원 경로에서는
닿지 않으므로 이제 진짜 잔여 경로(`ConfigureAwait(false)` 등)만 잡는다.

**후속 정정 (2026-09-05) — "거부가 새 분기를 만들지 않는다"는 한 자리에서 틀렸다.**

LC4 재진입 픽스처가 물어 왔다. `Component.Enabled` setter는 `ScriptSetEnabled`의
거짓을 **전달 실패**(표가 없거나 대상을 못 찾음)로 읽고 관리 측 폴백
`ScriptRegistry.ApplyEnabled`를 탄다. 거부가 일부러 "표가 없을 때"의 길을 타므로
그 둘이 구분되지 않았다.

실측: `await … .ConfigureAwait(false)` 뒤의 `Enabled = false`가 워커에서
`OnDisable` 사용자 훅을 돌리고 있었다. 거부가 막으려던 일의 축소판을 관리 측에
다시 만든 셈이다.

setter가 두 종류를 가르게 고쳤다 — 게임 스레드 밖이면 폴백을 태우지 않고 아무것도
적용하지 않은 채 오류로 남긴다. 나머지 호출부는 전수 확인 결과 값을 읽어 쓰는
자리뿐이라(무효 핸들·`false`가 그대로 흐른다) 보상 분기가 없다. **`Enabled`가
유일했다.**

게이트 축을 한 번 잘못 잡았다. 처음에는 `OnDisable` **건수**로 쟀는데 정지 시점
축소가 모든 인스턴스에 하나씩 주므로 고침 전후 모두 1이었다 — 이유만 달랐다
(고침 전에는 워커가 먼저 꺼 축소 때는 전이가 아니었다). 가르는 것은 **어느
스레드에서 왔는가**뿐이다. 이 세션에서 같은 함정을 두 번째로 밟았다(판정 F).

**남는 것 (LC5에서 닫지 않는다).** 이것은 **관리 측 진입**만 막는다.

- 네이티브가 스스로 다른 스레드에서 관리 코드를 부르는 경로가 생기면 여기서는
  보이지 않는다.
- 거부된 뒤의 저작 코드가 기본값(빈 문자열·False·영벡터)으로 무엇을 하는지까지는
  책임지지 않는다. 로그가 그것을 저작자에게 넘긴다.
- 외부 `await` 자체를 금지하지 않는다. 금지는 저작 표면을 바꾸는 일이라 PHASE 24의
  몫이다.

### LC6 — 기존 틱·스코프 비용의 선택적 개선 (P2 · LC0 기준선, W8과 조정)

- [ScriptSurfacePlan](../ScriptSurfacePlan.md)의 W8과 소유권을 맞춰 빈 훅 호출·오버라이드
  감지·활성 목록 비용을 측정한다. 수명 검사를 없애 얻은 속도를 개선으로 인정하지 않는다.
- **W8의 전제 수치는 낡았으니 착수 전에 다시 잰다.** W8은 "`override void PrePhysics`는
  0건인데 `Component` 파생 42개를 매 프레임 순회한다"를 근거로 삼는데, 2026-09-05
  `GameScripts` 실측은 PrePhysics 1건(`LifecycleAxisProbe`)·PostPhysics 18건·`Component`
  파생 28개다. 세는 범위(`GameScripts`만인지 `ScriptCore` 내장까지인지)도 함께 고정하지
  않으면 두 계획서가 서로 다른 분모로 같은 이득을 주장하게 된다.
- §2.1의 192 B/프레임 캡처 비용, `Scope`의 선생성 비용, 인스턴스별 생존 검사와 네이티브
  경계 비용, 활성 목록 제거 비용을 따로 잰다. 생성기 디스패치 등은 측정 후 선택한다.
- 루틴이 없는 컴포넌트의 스코프 지연 생성은 구독 등 다른 `Scope` 소비도 포함해 검토한다.
  `OnSimulate` 오버라이드가 없다는 이유만으로 스코프 소비가 없다고 가정하지 않는다.
- 동일 기능·프레임 의미·인스턴스 수로 할당, 유지 메모리, 평균/p95/p99 프레임 시간을 비교한다.

**완료 조건**: 채택한 변경의 독립 이득과 회귀가 확인된다. 병목이 아니라면 변경을 보류하고
측정 근거를 남겨도 된다. 이 항목의 성능 이득을 미래 계약/PrSM의 이득으로 계산하지 않는다.

#### 착지 — 측정 후 변경 보류 (2026-09-06)

**결론: 지금 규모에서는 병목이 아니다. 변경을 보류하고 근거를 남긴다.**

##### ① 범위를 못 박았다 — 그리고 W8의 분모가 비용과 무관하다는 것이 드러났다

`GameScripts` 49개 파일 중 **41개가 회귀 픽스처**이고 저작 코퍼스는 8개다. 이 트랙이
게이트를 세우면서 픽스처를 41개까지 늘렸으므로, 파일 수를 그대로 세면 분모가 부풀려진다.

| 세는 범위 | Component 파생 | PrePhysics override | PostPhysics override |
|---|---|---|---|
| `GameScripts` 전체 | 47 | 2 | 25 |
| 저작 코퍼스만(픽스처 제외) | 8 | **0** | 7 |
| `ScriptCore` 내장 | 1 | 0 | 0 |

W8의 "`override void PrePhysics`는 0건"은 **저작 코퍼스 기준으로는 맞다**. 2026-09-05에
이 문서가 "PrePhysics 1건"이라 적은 것은 픽스처(`LifecycleAxisProbe`)를 포함해 센 값이니
정정한다.

그런데 더 근본적인 문제가 있다. **프레임 비용은 타입 수가 아니라 런타임 인스턴스 수가
정한다.** 파생 타입이 몇 개든 씬에 붙지 않으면 순회 비용은 0이다. 실측:

- 저작 씬 16개 중 스크립트가 붙은 것은 3개, 각각 `ScriptComponent` 2개
- `Lifecycle3D` 재생 중 `script.status` → **활성 스크립트 1개**

즉 W8이 없애려는 "빈 가상 호출"의 실제 규모는 **프레임당 1회**다.

##### ② LC5-c 진입 검사의 비용을 쟀다 — 분해능 아래다

206곳에 넣고 한 번도 재지 않았던 것이라 여기서 잰다. Release · 호출 100만 × 표본 15
([measure-entry-guard-cost.ps1](../../../Tools/regression/measure-entry-guard-cost.ps1)):

| | 중앙값 | 범위 |
|---|---|---|
| 검사 있음 | 10.588 ns | 8.64 ~ 13.10 |
| 검사 없음(`Entered`의 TLS 비교 제거) | 9.648 ns | 8.03 ~ 13.02 |

두 분포가 거의 완전히 겹친다. 중앙값 차이 0.94 ns 는 표본 흔들림(±2.5 ns)보다 작다.
**검사의 몫은 이 하네스로 분리되지 않고, 상한이 ~1 ns/호출이라는 것까지가 말할 수 있는

결론이다.

정작 비싼 것은 검사가 아니라 **경계 크로싱**이다 — 엔진 API 호출 ~10 ns 대 관리 필드
읽기 0.3 ns, 30배. 검사는 그 10 ns 의 10% 안쪽이다.

LC7-b가 `SimulationScope.Tick`에 넣은 프레임 번호 읽기도 같은 규모다. 대기 목록이 비면
건너뛰므로 활성 1개 기준 프레임당 최대 1회 — 10 ns.

##### ③ 남긴 것과 다시 재야 할 때

측정은 **판정이 아니라 도구**로 남겼다(`verify-` 가 아니라 `measure-`). 회귀 세트에는
넣지 않는다 — 흔들림이 ±25% 라 임계값을 걸면 거짓 실패가 난다.

다시 재야 할 조건: **활성 스크립트 인스턴스가 수백 개 규모가 될 때.** 지금 결론은 "빈
훅 호출이 프레임당 1회"라는 사실에 전적으로 기대고 있고, 그 수가 커지면 결론이 뒤집힌다.
`script.status` 의 활성 스크립트 수가 그 임계를 재는 값싼 지표다.

§2.1의 192 B/프레임 캡처 비용, `Scope` 선생성 비용, 활성 목록 제거 비용은 **재지 않았다**.
위 ①이 "순회 대상이 1개"임을 보인 이상 그것들의 상한도 같은 규모라, 지금 재면 전부
분해능 아래로 나올 것이 예상되기 때문이다. 인스턴스 수가 늘어난 뒤에 함께 잰다.

### LC7 — 실제 엔진 통합 회귀와 종료 판정 (P1 · 필수 트랙 통합)

## 4. 적용 순서와 미래 계획에 넘길 결정

LC0으로 기준선을 고정한 뒤 LC1, LC2/LC3/LC4, LC5를 빌드 가능한 단위로 나눈다.
LC2~LC4는 같은 스코프를 수정하므로 각 슬라이스 후 결합 회귀를 실행한다. LC6은 별도
측정·변경으로 두고, LC7로 전체를 닫는다. 일정은 현재 리팩토링과 담당 범위를 맞춰 산정한다.

아래는 **미래 계약 도입 전 확정할 의미 차이**다. 현행 결함 수정에 새 의미를 몰래 섞지 않는다.

| 미래 결정 | 현재 기준과 이행 영향 |
|---|---|
| cold 시작 | 현재 Begin 직후 실행되는 첫 본문이 다음 Pump로 이동하면 컴포넌트 간 관측 순서·첫 물리 프레임이 달라진다 |
| 취소 시 본문 비재개 | 현재 두 `OnSimulate`가 사용하는 취소 catch 경로를 `Defer`/`Own`으로 이관하고 같은 정리 결과를 증명해야 한다 |
| 클럭과 준비된 루틴 순서 | 현재 프레임 dt와 미래 fixed tick의 차이, Wait(0), 동시 완료·Race 동률·프레임 예산을 명시해야 한다 |
| 네이티브 파괴 전 정리 | 종료 요청→현재 실행 구간 종료→정리→네이티브 해제의 경계를 일반/즉시 제거·리로드 모두에서 검증해야 한다 |
| 기록·재생의 적용 범위 | 입력·물리 조회·초기 상태·BT `Random.Shared`까지 다루지 않으면 효과 테이프만으로 게임 전체 결정성을 보장할 수 없다 |
| 지연 쓰기·롤백 | 직접 Transform 쓰기를 미루면 즉시 읽기의 값이 달라질 수 있다. read-your-writes, 유효성 검사, 부분 커밋 실패 규약이 필요하다 |
| PrSM 정리·수명 | Unity disable/destroy와 엔진 disable/detach/end/uninitialize를 구분해야 한다. 문법 단축과 런타임 안전성은 각각 검증한다 |

## 5. 계약을 당장 도입하지 않을 때의 남는 한계

LC 안정화를 마치면 현행 틱·Task 방식으로 개발을 계속할 수 있다. 남는 것은 모든 프로젝트가
즉시 겪는 장애가 아니라, 더 강한 계약이 필요한 기능을 추가할 때의 설계·저작 비용이다.

| 선택 | 장점 | 남는 비용·조건 |
|---|---|---|
| 현행 틱·Task + LC 안정화 | 작은 변경 범위, 익숙한 C# 디버깅, 기존 실행 의미 보존, 단순 프레임 연산에 추가 추상화 불필요 | 외부 호출·수명 규칙과 정리 코드를 저작/리뷰에서 관리. 직접 효과를 포함한 일반 코드는 자동 기록·롤백 대상이 아님 |
| 미래 효과 계약 런타임 | 허용 await·효과 실행 지점·취소/정리 소유권을 모으고 기록·대체 지점을 제공 | 실행 의미 이관, 루틴/대기/테이프 비용, 네이티브 커밋 정책과 분석기 유지 비용 |
| 미래 계약 + PrSM 도입 | 반복 훅·대기·구독 정리 코드를 생성하고 의도를 원문에서 검사할 수 있음 | 컴파일러 의미 분석·빌드·소스 맵·인스펙터·리로드까지 유지해야 효율이 실현됨. 원문 감소만으로 런타임 가속은 보장되지 않음 |

롤백 넷코드나 재현 가능한 시뮬레이션이 필요해지는 시점에는 직접 효과 호출의 분류·대체
경계가 필요하다. 그 기능이 필요하기 전에 현재 결함을 안정화하고, 미래 PHASE 24가 착수할
때 실제 저작 규모와 요구 기능으로 전환 범위를 다시 정하는 것이 이번 결정이다.
