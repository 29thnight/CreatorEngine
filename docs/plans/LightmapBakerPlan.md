# 라이트맵 베이커 재작성 (PHASE 4 · 트랙 L)

2026-08-25 신설. 삭제된 DX11 베이커를 실측한 결과 **복원이 아니라 재작성**이 맞다는
결론에서 출발한다. 고칠 지점이 성능만이 아니라 **정확성에도** 있어서 그대로 되살리면
결함까지 함께 온다.

```
정적 지오메트리 → [UV1 언랩] → [아틀라스 패킹] → [BVH] → 직접광 → 블러 → 간접광 → dilate
                      ↑ 없음        ↑ Shelf FF      ↑ median split      ↑ 코루틴 페이싱
```

---

## 0. 왜 이 페이즈인가 — GI가 있어도 라이트맵을 쓴다

현재 이 엔진의 GI 는 **전부 스크린스페이스**다(SSAO·SSGI·SSR·SSS + IBL). 화면 밖을
아는 경로가 하나도 없다 — 프로브도 볼륨도 라이트맵도 없다. 실내 씬에서 카메라 밖
벽면의 간접광은 **구조적으로 계산할 방법이 없다.**

스크린스페이스 GI 의 원리적 한계는 넷이다.

| 못 하는 것 | 결과 |
|---|---|
| 화면 밖 지오메트리의 간접광 | 시야 밖 벽의 반사광이 없다 |
| 카메라 회전 시 일관성 | 시선을 돌리면 조명이 변한다 |
| 시간축 안정성 | 히스토리 누적 → 잔상·노이즈, 디노이징 비용 |
| 원거리 바운스 | 트레이스 거리에 묶인다 |

상용 엔진이 실시간 GI 를 갖고도 라이트맵을 유지하는 이유가 이것이다. **둘은
대체재가 아니라 보완재다** — 라이트맵이 간접광의 본체를 담당하고, 스크린스페이스는
라이트맵 해상도가 못 잡는 접촉 음영을 메꾼다.

세 노선의 비용 비교:

| 노선 | 비용 | 이 엔진의 상태 |
|---|---|---|
| **라이트맵** | 언랩 + 베이커 + UV1 스트림 | 저작 표면 있음 · 삭제된 구현 있음 |
| 프로브/볼륨 | 프로브 배치 + 볼륨 구조 | 전부 신설 |
| 실시간 GI | 매우 큼 | 전부 신설 |

라이트맵이 가장 싸고 절반쯤 깔려 있다.

### 1.2 구조 — 코루틴 프레임 페이싱

`GenerateLightmapCoroutine` 이 `co_yield OnRender()` 로 프레임마다 양보한다.
**활성 yield 30개**(주석 포함 36).

| 위치 | yield 수 |
|---|---|
| 준비 단계 | 4 |
| 메시렌더러당 삼각형 수집 | 1 × 메시 수 |
| 직접광 디스패치 | 1 × 렉트 수 |
| MSAA 블러 | 8 × 라이트맵 수 × 2 |
| 간접광 | 바운스당 다수 |

문제 셋:

1. **베이크 속도가 프레임레이트에 묶인다.** 60fps 면 yield 하나가 16.6ms 다.
   렉트 100 + 라이트맵 4장이면 준비만 500회 yield → **8초가 순수 대기**이고 그동안
   GPU 는 논다.
2. **에디터와 GPU 를 경합한다.** `co_yield OnRender()` 가 렌더 프레임을 그대로
   돌리므로 베이크 디스패치와 에디터 렌더가 같은 큐를 나눠 쓴다.
3. **중단·재개가 코루틴 프레임에 묶인다.** 취소하면 어디까지 했는지 복구할 구조가
   없다.

★ 코루틴의 **의도는 옳았다** — "에디터가 얼어붙지 않게". 수단이 틀렸을 뿐이다.
GPU 작업을 프레임마다 하나씩 던지는 대신 워커에서 연속 기록하고 타임슬라이스로
제어해야 한다(§2.3).

### 1.3 알고리즘 — 여덟 군데

| # | 문제 | 실측/근거 |
|---|---|---|
| ① | **디스패치가 렉트마다 전체 캔버스** | `Dispatch(canvasSize/16, canvasSize/16)` 후 셰이더가 `Offset`/`Size` 밖에서 `return`. `canvasSize=1024`·`rectSize=400` 이면 **유효 스레드 15.6%** — 84% 낭비. 렉트가 작을수록 악화(128²면 98.5% 낭비) |
| ② | **BVH median split + 축 라운드로빈** | `axis = depth % 3`(최장축 아님), `mid = (start+end)/2`(SAH 아님). SAH 대비 트래버설 통상 1.5~2배 |
| ③ | **분할마다 `std::sort` → O(N log²N)** | `nth_element` 면 분할당 O(N) → 전체 O(N log N). **log N 배** |
| ④ | **비교자가 데이터를 쓴다** | `t2.tempColor = {1,0,0}` — `std::sort` 의 `Compare` 는 인자를 수정하면 안 된다(표준 요구 위반) |
| ⑤ | **패킹이 Shelf First-Fit** | 헤더 주석은 `// Guillotine Algorithm` 인데 구현부는 `// Shelf First-Fit`. MaxRects 대비 점유율 통상 10~20%p 낮다 |
| ⑥ | **패킹 정렬이 오름차순** | `return a.h < b.h` — Shelf 계열 표준은 Decreasing Height(큰 것부터) |
| ⑦ | **렉트 크기가 표면적과 무관** | `size = rectSize * lightmapScale` 로 **정사각형 고정**. 거대한 바닥과 작은 소품이 같은 400×400 → 텍셀 밀도 통제 불가 |
| ⑧ | **라이트 루프가 항상 20회** | `for (i = 0; i < MAX_LIGHTS; ++i)` — `lightSize` 가 CB 에 있는데 미사용 |

간접광 커널은 `[numthreads(32,32,1)]` = **1024 스레드/그룹**(API 한계치)이다.
스레드마다 `uint stack[64]` BVH 스택을 들므로 레지스터·스크래치 압박이 크다 —
occupancy 측정 후 8×8 또는 16×16 로 내리는 것을 검토한다.

### 1.4 조용히 틀리는 결함 다섯

| # | 결함 | 증상 |
|---|---|---|
| 1 | **BVH 리프 off-by-one** — 셰이더가 `i <= node.end` 인데 C++ 은 `[start, end)` | 이웃 리프의 삼각형을 잘못 검사. 마지막 리프는 **버퍼 범위 밖** → 가짜 그림자. **직접광·간접광 커널 양쪽에 있다** |
| 2 | **패킹 롤백 `j--; i++;`** | else 분기 직후 발동하면 이미 배치된 렉트를 재배치 → 중복/누락 |
| 3 | **padding 미확보** — `rect.y = nextPoint.h + padding` 인데 shelf 증가는 `maxHeight + padding` | 이웃 차트 블리딩. MSAA 블러를 4회 도는 것이 이 증상을 뭉개고 있을 가능성 |
| 4 | **efficiency 로그** — `useSpace` 가 새 라이트맵에서 리셋 | 로그가 마지막 장만 보고한다 |
| 5 | **바운스마다 텍스처 배열 재생성** — `CreateTexture2D` 가 `indirectCount` 루프 안 | 해제 경로 확인 필요(누수 의심) |

★ 1번은 git 이력의 `7a4f1a79 "SSR, lightmap BVH indice 오류 수정"` 과 같은 자리다 —
한 번 만졌지만 남아 있다.

### 1.5 살릴 것과 버릴 것

| 살릴 것 | 버릴 것 |
|---|---|
| BVH **트래버설** 셰이더 — 스택 기반 + 근거리 우선 정렬로 잘 짜였다 | BVH **빌드** — SAH + `nth_element` 로 재작성 |
| 파이프라인 단계 구성(직접→블러→간접→dilate) | 코루틴 페이싱 → 워커 + 타임슬라이스 |
| `LightMapping` 저작 구조 | 패킹·렉트 산출 → xatlas |

어차피 전면 재작성이 강제된다. 이 코드는 `DirectX11::CSSetShaderResources` 같은
DX11 API 를 직접 부르므로 **DX12 RHI 로는 한 줄도 그대로 오지 않는다.**

## 2. 병렬화 설계

### 2.1 병렬 축 전수

| 축 | 현재 | 가능한 것 | 기대 |
|---|---|---|---|
| **텍셀** | GPU 스레드 — 이미 병렬 | 디스패치를 **렉트 크기로** | 활용률 15.6% → ~100% (**6.4배**) |
| **렉트** | 렉트당 Dispatch 1회 + CB·SRV 재바인딩 | 렉트 표를 StructuredBuffer 로 올리고 **배치 디스패치 1회** | Dispatch N→1, 상태 변경 소멸 |
| **라이트맵 장** | 순차 | async compute 큐로 겹침 | GPU 미포화일 때만 |
| **간접광 샘플** | 텍셀 내부 루프 512회 | 샘플을 여러 디스패치로 쪼개 **누적(progressive)** | 응답성·미리보기·취소 |
| **BVH 빌드** | 단일 스레드 재귀 + `std::sort` | 상위 레벨 순차 + 서브트리 태스크 병렬, 또는 GPU LBVH(Morton+radix sort) | CPU 시간 |
| **삼각형 수집** | 단일 스레드 | 메시별 병렬 후 concat | 소소 |
| **전체 진행** | 프레임당 1스텝 | 워커 스레드 + 전용 큐 | **페이싱 제거** |

### 2.2 ★ 순서 — 낭비 제거가 병렬화보다 먼저다

**84% 낭비를 그대로 두고 병렬화하면 낭비를 병렬로 하는 것이다.**

착수 순서는 이렇게 고정한다.

```
① 디스패치를 렉트 크기로        → 6.4배 (병렬화 아님, 낭비 제거)
② 코루틴 페이싱 제거            → yield 수만큼의 순수 대기 소멸
③ BVH를 SAH + nth_element로     → 트래버설·빌드 양쪽
④ 그다음에 비로소 병렬화 판정
```

①②를 하기 전의 측정치로 병렬화 이득을 추정하면 안 된다. 이 저장소에는 그 전례가
있다 — `encoder-bench` 가 모형만 재고 있었고, 자를 먼저 고치자 결론이 뒤집혔다.
**Release 로만 판정한다**(Debug 는 같은 조건에서 25배 느리고 규모별 개선 방향까지
뒤집는다).

### 2.3 백그라운드 베이킹 — 에디터를 막지 않는다

목표를 정확히 적는다. **"에디터에 영향이 없다"는 상용 엔진도 못 한다.** Unity
Progressive Lightmapper 도 UE5 GPU Lightmass 도 베이크 중 뷰포트가 느려진다 — 같은
GPU 를 나눠 쓰기 때문이다. 달성 가능한 목표는 **non-blocking** 이다.

| 요구 | 뜻 |
|---|---|
| 씬 편집·이동·저장이 계속 된다 | 베이크가 게임 스레드를 잡지 않는다 |
| 뷰포트가 계속 갱신된다 | 느려질 뿐 멈추지 않는다 |
| 진행률이 보이고 취소된다 | 상태가 코루틴 프레임에 숨지 않는다 |
| 편집하면 무효화·재시작 | 밀봉 스냅샷과 무효화 정책 |

현재 코루틴 방식은 이 중 **하나도 제대로 못 한다.** 프레임마다 한 단계씩만 던지므로
GPU 가 놀고, 진행이 프레임레이트에 묶이며, 상태가 코루틴 프레임에 갇힌다.

#### ★ 실측 — 지금 큐가 하나뿐이다

```
CreateCommandQueue(D3D12_COMMAND_LIST_TYPE_DIRECT)   ← 유일
```

`DX12DeviceResources.cpp:296` 의 그래픽스 큐 하나가 전부다. **COMPUTE 큐도 COPY 큐도
없고**, 커맨드 리스트도 전부 `TYPE_DIRECT` 다. `AsyncCompute` 는 코드에 0건이다.
공통 queue/fence 기반은 `RenderGraphDependencySchedulingPlan` RG8에 배치했다.

같은 DIRECT 큐에 베이크를 넣으면 에디터 프레임과 **직렬화**된다 — 베이크 디스패치가
길면 그만큼 프레임이 통째로 밀린다. 백그라운드 베이킹의 1번 전제가 별도 큐다.

#### 필요한 것 셋

| # | 필요 | 현 상태 |
|---|---|---|
| 1 | **별도 COMPUTE 큐** + 큐 간 펜스 | **없음** — 신설 |
| 2 | **GPU 타임슬라이스** — 디스패치를 예산 단위로 분할 | 없음(코루틴은 프레임 단위) |
| 3 | **씬 밀봉 스냅샷** + 무효화 정책 | 인프라 있음 — 프레임 스냅샷 이중 버퍼 게시를 같은 원리로 |

2번을 빼면 큐를 나눠도 소용이 없다. 디스패치 하나가 길면 GPU 가 그동안 점유되고,
**Windows TDR(기본 2초)** 에 걸리면 디바이스가 리셋된다. 렉트 단위·샘플 단위로 쪼개
프레임당 예산(예: 8ms) 안에 넣어야 한다 — 이것이 progressive baking 의 본질이고,
코루틴이 하려던 것과 같지만 **단위가 프레임이 아니라 GPU 시간**이어야 한다.

#### 재사용할 수 있는 것 / 없는 것

`RHIParallelCommandPool` 이 이미 워커 8개 병렬 커맨드 기록을 제공한다(3-15A). 다만
`RunParallel` 이 **join 까지 대기**하는 fork-join 이라 *프레임 안의* 작업용이다.
베이크는 프레임 경계를 넘어 살아야 하므로 **수명 모델이 다르다** — 기록 인프라는
빌리되 스케줄링은 별도로 세운다.

### 2.3-a 스레드 모델

현재 엔진은 Game / CommandBuild / CommandExecute 3스레드 락스텝이다. 베이크는
**에디터 전용 작업**이므로 그 락스텝에 끼워 넣지 않는다.

```
[베이크 워커 스레드]  ─ 커맨드 기록 ─→ [전용 컴퓨트 큐] ─→ GPU
        │                                     │
        └─ 진행률/취소 (원자적 상태)          └─ 프레임당 타임슬라이스 예산
                    ↓
            [Game 스레드] 진행률 UI 만 읽는다
```

- D3D12 는 커맨드 리스트 기록이 스레드 안전하므로 워커에서 기록할 수 있다.
- **프레임당 GPU 예산**(예: 8ms)을 두어 에디터 응답성을 확보한다 — 코루틴이 이루려던
  목적을 더 정밀하게 달성한다.
- 취소·재개는 **단계 경계의 명시적 체크포인트**로 처리한다. 코루틴 프레임에 상태를
  숨기지 않는다.

★ 주의: 베이크 중 씬이 바뀌면 결과가 무의미해진다. 베이크 시작 시 **지오메트리·조명을
밀봉**하고(스냅샷) 그 위에서만 돈다 — 렌더 스레드의 프레임 스냅샷과 같은 원리다.

### 2.4 병렬화가 이득이 아닌 경우

- **async compute** 는 두 큐가 같은 SM 을 나눠 쓰므로, 베이크가 이미 GPU 를 채우면
  오히려 느려진다. `RhiBoundaryPlan` 의 판정 기준을 그대로 적용해 패스별로 잰다.
- **CPU 병렬 BVH** 는 삼각형 수가 적으면 태스크 오버헤드가 이득을 먹는다. 실측 후
  임계 삼각형 수를 정한다.

---

## 3. 설계 결정

### 3.1 UV1 언랩은 xatlas 로

라이트맵은 non-overlapping UV 언랩이 전제인데 **현 자산에 UV1 이 하나도 없다**
(원본 glb 12개 전수 `TEXCOORD_1` 0건). xatlas 는 언랩과 아틀라스 패킹을 함께
해결하므로 §1.3 의 ⑤⑥⑦을 한 번에 닫는다.

이 저장소는 이미 `fastgltf`·`ufbx`·`mikktspace` 를 **원본 무수정**으로 벤더링하는
관행이 있다. 같은 규약을 따른다.

### 3.2 UV1 은 옵셔널 스트림이다

`ModelImportPipelinePlan` 트랙 V3 의 첫 소비자가 이 계획이다. 라이트맵 대상 메시에만
UV1 스트림이 붙는다 — 스킨 캐릭터를 포함한 전 정점에 8B 를 부과하지 않는다.

★ 언랩은 이음매에서 **정점을 쪼개므로 정점 수 자체가 바뀐다.** 즉 기존 uv1 슬롯을
재사용하는 것이 아니라 언랩 단계에서 스트림을 새로 만든다.

### 3.3 텍셀 밀도가 정본이다

렉트 크기는 `표면적 × 텍셀밀도(texels per unit)` 로 산출한다. `lightmapScale` 은
그 위의 배율로 남긴다 — 지금처럼 크기의 유일한 결정자가 되어서는 안 된다.

## 4. 이행 — 슬라이스

### L0. 기준선 — 삭제된 구현 복구·계측

되살려 돌리는 것이 목적이 아니라 **재작성의 정답지를 만드는 것**이 목적이다.

- 삭제분을 참조용으로 뽑아 두고(이 문서 §1 이 그 요약이다) 알고리즘 의도를 확정
- 비교용 씬 확보 — 실내(간접광이 지배적) 1개 이상 필요
- ★ 현 자산에 UV1 이 없으므로 **L1 전에는 실행 자체가 불가능하다**

### L1. UV1 언랩 — xatlas 벤더링

- `ThirdParty/xatlas` 원본 무수정 벤더링
- 임포트 후처리 패스로 편입(`ImportedScene` 트랙) 또는 에디터 오프라인 도구
- 정점 분할 계수 — 손실은 변환 경계에서 계수한다는 성질 유지
- 게이트: 차트 겹침 0 · UV 범위 [0,1] · seam 정점 수 계수

의존: `ModelImportPipelinePlan` V1(속성 기술표)·V3(옵셔널 스트림).

### L2. BVH 재작성 — SAH + `nth_element`

- 최장축 분할 + SAH 비용 함수
- `std::sort` → `nth_element`, 무게중심 사전 계산
- **비교자의 데이터 쓰기 제거**(§1.3 ④)
- ★ **리프 순회 off-by-one 을 양쪽 커널에서 고친다**(§1.4 ①) — 고치기 전에
  현재 동작을 재현하는 검사를 먼저 세워 **변이로 이빨을 증명**한다
- 게이트: 합성 씬에서 해석적 정답(구·평면 교차)과 대조

의존: 없음. **가장 먼저 할 수 있다.**

### L3. 직접광 패스 — DX12 RHI 재작성

- 디스패치를 **렉트 크기로**(§1.3 ①) — 이 슬라이스의 본체
- 렉트 표를 StructuredBuffer 로, 배치 디스패치 1회
- 라이트 루프를 `lightSize` 로(§1.3 ⑧)
- 게이트: 삭제분과 같은 씬에서 픽셀 대조 + 디스패치 스레드 활용률 계측

의존: L1(UV1)·L2(BVH).

### L4. 백그라운드 베이킹 — 에디터를 막지 않는다

이 계획의 사용자 체감 본체다. §2.3 의 셋을 순서대로 세운다.

- **L4-a 별도 COMPUTE 큐 + 큐 간 펜스** — 지금 DIRECT 큐 하나뿐이다.
  큐를 넘나드는 리소스의 상태 전이(COMMON 경유) 규칙을 함께 정한다.
  ★ `RenderGraphDependencySchedulingPlan` RG8의 async compute와 **같은 기반**이므로
  어느 쪽이 먼저 세우든 공통 RHI 계약을 소유하고 다른 쪽이 소비한다 — 두 번 만들지 않는다.
- **L4-b GPU 타임슬라이스** — 디스패치를 렉트·샘플 단위로 쪼개 프레임당 예산
  (예: 8ms) 안에 넣는다. 코루틴 페이싱 제거는 이 단계의 결과다.
  ★ **Windows TDR(기본 2초)** 이 상한이다. 단일 디스패치가 그것을 넘으면 디바이스가
  리셋된다 — 분할은 성능이 아니라 **안전** 요구다.
- **L4-c 씬 밀봉 + 무효화** — 시작 시 지오메트리·조명을 스냅샷으로 밀봉하고,
  편집이 감지되면 무효화·재시작한다. 프레임 스냅샷 이중 버퍼 게시와 같은 원리.
- 진행률·취소·재개를 **명시적 체크포인트**로. 코루틴 프레임에 상태를 숨기지 않는다.

게이트: ① 베이크 중 씬 편집·저장이 되는가 ② 뷰포트 프레임타임이 예산 안에 있는가
③ 취소 후 재개 결과가 무중단 결과와 같은가 ④ 편집 시 무효화가 동작하는가

의존: L3. `RHIParallelCommandPool` 의 기록 인프라는 빌리되 스케줄링은 별도다(§2.3).

### L5. 간접광 — progressive 누적

- 샘플을 분할 디스패치로 쪼개 누적
- `numthreads` occupancy 측정 후 조정(현재 32×32 = 1024)
- 바운스마다 텍스처 재생성 제거(§1.4 ⑤)
- 게이트: 샘플 수 대비 수렴 곡선, 중단·재개 시 동일 결과

의존: L4.

### L6. dilate·seam 처리

- 삭제분에서 주석 처리돼 있던 `DilateLightMap` 복원
- padding 계산 수정(§1.4 ③) — 블러로 뭉개지 말고 원인을 고친다
- 게이트: 차트 경계 블리딩 검사

### L7. 병렬화 판정 — **여기서 비로소 잰다**

§2.2 순서대로 ①②③을 끝낸 뒤 재측정하고, §2.1 의 남은 축(async compute · CPU 병렬
BVH)이 실제로 이득인지 판정한다. **재기 전에 열지 않는다.**

## 5. 완료 기준

- [ ] UV1 언랩이 자산 파이프라인에 있고 차트 겹침 0
- [ ] BVH 리프 순회 off-by-one 이 **양쪽 커널에서** 닫혔고 변이로 증명됐다
- [ ] 디스패치 스레드 활용률이 계측되고 렉트 크기 디스패치로 ~100%
- [ ] 베이크가 프레임레이트와 무관하게 진행된다(코루틴 yield 0)
- [ ] **베이크 중 씬 편집·오브젝트 이동·저장이 된다** — 에디터가 막히지 않는다
- [ ] 베이크 중 뷰포트 프레임타임이 예산 안에 있다(느려지되 멈추지 않는다)
- [ ] **단일 디스패치가 TDR 상한 아래**임이 계측으로 확인됐다
- [ ] 베이크 중 씬을 편집하면 무효화·재시작이 동작한다
- [ ] 취소·재개가 단계 경계에서 동작하고 재개 결과가 무중단 결과와 같다
- [ ] 렉트 크기가 표면적 × 텍셀밀도로 산출된다
- [ ] 실내 씬에서 SSGI 단독 대비 간접광 개선이 스크린샷으로 확인된다
- [ ] **Release 로 측정한** 베이크 시간이 기준선 대비 개선됐다
- [ ] 패킹 점유율이 로그에 **전체 라이트맵 기준으로** 찍힌다

| 리스크 | 근거 | 완화 |
|---|---|---|

| off-by-one 을 고치며 다른 것을 깬다 | 두 커널에 같은 패턴 | 현 동작 재현 검사를 **먼저** 세우고 변이로 이빨 증명 |
| 병렬화를 낭비 위에 얹는다 | 디스패치 84% 낭비 | §2.2 순서 고정 — ①②③ 뒤에 판정 |
| UV1 없이 착수 | 자산 전수 `TEXCOORD_1` 0건 | L1 이 L0 를 제외한 모든 슬라이스의 선행 |
| 베이크 중 씬 변경 | 결과 무의미 | 시작 시 지오메트리·조명 밀봉 + 무효화 정책(L4-c) |
| 소비자 0 상태 재발 | 이 저장소의 전례 다수 | L3 에서 `LightMapPass` 를 라이브 그래프에 배선하고 화면으로 확인 |
| **TDR 로 디바이스 리셋** | 큐가 DIRECT 하나뿐이라 긴 디스패치가 프레임을 통째로 민다. 기본 상한 2초 | L4-b 분할을 **성능이 아니라 안전 요구**로 다룬다. 단일 디스패치 시간을 계측해 상한을 못박는다 |
| **큐를 두 번 만든다** | async compute 공통 기반이 트랙 RG8에도 필요하다 | L4-a와 RG8을 **공유 기반**으로 명시 — 먼저 세우는 쪽이 공통 RHI 계약을 소유하고 다른 쪽이 소비 |
| async compute 가 오히려 느리다 | 두 큐가 같은 SM 을 나눠 쓴다 | 베이크가 GPU 를 이미 채우면 이득이 없다. `RhiBoundaryPlan` 판정 기준으로 재고 결정 |

## 7. 다른 계획과의 관계

| 계획 | 관계 |
|---|---|
| **`ModelImportPipelinePlan` (같은 PHASE 4)** | **L1 이 트랙 V3(옵셔널 스트림)의 첫 소비자다.** UV1 은 라이트맵 대상 메시에만 붙는다. V6 는 이 계획으로 대체된다 |
| **`RenderGraphDependencySchedulingPlan` (같은 PHASE 4 · 트랙 RG)** | L4-a는 RG8의 queue-neutral multi-queue·cross-queue fence 기반을 공유한다. RG0~RG7 완료 전 L4가 먼저 필요하면 같은 RHI 계약만 선행하고 별도 큐 계층을 만들지 않는다 |
| **`ScriptableRenderPipelinePlan` (같은 PHASE 4)** | `LightMapPass` 를 Pipeline Asset 이 선택하는 Pass 로 둘지, 소스 Native Pass 로 둘지 결정 필요 |
| PHASE 4 Stochastic Lighting | 정적 간접광이 라이트맵에 있으면 그쪽이 담당할 범위가 줄어든다 — 설계 게이트에서 경계를 정한다 |
| PHASE 4 DXR | BLAS 가 서면 **베이크의 BVH 를 DXR 가속 구조로 대체**할 수 있다. L2 의 자체 BVH 는 그때까지의 다리다 |
| `RhiBoundaryPlan` (PHASE 3) | L3 이 DX12 RHI 로 재작성. async compute 판정 기준을 그대로 적용 |
| `MaterialPipelinePlan` (PHASE 3.5) | 베이크 커널의 셰이더 퍼뮤테이션이 `.shadermeta` 정본을 따른다 |
| `SerializationPlan` (PHASE 17) | 구운 라이트맵 텍스처의 자산 형식·쿠킹 결정을 공유 |
