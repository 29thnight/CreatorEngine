# PrSM 기반 시뮬레이션 효과 계약 및 도입 계획 (PHASE 24)

> **상태: 미래 계획 · 현재 리팩토링 이후 · 구현 미착수.**
> 2026-09-05 결정: 효과 계약 런타임뿐 아니라 **PrSM을 CreatorEngine 대상으로 수정하고
> 실제 저작·빌드·실행 경로에 도입하는 것까지** 이 계획의 목표로 정한다.
> 현재 리팩토링에 이 계획의 런타임·언어 변경을 끼워 넣지 않는다. 착수 시점의 코드와
> 저작분을 다시 조사해 범위·공수·이행 순서를 산정한다.
>
> 현행 생명주기·Task 스코프의 결함 수정은
> [ScriptLifecycleContractHardeningPlan.md](archive/ScriptLifecycleContractHardeningPlan.md)로 분리한다.
> 그 작업은 PHASE 24를 기다리지 않으며, 이 문서의 PrSM 도입과 완료를 서로 대신하지 않는다.
>
> 기존 결정인 **폐쇄 효과 카탈로그, 즉시 효과와 중단의 분리, `Var<T>` 이름**은 유지한다.
> 아래 참조 구현 측정은 과거 검토 자료이며 CreatorEngine 구현 완료나 성능 보장이 아니다.

## 0. 결정한 목표와 착수 조건

PrSM은 저작 의도와 정적 계약을 표현하고, 생성된 C#은 기존 `ScriptCore` 위에서 실행한다.
엔진은 시간·수명·취소·효과의 실제 의미를 보장한다. C# API 정리만으로 이 계획을 완료하지
않는다. PrSM 원문을 수정한 결과가 인스펙터·실행·진단·리로드까지 도달해야 한다.

| 구분 | 결정 |
|---|---|
| 착수 시점 | 현재 리팩토링 완료 후. 진행 중인 생명주기·스크립트 표면·클럭 정리의 결과를 입력으로 받는다 |
| 최종 산출물 | 효과 계약 런타임 + CreatorEngine용 PrSM 변환·검사 + 기존 엔진 빌드·등록·직렬화·진단·리로드 연결 |
| 현재 독립 작업 | 실패한 훅의 단계 처리, 대기 참조 유지, 취소 정리 예외, 재진입·스레드 경계 및 관리 생명주기 회귀. 별도 문서 LC0~LC7 |
| 저작 방식 | 프레임 연산은 틱, 판단·우선순위는 행동 트리, 짧은 연출은 단계 목록, 필요한 다중 프레임 흐름은 루틴. PrSM이 각 형태의 표면을 제공한다 |
| 보류하는 것 | 현재 엔진의 `OnSimulate` 반환형 교체, PrSM 코드 수정·패키지 도입, 전면 스크립트 이관. 이번 결정은 문서화다 |
| 공수 | 종전의 트랙별 단기 일수 추정을 일정에서 제외한다. 엔진·컴파일러·도구 통합 범위로 착수 시 재산정한다 |

### 현재 관측은 미래 이관 규모의 확정값이 아니다

2026-09-05 소스 조사 기준: `OnSimulate` 오버라이드 2건, `await` 8곳(모두 `Scope.Delay`),
`PrePhysics` 오버라이드 **1건**, `PostPhysics` 18건, 네이티브 함수 포인터 표 207항목이다.
`GameScripts`에 난수 호출이 없더라도 `ScriptCore/BehaviorTree.cs`의 가중 선택 노드는
`Random.Shared.NextSingle()`을 사용한다. 소비자 범위는 게임 스크립트 두 파일보다 넓다.

현재 두 루틴도 취소 예외를 잡는 본문에 의존한다. `cold` 시작, 취소 시 비재개, 네이티브
파괴 전 정리 경계는 실행 의미를 바꾼다. 따라서 **저작분이 작다는 사실을 이관 비용 0이나
즉시 착수의 근거로 사용하지 않는다.** 현재 코퍼스 수와 런타임 인스턴스 수도 구분한다.

기준점과 재개 조건:

1. [현행 안정화 계획](archive/ScriptLifecycleContractHardeningPlan.md)의 필수 항목과 관리 생명주기
   게이트를 완료하거나, 적용하지 않는 항목의 근거를 명시한다.
2. 현재 리팩토링의 결과로 확정된 `ScriptCore`, 클럭, 에셋·빌드·리로드 경계를 다시 조사한다.
3. §3의 전환 의미와 §7의 PrSM 대상 계약을 확정하고, 원문부터 실행까지 연결되는 작은 슬라이스로 진행한다.
4. §8의 최종 도입 기준을 통과해야 PHASE 24 완료로 판정한다.

## 1. 결정 — 두 절반을 합치되, 즉시 효과와 중단을 가른다

검토한 기성 라이브러리 둘은 각각 필요한 절반만 준다.

| | 주는 것 | 안 주는 것 | 채택 |
|---|---|---|---|
| `jbakic/Shielded` (STM) | 커밋까지 미루는 부수효과(`SideEffect`) | 정적 계약 없음. MVCC·재시도는 단일 게임 스레드에 무용. `Shielded<T>` 박스 밖(=네이티브 상태)을 못 감쌈 | **기각** (2020-04 정지 · 정본 이중화) |
| `nessos/Eff` (대수적 효과) | 효과를 데이터로 · 핸들러 교체 · cold semantics | **await 제약 없음** — 빌더가 표준 `INotifyCompletion` 제약이고 상태 머신이 `TaskAwaiter`를 1급 필드로 든다 | **기각** (리플렉션 상태 머신 복제 · NuGet 2020-07 정지) |

**개념만 가져와 직접 세운다.** 합치면 어느 쪽도 혼자 못 주는 것이 나온다.

```
awaiter 제약 (자체 검증)          → 잘못된 await를 컴파일이 차단
        +
즉시 효과는 폐쇄 카탈로그 (자체)   → 값을 동기로 돌려준다 · 어휘 누락은 컴파일이 차단
        +
중단은 실행기 원시 (자체)          → Wait · WaitUntil · Race 는 핸들러를 거치지 않는다
        +
부수효과 지연 (Shielded의 개념)   → 되돌릴 수 없는 것을 금지가 아니라 유예
```

★ **둘째·셋째 줄이 한 쌍이다.** 효과를 하나의 축으로 두면 "핸들러가 답을 주지 않는" 경로가
생긴다. 즉시 효과는 **값을 돌려주는 메서드**라 그 경로가 원리적으로 없고, 시간이 걸리는
것은 핸들러가 아니라 **실행기**가 든다. 어휘를 늘리고 구현을 빠뜨리면 **CS0535**다.

### 결정 이력 — 제네릭 판을 왜 버렸나

초안(같은 날 오전)은 효과를 `readonly struct` + `IEffect<TResult>`, 핸들러를 효과당
`IEffectHandler<TEffect, TResult>`로 두는 판이었다. 그 판도 CS0535와 즉시 효과 할당 0을
줬다(§2 초안 실측). 그런데 참조 구현을 검증하며 셋이 드러났다.

| 제네릭 판의 문제 | 폐쇄 카탈로그에서 |
|---|---|
| **핸들러가 `SetResult`도 `Defer()`도 부르지 않으면 루틴이 조용히 멈춘다.** 이 페이즈가 없애려던 무음 실패를 새로 만들었다 | 즉시 효과는 반환값이 있어 답을 잊을 수 없다. 중단은 실행기 원시라 핸들러가 관여하지 않는다 |
| **조합자의 열린 제네릭 벽.** `Race<A,B>`를 핸들러 인터페이스로 못 받아 arity가 타입에 박히고 `params`를 잃는다. 잎(leaf) 효과 둘만 경주할 수 있다 | `Race`는 cold 루틴 **전체**를 받는다 — 여러 단계짜리 분기가 경주한다. `params` 그대로 |
| 효과마다 `GetAwaiter()` 한 줄을 생성기가 내야 한다 | 생성기 의존 없음 |

즉시 효과 할당은 **잃지 않는다** — awaiter가 아예 없으니 잴 것이 없다(§2 참조 구현 실측
0.007 B/효과). 잃는 것은 **개방형 확장**이다: 스크립트가 자기 효과를 낼 수 없고, 어휘는
엔진의 것이다. 이것은 의도다 — 어휘가 곧 결정성의 경계이고 그 경계는 엔진이 든다.

### 왜 "금지"가 아니라 "라우팅"인가

착수 전 초안은 `Random.Shared`·`DateTime.Now`를 금지 목록(분석기 경고)으로 막으려 했다.
그 방향은 두 가지로 약하다. 분석기 경고만으로는 우회 경계를 설명하지 못하며, 네이티브
진입점 207개를 일괄 금지하면 필요한 조회와 변경까지 막는다. 읽기·쓰기의 실제 분포와
트랜잭션 정책은 E2에서 다시 분류한다.

카탈로그로 표현하면 같은 코드가 해석기 선택만으로 달라진다.

```
실행 시각   → LiveSimulationEffects        (실제 난수 · 실제 방출)
기록        → RecordingSimulationEffects   (실행하면서 테이프에 적는다)
리플레이    → ReplaySimulationEffects      (테이프 대조 · 방출 생략)
테스트      → ScriptedSimulationEffects    (대본)
넷코드 롤백 → 재예측 핸들러
```

카탈로그를 통과하는 효과의 기록·대체 지점이 생긴다. 게임 전체의 결정성에는 입력·물리
조회·BT 난수·클럭·초기 상태의 계약도 필요하다. PrSM은 이 경계를 표현하고 검사한다(§7).

## 2. 과거 참조 구현 검증 기록 — 엔진 도입 증거와 구분

이 절은 2026-09-05 초기 검토 문서에 기록된 결과를 보존한다. 이번 미래 계획 개정에서
참조 구현을 다시 빌드·실행한 것은 아니다. 엔진 구현과 PrSM 도입 게이트로 재현하기 전에는
일정 산정이나 성능 개선 배수의 근거로 사용하지 않는다.

### 초안 프로토타입 (제네릭 판, 2026-09-05 오전, .NET 10 / C# 14, Release)

| 주장 | 확인 방법 | 결과 |
|---|---|---|
| `async SimulationTask` 본문에서 스코프 밖 awaiter를 await하면 컴파일이 막힌다 | `await Task.Delay(1)` 변이 | **CS0315 2건** |
| 같은 스크립트가 핸들러 교체만으로 리플레이된다 | 기록 후 테이프 재생, 방출 결과 대조 | **일치** |
| 그 대조가 눈멀지 않았다 | 테이프를 `[1, 1]`로 바꾸는 변이 | **갈림(붉음)** |
| 핸들러가 어휘 전부를 다뤘는지 컴파일이 강제한다 | 어휘에 효과를 더하고 구현을 빠뜨리는 변이 | **CS0535** |
| 즉시 완료 효과는 힙을 쓰지 않는다 | 100,000회 `GC.GetAllocatedBytesForCurrentThread()` 대조 | 0.00 B/효과 (클래스 판 48.00 B) |

첫 넷은 폐쇄 카탈로그에서도 같은 기제로 성립한다(awaiter 제약은 그대로, CS0535는
인터페이스 메서드 누락으로). 다섯째는 아래에서 다시 쟀다.

### 참조 구현 (`CreatorEngine.VerseLike`, 2026-09-05 오후)

초안 프로토타입 여섯 파일에서 파생된 참조 구현을 저장소 밖(`Downloads`)에서 검증했다.
초기 검토 문서에는 `VALIDATION.json`의 `SOURCE_AUDITED_NOT_COMPILED` 상태에서
처음 빌드했다고 기록되어 있다. 당시 `net8.0` 고정을 `net10.0`으로 바꾼 스크래치 사본에서
측정했으며 원본은 변경하지 않았다는 기록이다. 아래는 그 결과의 보존이다.

| 항목 | 결과 |
|---|---|
| `dotnet build` Release | **경고 0 · 오류 0** |
| 런타임 회귀 | **31/31** |
| 데모 | Live/Replay 방출 일치, 정리 콜백 1/1 |
| 계약 검사기 자가 시험 | **8/8** (CE1001~CE1007) |
| `[Suspends] async Routine`에 `await Task.Delay(1)` 변이 | 빌드 **CS0315 ×2** + 검사기 **CE1001·CE1004** — 두 겹이 각각 잡는다 |
| 즉시 효과 할당 — `RollDice` 100,000회 | **704 B 총합, 0.007 B/효과** |
| 루틴 시작 구성(코어 + 상태 머신 홀더 + 스코프 + 대기 1건) | **992 B** |
| `Emit` 100,000회 | 104.9 B/효과 — **전부 `Delivered` 목록 성장**. 싱크 비용이지 효과 기제가 아니다 |

즉시 효과를 동기 메서드로 표현하면 효과·awaiter 객체를 매번 만들 필요가 없다. 이것은
문자열·싱크·기록 테이프까지 0할당이라는 뜻은 아니다. 0.007 B/효과는 해당 시험의 평균값이며,
직접 C# 호출도 0할당일 수 있으므로 기존 틱 대비 성능 우위로 환산하지 않는다.

**측정 단위 정정:** 992 B는 위 표대로 코어·홀더·스코프와 **대기 1건을 포함한 구성**이다.
이를 대기를 제외한 고정 비용으로 인용하지 않는다. 루틴 시작·추가 대기·조합자·싱크 비용은
E6에서 각각 분리해 측정한다.

★ **참조 구현은 저장소에 없고 그대로 가져오지도 않는다.** E0·E1이 실물을 세울 때 이 표의
확인을 회귀로 옮기는 것이 그 트랙의 완료 조건이다. 지금 이 표를 "게이트가 있다"로 읽으면
안 된다. 이름은 저장소 규약을 따른다(§6 원칙 5 — `Verse.Sleep`이 아니라
`Simulation.Wait`, `state_`가 아니라 `_state`).

계약이 사는 자리는 빌더의 제약 한 줄이다.

```csharp
public void AwaitUnsafeOnCompleted<TAwaiter, TStateMachine>(ref TAwaiter awaiter, ref TStateMachine stateMachine)
    where TAwaiter : ISimulationAwaiter          // ← 이 줄이 전부다
    where TStateMachine : IAsyncStateMachine
```

컴파일러가 `await`마다 이 메서드 호출 코드를 낸다. `TaskAwaiter`는 이 인터페이스를
구현하지 않으므로 오버로드 해결이 실패한다. **분석기가 아니라 타입 시스템이 막으므로
`#pragma`로 뚫리지 않는다.**

## 3. 목표 실행 계약과 C# 생성 표면

세 가지가 문법에 그대로 보인다 — **중단은 `await`한다, 즉시 효과는 `await`하지 않는다,
정리는 `finally`가 아니라 `Defer`에 적는다.**

### C# 백엔드 기준 예시

다음 C#은 실행 계약을 검토하고 생성 결과를 비교하기 위한 기준 예시다. 최종 저작 표면은
PrSM이며, `partial` 컴포넌트·직렬화 속성·등록은 기존 엔진 생성기 규약에 맞춘다(§7).
아래 예시를 현재 저장소에서 바로 실행할 수 있는 API로 읽지 않는다.

```csharp
public sealed class TreasureChest : Component
{
    private enum Outcome { Opened, TimedOut }

    private bool _opened;

    public void Open() => _opened = true;

    public override async SimulationTask OnSimulate()
    {
        // 정리는 여기 적는다. 취소는 상태 머신을 재개하지 않으므로 finally가 돌지 않는다(§3 취소 모델).
        Simulation.Defer(() => _opened = false);

        // 두 분기는 cold다 — Race가 붙이는 순간까지 아무것도 하지 않는다.
        Outcome outcome = (await Simulation.Race(OpenPath(), TimeoutPath())).Value;

        if (Outcome.TimedOut == outcome)
        {
            Simulation.Emit("log", "상자가 열리지 않았다");      // 즉시 효과 — await 없음
            return;
        }

        int roll = Simulation.RollDice(6);                        // 값이 그 자리에서 온다
        Simulation.Emit("loot", $"주사위 {roll} → 보상 등급 {(roll >= 5 ? "희귀" : "일반")}");
    }

    private async SimulationTask<Outcome> OpenPath()
    {
        await Simulation.WaitUntil(() => _opened);
        await Simulation.Wait(0.5f);                              // 여러 단계짜리 분기가 경주한다
        return Outcome.Opened;
    }

    private async SimulationTask<Outcome> TimeoutPath()
    {
        await Simulation.Wait(3f);
        return Outcome.TimedOut;
    }
}
```

승자를 번호가 아니라 **값**으로 받는다 — `winner == 1` 같은 마법 숫자가 저작 코드에
남지 않는다.

이제 컴파일되지 않는 것:

```csharp
await Task.Delay(500);            // CS0315 — 타입 시스템이 막는다 (우회 불가)
await Task.Yield();               // CS0315 — ICriticalNotifyCompletion 경로도 같다
```

그리고 분석기가 막는 것(E7):

```csharp
using (var handle = Acquire())    // CE1002 — await를 가로지르는 using/try-finally
{
    await Simulation.Wait(1f);    //         취소되면 Dispose가 영원히 안 돈다
}
```

### 어휘 창구 `Simulation`

호출부에 `new`를 두지 않는다. 창구가 두 축을 한 자리에서 보여 준다 — 위는 중단(await),
아래는 즉시 효과(값).

```csharp
public static class Simulation
{
    // ── 중단: 실행기 원시. 핸들러를 거치지 않는다 ──────────────────────────
    public static WaitAwaitable      Wait(float seconds);
    public static WaitUntilAwaitable WaitUntil(Func<bool> predicate);
    public static RaceAwaitable<TResult> Race<TResult>(params SimulationTask<TResult>[] branches);

    // ── 정리: finally 대신 ─────────────────────────────────────────────────
    public static void      Defer(Action cleanup);
    public static TResource Own<TResource>(TResource resource) where TResource : class, IDisposable;

    // ── 즉시 효과: 카탈로그로 간다. 값이 그 자리에서 온다 ───────────────────
    public static int  RollDice(int sides)                => Frame.Effects.RollDice(NextContext(), sides);
    public static void Emit(string channel, string payload) => Frame.Effects.Emit(NextContext(), channel, payload);
}
```

### 폐쇄 카탈로그 — 어휘 전부를 다뤘는지 컴파일이 강제한다

```csharp
/// 효과가 일어난 자리. 리플레이가 "같은 틱, 같은 루틴, 몇 번째 효과"를 대조하는 열쇠다.
public readonly record struct EffectContext(long Tick, long RoutineId, int Sequence);

/// 폐쇄 카탈로그. 여기 메서드를 더하면 구현하지 않은 핸들러 전부가 CS0535다 — 그것이 요점이다.
/// 즉시 효과는 값을 동기로 돌려준다. 핸들러가 "답을 잊을" 경로가 원리적으로 없다.
/// 시간이 걸리는 것은 여기 넣지 않는다 — 그것은 실행기 원시다(위 창구의 Wait·WaitUntil·Race).
public interface ISimulationEffects
{
    int  RollDice(EffectContext context, int sides);
    void Emit(EffectContext context, string channel, string payload);
}
```

핸들러 셋이 같은 인터페이스를 든다.

디스패치는 타입 검사가 아니라 인터페이스 호출이다 — `switch`도, *"해석할 수 없는 효과"*
예외도, **핸들러가 답을 잊는 경로도** 없다.

### 중단은 실행기 원시다

`Wait`·`WaitUntil`·`Race`는 `ISimulationAwaiter`를 구현하는 구조체이고, 빌더가 그것을
실행기에 등록한다. 핸들러는 보지 못한다.

```csharp
public readonly struct WaitAwaitable : ISimulationAwaiter
{
    public bool IsCompleted => false;                  // 항상 중단한다 — 등록·소유 검사를 건너뛰지 않는다
    public void Suspend(ResumeToken continuation)
        => continuation.Owner.Engine.RegisterWait(continuation, ticks, predicate: null);
    public void GetResult() { }
}
```

세 가지 실행기 규약이 이 위에 선다.

| 규약 | 뜻 |
|---|---|
| **cold** | `async SimulationTask` 메서드를 부르는 것은 상태 머신을 잡아 두는 것이지 실행이 아니다. 실행기가 `Pump`할 때 첫 `MoveNext`가 돈다. `Race`가 분기 둘을 받아 **동시에** 시작할 수 있는 이유다 |
| **결정적 순서** | 같은 틱에 깨어나는 루틴은 부모/자식 경로(`[1] → [1,1] → [1,2]`)로 정렬된 우선순위 큐로 돈다. 대기 목록 순회 순서에 승패가 달리지 않는다 |
| **평가와 실행 분리** | 틱 안에서 대기 조건 평가 단계와 본문 실행 단계가 갈린다 — `WaitUntil` 술어가 다른 본문의 중간 상태를 보지 않는다 |

### 취소 모델 — `finally`를 믿지 않는다

취소는 중단된 상태 머신을 **재개하지 않는다**. 예외를 던져 풀지도 않는다. 그래서:

- `await`를 가로지르는 `using`·`try/finally`는 취소되면 **영원히 안 돈다** → 분석기가
  막는다(E7 · CE1002). 정리는 `Simulation.Defer`, 자원은 `Simulation.Own`에 적는다
- `Race`에서 진 분기는 취소된다 — **취소는 롤백이 아니다.** 진 분기가 이미 낸 즉시 효과는
  남는다. 상태 되돌리기는 E2·E8의 축이지 이 축이 아니다
- `ResumeToken`이 버전을 든다 — 취소된 뒤 늦게 도착한 깨우기는 무시된다

### 전환 전에 확정할 실행 의미

| 경계 | 목표 계약과 검증 |
|---|---|
| 첫 본문 실행 | 현재의 `OnBeginSimulation` 직후 실행과 `cold`의 첫 `Pump`는 다르다. 컴포넌트 간 시작 순서·첫 효과의 물리 반영 프레임을 골든으로 고정한다 |
| 시간 | `Wait(0)`, 같은 틱에 등록된 대기, 음수·비정상 시간, 최초 대기의 만료 시점을 정의한다. 프레임 틱을 고정 클럭으로 이름만 바꾸지 않는다 |
| 비활성화 | 현행의 `Enabled=false`는 전·후 틱을 멈추지만 실행 중인 대기는 진행한다. 시뮬레이션 종료와 구분하고 자동 재시작을 넣지 않는다 |
| 종료 | 현재 실행 중인 본문이 끝난 뒤, 네이티브 자원이 파괴되기 전에 정리를 소진한다. `End` 표시를 다음 일반 틱까지 방치하지 않는다. 즉시 컴포넌트 제거·리로드에도 같은 경계를 적용한다 |
| 취소 이관 | 기존 두 프로브의 `catch (OperationCanceledException)`도 비재개 취소에서는 실행되지 않는다. 정리와 취소 진단을 별도 종료 경로로 이전한다 |
| 정리 | 정상 완료·취소·실패 각각의 정리 순서와 정확히 한 번 실행을 정의한다. 정리 하나의 예외가 다른 정리나 스코프 해제를 막지 않아야 한다 |
| 스케줄링 | 같은 틱 순서 큐와 시간 만료 자료구조를 구분한다. `WaitUntil`은 순수한 조건 평가만 허용하고, 재개 횟수·본문 실행 예산과 늦은 토큰 무시를 검증한다 |
| 식별자 | 루트·자식 루틴 식별자, 효과 순번, PrSM 원문 위치 및 컴파일 세대의 연결을 정의한다. 코드 변경 후 옛 테이프를 무조건 재사용하지 않는다 |
| 트랜잭션 | 셀과 네이티브의 읽은 값이 일치하는 규약, 커밋 전 검증 및 부분 커밋 실패 정책을 정한다. 일반 필드·객체 내부 변경은 자동으로 되돌아오지 않는다 |

현재 Task 스코프의 결함은 [별도 안정화 문서](archive/ScriptLifecycleContractHardeningPlan.md)에서
먼저 다룬다. 위 표는 그 수정에 `cold`나 비재개 취소를 미리 섞으라는 뜻이 아니다.

### 이 형태가 치르는 값

| 대가 | 크기 |
|---|---|
| 개방형 확장이 없다 | **의도다.** 어휘는 엔진의 것이고 스크립트는 그 안에서 쓴다. 어휘가 커지면 카탈로그에 더한다 |
| 어휘를 늘리면 모든 핸들러를 수정해야 한다 | 누락 검출의 대가다. 예시는 Live/Recording/Replay 셋이며 실제 대상 수로 유지 비용을 산정한다 |
| 루틴 시작 비용 | 참조 시험의 코어 + 홀더 + 스코프 + 대기 1건 = **992 B**(§2). 엔진 구현의 고정 비용 상한은 E6에서 새로 정한다 |
| `Race`가 상태 객체와 분기 배열을 할당한다 | 분기 수와 사용 빈도에 따른 비용을 E6이 잰다 |
| 취소 시 중단을 가로지르는 `finally`가 돌지 않는다 | 수기 C#에는 명시적 정리와 E7 검사가 필요하다. PrSM은 수명 의도를 받아 정리 코드를 생성하고 검사한다 |
| 즉시 효과는 데이터가 아니라 호출이다 | 진단(E5)이 "지금 무엇을 기다리는가"를 답할 때 보는 것은 중단이고, 그것은 여전히 데이터다. 기록은 테이프가 데이터로 든다 |

## 4. 엔진 계약 트랙 — 전체 미래 보류

E0~E8은 리팩토링 이후의 목표 작업이다. P0/P1/P2는 이 페이즈 안의 상대 우선순위이며
현재 작업 큐의 긴급도를 뜻하지 않는다. **이 트랙만 끝내서는 완료가 아니며 §7의 PrSM
변경·통합 트랙을 함께 완료해야 한다.**

### E0 — 대기 원시와 awaiter 계약 (P0 · §0 재개 조건·§3 실행 의미 선행)

`SimulationTask` / `SimulationTask<TResult>` / `ISimulationAwaiter` / 빌더 넷을 세우고,
`Component.OnSimulate`의 반환형을 `Task` → `SimulationTask`로 바꾼다. 기존
`SimulationScope.Delay`(`TaskCompletionSource` 기반)를 `Simulation.Wait`로 교체한다.

- 과거 오버라이드 2건은 조사 시점의 값이다. 착수 시 호출자·프로브·생성 코드·빌드 및
  리로드 경계를 다시 세며, 반환형 변경 외의 의미 이관도 작업 범위에 포함한다
- **cold.** 빌더 `Start`는 상태 머신을 잡아 둘 뿐 `MoveNext`하지 않는다.
  `ScriptRegistry.StartSimulation`이 실행기에 붙이고 관리 틱이 `Pump`한다
- **오버라이드하지 않은 컴포넌트.** 기반 `OnSimulate() => default`는 코어가 없는
  값이다. 등록부는 **붙이기 전에 걸러** 미사용 루틴 코어를 만들지 않는다.
  기존 `Component.Scope`의 선할당을 없애는 작업과는 별개이므로 두 할당을 따로 잰다
- 취소는 경계에서만 — `Scope.End()`는 표시하고, 현재 본문 종료 후 네이티브 파괴 전
  종료 배리어가 정리를 돌린다. 프레임 종료·즉시 제거·씬 이동·리로드의 배선까지 검증한다
- 게임 스레드 확인(`CheckThread`)을 실행기 진입점 전부에 둔다. `ClrHost.h:27`의 게임
  스레드 계약을 관리 측이 스스로 검사하는 첫 자리다
- 관측되지 않은 예외 수거를 `ContinueWith`에서 루틴 종결 상태(`Faulted` + 진단 목록)로 옮긴다

**완료 조건**: `AwaitOnCompleted`와 `AwaitUnsafeOnCompleted` 양쪽에서 외부 awaiter를
거부한다. 미사용 루틴 할당 0, 관리 생명주기·취소·DDOL·리로드 게이트 통과를 각각 잰다.
200사건 네이티브 기준선에는 현재 `ScriptComponent` 행이 없으므로 그것만으로 완료하지
않는다. 의도적으로 바뀐 시작·취소 의미는 이전/이후 골든과 변경 근거를 함께 남긴다.

### E1 — 폐쇄 카탈로그와 중단 원시 (P0 · E0 선행)

`EffectContext` · `ISimulationEffects` · 핸들러 셋(Live/Recording/Replay) · 어휘 창구
`Simulation`, 그리고 중단 원시 `Wait` · `WaitUntil` · `Race` · 정리 `Defer` · `Own`.
카탈로그는 실제로 쓰이는 것만 낸다 — `RollDice` · `Emit`.

- **즉시 효과는 값을 돌려준다.** awaiter가 없다. 핸들러가 답을 잊는 경로가 없다
- **카탈로그는 폐쇄 인터페이스.** 메서드를 더하고 구현을 빠뜨리면 **CS0535** — 런타임
  `switch`와 *"해석할 수 없는 효과"* 예외가 통째로 사라진다
- **중단은 실행기 원시.** 우선순위 큐(루틴 경로 정렬) · 대기 평가/본문 실행 분리 ·
  `ResumeToken` 버전. `Race`는 cold 루틴을 `params`로 받고 승자를 `(Index, Value)`로 준다
- **호출부는 창구만 쓴다** — `await Simulation.Wait(0.5f)`, `Simulation.RollDice(6)`.
  생성자 직접 호출을 금지하는 것이 계약이다(§3)
- `Sync`·`Branch`는 저작분 0건이므로 내지 않는다. 트랜잭션 셀(`Var<T>`·`Decide`)은
  이 트랙이 아니라 E8이다

**완료 조건**: ① 핸들러 교체로 같은 스크립트가 다른 결과를 내는 것을 게이트가 잰다.
② 카탈로그에 메서드를 더하고 구현을 빠뜨리는 변이가 **CS0535로 막힌다**. ③ 즉시 효과의
프레임당 할당이 0인 것을 게이트가 잰다(§2 실측 0.007 B/효과). ④ 같은 틱 `Race` 승자가
대기 등록 순서를 뒤집는 변이에 **바뀌지 않는다**.

### E2 — 부수효과 분류와 공통 카탈로그 (P0 · §0 재개 조건 선행)

착수 시 네이티브 진입점과 관리 측 효과 호출을 다시 수집한다(2026-09-05 함수 포인터 표
207항목). 읽기/쓰기를 먼저 구분하고, 쓰기·외부 효과에는 다음 실행 정책을 붙인다.

| 분류 | 뜻 | 예 |
|---|---|---|
| 즉시 | 해당 문맥에서 지금 실행 가능. 롤백 가능 여부는 추적 기제가 결정 | 셀을 거치는 쓰기, 되읽어야 하는 값. 일반 관리 필드를 자동 롤백 대상으로 보지 않음 |
| **지연** | 커밋 시점까지 미룬다 | 렌더 프록시 델타, 사운드 재생, 네트워크 전송 |
| 불가 | 미룰 수도 되돌릴 수도 없다 | 즉시 값을 되읽어야 하는 쓰기 |

E3, PrSM 검사·변환, 향후 롤백 및 편집기 Undo가 분류를 활용할 수 있다. 소비 가능성이
현재 착수의 근거는 아니다. 기존 네트워크·Undo 설계가 먼저 만든 정본이 있으면 재사용하며
그 작업에 PHASE 24 선행 의존을 역으로 추가하지 않는다.

함수별 중단 가능 여부, 호출 스레드·실행 문맥, 효과 종류와 트랜잭션 참여 여부를 함께
제공한다. 이 카탈로그를 PrSM과 C# 검사·런타임 검증이 공유하며 목록을 별도로 복제하지
않는다. BT 가중 선택의 난수와 외부 C# 호출도 감사에 포함한다.

★ **착수 전 확인할 것**: `UndoManager::m_isGameMode`는 이름과 달리 *"에디터 UI의 Play
버튼을 눌렀는가"*다(그 파일 주석이 이미 경고한다). 게임 모드 스택이 지금 무엇을 담고
있는지 세지 않고 위에 얹으면 되돌리기 기제가 저장소에 둘이 된다.

★ 참조 구현은 트랜잭션 안에서 `Emit`·`RollDice`를 런타임에 거부한다
(`RequireNonTransactional`). 그것이 "불가" 분류를 런타임에 강제하는 형태다 — 분류표가
서면 같은 게이트를 경계 207개에 건다. 트랜잭션 셀(E8)이 네이티브 상태를 못 감싸는 이유는
`unmanaged` 제약이 아니라(그 제약은 비본질적이다 — E8 실측) **쓰기 경로가 셀을 거치지
않기 때문**이다. `Transform` setter는 곧장 네이티브로 간다. 그 경로를 커밋 시점까지 미루는
것이 "지연" 분류이고, 그래서 되돌리기 축은 이 표에서 시작한다.

**완료 조건**: 분류표가 문서가 아니라 코드 표로 서고(속성 또는 생성 표), 분류 없는 신규
진입점이 추가되면 게이트가 붉어진다.

### E3 — 효과 기록·재생 (P1 · E1·E2 선행)

`RecordingSimulationEffects` / `ReplaySimulationEffects`. 테이프 항목은
`(EffectContext, 종류, 인자, 결과)`다 — 결과 수열만이 아니다. 리플레이는 **요청**을
대조하고(같은 틱·루틴·순번·종류·인자가 아니면 예외), 끝에 남은 항목 0을 확인한다.
지연 분류(E2)의 부수효과는 재생에서 생략된다.

**리플레이는 효과 검증이지 롤백이 아니다.** 상태를 되돌리는 것은 E2의 분류표 위에 선다.
전체 게임 재현에는 입력·충돌·물리 조회, 초기 상태와 클럭을 별도로 통제해야 한다.
테이프에는 스키마·컴파일 세대 식별을 포함하고, 호환되지 않는 재생을 명시적으로 거부한다.

**완료 조건**: 기록 → 재생 왕복이 방출 수열을 보존하고, **테이프를 흔드는 변이에 붉어진다**
(결과값 변조 · 항목 삭제 · 순번 교체 셋 다).

### E4 — 실패 결과와 루틴 진단 통합 (P1 · E0·현행 안정화 LC1/LC2 선행)

`Result<TValue, TError>`와 루틴 종료 상태를 기존의 성공 단계·실패 격리 계약에 연결한다.
현행 훅 결함 수정은 [별도 문서 LC1/LC2](archive/ScriptLifecycleContractHardeningPlan.md)의 소관이다.

- 확정된 성공 단계와 대칭 정리 규약을 생성된 PrSM 컴포넌트에도 동일하게 적용한다
- 루틴의 `Faulted`(E0), 훅 실패, 정리 실패가 원인·소유자·원문 위치를 보존한 채 모인다
- 생성기나 PrSM 전용 등록부에 두 번째 생명주기 상태 기계를 만들지 않는다

**완료 조건**: 동일한 실패 시나리오에서 수기 C#과 PrSM 생성 코드의 단계·정리 결과가
일치한다. 정상 실패 값과 예외, 취소를 구분하고 원래 PrSM 문장까지 진단이 연결된다.

### E7 — 정적 계약 검사기 (P1 · E1·E2 선행)

차단은 타입 시스템이 하고(CS0315·CS0535), **설명은 분석기가 한다.** 그리고 타입 시스템이
못 잡는 계약이 하나 있다 — 취소 모델(§3)을 고른 순간 따라오는 `await`를 가로지르는
`using`/`try-finally`다.

| 규칙 | 잡는 것 | 타입 시스템이 잡나 |
|---|---|---|
| 외부 awaiter | `await Task.Delay` — CS0315의 **설명판**("스코프 밖 awaiter") | 잡는다 (이 규칙은 메시지용) |
| **정리가 중단을 가로지른다** | `using`·`try/finally` 안에 `await` | **못 잡는다** — 이 규칙이 신설 이유 |
| 정리 콜백이 비동기다 | `Defer(async () => …)` | 못 잡는다 |
| 미분류 호출 | 카탈로그도 창구도 아닌 메서드를 루틴 본문이 부른다 | 못 잡는다 — E2 분류표가 소비자 |

- **빌드에 물린 Roslyn 분석기**로 세운다. 참조 구현은 별도 CLI라 안 돌리면 그만이었다 —
  `GameScripts.csproj`가 `Analyzer` 항목으로 참조하고, **분석기가 실제로 도는지를 게이트가
  잰다**(초록 게이트가 배선 안 된 채 놓여 있던 전례가 이 저장소에 있다)
- 저장소에 `ScriptCore.Generators`가 이미 있다 — 같은 자리에 선다
- PrSM 저작 진단은 PrSM 의미 분석이 담당한다(PrSM2). Roslyn 검사는 생성 결과·수기 C#·
  외부 경계의 보조 검증이며 둘은 E2 카탈로그와 같은 양성/음성 사례를 사용한다.
  생성 파일로 인식되어 분석기가 건너뛰는 경로도 별도 게이트로 막는다
- 규칙마다 잡는 픽스처와 **못 잡는 변이**를 함께 적는다. 참조 구현 문서가 스스로 적었듯
  이것은 *"악의적인 스크립트의 샌드박스가 아니다"* — 호출 그래프 전수가 아니다

**완료 조건**: 규칙 4종 각각 붉은 픽스처 1 + 초록 픽스처 1. 분석기 참조를 제거하는 변이에
게이트가 붉어진다.

### E5 — 진단 표면 (P2 · E1·PrSM4 연계)

"지금 이 컴포넌트가 무엇을 기다리는가"를 구조화된 대기 레코드로 답한다. 실행기가 대기
종류·소유 루틴·중단 위치를 등록·해제하고, `EffectContext.Sequence`가 현재 틱의 효과
순번을 제공한다. 이를 PrSM 소스 맵과 연결한다. 상태 머신 내부 필드를 임의로 읽지 않는다.

**완료 조건**: 에디터·트레이스·게이트가 같은 레코드를 사용하고 PrSM 원문으로 이동한다.

### E6 — 할당·실행 시간 예산 (P2 · E1 선행, 최종 판정은 PrSM5)

즉시 효과의 디스패치와 싱크 비용을 분리한다. 생성된 C#까지 포함하여 다음을 측정한다.

| 남은 할당 | 실측(참조 구현) | 자리 |
|---|---:|---|
| 루틴 시작 구성(코어 + 홀더 + 스코프 + 대기 1건) | 참조 시험 992 B | 엔진의 고정 비용과 추가 대기 비용은 별도 산정 |
| 대기 레코드 | 대기 1건당 | `RegisterWait` — 풀링 후보 |
| `Race` 상태 + 분기 배열 · `Defer` 클로저 | 조합자당 | 실제 사용 빈도와 분기 수로 산정 |

시간 대기와 조건 대기, 같은 틱 대량 재개, 취소·파괴·리로드, Live/Recording/Replay를
나눠 잰다. 할당량·유지 메모리·평균/p95/p99 시간을 보고하며, 조건 술어와 네이티브 호출
비용을 숨기지 않는다. PrSM 변환 비용은 편집·빌드 지표로 분리한다. 동일한 실행 의미를
유지하면서 생성 방식과 런타임을 개선하는 것이 목표다.

**완료 조건**: 즉시 효과 디스패치의 할당 예산, 루틴·대기·조합자 상한 및 실행 시간
기준을 각각 게이트로 잰다. 기존 틱 최적화의 이득을 계약·DSL 도입의 이득으로 합산하지 않는다.

### E8 — 트랜잭션 셀 (P2 · E2·E7 선행)

관리 측 상태의 실패 가능한 변경을 **셀 단위 write set**으로 되돌린다. 참조 구현의
`Var<T>`/`Cell<T>`/`Decide`/`Require`가 원형이고, 이름도 그대로 둔다.

| 자리 | 이름 | 뜻 |
|---|---|---|
| 스크립트 공개 타입 | `Var<T>` | 트랜잭션에 참여하는 변수. 참조 구현 이름 그대로 — `State`는 애니메이터·입력의 "상태"와 뜻이 겹쳐 제외했다(2026-09-05 결정) |
| 내부 저장 단위 | `Cell<T>` | 저장 위치. 공개 표면이 아니다 |
| 실행 경계 | `Decide(…)` / `Require(…)` | 성공·실패 경계. 실패는 예외가 아니라 `Decision` 값 |

`Var`·`Cell`은 관리 측에 같은 이름의 타입이 없다(2026-09-05 확인). `State<T>`도 타입
충돌은 없었으나(`KeyState`·`AniStateProbe`뿐) 어휘가 겹쳐 버렸고, `TxValue<T>` 같은
약칭은 원칙 5로 제외한다.

**추적 계약 — 무엇이 되돌아오고 무엇이 안 오는가.** 참조 구현에서 `unmanaged` 제약을
지우고(빌드 0/0 · 31/31 불변 — **제약은 비본질적이다**) 실패한 `Decide` 뒤를 쟀다.

| 변경 | 결과 | 계약 |
|---|---|---|
| 참조 교체 `slot.Value = other` | **되돌아옴** | setter를 거친다 — write set이 잡는다 |
| 내부 변경 `slot.Value.Hp -= 10` | **★ 남음** (Hp 90) | getter로 얻은 객체의 필드 — 런타임은 못 잡는다. **정적 검사기 CE1005가 잡는다**(같은 줄을 정확히 지목함) |
| 필드별 셀 `player.Gold.Value -= 100` | **되돌아옴** | 객체가 클래스여도 변경이 셀을 거치면 된다 — 객체 전체를 감싸지 않고 **바뀌는 필드를 셀로 둔다** |
| 불변 참조형 `Var<string>` | 되돌아옴 | 교체만 있으므로 안전 |
| 가변 컬렉션 | 미구현 | 별도 트랜잭션 컬렉션 API — 소비자가 생길 때 낸다(원칙 3) |

즉 **"참조형을 저장할 수 있는가"와 "참조한 객체 내부까지 추적하는가"는 별개**이고, 이
설계는 앞의 것만 약속한다. 뒤의 것은 필드별 셀(런타임)과 CE1005(정적)가 짝으로 막는다.

- 커밋 시점에 네이티브로 쓰는 셀(`Var<Float3>` → `Transform`)은 E2의 "지연" 분류를
  커밋 훅으로 받는다 — 이 트랙이 E2에 기대는 이유
- 트랜잭션 안의 `Emit`·`RollDice`는 런타임이 거부한다(참조 구현 `RequireNonTransactional`).
  결정과 효과가 섞이지 않는다

**완료 조건**: 위 표의 다섯 행이 각각 게이트로 서고, 내부 변경 행은 **CE1005 붉음 + 런타임
잔존**을 둘 다 잰다(검사기를 빼면 조용히 새는 것을 증명하는 변이).
참조 시험의 직접 필드 변경 검출을 전체 별칭·호출 그래프 보장으로 확대하지 않는다.
PrSM의 트랜잭션 참여 선언·외부 호출 정책과 네이티브 커밋의 읽기·실패 규약도 검증한다.

## 6. 이 페이즈가 지키는 원칙

1. **PrSM 도입까지 완료한다.** C# 런타임 샘플이나 문법 변환만으로 완료하지 않는다.
   틱·행동 트리·단계 목록·루틴은 필요한 자리에 쓰며 모든 저작을 비동기 루틴으로 바꾸지 않는다.
2. **효과의 실행 지점을 명시한다.** 허용된 비결정적 효과는 해석기로, 지연 가능한 쓰기는
   커밋 경계로 보낸다. 읽기·실패 의미를 보장할 수 없는 호출은 해당 문맥에서 명시적으로 거부한다.
3. **실제 저작분으로 표면을 정한다.** 공통 카탈로그와 최소 조합자를 먼저 만들고,
   대표 콘텐츠가 요구하는 순서로 확장한다. 언어 기능 수 자체를 완료 지표로 삼지 않는다.
4. **검사가 실패를 검출하는지도 검증한다.** 양성·음성 픽스처와 검사기 배선 제거 변이를
   둔다. 검사하지 못하는 외부 호출·별칭·원시 C# 경계를 함께 명시한다.
5. **이름을 일관되게 쓴다.** `SimulationTask`, `SimulationScope`, `transaction`을 사용한다.
   트랜잭션 참여 변수의 공개 이름은 기존 결정대로 `Var<T>`, 내부 저장 단위는 `Cell<T>`다.
6. **검토 라이브러리를 그대로 의존으로 넣지 않는다.** `Shielded`·`Eff`·저장소 밖 참조
   구현은 개념·검증 자료다. 사용자 소유 PrSM 저장소의 수정·통합은 별도의 명시적 목표다.
7. **효과 카탈로그 누락을 컴파일 단계에서 검출한다.** 폐쇄 인터페이스와 공통 선언을
   사용한다. PrSM 검사와 생성된 C#의 검사가 다른 허용 목록을 갖지 않게 한다.
8. **즉시 효과는 값을 반환하고, 중단은 실행기가 관리한다.** PrSM은 기존 C# 백엔드를
   유지한다. 별도 VM·틱 루프·컴포넌트 등록부를 만들지 않는다.
9. **미래 취소 모델과 현행 Task 취소를 구분한다.** 미래 루틴은 취소 시 본문을 재개하지
   않고 `Defer`·`Own`으로 정리한다. 중단을 가로지르는 정리를 PrSM/E7이 검사한다.
   현행 `catch (OperationCanceledException)`/`finally` 의미 변경은 이행 검증을 거친다.

조사 기준 로컬 커밋은 `ef28e7b52d1fe03c9f79accee1a9de50aea7849e`, 원격 기본 브랜치의

| 현재 PrSM 구조 | 확인한 제약 | 도입 시 처리 |
|---|---|---|

| 의미 분석과 출력 경계 | HIR 분석 후 AST에서 직접 C# lowering, 문자열/Raw 출력 존재 | 효과·중단·수명 정보는 문자열로 사라지기 전에 검사·전달 |

### PrSM0 — 대상 프로필 분리 (미래 착수 첫 단계)

- 공통 언어·C# 출력과 Unity/CreatorEngine의 타입·생명주기·대기·메타데이터·도구 어댑터를 나눈다.
- 엔진 대상에서 Unity/UniTask 참조가 암묵적으로 유입되지 않게 한다. Unity 대상의 기존
  유지 범위도 명시해 공유 컴파일러 변경의 영향을 검증한다.
- 지원 문법·외부 API·진단 규칙을 대상별로 문서화한다. 새 언어 전체를 설계하지 않는다.

**완료 조건**: 같은 작은 입력을 각 대상에 빌드해 서로의 런타임 참조 없이 의도한 C#을 낸다.
지원하지 않는 대상 기능은 빌드 단계에서 원문 위치와 함께 거부한다.

### PrSM1 — 기존 컴포넌트·직렬화·등록 경로 연결 (PrSM0 선행)

- `CreatorEngine.Component`를 상속하는 `partial` 타입, 실제 훅 signature와 직렬화
  특성을 생성한다. `Start`→이름 치환만 하지 않고 공개 override·호출 단계·인자를 검증한다.
- 기존 [ScriptCore.Generators](../../ScriptCore.Generators/ScriptGenerator.cs)의 팩터리·
  필드 접근자 생성 경로와 `GameScripts` 빌드를 사용한다. PrSM 전용 생명주기 등록부를 만들지 않는다.
- 첫 슬라이스는 필드·초기화·틱·제거만으로 작게 닫는다. 현행 Task 기준선에서의 연결 시험은
  가능하지만, 이 단계만으로 효과 계약 도입을 완료했다고 하지 않는다.

**완료 조건**: PrSM 컴포넌트를 씬에 붙여 필드 저장/복원, 훅 한 번 호출, 활성 전환·제거를
실제 엔진에서 확인한다. 같은 수기 C# 컴포넌트와 생명주기 결과가 일치한다.

### PrSM2 — 효과·중단·수명 의미 분석 (E2·PrSM0 선행, E7과 공동 검증)

- E2의 공통 카탈로그에서 호출별 효과·중단 가능성·허용 스레드·트랜잭션 참여 정보를 읽는다.
- 함수 호출을 통한 효과 전파와 문맥 검사를 수행한다. 필요한 타입·효과 정보를 AST/HIR와
  lowering 사이에 보존하며, 문자열 기반 C# IR에 도달한 뒤 추측하지 않는다.
- intrinsic·외부 C#·네이티브 호출은 명시한 서명과 신뢰 경계로 처리한다. 분류 없는 호출을
  순수하다고 추정하지 않는다. 분석하지 못하는 호출 경로는 지원 제한으로 드러낸다.
- 일반 변수, 셀의 값 교체, 참조 객체 내부 변경을 구분한다. 모든 `var`를 암묵적으로
  `Var<T>`로 만들지 않는다. 기존 state machine 문법도 자동 롤백을 뜻하지 않는다.

**완료 조건**: 직접·간접 외부 await, 정리 중 중단, 트랜잭션 내 금지 효과, 내부 참조 변경의
양성·음성 사례가 원문 위치로 진단된다. 생성 C#의 E7 검사가 같은 계약을 검증한다.

### PrSM3 — 루틴·정리·트랜잭션 lowering (E0/E1·PrSM1/2 선행, 트랜잭션은 E8 선행)

- 엔진 대상 대기·조건 대기·경주 분기를 E0/E1 실행기로 변환한다. 실제 문법은 최소 슬라이스로
  확정하며, 기존 Unity coroutine의 `yield`를 무조건 동일 의미로 간주하지 않는다.
- 구독·자원 소유·정리를 엔진 스코프에 연결한다. `listen until disable`과 시뮬레이션 종료
  정리를 같은 수명으로 합치지 않는다. 정리 exactly-once와 예외 격리는 엔진이 보장한다.
- 명시적으로 참여하는 변수와 결정 구간을 E8의 `Var<T>`·`Decide`·`Require`로 내린다.
  중단 가능한 본문의 `using`을 무조건 `finally`로 내리지 않는다.
- 반환형·await 결과 타입을 정확히 검증하고, 비동기 의미가 필요한 곳만 상태 머신을 생성한다.

**완료 조건**: §3의 시작 시점·disable·취소·파괴·부분 커밋 규약을 수기 C#과 PrSM에서
같은 테스트로 검증한다. 지원한 문법의 동작과 생성 코드 예제를 함께 고정한다.

### PrSM4 — 빌드·에디터·진단·리로드 연결 (PrSM1 이후 점진 연결, E5 연계)

- `.prsm` 변경→C# 생성→기존 생성기/컴파일→어셈블리 발행의 순서를 기존 빌드에 연결한다.
  캐시 입력에 대상·컴파일러·카탈로그·ScriptCore 참조 버전을 포함한다.
- 생성 또는 컴파일 실패를 이전 산출물의 성공처럼 표시하지 않는다. 마지막 성공본 유지와
  새 버전 적용 실패를 구분하고 검증된 산출물만 일관된 한 세대로 발행한다.
- 컴파일 진단·런타임 오류·중단 위치를 PrSM 원문에 매핑한다. LSP/에디터의 훅·타입 제안도
  엔진 대상과 일치시킨다. 기존 선언 단위 소스 맵만으로 문장 단위 진단 완료라 하지 않는다.
- 인스펙터의 타입·필드 식별자와 스크립트 이름 변경 정책을 정한다. 리로드 시 이전 어셈블리의
  루틴·정리 콜백·테이프·소스 맵 참조를 해제하고 새 세대와 섞지 않는다.

**완료 조건**: 정상 수정, 구문 오류, 계약 오류, 생성 C# 오류, 리로드 중 대기/실패를 편집에서
실행까지 재현한다. 원문 위치·저장한 필드·실행 중 버전이 일치하고 이전 로드 문맥이 회수된다.

### PrSM5 — 실제 콘텐츠 도입과 비교 검증 (필수 엔진·PrSM 트랙 통합)

- 틱 컴포넌트, BT 연계, 짧은 단계 흐름, 여러 프레임을 기다리는 루틴의 대표 사례를 정한다.
  신규 BT 언어 전체 구현보다 기존 관리 BT를 올바르게 호출·진단하는 경계를 먼저 닫는다.
- 활성 전환·일시 정지·DDOL 이동·일반/즉시 파괴·씬 종료·스크립트 리로드를 실제 콘텐츠에서 검증한다.
- 저작량, 반복되는 정리 코드, 진단의 원문 도달률, 수정→실행 시간, 이관 중 결함을 수기 C#과
  비교한다. 짧아진 원문만으로 생산성 향상을 확정하지 않는다.
- E6의 실행·할당·유지 메모리를 같은 기능·인스턴스 수·클럭·빌드 조건에서 비교한다.
  DSL 도입 자체의 FPS 개선을 목표나 보장으로 삼지 않는다.

**완료 조건**: PrSM 저장소의 변경과 CreatorEngine의 런타임·도구 연결이 함께 배포 가능한
상태이며, 대표 콘텐츠가 PrSM 원문을 정본으로 편집·빌드·실행된다. 남은 미지원 기능은 명시한다.

## 8. 최종 완료 판정

이 문서의 작성·정적 링크 검사·참조 구현 데모는 아래 항목의 완료 증거가 아니다.
**효과 계약 런타임과 PrSM 변경 도입을 모두 끝내야 PHASE 24를 완료 처리한다.**

- [ ] 재착수 시 코드·저작분·관련 리팩토링 결과를 재조사하고 §3 실행 의미를 확정했다.
- [ ] E0~E8의 적용 범위와 완료 게이트를 실제 엔진에 구현·연결했다.
- [ ] PrSM0~PrSM5를 완료하고 Unity 의존 분리·CreatorEngine 대상 빌드를 검증했다.
- [ ] PrSM과 수기 C#이 같은 카탈로그·등록·생명주기·직렬화 계약을 사용한다.
- [ ] 분석기와 PrSM 의미 검사의 실제 빌드 배선, 거부 사례와 우회 한계를 검증했다.
- [ ] 원문 수정→생성→빌드→등록→실행→진단→리로드 전 경로를 실제 엔진에서 검증했다.
