Script API Migration Design

ModuleBehavior → CoreCLR 스크립트 API 이전 설계

전제: C++ 핫리로드(Dynamic_CPP)를 CoreCLR로 전면 대체 · 관련: 리팩토링 대시보드 2-0 / 2-10 · 작성일: 2026-07-29

01설계 원칙

핵심 원칙 — 경계는 얇게, 순회는 안쪽에서

네이티브↔관리 경계를 넘는 횟수가 성능을 지배합니다. 개별 스크립트마다 경계를 넘으면 프레임당 수천 회가 되지만, 틱마다 한 번만 넘고 C# 내부에서 순회하면 프레임당 몇 회로 끝납니다. 이 원칙 하나가 아래 모든 설계를 규정합니다.

원칙이유
객체는 세대 핸들로만 주고받는다관리 코드는 포인터의 유효성을 알 수 없다. 세대가 있으면 해제된 참조가 자동 무효화된다.
스크립트 간 상호작용은 C# 내부에서 완결Entity* sender 같은 참조가 경계를 넘을 필요가 없어져 바인딩 표면이 급감한다.
필드 노출은 소스 제너레이터로런타임 리플렉션은 Native AOT에서 트리밍된다. 엔진의 C++ 코드젠 철학과도 일치.
관리 코드 호출은 게임 스레드에서만CoreCLR GC는 스레드를 정지시킨다. 렌더 스레드가 물리면 프레임이 GC에 묶인다.
경계 함수는 평면 C ABIP/Invoke는 C++ 객체를 넘길 수 없다. JIT/AOT 두 모드가 같은 바인딩을 공유하게 된다.

02라이프사이클 디스패치

현재 ModuleBehavior는 가상 함수 14종과 델리게이트 핸들 14개로 구성됩니다. 이름은 Unity 관례를 따르고 있어 그대로 유지하길 권합니다 — 팀의 학습 비용이 0이고, 기존 348개 스크립트를 포팅할 때 구조를 그대로 옮길 수 있습니다.

2.1 디스패치 방식 비교

방식구조평가
비권장 스크립트 인스턴스마다 네이티브가 개별 콜백 호출 현재 C++ 델리게이트 구조를 그대로 옮기는 형태. 직관적이지만 프레임당 경계 통과가 스크립트 수만큼 발생해 P/Invoke 오버헤드가 누적된다.
권장 틱당 한 번 진입 → C# 내부에서 순회 네이티브는 OnUpdate(dt)를 한 번만 호출하고, C#의 BehaviourRegistry가 활성 스크립트를 순회한다. 경계 통과가 프레임당 3~4회(Fixed/Update/LateUpdate)로 고정된다.
부분 물리·충돌 콜백은 이벤트 시점에 개별 전달 발생 빈도가 낮아 개별 호출이 타당하다. 다만 한 프레임에 몰릴 수 있으므로 큐에 모아 틱 경계에서 일괄 전달하는 편이 안전하다.

2.2 권장 형태

// ── 네이티브 → 관리: 진입점은 이것뿐 (P/Invoke 대상)
//    [UnmanagedCallersOnly] 로 export 하여 함수 포인터로 호출
Script_Awake()            // 새로 활성화된 것들 일괄 처리
Script_FixedUpdate(float) // 고정 틱
Script_Update(float)      // 프레임 틱
Script_LateUpdate(float)
Script_FlushPhysicsEvents() // 큐에 모인 충돌/트리거 일괄 디스패치
Script_OnSceneUnload()      // OnDisable/OnDestroy 일괄

// ── C# 내부: 순회는 여기서
internal static class BehaviourRegistry
{
    static readonly List<Behaviour> _update = new();

    public static void Update(float dt)
    {
        // 순회 중 추가/삭제가 일어나므로 스냅샷 또는 인덱스 순회
        for (int i = 0; i < _update.Count; ++i)
        {
            var b = _update[i];
            if (b.IsAlive && b.Enabled) b.Update(dt);
        }
    }
}
순회 중 수정 문제

Unity가 겪은 것과 같은 문제입니다 — Update 안에서 오브젝트를 파괴하거나 컴포넌트를 추가하면 순회 중인 리스트가 바뀝니다. 추가·삭제를 보류 큐에 모아 틱 경계에서 반영하는 규칙을 처음부터 넣어야 합니다. 지금 C++ 구조도 AllDestroyMark 같은 지연 파괴를 쓰고 있으므로 같은 철학입니다.

03객체 참조 모델

엔진에는 이미 HashedGuid(인스턴스 식별)와 FileGuid(에셋 식별)가 있습니다. 핸들 인프라를 밑바닥부터 만들 필요는 없고, 세대 필드만 더하면 됩니다.

// 네이티브 측: 기존 HashedGuid에 세대를 더한 형태
struct ObjectHandle
{
    uint32 index;       // 슬롯 인덱스 (O(1) 조회)
    uint32 generation;  // 슬롯 재사용 시 증가 → 낡은 핸들 자동 무효
};

// C# 측: blittable struct 그대로 대응 (마샬링 비용 없음)
public readonly struct ObjectHandle : IEquatable<ObjectHandle>
{
    readonly uint _index;
    readonly uint _generation;
}

// 사용자에게 보이는 얼굴은 얇은 래퍼
public class GameObject
{
    internal ObjectHandle Handle;
    public Transform transform => new(Native.GetTransform(Handle));
    public bool IsAlive => Native.IsAlive(Handle);   // 세대 비교 한 번
}
이 모델이 해결하는 것

Phase 1에서 잡은 본 팔레트 UAF(12.3-②)와 같은 부류의 문제가 구조적으로 불가능해집니다. 네이티브가 객체를 파괴하면 세대가 올라가고, C#이 들고 있던 핸들은 다음 접근에서 자동으로 무효 판정됩니다. Unity의 "destroyed object 접근" 예외와 같은 안전망입니다.

3.1 스크립트 간 참조는 경계를 넘지 않는다

현재 Entity::SendDamage(Entity* sender, int, HitInfo)처럼 스크립트가 서로를 직접 참조합니다. C#으로 옮기면 이건 평범한 C# 참조가 되어 경계와 무관해집니다. HitInfo 같은 커스텀 구조체도 C# 내부 타입이면 바인딩이 필요 없습니다.

즉 바인딩해야 할 표면은 "엔진이 제공하는 것"뿐입니다 — Transform, 물리 질의, 입력, 에셋 로드, 사운드 등. 스크립트끼리의 상호작용은 전부 관리 영역에서 끝납니다. 이것이 이전 작업량을 크게 줄여줍니다.

04필드 노출 (인스펙터·직렬화)

현재 C++ 스크립트는 [[ScriptReflectionField]] 어노테이션 → ScriptReflectionHeaderTool → .generated.h 흐름으로 인스펙터에 필드를 노출합니다.

런타임 리플렉션을 쓰면 AOT 문이 닫힌다

C#에서 System.Reflection으로 필드를 순회하는 방식이 가장 쉬워 보이지만, Native AOT는 사용처가 정적으로 보이지 않는 멤버를 트리밍합니다. 나중에 iOS·콘솔로 갈 때 인스펙터가 통째로 동작하지 않는 상황이 됩니다.

권장: 소스 제너레이터. 엔진이 이미 C++에서 하고 있는 것과 동일한 철학이고, 컴파일 타임에 메타데이터가 확정되므로 AOT에서도 안전합니다.

// 사용자가 쓰는 모습 — Unity와 동일한 감각
public partial class Player : Behaviour
{
    [SerializeField] float _moveSpeed = 5f;
    [SerializeField] int _maxHp = 100;

    public override void Update(float dt) { ... }
}

// 소스 제너레이터가 생성 (partial 로 합쳐짐)
partial class Player
{
    public override int FieldCount => 2;

    public override string GetFieldName(int i) => i switch
    {
        0 => "Move Speed",      // _moveSpeed 를 다듬은 표시 이름
        1 => "Max Hp",
        _ => string.Empty,
    };

    public override float GetFloat(int i) => i switch { 0 => _moveSpeed, _ => 0f };
    public override void SetFloat(int i, float v) { switch (i) { case 0: _moveSpeed = v; break; } }
}

오프셋이 아니라 인덱스 + 접근자 (구현하며 수정됨)

이 절의 초안은 FieldDesc에 필드 오프셋을 담아 네이티브가 주소로 직접 읽고 쓰는 형태였습니다. C#에서는 성립하지 않습니다 — 관리 객체의 필드 배치는 런타임이 정하고 GC가 객체를 옮길 수도 있어, 네이티브가 잡아 둔 주소는 언제든 어긋납니다.

그래서 인덱스를 키로 하는 타입별 접근자를 생성하는 쪽으로 바꿨습니다. 생성된 switch는 AOT에서도 그대로 남고 비용은 분기 한 번뿐입니다. 부수 효과로 __Serialize/__Deserialize를 따로 만들 필요가 없어졌습니다 — 인스펙터와 직렬화가 같은 접근자를 공유하면 되기 때문입니다. 네이티브는 FieldCount만큼 돌며 이름·타입을 묻고 값을 주고받습니다. 기존 YAML 포맷과의 호환은 네이티브 쪽 저장 코드에서 흡수합니다.

05핫리로드 (AssemblyLoadContext)

현재는 MSBuild로 Dynamic_CPP를 재빌드하고 LoadLibrary로 교체한 뒤, HotLoadSystem::ReplaceScriptComponent()로 씬의 인스턴스를 새 클래스로 마이그레이션합니다. CoreCLR에서는 이 흐름이 더 단순해집니다.

단계현재 (C++ DLL)CoreCLR
빌드MSBuild로 vcxproj 재빌드dotnet build (훨씬 빠름)
로드LoadLibrary + GetProcAddress 팩토리 바인딩collectible AssemblyLoadContext에 로드
상태 보존인스턴스 교체 + 필드 수동 복사직렬화 → 언로드 → 재로드 → 역직렬화
언로드FreeLibrary (참조 남으면 크래시)ALC 언로드 (참조 남으면 언로드 실패로 안전하게 드러남)
언로드의 유일한 조건

collectible ALC는 그 컨텍스트의 객체에 대한 참조가 하나도 남지 않아야 언로드됩니다. 네이티브가 GCHandle을 붙들고 있으면 조용히 실패하고 메모리가 쌓입니다. 따라서 네이티브는 관리 객체를 직접 들지 않고, 스크립트 인스턴스도 핸들(정수)로만 참조해야 합니다. 이것이 03절의 핸들 모델이 핫리로드에서도 필수인 이유입니다.

상태 보존은 04절의 생성된 직렬화 코드를 재사용하면 됩니다 — 리로드 전 __Serialize로 덤프하고, 새 어셈블리 로드 후 __Deserialize로 복원합니다. 현재 필드 수동 복사보다 견고합니다.

06AOT 대응

IL2CPP 같은 별도 라이브러리는 필요 없다

Unity가 IL2CPP를 만든 건 Mono의 AOT가 부족했기 때문입니다. CoreCLR은 Native AOT를 공식 제공하므로 그 계층을 직접 만들 이유가 없습니다. Mono를 버리고 CoreCLR로 가는 판단의 실질적 이득 중 하나입니다.

6.1 모드 분리

핫리로드와 Native AOT는 양립할 수 없습니다(AOT에는 동적 어셈블리 로딩이 없음). 따라서 하나를 고르는 게 아니라 빌드 모드를 나눕니다.

모드런타임핫리로드용도
에디터CoreCLR JIT + collectible ALC가능개발 중 반복
배포 (기본)CoreCLR JIT 또는 ReadyToRun불필요Windows 데스크톱
배포 (AOT)Native AOT 정적 링크불가iOS·일부 콘솔 진출 시

6.2 지금 지켜야 할 것

AOT를 지금 구현할 필요는 없습니다. Windows 데스크톱 타이틀이면 JIT가 금지되지 않고, 시작 시간은 ReadyToRun으로 해결됩니다. 대신 나중에 켤 수 있는 상태만 유지하면 됩니다.

금지

  • System.Reflection 기반 필드 순회
  • Expression.Compile(), Reflection.Emit
  • Activator.CreateInstance(Type) 동적 생성
  • 런타임 제네릭 인스턴스화에 의존하는 설계

권장

  • 소스 제너레이터로 메타데이터·직렬화 생성
  • 팩토리는 생성된 switch 테이블로
  • blittable struct로 경계 마샬링 회피
  • CI에 AOT 빌드 검증 잡을 일찍 추가

마지막 항목이 중요합니다 — AOT 호환성은 한 번 깨지면 원인을 찾기 어렵습니다. 실제 AOT 배포를 안 하더라도 CI에서 주기적으로 AOT 빌드를 돌려두면 위반을 즉시 잡습니다.

07이전 전략

스크립트가 348개입니다. 한 번에 옮기는 것은 비현실적이고, 그렇다고 두 스크립팅 계층을 오래 공존시키면 복잡도가 두 배가 됩니다.

권장 순서

  1. 수직 슬라이스 먼저 — 가장 단순한 스크립트 하나를 C#으로 옮겨 전 구간(빌드 → 로드 → 라이프사이클 → 인스펙터 → 직렬화 → 핫리로드)을 관통시킵니다. 여기서 설계 구멍이 전부 드러납니다.
  2. 대표 케이스 검증 — 물리 콜백을 쓰는 것, 다른 스크립트를 참조하는 것, 코루틴 성격의 것을 각각 하나씩. 바인딩 표면이 여기서 확정됩니다.
  3. 공존 기간 최소화 — 위 검증이 끝나면 일괄 포팅에 들어갑니다. C++ 스크립트와 C# 스크립트가 서로를 참조하지 못하게 막아두면(같은 씬에 섞이더라도) 공존 복잡도를 낮출 수 있습니다.
  4. Dynamic_CPP 제거 — 포팅 완료 후 HotLoadSystem·CreateFactory·코드젠 도구 2종을 정리합니다. Phase 5의 커플링 제거와 맞물립니다.
자동 변환은 기대하지 마십시오

C++ → C# 자동 변환은 포인터·매크로·템플릿 때문에 실무적으로 신뢰할 수 없습니다. 다만 라이프사이클 골격과 [[Property]] 필드 선언은 기계적이므로, 스켈레톤 생성기 정도는 만들 가치가 있습니다. 본문 로직은 수동 포팅이 전제입니다.

08프로토타입 검증 결과

설계 타당성과 디버깅 환경을 실제 코드로 확인했습니다. 네이티브 호스트(C++ exe)가 CoreCLR을 임베딩하고 C# 어셈블리를 호출하는 최소 구성으로 검증했습니다.

검증 통과 — 설계가 실제로 동작합니다

02~03절에서 제안한 구조(틱당 1회 경계 통과 + 관리 내부 순회 + 핸들 전달 + 역방향 콜백)가 그대로 작동하는 것을 확인했습니다.

결과항목확인 내용
PASShostfxr 로드 / 런타임 초기화 get_hostfxr_path → hostfxr_initialize_for_runtime_config 정상. 클래스 라이브러리는 GenerateRuntimeConfigurationFiles를 켜야 runtimeconfig.json이 생성된다.
PASSUnmanagedCallersOnly 바인딩 UNMANAGEDCALLERSONLY_METHOD로 4개 진입점을 함수 포인터로 획득. 델리게이트 마샬링 없이 직접 호출된다.
PASS틱당 1회 경계 + 내부 순회 스크립트 3개 × 5프레임 = 누적 15. 경계 통과는 프레임당 1회로 고정.
PASS관리 → 네이티브 역호출 네이티브 함수 포인터를 nint로 넘겨 C#에서 delegate* unmanaged<>로 호출. 엔진 API 제공 방식으로 유효.
PASS런타임 모듈 적재 네이티브 프로세스 안에 coreclr.dll, clrjit.dll, System.Private.CoreLib.dll, 스크립트 어셈블리가 모두 로드됨(총 35개 모듈).
제약혼합 모드 디버깅 x64에서 미지원. 아래 참조.

8.1 혼합 모드 디버깅 — 확인된 제약

CoreCLR은 x64 혼합 모드 디버깅을 지원하지 않습니다

PDB와 런타임 모듈은 모두 갖춰지지만, 관리 코드에서 네이티브로 스텝인하거나 한 세션에서 양쪽 콜스택을 함께 보는 것이 불가능합니다. .NET Framework에서는 되던 것이 CoreCLR에서 빠진 회귀 사항이며(dotnet/runtime #7547), 현재까지 해소되지 않았습니다.

실제 영향 범위

다행히 타격은 경계 지점에 국한됩니다. 01절의 "경계는 얇게" 원칙이 여기서 두 번째 이득을 줍니다.

작업디버깅영향
게임 로직 개발 (스크립트)관리 전용 디버거영향 없음 — C# 세계 안에서 완결된다
엔진 개발 (렌더/물리)네이티브 전용 디버거영향 없음 — 지금과 동일
바인딩 경계 문제 추적세션 분리 필요불편 — 아래 대응 필요

대응 방안

  1. 경계에 로깅을 의무화 — 이미 HTML 로그 시스템(0-6)과 크래시 훅이 있습니다. 경계 통과 지점(진입점 6개 내외)에 진단 로그를 넣으면 스텝 디버깅 없이도 흐름을 추적할 수 있습니다. 경계가 얇기 때문에 이 방법이 현실적으로 통합니다.
  2. 디버거 세션 분리 — 네이티브는 VS로 시작하고, 관리 코드는 별도로 "프로세스에 연결(관리 전용)"합니다. 두 세션을 동시에 띄울 수 있으며, 각각의 브레이크포인트는 정상 동작합니다.
  3. 경계 계약을 단순하게 유지 — 경계 함수가 blittable 타입만 주고받으면 마샬링 버그 자체가 발생하지 않아 디버깅 필요성이 줄어듭니다.
  4. 관리 측 예외를 네이티브로 전파하지 않기 — 경계에서 예외를 잡아 오류 코드로 변환하고 로그를 남깁니다. 경계를 넘는 예외는 디버깅이 가장 어려운 형태입니다.
전환 판단에 미치는 영향

이 제약은 CoreCLR 전환을 재고할 사유는 아닙니다. 현재 C++ 핫리로드 구조에서도 DLL 경계를 넘는 디버깅은 이미 제한적이고, Mono를 택해도 같은 문제가 있습니다. 다만 팀에 미리 공유해야 할 사항입니다 — 모르고 있다가 겪으면 전환 자체를 의심하게 됩니다.

09확정 사항

9.0 런타임 버전 — .NET 10 (LTS)

확정. .NET은 짝수 버전이 LTS이며, 10은 3년 지원을 받습니다. 게임 프로젝트는 개발·서비스 기간이 길어 LTS 고정이 맞습니다. 현재 개발 머신에 Microsoft.NETCore.App 10.0.10이 설치되어 있어 즉시 착수 가능합니다.

TargetFramework는 net10.0으로 고정하고, 배포 시 RollForward 정책을 latestPatch로 두어 보안 패치만 따라가게 합니다(마이너 버전 자동 상승 금지).

9.1 코루틴 — C# async / IEnumerator

확정. C++의 Core.Coroutine은 스크립트 관례에서 제외하고 C# 표준 방식을 씁니다. 둘의 성격이 다르므로 용도를 나누는 편이 혼란이 적습니다.

방식용도주의
IEnumerator + 커스텀 스케줄러프레임 단위 연출 (Unity의 WaitForSeconds 감각)엔진 틱에 맞춰 직접 펌핑해야 한다. 게임 시간·일시정지와 연동 가능.
async/await에셋 로드, 파일 I/O 등 비동기 작업기본 SynchronizationContext는 스레드풀이다. 게임 스레드 컨텍스트를 직접 설치하지 않으면 continuation이 워커 스레드에서 돌아 엔진 API를 건드린다.
필수 선행: SynchronizationContext

01절의 "관리 코드는 게임 스레드에서만" 규칙을 지키려면, 프레임 틱에서 continuation을 펌핑하는 커스텀 SynchronizationContext를 반드시 설치해야 합니다. 이걸 빼먹으면 await 이후 코드가 조용히 워커 스레드로 넘어가 재현이 어려운 크래시가 됩니다.

구현 범위 — Unity 친화적이되 전부는 아님

Unity 사용 경험을 그대로 살릴 수 있는 핵심만 구현하고, 렌더 파이프라인에 깊이 얽히거나 대체 수단이 있는 것은 제외합니다.

구분원형비고
필수yield return null다음 프레임까지 대기. 가장 기본.
필수WaitForSeconds(t)게임 시간 기준. 타임스케일·일시정지 영향을 받는다.
필수WaitForSecondsRealtime(t)일시정지 중에도 흐르는 UI·연출용. 위와 짝이라 함께 두는 편이 혼란이 적다.
필수WaitUntil(pred) / WaitWhile(pred)조건 대기. 구현이 단순하고 활용도가 높다.
필수WaitForFixedUpdate()물리 틱 동기화. 물리 코드와 엮인 연출에 필요.
필수중첩 코루틴 (yield return StartCoroutine(...))하위 시퀀스 대기. 없으면 연출 조합이 어렵다.
선택WaitForEndOfFrame()렌더 완료 시점 의존. 현재 멀티스레드 렌더 구조(프록시 커맨드 큐)에서 의미가 모호해 보류 권장. 스크린샷 등 실제 요구가 생기면 그때 정의.
제외AsyncOperation yield에셋 로딩 대기는 async/await 쪽으로 일원화한다. 두 갈래를 만들면 혼란만 커진다.
제외Unity 특화 타입 (UnityWebRequest 등)해당 없음.

수명 규칙 (Unity와 동일하게)

  • 오브젝트가 파괴되면 그 오브젝트의 코루틴은 자동 중단된다.
  • 컴포넌트가 비활성화되면 중단된다(재활성화해도 재개되지 않음). Unity 동작과 같게 하여 학습 비용을 없앤다.
  • StartCoroutine / StopCoroutine / StopAllCoroutines 제공.
  • 펌핑은 Update 직후 게임 스레드에서 수행하고, WaitForFixedUpdate만 물리 틱에서 처리한다.

9.2 BehaviorTree · AniBehavior — C#으로 함께 이동

확정. 현재 Dynamic_CPP가 CreateBTActionNode, CreateAniBehavior 팩토리를 함께 제공하므로, 스크립트만 옮기고 이 둘을 남기면 네이티브 핫리로드 인프라를 계속 유지해야 합니다. 함께 옮겨야 HotLoadSystem과 코드젠 도구 2종을 완전히 제거할 수 있습니다.

노드 팩토리는 소스 제너레이터로 생성한 switch 테이블로 대체하면 되고(06절 AOT 규칙과 동일), 기존 .bt 에셋 포맷은 그대로 유지한 채 노드 구현체만 관리 측으로 옮기는 형태가 됩니다.

9.3 에디터 인스펙터 — 렌더링은 네이티브 유지 (권고)

결론: 에디터 UI를 관리 코드로 옮기지 않기를 권합니다

현재 인스펙터가 이미 타입 무관 범용 렌더러이기 때문입니다. ImGuiDrawHelperModuleBehavior.cpp는 스크립트 종류마다 코드가 있는 게 아니라, Meta::Find(타입명)으로 메타데이터를 찾아 Meta::DrawProperties()에 넘기는 50줄짜리 위임 코드입니다. C# 필드 메타데이터를 같은 형태로 등록하면 기존 렌더러가 그대로 그립니다.

관점렌더링을 관리 코드로 이전메타데이터만 이전 (권고)
경계 통과 빈도치명적 ImGui는 즉시 모드라 매 프레임 수백~수천 회양호 선택 변경 시 1회, 값 편집 시 1회. 매 프레임 0회
기존 자산InspectorWindow(60KB)·MenuBar(110KB) 등 전면 재작성그대로 재사용
디버깅UI가 경계에 걸쳐 있어 08절 제약이 상시 발목UI는 순수 네이티브라 영향 없음
추가 의존성ImGui.NET 바인딩 유지보수없음

즉 C#은 "무엇을 그릴지"(필드 이름·타입·값)만 넘기고, "어떻게 그릴지"는 네이티브가 담당합니다. 01절의 경계 원칙과도 정확히 일치합니다.

다만 "C#으로 에디터 확장 작성"(Unity의 커스텀 에디터 같은 것)은 별개 주제입니다. 지금 결정할 필요는 없고, 필요해지면 확장 지점만 열어주는 방식으로 나중에 추가할 수 있습니다.

9.4 배포 형태 — 에디터와 게임을 분리 (권고)

게임 배포에는 framework-dependent를 권하지 않습니다

최종 사용자에게 ".NET 런타임을 설치하세요"를 요구하는 순간 이탈이 발생합니다. Steam 등 배포 플랫폼에서도 마찰이 되고, 사용자가 다른 버전을 설치해 두면 버전 불일치 문제가 생깁니다. 게임은 이미 수 GB 규모라 런타임 동봉분(약 70MB)은 실질적 부담이 아닙니다.

대상권장이유
에디터framework-dependent개발자는 SDK를 이미 갖고 있다. 빌드가 빠르고 산출물이 가볍다. 말씀하신 방향이 여기서는 맞습니다.
게임 배포self-contained + ReadyToRun설치 요구 제거, 버전 고정. R2R로 시작 시간 단축. 필요하면 트리밍으로 크기 축소.

두 형태는 같은 스크립트 어셈블리를 공유하므로 코드가 갈라지지 않습니다. 차이는 배포 시 PublishSelfContained 설정뿐이라 전환 비용이 거의 없습니다.

10디버깅 워크플로 규칙 (확정)

08절에서 확인한 제약(x64 혼합 모드 미지원)을 전제로 한 운영 규칙입니다.

10.1 경계 로깅 — 디버그는 항상, 릴리스는 옵트인

혼합 모드 디버깅이 막힌 만큼 경계 로그가 사실상 유일한 추적 수단입니다. 개발 중에는 항상 남기고, 배포 빌드에서는 필요할 때만 켭니다.

빌드동작
Debug / Editor경계 통과를 TRACE 레벨로 항상 기록. 기존 HTML 로그의 레벨 필터로 화면에서 걸러 볼 수 있다.
Release / 배포기본 꺼짐. 환경 변수 또는 실행 인자(--clr-trace)로 켠다. 사용자 환경에서 문제가 보고되면 로그만 켜서 재현 요청 가능.

로그 포맷

// 진입점 이름 · 인자 요약 · 처리량 · 소요 시간
[CLR] Update(dt=0.0160) → behaviours=142, 0.21ms
[CLR] FlushPhysicsEvents() → events=7, 0.03ms
[CLR] CreateBehaviour(handle=1042, type="PlayerController") → ok

소요 시간을 함께 남기는 이유는, 경계 비용이 설계 가정(틱당 1회)을 벗어나는지 감시하기 위해서입니다. Update 한 번이 수 ms로 늘어나면 관리 측 순회에 문제가 생겼다는 신호입니다.

10.2 예외 정책 — 잡아서 로그 남기고 해당 스크립트만 비활성화

스크립트 하나의 버그가 에디터 전체를 죽이지 않도록 합니다. Unity와 같은 감각이라 학습 비용도 없습니다.

public static int Update(float dt)
{
    for (int i = 0; i < _active.Count; ++i)
    {
        var b = _active[i];
        if (!b.IsAlive || !b.Enabled) continue;

        try { b.Update(dt); }
        catch (Exception ex)
        {
            // 스택 트레이스를 그대로 로그에 남긴다(ToString에 내부 예외까지 포함).
            Engine.LogError($"[{b.GetType().Name}] Update 예외 — 이 스크립트를 비활성화합니다.\n{ex}");

            // 같은 예외가 매 프레임 반복되어 로그가 폭주하는 것을 막는다.
            b.Enabled = false;
        }
    }
    return 0;
}
비활성화를 사용자에게 알리기

예외로 꺼진 스크립트는 인스펙터에 경고 표시를 남깁니다. 조용히 동작을 멈추면 "왜 안 되지"로 시간을 버리게 됩니다. 핫리로드 시 다시 활성화되므로, 코드를 고쳐 저장하면 자연스럽게 복구됩니다.

물리 콜백·Awake·Start 등 다른 진입점도 동일하게 감쌉니다. 경계를 넘어 네이티브로 전파되는 관리 예외는 0건이어야 합니다.

10.3 세션 분리 절차

네이티브와 관리를 한 세션에서 동시에 볼 수 없으므로, 필요에 따라 두 방식 중 하나를 씁니다.

상황절차
엔진 코드 디버깅평소대로 VS에서 Academy_4Q를 F5로 시작. 지금과 완전히 동일하다.
스크립트 디버깅① 에디터를 실행(F5 또는 직접 실행) → ② VS 디버그 → 프로세스에 연결 → ③ 대상 Academy_4Q.exe 선택 → ④ 연결할 코드 유형에서 "관리(.NET Core)" 선택 → ⑤ C# 브레이크포인트 설정.
경계 문제 추적스텝인이 불가하므로 10.1의 경계 로그로 좁힌 뒤, 어느 쪽 문제인지 판명되면 해당 유형으로 연결해 디버깅.

④를 빠뜨리면 네이티브 유형으로 연결되어 C# 브레이크포인트가 걸리지 않습니다. 가장 흔한 실수이므로 팀 온보딩 문서에 명시할 것.

10.4 경계 시그니처 체크리스트

마샬링 버그는 디버깅이 가장 어려운 부류이므로, 경계 함수는 리뷰 시 아래를 확인합니다.

허용

  • 정수·부동소수 (int, float, long…)
  • 포인터/핸들 (nint, ObjectHandle)
  • blittable 고정 크기 struct
  • UTF-8 바이트 포인터 + 길이 (문자열)

금지

  • string 직접 전달 (마샬링 발생)
  • 배열·컬렉션 직접 전달
  • 클래스 참조
  • bool (크기가 플랫폼마다 다름 → int 사용)

11바인딩 표면 설계 (실측 기반)

07절이 “바인딩 표면은 대표 케이스 검증에서 확정된다”고 미뤄둔 부분입니다. 추측으로 API 목록을 만드는 대신, 기존 스크립트 348개 파일 · 32,010줄이 실제로 무엇을 얼마나 호출하는지 전수 조사한 결과를 근거로 삼았습니다.

11.1 실측 호출 분포

이 분포가 바인딩 우선순위와 최적화 대상을 결정합니다. 상위 6종이 전체 호출의 대부분을 차지합니다.

조사가 뒤집은 가정 세 가지

  • 코루틴은 실제로 쓰이지 않는다. 스크립트 전체에서 Coroutine·co_await·IEnumerator 검색 결과 0건입니다. 상태 플래그 + Update(tick) 폴링으로 대체하는 패턴이 일관되게 쓰이고 있습니다. 따라서 09.1에서 확정한 코루틴 스케줄러(필수 6종)는 포팅 경로의 선행 과제가 아니라 신규 편의 기능입니다. 이전 작업에서 빼고 나중에 독립적으로 넣어도 됩니다 — 일정에서 상당 부분을 덜어냅니다.
  • Time 클래스도 거의 쓰이지 않는다. 델타타임은 Update(float tick) 매개변수로 직접 받는 방식이 202곳입니다. Time 바인딩은 최소 표면만 두면 됩니다.
  • Transform은 컴포넌트가 아니다. GameObject의 값 멤버(m_transform)입니다. 다만 스크립트가 GetComponent<Transform>()도 실제로 쓰고 있어(Player.cpp:79), C# 측은 두 접근을 모두 지원해야 합니다.

11.2 경계를 넘는 것과 넘지 않는 것

03.1에서 확정한 “스크립트 간 참조는 경계를 넘지 않는다”를 실측에 적용하면, 상위 호출 상당수가 경계를 통과하지 않습니다. 이것이 이 설계의 핵심 이점입니다.

구분대상처리
C# 내부 완결스크립트 → 스크립트 참조, GetOwner(), 스크립트의 SetEnabled, 스크립트 간 이벤트관리 객체 그래프에서 직접 해결. P/Invoke 없음.
경계 통과엔진 컴포넌트(Transform·Animator·SoundComponent·ImageComponent) 접근, 씬 조회, 프리팹, 물리, 입력평면 C ABI. 아래 표면 정의.
// GetComponent는 T가 무엇이냐에 따라 갈린다 — 685회 호출의 성격을 나누는 지점
public T GetComponent<T>() where T : Component
{
    if (ComponentKind<T>.IsManaged)          // 스크립트(Behaviour 파생)
        return _managedComponents.Get<T>();   // 경계 없음

    // 엔진 컴포넌트 — 핸들만 받아 얇은 래퍼로 감싼다
    ObjectHandle h = Native.GameObject_GetComponent(_handle, ComponentKind<T>.NativeTypeId);
    return h.IsValid ? NativeComponentCache.Wrap<T>(h) : null;
}

ComponentKind<T>의 IsManaged와 NativeTypeId는 소스 제너레이터가 컴파일 타임에 채웁니다(04절·06절과 같은 방식). 런타임 리플렉션을 쓰지 않으므로 AOT에서도 안전합니다.

11.3 문자열 — 해시로 넘긴다

문자열 인자를 받는 호출이 Find 181 + LoadPrefab 94 + 사운드 이름 183 등 460회 이상입니다. string을 그대로 넘기면 호출마다 마샬링이 발생합니다. 다행히 엔진은 이미 HashingString을 쓰고 있으므로, 해시 값(blittable)을 넘기는 것이 자연스러운 대응입니다.

// 사용자가 쓰는 모습은 그대로 문자열
var boss = GameObject.Find("Boss");

// 소스 제너레이터가 리터럴을 컴파일 타임 해시로 치환 → 마샬링 0
var boss = GameObject.FindByHash(0x8A31_C4E2 /* "Boss" */);

// 런타임 문자열은 캐시를 거친다(같은 문자열 반복 조회가 대부분이다)
var obj = GameObject.Find(runtimeName);   // 내부에서 해시 캐시 조회

해시 충돌 시 동작은 네이티브 쪽 기존 규칙을 그대로 따릅니다(이름 조회는 원래도 충돌 가능성을 안고 있었습니다). 진단이 필요한 디버그 빌드에서만 원본 문자열을 함께 넘겨 검증하는 옵션을 둡니다.

11.5 물리 결과 배열 규약

T3에서 유일하게 형태를 미리 정해둬야 하는 부분입니다. 관리 측 배열을 네이티브가 할당하게 하면 소유권이 복잡해지므로, 호출자가 버퍼를 주고 네이티브는 채우기만 하는 형태로 고정합니다.

// 네이티브: 채운 개수를 반환. 버퍼가 모자라면 cap까지만 채우고 실제 필요 개수를 음수로 알린다.
extern "C" int Physics_RaycastAll(float3 origin, float3 dir, float dist,
                                 uint32 layerMask, RaycastHit* buffer, int capacity);

// C#: stackalloc으로 할당 없이 처리. 대부분의 호출은 결과가 몇 개뿐이다.
Span<RaycastHit> hits = stackalloc RaycastHit[16];
int n = Physics.RaycastAll(origin, dir, dist, mask, hits);

RaycastHit은 blittable struct로 정의합니다(위치·법선·거리·ObjectHandle). 08절에서 검증한 물리 콜백 구조체와 같은 원칙입니다.

규모 재평가

스크립트 본문 32,010줄에 BT·AniBehavior 5,300줄이 더해집니다. 자동 변환은 여전히 기대할 수 없지만(07절), 조사에서 코루틴 0건 · Time 사실상 미사용이 확인되어 선행 인프라가 줄었습니다. 반대로 사운드 API 435회는 초기 예상보다 훨씬 큰 비중이라 T2에서 확실히 다뤄야 합니다. [[Property]] 413개 · [[Method]] 112개는 소스 제너레이터가 기계적으로 흡수하므로 수동 작업 대상이 아닙니다.

이 문서는 스크립트 계층을 Dynamic_CPP(C++ 핫리로드)에서 CoreCLR로 전면 대체한다는 결정을 전제로 작성되었습니다. 구현 전 대시보드 2-0(경계 설계)에서 핸들 타입과 소유권 규칙이 먼저 확정되어야 합니다. 11절의 호출 분포는 2026-07-29 기준 Dynamic_CPP\Assets\Script 전수 조사 결과입니다.
