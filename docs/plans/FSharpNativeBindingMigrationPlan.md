# F# 네이티브 바인딩 전환 계획

> 2026-10-29 진행 기록: API 46 F# 바인딩과 제품 기본 경로를 구현했고 Editor·Player·Headless의 Debug/Release 실행, 에셋·오디오, 재로드 및 성능 비교를 수행했다. 기존 ScriptCore는 별도 비교 빌드에서만 선택된다. 상세 결과와 성능 차이는 [검증 기록](../analysis/FSharpNativeBindingAcceptance20261029.md)을 따른다. 아래 작성 당시의 기준과 단계 완료 조건은 그대로 보존한다.

> 2026-10-28 작성 · 기준 HEAD `27394992c` · 계획, 미구현. 기존 [F# 스크립팅 계약](../design/FSharpScriptingContract.md)의 C# ScriptCore 유지 결정을 이 전환의 목표로 대체한다. 실제 계약 문서는 전환 수용 시 갱신한다.

## 목표와 범위

게임 스크립트와 공통 관리 실행기에 더해 엔진의 관리 API와 네이티브 진입점도 F#으로 구현한다. C++ 엔진과 CoreCLR 사이는 기존처럼 명시적인 네이티브 ABI로 연결한다. 최종 제품 경로에서 `ScriptCore.dll`과 C# 바인딩에 의존하지 않는다. C++ 클래스 ABI를 F#에 직접 노출하거나 CoreCLR을 제거하는 계획은 아니다.

제품 스크립트의 기존 소스 사용법, 직렬화 형식, 고정틱 및 생명주기 의미, 수명·세대·스레드 규칙을 기본적으로 유지한다. C#으로 작성된 빌드 도구와 내부 회귀 픽스처의 언어까지 일괄 제거하는 것은 범위 밖이며, ScriptCore 참조를 없애거나 별도 비교 fixture로 전환하는 작업은 포함한다. 공개 C# 스크립트 호환성을 새로 약속하지 않는다.

## 현재 기준과 전환 대상

- `Engine/SceneRuntime/ClrHost.cpp`는 `ScriptCore.dll` 및 runtimeconfig를 찾고 관리 진입점을 바인딩한 뒤 API 테이블을 전달한다. `ManagedAssembly.cpp`는 hostfxr로 관리 함수를 로드한다.
- `ScriptCore/Native.cs`의 순차 API 테이블은 버전 45와 구조체 크기를 검사한다. `Bootstrap.cs`의 unmanaged 진입점은 초기화·종료, 틱, 스크립트·필드 및 각종 이벤트를 연결한다. 양방향 호출 계약을 전부 목록화한다.
- `ScriptCore`는 `Component`, `Entity`, 네이티브 컴포넌트 wrapper, 값 형식, 에셋·오디오·물리·입력, 직렬화, 메시지 및 예외/수명 처리도 소유한다.
- `ScriptRuntime`은 F# 실행기이지만 `ScriptCore` 계약을 참조한다. `Loader.fs`는 실제 엔진 바인딩 어셈블리를 공유하고 게임 의존성을 collectible 세대별로 로드한다.
- `GameScripts.fsproj`와 외부 `FSharp_Tool_Pakage_for_CreatorEngine`의 FCS 분석기·생성기는 Component, 필드 접근자, 메시지, factory와 typed lifecycle 계약을 소비한다. `ScriptCore.Generators`는 C#용 생성기이며 F# 제품 생성기와 구분한다.
- 2026-10-23의 [기존 수용 기록](../analysis/FSharpManagedRuntimeAcceptance20261023.md)은 API45의 기준 사례다. 새 구현의 실행 결과로 간주하지 않는다.

## 유지할 불변 조건

- API 테이블의 호출 규약, 필드 순서·크기·정렬, 구조체 레이아웃, 문자열 인코딩, null·오류 및 포인터 수명을 양쪽에서 검증한다. 계약이 변하면 버전을 올리고 구버전을 명시적으로 거절한다. 구현 언어 변경만으로 ABI 버전 변경이 필수인 것은 아니다.
- 네이티브는 고정틱당 한 번 관리 배치로 진입한다. API45의 선택적 일반 멤버 11종, 정적 콜백, `OnTickSimulate(single)` 및 tick/물리/접촉/snapshot 순서를 유지한다. 핫 경로에 reflection과 반복 할당을 추가하지 않는다.
- Entity generation, PhysicsBody/CCT의 NativeInstance, 게임 스레드, Enabled, 재진입 및 예외 격리, 구독·continuation 정리와 에셋 수명을 유지한다. 네이티브 경계로 관리 예외가 넘어가지 않는다.
- 실패한 reload는 이전 코드·인스턴스·등록을 보존한다. 성공 시 이전 세대의 callback·인스턴스·구독·재개 참조를 해제하고 collectible ALC 수거를 확인한다. hostfxr의 실제 엔진 컨텍스트를 사용하며 Default라고 가정하지 않는다.
- `compile.order`, 지원 직렬화 필드 종류·이름·기본값, 인스펙터와 기존 씬 데이터의 의미를 유지한다. 게임과 엔진 측 FSharp.Core의 소유 컨텍스트 및 배포 경로를 각각 확인한다.

## 단계별 작업

### FNB-0 — 기준선과 전체 소비자 목록

1. 현재 API 테이블, C++ `FillApiTable`, 관리 진입점과 host 바인딩을 이름·순서·서명·호출 규약별로 대조한다. 비필수 진입점과 버전/크기 오류 처리까지 기록한다.
2. ScriptCore의 공개 타입과 각 멤버의 실제 소비자, 소유·해제 책임, 직렬화 및 생성 코드 계약을 분류한다. Editor, Player, HeadlessHost, BuildTool, SDK/패키징, 회귀 도구와 외부 F# 저장소도 포함한다.
3. 기존 API45의 관리·Editor·cooked Player·Headless 회귀와 Debug/Release 성능 및 할당 기준을 현재 소스 신원으로 재측정한다. 기존 기록은 비교 자료로만 사용한다. 테스트용 입력과 패키지 hash를 보존한다.

**완료:** 양방향 ABI 및 소비자 목록, 실행 가능한 회귀 매트릭스, 동일 조건의 기준 결과가 기록된다. 누락된 기준은 미수용으로 남긴다.

### FNB-1 — F# 양방향 ABI 실험과 방식 결정

1. 별도 작은 F# 실험에서 C++ 테이블 바인딩, 버전/크기 거부, 로그, 핸들, UTF-8, 포인터, 구조체 인자·반환값을 검증한다. C++에서 F#의 unmanaged 진입점을 hostfxr로 얻어 초기화·틱·종료하고 예외를 차단한다.
2. 기존 테이블의 함수 포인터를 F#에서 호출할 수 있는 구현을 평가한다. 델리게이트 변환은 초기화 때 캐시하고 호출 규약·수명·마샬링을 검사한다. 대안으로 C ABI export와 F# P/Invoke를 평가하되 호스트/배포 변경을 함께 명시한다. 함수 포인터 직접 호출과 동등하다고 가정하지 않는다.
3. 동일한 네이티브 작업에 대해 기존 C#과 후보를 Debug/Release에서 반복 측정한다. 호출 비용·할당 외에도 실제 스크립트 틱과 전체 프레임을 짝지어 비교한다. 실패·불일치 및 성능 결과를 기록하고 채택 방식을 정한다.

**완료:** 양방향 실행, ABI 검사와 후보별 측정이 통과하고 채택 경로 및 비용이 결정된다. 후보가 기존 필수 동작이나 예산을 만족하지 못하면 다음 단계로 넘어가지 않고 원인을 해결한다.

### FNB-2 — F# 바인딩 기반과 호스트 부팅

1. F# 바인딩 어셈블리의 이름, 프로젝트 및 파일 순서를 정하고 ABI 타입, 테이블 바인딩·해제, `ObjectHandle`, 수학 값 형식과 로그를 구현한다. ABI 정의의 정본과 대조 검사를 추가한다.
2. F# unmanaged 진입점에 초기화·종료 및 오류 변환을 옮긴다. 호스트가 새 어셈블리/runtimeconfig를 선택하게 하며 초기화 실패 시 자산 세션 및 바인딩을 정리한다.
3. 상주 엔진 컨텍스트, 엔진 FSharp.Core와 스크립트 private FSharp.Core의 로딩을 연결한다. 참조 순환을 피하도록 공개 계약과 실행기 프로젝트 경계를 확정한다.

**완료:** Editor, Player, Headless에서 관리 초기화·종료와 실패 경로가 동작하고 실제 바인딩 어셈블리의 단일 타입 정체성이 확인된다.

### FNB-3 — 최소 스크립트 종단 경로

1. `Component`, `Entity`, `NativeComponent`, `Transform`, lifecycle 및 factory 계약을 F#으로 옮긴다. 기존 API의 null, 캐시, 유효성·소유권 의미를 보존한다.
2. 기존 F# 실행기의 계약 참조를 새 바인딩으로 옮기고 생성·등록·고정틱·제거를 연결한다. F# 생성기 출력과 `FSharpNativeMover.fs`를 새 계약으로 빌드한다.
3. 실제 엔진에서 스크립트 생성 → `GetComponent<Transform>` → 캐시 → 틱 이동 → 종료를 검증한다. 없는 Transform, 죽은 핸들, 중복 틱, 예외와 자기 비활성화도 확인한다.

**완료:** 동일 씬의 이동 결과, 호출 순서 및 실패 처리와 기존 경로가 일치하고 핫 틱의 추가 할당·호출 비용을 기록한다.

### FNB-4 — 직렬화·생성기·재로드

1. `SerializeField`, 필드 종류·인덱스 기반 읽기/쓰기, 메시지 dispatch 및 `ScriptLifecycle`의 CLR 표면을 옮긴다. 외부 F# 분석기/생성기와 도구 버전·참조 경로를 갱신한다.
2. 기존 씬/스크립트의 필드 이름·종류·기본값과 Inspector 편집·저장·재로드 결과를 비교한다. 누락 필드와 잘못된 lifecycle 서명은 기존 규칙대로 거절한다.
3. 실패한 후보 reload의 기존 세대 보존, 성공한 reload의 객체·callback·구독·continuation 정리 및 이전 ALC 수거를 검사한다. 엔진과 게임의 FSharp.Core 및 private dependency 해석을 검증한다.

**완료:** 기존 직렬화 자산 왕복과 생성기 계약 비교, 성공/실패 reload 및 반복 수거 검사가 통과한다.

### FNB-5 — 전체 API 및 수명 이전

1. 실제 소비자를 기준으로 입력·카메라·렌더 컴포넌트, 물리/CCT·접촉, 오디오, 에셋·프리팹, 애니메이션·BT, simulation·diagnostics 순으로 옮긴다. 각 기능은 선언만이 아니라 C++ 호출과 반환·오류 경로까지 완성한다.
2. 각 묶음에서 C++과 타입·레이아웃을 비교하고 실제 F# 스크립트의 정상/실패·생성/해제·씬 전환 및 stale handle을 검증한다. 에셋 release queue, 게임 스레드 재개, 이벤트 payload와 리로드 시 구독 해제를 포함한다.
3. Span/byref, null, out, bool, 문자열, 구조체의 F# 소비·네이티브 표현을 개별 확인한다. 반복 접촉 및 캐시된 컴포넌트 접근의 기존 할당 기준을 유지한다.

**완료:** FNB-0의 공개 API·소비자 목록에 미이전 항목이 없고 각 기능의 실행 및 수명 회귀가 통과한다.

### FNB-6 — 제품 빌드·패키징 전환

1. Editor/Player/Headless, BuildTool 및 SDK의 참조와 파일 목록, runtimeconfig/deps, FSharp.Core 복사, 스크립트 컴파일 및 IDE 참조를 새 산출물로 전환한다. `Tools/build/stage-headless.ps1` 등 명시적 ScriptCore 목록을 갱신한다.
2. 깨끗한 출력에서 Debug/Release 빌드 및 패키징한다. Editor 저작·컴파일·재로드, cooked Player 실행, Headless 실행을 검증하고 패키지 파일과 hash를 확인한다. 이전 빌드 산출물이 성공을 가리지 않도록 각 실행의 산출물 신원을 기록한다.
3. 내부 C# 회귀는 새 공개 .NET 계약을 참조하도록 전환하거나 F# 회귀로 대체한다. C# 생성기 및 비교 fixture의 필요성을 소비자별로 판정한다.

**완료:** 세 제품 경로가 새 산출물만으로 실행되고 `ScriptCore.dll` 없이 배포·저작·재로드가 성립한다.

### FNB-7 — 기존 경로 제거와 최종 수용

1. 제품 참조 및 배포물에서 ScriptCore와 이전 unmanaged 바인딩을 제거한다. 저장소와 외부 도구의 참조를 다시 검색하여 남은 비교 도구는 목적을 기록한다. 오래된 DLL이 있더라도 선택되지 않는지 확인한다.
2. 전체 생명주기, 고정틱·물리·접촉, Editor 직렬화, 재로드, 오디오/에셋, 예외·스레드·수명, cooked Player 및 Headless 회귀를 실행한다. ABI 버전 불일치, 누락 파일과 잘못된 스크립트의 실패 경로를 포함한다.
3. 기준과 같은 장면·설정에서 Debug/Release 할당 및 성능을 비교한다. 호출 미세 측정과 전체 프레임을 별도로 보고한다. 결과에 회귀가 있으면 원인을 해결하거나 명시된 예산과 함께 판정한다.
4. 현재 계약과 `ScriptSurfacePlan`을 새 구현에 맞게 갱신하고 이전 C# 바인딩 유지 결정을 역사 기록으로 구분한다. 코드 신원·명령·결과·미수용 항목을 수용 기록에 남긴다.

**최종 완료:** 제품의 C# ScriptCore 참조와 배포 의존성이 없고, 위 제품·계약·수명 회귀와 성능 판정이 새 소스 신원으로 완료된다.

## 의존 관계와 전환 원칙

`FNB-0 → FNB-1 → FNB-2 → FNB-3 → FNB-4 → FNB-5 → FNB-6 → FNB-7`. FNB-5의 독립 API 묶음은 FNB-3 기반 위에서 병행할 수 있지만 공통 ABI·프로젝트 파일 변경은 단일 소유자가 통합한다. 각 단계에서 기존 동작을 비교 기준으로 유지하고 최종 수용 전 기존 경로를 삭제하지 않는다. 두 경로가 같은 실행에서 상태를 이중 소유하거나 틱을 중복 호출하지 않게 전환 경계를 둔다.

공수는 FNB-0 소비자 목록과 FNB-1 호출 방식 결정 후 산정하도록 계획했다. 이 문서 작성 당시에는 모든 단계가 미착수였으며, 계획 작성 자체는 빌드·실행·성능 수용이 아니었다. 이후 실행 결과와 범위는 상단의 검증 기록을 따른다.
