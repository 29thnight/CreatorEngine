§0

0. 왜 이 페이즈인가 — GI가 있어도 라이트맵을 쓴다

현재 이 엔진의 GI 는 전부 스크린스페이스다(SSAO·SSGI·SSR·SSS + IBL). 화면 밖을 아는 경로가 하나도 없다 — 프로브도 볼륨도 라이트맵도 없다. 실내 씬에서 카메라 밖 벽면의 간접광은 구조적으로 계산할 방법이 없다.

스크린스페이스 GI 의 원리적 한계는 넷이다.

못 하는 것결과
화면 밖 지오메트리의 간접광시야 밖 벽의 반사광이 없다
카메라 회전 시 일관성시선을 돌리면 조명이 변한다
시간축 안정성히스토리 누적 → 잔상·노이즈, 디노이징 비용
원거리 바운스트레이스 거리에 묶인다

상용 엔진이 실시간 GI 를 갖고도 라이트맵을 유지하는 이유가 이것이다. 둘은 대체재가 아니라 보완재다 — 라이트맵이 간접광의 본체를 담당하고, 스크린스페이스는 라이트맵 해상도가 못 잡는 접촉 음영을 메꾼다.

세 노선의 비용 비교:

노선비용이 엔진의 상태
라이트맵언랩 + 베이커 + UV1 스트림저작 표면 있음 · 삭제된 구현 있음
프로브/볼륨프로브 배치 + 볼륨 구조전부 신설
실시간 GI매우 큼전부 신설

라이트맵이 가장 싸고 절반쯤 깔려 있다.

1.2 구조 — 코루틴 프레임 페이싱

GenerateLightmapCoroutine 이 co_yield OnRender() 로 프레임마다 양보한다. 활성 yield 30개(주석 포함 36).

문제 셋:

  1. 베이크 속도가 프레임레이트에 묶인다. 60fps 면 yield 하나가 16.6ms 다. 렉트 100 + 라이트맵 4장이면 준비만 500회 yield → 8초가 순수 대기이고 그동안 GPU 는 논다.
  2. 에디터와 GPU 를 경합한다. co_yield OnRender() 가 렌더 프레임을 그대로 돌리므로 베이크 디스패치와 에디터 렌더가 같은 큐를 나눠 쓴다.
  3. 중단·재개가 코루틴 프레임에 묶인다. 취소하면 어디까지 했는지 복구할 구조가 없다.

★ 코루틴의 의도는 옳았다 — "에디터가 얼어붙지 않게". 수단이 틀렸을 뿐이다. GPU 작업을 프레임마다 하나씩 던지는 대신 워커에서 연속 기록하고 타임슬라이스로 제어해야 한다(§2.3).

1.3 알고리즘 — 여덟 군데

#문제실측/근거
①디스패치가 렉트마다 전체 캔버스Dispatch(canvasSize/16, canvasSize/16) 후 셰이더가 Offset/Size 밖에서 return. canvasSize=1024·rectSize=400 이면 유효 스레드 15.6% — 84% 낭비. 렉트가 작을수록 악화(128²면 98.5% 낭비)
②BVH median split + 축 라운드로빈axis = depth % 3(최장축 아님), mid = (start+end)/2(SAH 아님). SAH 대비 트래버설 통상 1.5~2배
③분할마다 std::sort → O(N log²N)nth_element 면 분할당 O(N) → 전체 O(N log N). log N 배
④비교자가 데이터를 쓴다t2.tempColor = {1,0,0} — std::sort 의 Compare 는 인자를 수정하면 안 된다(표준 요구 위반)
⑤패킹이 Shelf First-Fit헤더 주석은 // Guillotine Algorithm 인데 구현부는 // Shelf First-Fit. MaxRects 대비 점유율 통상 10~20%p 낮다
⑥패킹 정렬이 오름차순return a.h < b.h — Shelf 계열 표준은 Decreasing Height(큰 것부터)
⑦렉트 크기가 표면적과 무관size = rectSize * lightmapScale 로 정사각형 고정. 거대한 바닥과 작은 소품이 같은 400×400 → 텍셀 밀도 통제 불가
⑧라이트 루프가 항상 20회for (i = 0; i < MAX_LIGHTS; ++i) — lightSize 가 CB 에 있는데 미사용

간접광 커널은 [numthreads(32,32,1)] = 1024 스레드/그룹(API 한계치)이다. 스레드마다 uint stack[64] BVH 스택을 들므로 레지스터·스크래치 압박이 크다 — occupancy 측정 후 8×8 또는 16×16 로 내리는 것을 검토한다.

1.4 조용히 틀리는 결함 다섯

#결함증상
1BVH 리프 off-by-one — 셰이더가 i <= node.end 인데 C++ 은 [start, end)이웃 리프의 삼각형을 잘못 검사. 마지막 리프는 버퍼 범위 밖 → 가짜 그림자. 직접광·간접광 커널 양쪽에 있다

4efficiency 로그 — useSpace 가 새 라이트맵에서 리셋로그가 마지막 장만 보고한다
5바운스마다 텍스처 배열 재생성 — CreateTexture2D 가 indirectCount 루프 안해제 경로 확인 필요(누수 의심)

★ 1번은 git 이력의 7a4f1a79 "SSR, lightmap BVH indice 오류 수정" 과 같은 자리다 — 한 번 만졌지만 남아 있다.

2. 병렬화 설계

2.1 병렬 축 전수

축현재가능한 것기대
텍셀GPU 스레드 — 이미 병렬디스패치를 렉트 크기로활용률 15.6% → ~100% (6.4배)
렉트렉트당 Dispatch 1회 + CB·SRV 재바인딩렉트 표를 StructuredBuffer 로 올리고 배치 디스패치 1회Dispatch N→1, 상태 변경 소멸
라이트맵 장순차async compute 큐로 겹침GPU 미포화일 때만
간접광 샘플텍셀 내부 루프 512회샘플을 여러 디스패치로 쪼개 누적(progressive)응답성·미리보기·취소
BVH 빌드단일 스레드 재귀 + std::sort상위 레벨 순차 + 서브트리 태스크 병렬, 또는 GPU LBVH(Morton+radix sort)CPU 시간
삼각형 수집단일 스레드메시별 병렬 후 concat소소
전체 진행프레임당 1스텝워커 스레드 + 전용 큐페이싱 제거

2.2 ★ 순서 — 낭비 제거가 병렬화보다 먼저다

84% 낭비를 그대로 두고 병렬화하면 낭비를 병렬로 하는 것이다.

착수 순서는 이렇게 고정한다.

① 디스패치를 렉트 크기로        → 6.4배 (병렬화 아님, 낭비 제거)
② 코루틴 페이싱 제거            → yield 수만큼의 순수 대기 소멸
③ BVH를 SAH + nth_element로     → 트래버설·빌드 양쪽
④ 그다음에 비로소 병렬화 판정

①②를 하기 전의 측정치로 병렬화 이득을 추정하면 안 된다. 이 저장소에는 그 전례가 있다 — encoder-bench 가 모형만 재고 있었고, 자를 먼저 고치자 결론이 뒤집혔다. Release 로만 판정한다(Debug 는 같은 조건에서 25배 느리고 규모별 개선 방향까지 뒤집는다).

2.3 백그라운드 베이킹 — 에디터를 막지 않는다

목표를 정확히 적는다. "에디터에 영향이 없다"는 상용 엔진도 못 한다. Unity Progressive Lightmapper 도 UE5 GPU Lightmass 도 베이크 중 뷰포트가 느려진다 — 같은 GPU 를 나눠 쓰기 때문이다. 달성 가능한 목표는 non-blocking 이다.

요구뜻
씬 편집·이동·저장이 계속 된다베이크가 게임 스레드를 잡지 않는다
뷰포트가 계속 갱신된다느려질 뿐 멈추지 않는다
진행률이 보이고 취소된다상태가 코루틴 프레임에 숨지 않는다
편집하면 무효화·재시작밀봉 스냅샷과 무효화 정책

현재 코루틴 방식은 이 중 하나도 제대로 못 한다. 프레임마다 한 단계씩만 던지므로 GPU 가 놀고, 진행이 프레임레이트에 묶이며, 상태가 코루틴 프레임에 갇힌다.

★ 실측 — 지금 큐가 하나뿐이다

CreateCommandQueue(D3D12_COMMAND_LIST_TYPE_DIRECT)   ← 유일

DX12DeviceResources.cpp:296 의 그래픽스 큐 하나가 전부다. COMPUTE 큐도 COPY 큐도 없고, 커맨드 리스트도 전부 TYPE_DIRECT 다. AsyncCompute 는 코드에 0건이다. 공통 queue/fence 기반은 RenderGraphDependencySchedulingPlan RG8에 배치했다.

같은 DIRECT 큐에 베이크를 넣으면 에디터 프레임과 직렬화된다 — 베이크 디스패치가 길면 그만큼 프레임이 통째로 밀린다. 백그라운드 베이킹의 1번 전제가 별도 큐다.

필요한 것 셋

#필요현 상태
1별도 COMPUTE 큐 + 큐 간 펜스없음 — 신설
2GPU 타임슬라이스 — 디스패치를 예산 단위로 분할없음(코루틴은 프레임 단위)
3씬 밀봉 스냅샷 + 무효화 정책인프라 있음 — 프레임 스냅샷 이중 버퍼 게시를 같은 원리로

2번을 빼면 큐를 나눠도 소용이 없다. 디스패치 하나가 길면 GPU 가 그동안 점유되고, Windows TDR(기본 2초) 에 걸리면 디바이스가 리셋된다. 렉트 단위·샘플 단위로 쪼개 프레임당 예산(예: 8ms) 안에 넣어야 한다 — 이것이 progressive baking 의 본질이고, 코루틴이 하려던 것과 같지만 단위가 프레임이 아니라 GPU 시간이어야 한다.

재사용할 수 있는 것 / 없는 것

RHIParallelCommandPool 이 이미 워커 8개 병렬 커맨드 기록을 제공한다(3-15A). 다만 RunParallel 이 join 까지 대기하는 fork-join 이라 프레임 안의 작업용이다. 베이크는 프레임 경계를 넘어 살아야 하므로 수명 모델이 다르다 — 기록 인프라는 빌리되 스케줄링은 별도로 세운다.

2.3-a 스레드 모델

현재 엔진은 Game / CommandBuild / CommandExecute 3스레드 락스텝이다. 베이크는 에디터 전용 작업이므로 그 락스텝에 끼워 넣지 않는다.

                    ↓
            [Game 스레드] 진행률 UI 만 읽는다
  • D3D12 는 커맨드 리스트 기록이 스레드 안전하므로 워커에서 기록할 수 있다.
  • 프레임당 GPU 예산(예: 8ms)을 두어 에디터 응답성을 확보한다 — 코루틴이 이루려던 목적을 더 정밀하게 달성한다.
  • 취소·재개는 단계 경계의 명시적 체크포인트로 처리한다. 코루틴 프레임에 상태를 숨기지 않는다.

★ 주의: 베이크 중 씬이 바뀌면 결과가 무의미해진다. 베이크 시작 시 지오메트리·조명을 밀봉하고(스냅샷) 그 위에서만 돈다 — 렌더 스레드의 프레임 스냅샷과 같은 원리다.

2.4 병렬화가 이득이 아닌 경우

  • async compute 는 두 큐가 같은 SM 을 나눠 쓰므로, 베이크가 이미 GPU 를 채우면 오히려 느려진다. RhiBoundaryPlan 의 판정 기준을 그대로 적용해 패스별로 잰다.
  • CPU 병렬 BVH 는 삼각형 수가 적으면 태스크 오버헤드가 이득을 먹는다. 실측 후 임계 삼각형 수를 정한다.

§3

3. 설계 결정

3.1 UV1 언랩은 xatlas 로

라이트맵은 non-overlapping UV 언랩이 전제인데 현 자산에 UV1 이 하나도 없다 (원본 glb 12개 전수 TEXCOORD_1 0건). xatlas 는 언랩과 아틀라스 패킹을 함께 해결하므로 §1.3 의 ⑤⑥⑦을 한 번에 닫는다.

이 저장소는 이미 fastgltf·ufbx·mikktspace 를 원본 무수정으로 벤더링하는 관행이 있다. 같은 규약을 따른다.

3.2 UV1 은 옵셔널 스트림이다

PHASE 3.75가 게시한 vertex attribute schema의 UV1 optional slot을 이 계획이 처음 생산·소비한다. 라이트맵 대상 메시에만 UV1 스트림이 붙는다 — 스킨 캐릭터를 포함한 전 정점에 8B를 부과하지 않는다.

★ 언랩은 이음매에서 정점을 쪼개므로 정점 수 자체가 바뀐다. 즉 기존 uv1 슬롯을 재사용하는 것이 아니라 언랩 단계에서 스트림을 새로 만든다.

3.3 텍셀 밀도가 정본이다

렉트 크기는 표면적 × 텍셀밀도(texels per unit) 로 산출한다. lightmapScale 은 그 위의 배율로 남긴다 — 지금처럼 크기의 유일한 결정자가 되어서는 안 된다.

§4

4. 이행 — 슬라이스

L0. 기준선 — 삭제된 구현 복구·계측

되살려 돌리는 것이 목적이 아니라 재작성의 정답지를 만드는 것이 목적이다.

  • 삭제분을 참조용으로 뽑아 두고(이 문서 §1 이 그 요약이다) 알고리즘 의도를 확정
  • 비교용 씬 확보 — 실내(간접광이 지배적) 1개 이상 필요
  • ★ 현 자산에 UV1 이 없으므로 L1 전에는 실행 자체가 불가능하다

L1. UV1 언랩 — xatlas 벤더링

2026-09-02 — PHASE 3.75 선행 계약으로 개정. UV1 스트림의 유일한 생산자는 이 슬라이스다. 계약: ① UV1은 라이트맵 대상 메시에만 붙는 optional stream ② 언랩이 정점을 쪼개므로 stream은 언랩 단계에서 생성되고 기존 slot을 재사용하지 않는다 ③ 완료 기준 "전 정점 부과 0". identity·generation·layout schema는 PHASE 3.75가 소유하고 L1은 그 authoring transaction을 통해 새 generation을 게시한다.

  • ThirdParty/xatlas 원본 무수정 벤더링
  • PHASE 3.75 authoring transaction을 호출하는 에디터 오프라인 도구
  • 정점 분할 계수 — 손실은 변환 경계에서 계수한다는 성질 유지
  • 게이트: 차트 겹침 0 · UV 범위 [0,1] · seam 정점 수 계수

의존: ModelAssetBigBangCutoverPlan MBC3(authoring writer)·MBC6(vertex schema).

L2. BVH 재작성 — SAH + nth_element

  • 최장축 분할 + SAH 비용 함수
  • std::sort → nth_element, 무게중심 사전 계산
  • 비교자의 데이터 쓰기 제거(§1.3 ④)
  • ★ 리프 순회 off-by-one 을 양쪽 커널에서 고친다(§1.4 ①) — 고치기 전에 현재 동작을 재현하는 검사를 먼저 세워 변이로 이빨을 증명한다
  • 게이트: 합성 씬에서 해석적 정답(구·평면 교차)과 대조

의존: 없음. 가장 먼저 할 수 있다.

L3. 직접광 패스 — DX12 RHI 재작성

  • 디스패치를 렉트 크기로(§1.3 ①) — 이 슬라이스의 본체
  • 렉트 표를 StructuredBuffer 로, 배치 디스패치 1회
  • 라이트 루프를 lightSize 로(§1.3 ⑧)
  • 게이트: 삭제분과 같은 씬에서 픽셀 대조 + 디스패치 스레드 활용률 계측

의존: L1(UV1)·L2(BVH).

L4. 백그라운드 베이킹 — 에디터를 막지 않는다

이 계획의 사용자 체감 본체다. §2.3 의 셋을 순서대로 세운다.

  • L4-a 별도 COMPUTE 큐 + 큐 간 펜스 — 지금 DIRECT 큐 하나뿐이다. 큐를 넘나드는 리소스의 상태 전이(COMMON 경유) 규칙을 함께 정한다. ★ 2026-09-01 정정 — "어느 쪽이 먼저 세우든 소유"는 순서를 정하지 않는 문장이었고, RenderGraphDependencySchedulingPlan §7은 반대로 "L4는 RG8을 기다린다"고 적어 P0인 L4를 P1 뒤 임계 경로 142일째에 묶고 있었다. 큐/펜스 RHI 계약을 RG8에서 떼어 **독립 슬라이스 Q0**으로 승격했다 — 소유는 RHI 계층이고 어느 트랙도 아니다. L4-a는 Q0의 소비자이며, Q0은 RG8·L4 중 먼저 필요해지는 쪽의 착수 시점에 세운다. 근거와 판정: Phase4UnifiedPlan.md §6.2~§6.3.
  • L4-b GPU 타임슬라이스 — 디스패치를 렉트·샘플 단위로 쪼개 프레임당 예산 (예: 8ms) 안에 넣는다. 코루틴 페이싱 제거는 이 단계의 결과다. ★ Windows TDR(기본 2초) 이 상한이다. 단일 디스패치가 그것을 넘으면 디바이스가 리셋된다 — 분할은 성능이 아니라 안전 요구다.
  • L4-c 씬 밀봉 + 무효화 — 시작 시 지오메트리·조명을 스냅샷으로 밀봉하고, 편집이 감지되면 무효화·재시작한다. 프레임 스냅샷 이중 버퍼 게시와 같은 원리.
  • 진행률·취소·재개를 명시적 체크포인트로. 코루틴 프레임에 상태를 숨기지 않는다.

게이트: ① 베이크 중 씬 편집·저장이 되는가 ② 뷰포트 프레임타임이 예산 안에 있는가 ③ 취소 후 재개 결과가 무중단 결과와 같은가 ④ 편집 시 무효화가 동작하는가

의존: L3. RHIParallelCommandPool 의 기록 인프라는 빌리되 스케줄링은 별도다(§2.3).

L5. 간접광 — progressive 누적

  • 샘플을 분할 디스패치로 쪼개 누적
  • numthreads occupancy 측정 후 조정(현재 32×32 = 1024)
  • 바운스마다 텍스처 재생성 제거(§1.4 ⑤)
  • 게이트: 샘플 수 대비 수렴 곡선, 중단·재개 시 동일 결과

의존: L4.

L6. dilate·seam 처리

  • 삭제분에서 주석 처리돼 있던 DilateLightMap 복원
  • padding 계산 수정(§1.4 ③) — 블러로 뭉개지 말고 원인을 고친다
  • 게이트: 차트 경계 블리딩 검사

L7. 병렬화 판정 — 여기서 비로소 잰다

§2.2 순서대로 ①②③을 끝낸 뒤 재측정하고, §2.1 의 남은 축(async compute · CPU 병렬 BVH)이 실제로 이득인지 판정한다. 재기 전에 열지 않는다.

§5

5. 완료 기준

  • UV1 언랩이 자산 파이프라인에 있고 차트 겹침 0
  • BVH 리프 순회 off-by-one 이 양쪽 커널에서 닫혔고 변이로 증명됐다
  • 디스패치 스레드 활용률이 계측되고 렉트 크기 디스패치로 ~100%
  • 베이크가 프레임레이트와 무관하게 진행된다(코루틴 yield 0)
  • 베이크 중 씬 편집·오브젝트 이동·저장이 된다 — 에디터가 막히지 않는다
  • 베이크 중 뷰포트 프레임타임이 예산 안에 있다(느려지되 멈추지 않는다)
  • 단일 디스패치가 TDR 상한 아래임이 계측으로 확인됐다
  • 베이크 중 씬을 편집하면 무효화·재시작이 동작한다
  • 취소·재개가 단계 경계에서 동작하고 재개 결과가 무중단 결과와 같다
  • 렉트 크기가 표면적 × 텍셀밀도로 산출된다
  • 실내 씬에서 SSGI 단독 대비 간접광 개선이 스크린샷으로 확인된다
  • Release 로 측정한 베이크 시간이 기준선 대비 개선됐다
  • 패킹 점유율이 로그에 전체 라이트맵 기준으로 찍힌다
