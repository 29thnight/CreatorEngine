§0

0. 결정한 목표와 착수 조건

PrSM은 저작 의도와 정적 계약을 표현하고, 생성된 C#은 기존 ScriptCore 위에서 실행한다. 엔진은 시간·수명·취소·효과의 실제 의미를 보장한다. C# API 정리만으로 이 계획을 완료하지 않는다. PrSM 원문을 수정한 결과가 인스펙터·실행·진단·리로드까지 도달해야 한다.

  2. 현재 리팩토링의 결과로 확정된 ScriptCore, 클럭, 에셋·빌드·리로드 경계를 다시 조사한다.
  3. §3의 전환 의미와 §7의 PrSM 대상 계약을 확정하고, 원문부터 실행까지 연결되는 작은 슬라이스로 진행한다.
  4. §8의 최종 도입 기준을 통과해야 PHASE 24 완료로 판정한다.

결정 이력 — 제네릭 판을 왜 버렸나

초안(같은 날 오전)은 효과를 readonly struct + IEffect<TResult>, 핸들러를 효과당 IEffectHandler<TEffect, TResult>로 두는 판이었다. 그 판도 CS0535와 즉시 효과 할당 0을 줬다(§2 초안 실측). 그런데 참조 구현을 검증하며 셋이 드러났다.

즉시 효과 할당은 잃지 않는다 — awaiter가 아예 없으니 잴 것이 없다(§2 참조 구현 실측 0.007 B/효과). 잃는 것은 개방형 확장이다: 스크립트가 자기 효과를 낼 수 없고, 어휘는 엔진의 것이다. 이것은 의도다 — 어휘가 곧 결정성의 경계이고 그 경계는 엔진이 든다.

왜 "금지"가 아니라 "라우팅"인가

착수 전 초안은 Random.Shared·DateTime.Now를 금지 목록(분석기 경고)으로 막으려 했다. 그 방향은 두 가지로 약하다. 분석기 경고만으로는 우회 경계를 설명하지 못하며, 네이티브 진입점 207개를 일괄 금지하면 필요한 조회와 변경까지 막는다. 읽기·쓰기의 실제 분포와 트랜잭션 정책은 E2에서 다시 분류한다.

카탈로그로 표현하면 같은 코드가 해석기 선택만으로 달라진다.

실행 시각   → LiveSimulationEffects        (실제 난수 · 실제 방출)
기록        → RecordingSimulationEffects   (실행하면서 테이프에 적는다)
리플레이    → ReplaySimulationEffects      (테이프 대조 · 방출 생략)
테스트      → ScriptedSimulationEffects    (대본)
넷코드 롤백 → 재예측 핸들러

카탈로그를 통과하는 효과의 기록·대체 지점이 생긴다. 게임 전체의 결정성에는 입력·물리 조회·BT 난수·클럭·초기 상태의 계약도 필요하다. PrSM은 이 경계를 표현하고 검사한다(§7).

§3

세 가지가 문법에 그대로 보인다 — 중단은 await한다, 즉시 효과는 await하지 않는다, 정리는 finally가 아니라 Defer에 적는다.

C# 백엔드 기준 예시

다음 C#은 실행 계약을 검토하고 생성 결과를 비교하기 위한 기준 예시다. 최종 저작 표면은 PrSM이며, partial 컴포넌트·직렬화 속성·등록은 기존 엔진 생성기 규약에 맞춘다(§7). 아래 예시를 현재 저장소에서 바로 실행할 수 있는 API로 읽지 않는다.

public sealed class TreasureChest : Component
{
    private enum Outcome { Opened, TimedOut }

    private bool _opened;

    public void Open() => _opened = true;

    public override async SimulationTask OnSimulate()
    {
        // 정리는 여기 적는다. 취소는 상태 머신을 재개하지 않으므로 finally가 돌지 않는다(§3 취소 모델).
        Simulation.Defer(() => _opened = false);

        // 두 분기는 cold다 — Race가 붙이는 순간까지 아무것도 하지 않는다.
        Outcome outcome = (await Simulation.Race(OpenPath(), TimeoutPath())).Value;

        if (Outcome.TimedOut == outcome)
        {
            Simulation.Emit("log", "상자가 열리지 않았다");      // 즉시 효과 — await 없음
            return;
        }

        int roll = Simulation.RollDice(6);                        // 값이 그 자리에서 온다
        Simulation.Emit("loot", $"주사위 {roll} → 보상 등급 {(roll >= 5 ? "희귀" : "일반")}");
    }

    private async SimulationTask<Outcome> OpenPath()
    {
        await Simulation.WaitUntil(() => _opened);
        await Simulation.Wait(0.5f);                              // 여러 단계짜리 분기가 경주한다
        return Outcome.Opened;
    }

    private async SimulationTask<Outcome> TimeoutPath()
    {
        await Simulation.Wait(3f);
        return Outcome.TimedOut;
    }
}

승자를 번호가 아니라 값으로 받는다 — winner == 1 같은 마법 숫자가 저작 코드에 남지 않는다.

이제 컴파일되지 않는 것:

await Task.Delay(500);            // CS0315 — 타입 시스템이 막는다 (우회 불가)
await Task.Yield();               // CS0315 — ICriticalNotifyCompletion 경로도 같다

그리고 분석기가 막는 것(E7):

using (var handle = Acquire())    // CE1002 — await를 가로지르는 using/try-finally
{
    await Simulation.Wait(1f);    //         취소되면 Dispose가 영원히 안 돈다
}

어휘 창구 Simulation

호출부에 new를 두지 않는다. 창구가 두 축을 한 자리에서 보여 준다 — 위는 중단(await), 아래는 즉시 효과(값).

public static class Simulation
{
    // ── 중단: 실행기 원시. 핸들러를 거치지 않는다 ──────────────────────────
    public static WaitAwaitable      Wait(float seconds);
    public static WaitUntilAwaitable WaitUntil(Func<bool> predicate);
    public static RaceAwaitable<TResult> Race<TResult>(params SimulationTask<TResult>[] branches);

    // ── 정리: finally 대신 ─────────────────────────────────────────────────
    public static void      Defer(Action cleanup);
    public static TResource Own<TResource>(TResource resource) where TResource : class, IDisposable;

    // ── 즉시 효과: 카탈로그로 간다. 값이 그 자리에서 온다 ───────────────────
    public static int  RollDice(int sides)                => Frame.Effects.RollDice(NextContext(), sides);
    public static void Emit(string channel, string payload) => Frame.Effects.Emit(NextContext(), channel, payload);
}

중단은 실행기 원시다

Wait·WaitUntil·Race는 ISimulationAwaiter를 구현하는 구조체이고, 빌더가 그것을 실행기에 등록한다. 핸들러는 보지 못한다.

public readonly struct WaitAwaitable : ISimulationAwaiter
{
    public bool IsCompleted => false;                  // 항상 중단한다 — 등록·소유 검사를 건너뛰지 않는다
    public void Suspend(ResumeToken continuation)
        => continuation.Owner.Engine.RegisterWait(continuation, ticks, predicate: null);
    public void GetResult() { }
}

세 가지 실행기 규약이 이 위에 선다.

규약뜻
coldasync SimulationTask 메서드를 부르는 것은 상태 머신을 잡아 두는 것이지 실행이 아니다. 실행기가 Pump할 때 첫 MoveNext가 돈다. Race가 분기 둘을 받아 동시에 시작할 수 있는 이유다
결정적 순서같은 틱에 깨어나는 루틴은 부모/자식 경로([1] → [1,1] → [1,2])로 정렬된 우선순위 큐로 돈다. 대기 목록 순회 순서에 승패가 달리지 않는다
평가와 실행 분리틱 안에서 대기 조건 평가 단계와 본문 실행 단계가 갈린다 — WaitUntil 술어가 다른 본문의 중간 상태를 보지 않는다

취소 모델 — finally를 믿지 않는다

취소는 중단된 상태 머신을 재개하지 않는다. 예외를 던져 풀지도 않는다. 그래서:

  • await를 가로지르는 using·try/finally는 취소되면 영원히 안 돈다 → 분석기가 막는다(E7 · CE1002). 정리는 Simulation.Defer, 자원은 Simulation.Own에 적는다
  • Race에서 진 분기는 취소된다 — 취소는 롤백이 아니다. 진 분기가 이미 낸 즉시 효과는 남는다. 상태 되돌리기는 E2·E8의 축이지 이 축이 아니다
  • ResumeToken이 버전을 든다 — 취소된 뒤 늦게 도착한 깨우기는 무시된다

전환 전에 확정할 실행 의미

경계목표 계약과 검증
첫 본문 실행현재의 OnBeginSimulation 직후 실행과 cold의 첫 Pump는 다르다. 컴포넌트 간 시작 순서·첫 효과의 물리 반영 프레임을 골든으로 고정한다
시간Wait(0), 같은 틱에 등록된 대기, 음수·비정상 시간, 최초 대기의 만료 시점을 정의한다. 프레임 틱을 고정 클럭으로 이름만 바꾸지 않는다. 클럭의 정본은 NetworkFrameworkPlan §4.4 축 간 계약 A(Scope는 고정 축 하나)이며 어긋나면 그쪽이 이긴다
비활성화현행의 Enabled=false는 전·후 틱을 멈추지만 실행 중인 대기는 진행한다. 시뮬레이션 종료와 구분하고 자동 재시작을 넣지 않는다
종료현재 실행 중인 본문이 끝난 뒤, 네이티브 자원이 파괴되기 전에 정리를 소진한다. End 표시를 다음 일반 틱까지 방치하지 않는다. 즉시 컴포넌트 제거·리로드에도 같은 경계를 적용한다
취소 이관기존 두 프로브의 catch (OperationCanceledException)도 비재개 취소에서는 실행되지 않는다. 정리와 취소 진단을 별도 종료 경로로 이전한다
정리정상 완료·취소·실패 각각의 정리 순서와 정확히 한 번 실행을 정의한다. 정리 하나의 예외가 다른 정리나 스코프 해제를 막지 않아야 한다
스케줄링같은 틱 순서 큐와 시간 만료 자료구조를 구분한다. WaitUntil은 순수한 조건 평가만 허용하고, 재개 횟수·본문 실행 예산과 늦은 토큰 무시를 검증한다
식별자루트·자식 루틴 식별자, 효과 순번, PrSM 원문 위치 및 컴파일 세대의 연결을 정의한다. 코드 변경 후 옛 테이프를 무조건 재사용하지 않는다
트랜잭션셀과 네이티브의 읽은 값이 일치하는 규약, 커밋 전 검증 및 부분 커밋 실패 정책을 정한다. 일반 필드·객체 내부 변경은 자동으로 되돌아오지 않는다

현재 Task 스코프의 결함은 별도 안정화 문서에서 먼저 다룬다. 위 표는 그 수정에 cold나 비재개 취소를 미리 섞으라는 뜻이 아니다.

§4

4. 엔진 계약 트랙 — 전체 미래 보류

E0~E8은 리팩토링 이후의 목표 작업이다. P0/P1/P2는 이 페이즈 안의 상대 우선순위이며 현재 작업 큐의 긴급도를 뜻하지 않는다. 이 트랙만 끝내서는 완료가 아니며 §7의 PrSM 변경·통합 트랙을 함께 완료해야 한다.

E0 — 대기 원시와 awaiter 계약 (P0 · §0 재개 조건·§3 실행 의미 선행)

SimulationTask / SimulationTask<TResult> / ISimulationAwaiter / 빌더 넷을 세우고, Component.OnSimulate의 반환형을 Task → SimulationTask로 바꾼다. 기존 SimulationScope.Delay(TaskCompletionSource 기반)를 Simulation.Wait로 교체한다.

  • 과거 오버라이드 2건은 조사 시점의 값이다. 착수 시 호출자·프로브·생성 코드·빌드 및 리로드 경계를 다시 세며, 반환형 변경 외의 의미 이관도 작업 범위에 포함한다
  • cold. 빌더 Start는 상태 머신을 잡아 둘 뿐 MoveNext하지 않는다. ScriptRegistry.StartSimulation이 실행기에 붙이고 관리 틱이 Pump한다
  • 오버라이드하지 않은 컴포넌트. 기반 OnSimulate() => default는 코어가 없는 값이다. 등록부는 붙이기 전에 걸러 미사용 루틴 코어를 만들지 않는다. 기존 Component.Scope의 선할당을 없애는 작업과는 별개이므로 두 할당을 따로 잰다
  • 취소는 경계에서만 — Scope.End()는 표시하고, 현재 본문 종료 후 네이티브 파괴 전 종료 배리어가 정리를 돌린다. 프레임 종료·즉시 제거·씬 이동·리로드의 배선까지 검증한다
  • 게임 스레드 확인(CheckThread)을 실행기 진입점 전부에 둔다. ClrHost.h:27의 게임 스레드 계약을 관리 측이 스스로 검사하는 첫 자리다
  • 관측되지 않은 예외 수거를 ContinueWith에서 루틴 종결 상태(Faulted + 진단 목록)로 옮긴다

완료 조건: AwaitOnCompleted와 AwaitUnsafeOnCompleted 양쪽에서 외부 awaiter를 거부한다. 미사용 루틴 할당 0, 관리 생명주기·취소·DDOL·리로드 게이트 통과를 각각 잰다. 200사건 네이티브 기준선에는 현재 ScriptComponent 행이 없으므로 그것만으로 완료하지 않는다. 의도적으로 바뀐 시작·취소 의미는 이전/이후 골든과 변경 근거를 함께 남긴다.

E1 — 폐쇄 카탈로그와 중단 원시 (P0 · E0 선행)

EffectContext · ISimulationEffects · 핸들러 셋(Live/Recording/Replay) · 어휘 창구 Simulation, 그리고 중단 원시 Wait · WaitUntil · Race · 정리 Defer · Own. 카탈로그는 실제로 쓰이는 것만 낸다 — RollDice · Emit.

  • 즉시 효과는 값을 돌려준다. awaiter가 없다. 핸들러가 답을 잊는 경로가 없다
  • 카탈로그는 폐쇄 인터페이스. 메서드를 더하고 구현을 빠뜨리면 CS0535 — 런타임 switch와 "해석할 수 없는 효과" 예외가 통째로 사라진다
  • 중단은 실행기 원시. 우선순위 큐(루틴 경로 정렬) · 대기 평가/본문 실행 분리 · ResumeToken 버전. Race는 cold 루틴을 params로 받고 승자를 (Index, Value)로 준다
  • 호출부는 창구만 쓴다 — await Simulation.Wait(0.5f), Simulation.RollDice(6). 생성자 직접 호출을 금지하는 것이 계약이다(§3)
  • Sync·Branch는 저작분 0건이므로 내지 않는다. 트랜잭션 셀(Var<T>·Decide)은 이 트랙이 아니라 E8이다

완료 조건: ① 핸들러 교체로 같은 스크립트가 다른 결과를 내는 것을 게이트가 잰다. ② 카탈로그에 메서드를 더하고 구현을 빠뜨리는 변이가 CS0535로 막힌다. ③ 즉시 효과의 프레임당 할당이 0인 것을 게이트가 잰다(§2 실측 0.007 B/효과). ④ 같은 틱 Race 승자가 대기 등록 순서를 뒤집는 변이에 바뀌지 않는다.

E2 — 부수효과 분류와 공통 카탈로그 (P0 · §0 재개 조건 선행)

E3, PrSM 검사·변환, 향후 롤백 및 편집기 Undo가 분류를 활용할 수 있다. 소비 가능성이 현재 착수의 근거는 아니다. 기존 네트워크·Undo 설계가 먼저 만든 정본이 있으면 재사용하며 그 작업에 PHASE 24 선행 의존을 역으로 추가하지 않는다.

함수별 중단 가능 여부, 호출 스레드·실행 문맥, 효과 종류와 트랜잭션 참여 여부를 함께 제공한다. 이 카탈로그를 PrSM과 C# 검사·런타임 검증이 공유하며 목록을 별도로 복제하지 않는다. BT 가중 선택의 난수와 외부 C# 호출도 감사에 포함한다.

★ 착수 전 확인할 것: UndoManager::m_isGameMode는 이름과 달리 *"에디터 UI의 Play 버튼을 눌렀는가"*다(그 파일 주석이 이미 경고한다). 게임 모드 스택이 지금 무엇을 담고 있는지 세지 않고 위에 얹으면 되돌리기 기제가 저장소에 둘이 된다.

★ 참조 구현은 트랜잭션 안에서 Emit·RollDice를 런타임에 거부한다 (RequireNonTransactional). 그것이 "불가" 분류를 런타임에 강제하는 형태다 — 분류표가 서면 같은 게이트를 경계 207개에 건다. 트랜잭션 셀(E8)이 네이티브 상태를 못 감싸는 이유는 unmanaged 제약이 아니라(그 제약은 비본질적이다 — E8 실측) 쓰기 경로가 셀을 거치지 않기 때문이다. Transform setter는 곧장 네이티브로 간다. 그 경로를 커밋 시점까지 미루는 것이 "지연" 분류이고, 그래서 되돌리기 축은 이 표에서 시작한다.

완료 조건: 분류표가 문서가 아니라 코드 표로 서고(속성 또는 생성 표), 분류 없는 신규 진입점이 추가되면 게이트가 붉어진다.

E3 — 효과 기록·재생 (P1 · E1·E2 선행)

RecordingSimulationEffects / ReplaySimulationEffects. 테이프 항목은 (EffectContext, 종류, 인자, 결과)다 — 결과 수열만이 아니다. 리플레이는 요청을 대조하고(같은 틱·루틴·순번·종류·인자가 아니면 예외), 끝에 남은 항목 0을 확인한다. 지연 분류(E2)의 부수효과는 재생에서 생략된다.

리플레이는 효과 검증이지 롤백이 아니다. 상태를 되돌리는 것은 E2의 분류표 위에 선다. 전체 게임 재현에는 입력·충돌·물리 조회, 초기 상태와 클럭을 별도로 통제해야 한다. 테이프에는 스키마·컴파일 세대 식별을 포함하고, 호환되지 않는 재생을 명시적으로 거부한다.

완료 조건: 기록 → 재생 왕복이 방출 수열을 보존하고, 테이프를 흔드는 변이에 붉어진다 (결과값 변조 · 항목 삭제 · 순번 교체 셋 다).

E4 — 실패 결과와 루틴 진단 통합 (P1 · E0·현행 안정화 LC1/LC2 선행)

Result<TValue, TError>와 루틴 종료 상태를 기존의 성공 단계·실패 격리 계약에 연결한다. 현행 훅 결함 수정은 별도 문서 LC1/LC2의 소관이다.

  • 확정된 성공 단계와 대칭 정리 규약을 생성된 PrSM 컴포넌트에도 동일하게 적용한다
  • 루틴의 Faulted(E0), 훅 실패, 정리 실패가 원인·소유자·원문 위치를 보존한 채 모인다
  • 생성기나 PrSM 전용 등록부에 두 번째 생명주기 상태 기계를 만들지 않는다

완료 조건: 동일한 실패 시나리오에서 수기 C#과 PrSM 생성 코드의 단계·정리 결과가 일치한다. 정상 실패 값과 예외, 취소를 구분하고 원래 PrSM 문장까지 진단이 연결된다.

E7 — 정적 계약 검사기 (P1 · E1·E2 선행)

차단은 타입 시스템이 하고(CS0315·CS0535), 설명은 분석기가 한다. 그리고 타입 시스템이 못 잡는 계약이 하나 있다 — 취소 모델(§3)을 고른 순간 따라오는 await를 가로지르는 using/try-finally다.

  • 저장소에 ScriptCore.Generators가 이미 있다 — 같은 자리에 선다
  • PrSM 저작 진단은 PrSM 의미 분석이 담당한다(PrSM2). Roslyn 검사는 생성 결과·수기 C#· 외부 경계의 보조 검증이며 둘은 E2 카탈로그와 같은 양성/음성 사례를 사용한다. 생성 파일로 인식되어 분석기가 건너뛰는 경로도 별도 게이트로 막는다
  • 규칙마다 잡는 픽스처와 못 잡는 변이를 함께 적는다. 참조 구현 문서가 스스로 적었듯 이것은 "악의적인 스크립트의 샌드박스가 아니다" — 호출 그래프 전수가 아니다

완료 조건: 규칙 4종 각각 붉은 픽스처 1 + 초록 픽스처 1. 분석기 참조를 제거하는 변이에 게이트가 붉어진다.

E5 — 진단 표면 (P2 · E1·PrSM4 연계)

"지금 이 컴포넌트가 무엇을 기다리는가"를 구조화된 대기 레코드로 답한다. 실행기가 대기 종류·소유 루틴·중단 위치를 등록·해제하고, EffectContext.Sequence가 현재 틱의 효과 순번을 제공한다. 이를 PrSM 소스 맵과 연결한다. 상태 머신 내부 필드를 임의로 읽지 않는다.

완료 조건: 에디터·트레이스·게이트가 같은 레코드를 사용하고 PrSM 원문으로 이동한다.

6. 이 페이즈가 지키는 원칙

  1. PrSM 도입까지 완료한다. C# 런타임 샘플이나 문법 변환만으로 완료하지 않는다. 틱·행동 트리·단계 목록·루틴은 필요한 자리에 쓰며 모든 저작을 비동기 루틴으로 바꾸지 않는다.
  2. 효과의 실행 지점을 명시한다. 허용된 비결정적 효과는 해석기로, 지연 가능한 쓰기는 커밋 경계로 보낸다. 읽기·실패 의미를 보장할 수 없는 호출은 해당 문맥에서 명시적으로 거부한다.
  3. 실제 저작분으로 표면을 정한다. 공통 카탈로그와 최소 조합자를 먼저 만들고, 대표 콘텐츠가 요구하는 순서로 확장한다. 언어 기능 수 자체를 완료 지표로 삼지 않는다.
  4. 검사가 실패를 검출하는지도 검증한다. 양성·음성 픽스처와 검사기 배선 제거 변이를 둔다. 검사하지 못하는 외부 호출·별칭·원시 C# 경계를 함께 명시한다.
  5. 이름을 일관되게 쓴다. SimulationTask, SimulationScope, transaction을 사용한다. 트랜잭션 참여 변수의 공개 이름은 기존 결정대로 Var<T>, 내부 저장 단위는 Cell<T>다.
  6. 검토 라이브러리를 그대로 의존으로 넣지 않는다. Shielded·Eff·저장소 밖 참조 구현은 개념·검증 자료다. 사용자 소유 PrSM 저장소의 수정·통합은 별도의 명시적 목표다.
  7. 효과 카탈로그 누락을 컴파일 단계에서 검출한다. 폐쇄 인터페이스와 공통 선언을 사용한다. PrSM 검사와 생성된 C#의 검사가 다른 허용 목록을 갖지 않게 한다.
  8. 즉시 효과는 값을 반환하고, 중단은 실행기가 관리한다. PrSM은 기존 C# 백엔드를 유지한다. 별도 VM·틱 루프·컴포넌트 등록부를 만들지 않는다.
  9. 미래 취소 모델과 현행 Task 취소를 구분한다. 미래 루틴은 취소 시 본문을 재개하지 않고 Defer·Own으로 정리한다. 중단을 가로지르는 정리를 PrSM/E7이 검사한다. 현행 catch (OperationCanceledException)/finally 의미 변경은 이행 검증을 거친다.

§7

7. PrSM 수정·CreatorEngine 도입 트랙

7.1 조사 기준과 재사용 경계

PrSM 저장소의 C# 백엔드를 유지한다. 2026-09-05 조사 기준 로컬 커밋은 ef28e7b52d1fe03c9f79accee1a9de50aea7849e, 원격 기본 브랜치의 확인 커밋은 d3f11bf34feec71e716156818a2aaea1ecac9a7d다. 두 커밋 간 차이는 문서 사이트이며 아래 컴파일러 핵심의 차이는 없었다. 미래 착수 때 다시 확인한다.

PrSM의 문법과 기존 lowering은 저작 표면을 줄이는 자산이다. 그러나 wait를 다른 함수명으로 치환하는 것만으로 수명·취소·효과 계약이 생기지는 않는다. 엔진 실행 보장과 컴파일러 검사가 같은 계약을 사용해야 저작자가 C#의 반복적인 등록·정리 코드를 덜 작성할 수 있다.

조사한 소스: 컴파일 드라이버, C# lowering, 의미 분석, C# IR, 프로젝트 설정, 소스 맵.

PrSM0 — 대상 프로필 분리 미래 착수 첫 단계

  • 공통 언어·C# 출력과 Unity/CreatorEngine의 타입·생명주기·대기·메타데이터·도구 어댑터를 나눈다.
  • 엔진 대상에서 Unity/UniTask 참조가 암묵적으로 유입되지 않게 한다. Unity 대상의 기존 유지 범위도 명시해 공유 컴파일러 변경의 영향을 검증한다.
  • 지원 문법·외부 API·진단 규칙을 대상별로 문서화한다. 새 언어 전체를 설계하지 않는다.

완료 조건: 같은 작은 입력을 각 대상에 빌드해 서로의 런타임 참조 없이 의도한 C#을 낸다. 지원하지 않는 대상 기능은 빌드 단계에서 원문 위치와 함께 거부한다.

PrSM1 — 기존 컴포넌트·직렬화·등록 경로 연결 (PrSM0 선행)

  • CreatorEngine.Component를 상속하는 partial 타입, 실제 훅 signature와 직렬화 특성을 생성한다. Start→이름 치환만 하지 않고 공개 override·호출 단계·인자를 검증한다.
  • 기존 ScriptCore.Generators의 팩터리· 필드 접근자 생성 경로와 GameScripts 빌드를 사용한다. PrSM 전용 생명주기 등록부를 만들지 않는다.
  • 첫 슬라이스는 필드·초기화·틱·제거만으로 작게 닫는다. 현행 Task 기준선에서의 연결 시험은 가능하지만, 이 단계만으로 효과 계약 도입을 완료했다고 하지 않는다.

완료 조건: PrSM 컴포넌트를 씬에 붙여 필드 저장/복원, 훅 한 번 호출, 활성 전환·제거를 실제 엔진에서 확인한다. 같은 수기 C# 컴포넌트와 생명주기 결과가 일치한다.

PrSM2 — 효과·중단·수명 의미 분석 (E2·PrSM0 선행, E7과 공동 검증)

  • E2의 공통 카탈로그에서 호출별 효과·중단 가능성·허용 스레드·트랜잭션 참여 정보를 읽는다.
  • 함수 호출을 통한 효과 전파와 문맥 검사를 수행한다. 필요한 타입·효과 정보를 AST/HIR와 lowering 사이에 보존하며, 문자열 기반 C# IR에 도달한 뒤 추측하지 않는다.
  • intrinsic·외부 C#·네이티브 호출은 명시한 서명과 신뢰 경계로 처리한다. 분류 없는 호출을 순수하다고 추정하지 않는다. 분석하지 못하는 호출 경로는 지원 제한으로 드러낸다.
  • 일반 변수, 셀의 값 교체, 참조 객체 내부 변경을 구분한다. 모든 var를 암묵적으로 Var<T>로 만들지 않는다. 기존 state machine 문법도 자동 롤백을 뜻하지 않는다.

완료 조건: 직접·간접 외부 await, 정리 중 중단, 트랜잭션 내 금지 효과, 내부 참조 변경의 양성·음성 사례가 원문 위치로 진단된다. 생성 C#의 E7 검사가 같은 계약을 검증한다.

PrSM3 — 루틴·정리·트랜잭션 lowering (E0/E1·PrSM1/2 선행, 트랜잭션은 E8 선행)

  • 엔진 대상 대기·조건 대기·경주 분기를 E0/E1 실행기로 변환한다. 실제 문법은 최소 슬라이스로 확정하며, 기존 Unity coroutine의 yield를 무조건 동일 의미로 간주하지 않는다.
  • 구독·자원 소유·정리를 엔진 스코프에 연결한다. listen until disable과 시뮬레이션 종료 정리를 같은 수명으로 합치지 않는다. 정리 exactly-once와 예외 격리는 엔진이 보장한다.
  • 명시적으로 참여하는 변수와 결정 구간을 E8의 Var<T>·Decide·Require로 내린다. 중단 가능한 본문의 using을 무조건 finally로 내리지 않는다.
  • 반환형·await 결과 타입을 정확히 검증하고, 비동기 의미가 필요한 곳만 상태 머신을 생성한다.

완료 조건: §3의 시작 시점·disable·취소·파괴·부분 커밋 규약을 수기 C#과 PrSM에서 같은 테스트로 검증한다. 지원한 문법의 동작과 생성 코드 예제를 함께 고정한다.

PrSM4 — 빌드·에디터·진단·리로드 연결 (PrSM1 이후 점진 연결, E5 연계)

  • .prsm 변경→C# 생성→기존 생성기/컴파일→어셈블리 발행의 순서를 기존 빌드에 연결한다. 캐시 입력에 대상·컴파일러·카탈로그·ScriptCore 참조 버전을 포함한다.
  • 생성 또는 컴파일 실패를 이전 산출물의 성공처럼 표시하지 않는다. 마지막 성공본 유지와 새 버전 적용 실패를 구분하고 검증된 산출물만 일관된 한 세대로 발행한다.
  • 컴파일 진단·런타임 오류·중단 위치를 PrSM 원문에 매핑한다. LSP/에디터의 훅·타입 제안도 엔진 대상과 일치시킨다. 기존 선언 단위 소스 맵만으로 문장 단위 진단 완료라 하지 않는다.
  • 인스펙터의 타입·필드 식별자와 스크립트 이름 변경 정책을 정한다. 리로드 시 이전 어셈블리의 루틴·정리 콜백·테이프·소스 맵 참조를 해제하고 새 세대와 섞지 않는다.

완료 조건: 정상 수정, 구문 오류, 계약 오류, 생성 C# 오류, 리로드 중 대기/실패를 편집에서 실행까지 재현한다. 원문 위치·저장한 필드·실행 중 버전이 일치하고 이전 로드 문맥이 회수된다.

PrSM5 — 실제 콘텐츠 도입과 비교 검증 (필수 엔진·PrSM 트랙 통합)

  • 틱 컴포넌트, BT 연계, 짧은 단계 흐름, 여러 프레임을 기다리는 루틴의 대표 사례를 정한다. 신규 BT 언어 전체 구현보다 기존 관리 BT를 올바르게 호출·진단하는 경계를 먼저 닫는다.
  • 활성 전환·일시 정지·DDOL 이동·일반/즉시 파괴·씬 종료·스크립트 리로드를 실제 콘텐츠에서 검증한다.
  • 저작량, 반복되는 정리 코드, 진단의 원문 도달률, 수정→실행 시간, 이관 중 결함을 수기 C#과 비교한다. 짧아진 원문만으로 생산성 향상을 확정하지 않는다.
  • E6의 실행·할당·유지 메모리를 같은 기능·인스턴스 수·클럭·빌드 조건에서 비교한다. DSL 도입 자체의 FPS 개선을 목표나 보장으로 삼지 않는다.

완료 조건: PrSM 저장소의 변경과 CreatorEngine의 런타임·도구 연결이 함께 배포 가능한 상태이며, 대표 콘텐츠가 PrSM 원문을 정본으로 편집·빌드·실행된다. 남은 미지원 기능은 명시한다.

§8

8. 최종 완료 판정

이 문서의 작성·정적 링크 검사·참조 구현 데모는 아래 항목의 완료 증거가 아니다. 효과 계약 런타임과 PrSM 변경 도입을 모두 끝내야 PHASE 24를 완료 처리한다.

  • 재착수 시 코드·저작분·관련 리팩토링 결과를 재조사하고 §3 실행 의미를 확정했다.
  • E0~E8의 적용 범위와 완료 게이트를 실제 엔진에 구현·연결했다.
  • PrSM0~PrSM5를 완료하고 Unity 의존 분리·CreatorEngine 대상 빌드를 검증했다.
  • PrSM과 수기 C#이 같은 카탈로그·등록·생명주기·직렬화 계약을 사용한다.
  • 분석기와 PrSM 의미 검사의 실제 빌드 배선, 거부 사례와 우회 한계를 검증했다.
  • 원문 수정→생성→빌드→등록→실행→진단→리로드 전 경로를 실제 엔진에서 검증했다.
  • 실패·취소·disable·DDOL·파괴·리로드 회귀와 오래된 세대의 참조 회수를 통과했다.
  • E6 성능 비교와 PrSM5 저작 효율 비교를 별도로 보고하고 수용 기준을 충족했다.
  • 대표 콘텐츠 이관, 사용 문서, 미지원 경계, 되돌릴 수 있는 이행 절차를 제공했다.
