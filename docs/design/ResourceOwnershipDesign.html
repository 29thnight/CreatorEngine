Phase 2-0 · Ownership & Boundary Design

자원 소유권 · 경계 설계

전제: 스크립트 계층을 CoreCLR로 전면 대체 · 관련: 대시보드 · 스크립트 API 설계 · 구조 분석 12장

01결정 ① 핸들 타입 — 별도 테이블

결정: 기존 HashedGuid는 그대로 두고, 런타임 전용 ObjectHandle을 새로 둔다

두 식별자는 역할이 다릅니다. 하나로 합치려는 시도가 오히려 문제를 만듭니다.

1.1 왜 HashedGuid에 세대를 더하면 안 되는가

처음에는 기존 HashedGuid에 세대 필드를 추가하는 안을 검토했으나, 코드를 확인한 결과 부적합합니다.

근거내용
영속 식별자다Object::m_instanceID가 [[Property]]로 직렬화된다. 구조를 바꾸면 기존 씬·프리팹 파일과 호환이 깨진다.
개념이 다르다HashedGuid는 make_guid()로 만든 논리적 ID이고 맵 키로 쓰인다. 세대는 슬롯 재사용이라는 런타임 개념이라 층이 다르다.
암묵 변환 의존operator size_t()가 있어 엔진 전반이 정수처럼 쓰고 있다. 크기를 바꾸면 파급이 크다.

1.2 역할 분리

타입수명용도
FileGuid영구 (파일)에셋 식별. 기존 그대로.
HashedGuid영속 (씬 파일)오브젝트 논리 ID. 직렬화·맵 키. 기존 그대로.
ObjectHandle런타임 (프로세스)신규. 경계를 넘는 유일한 참조 형태. 세대로 무효화 감지.

1.3 형태

struct ObjectHandle
{
    uint32_t index;       // 슬롯 인덱스 → O(1) 조회
    uint32_t generation;  // 슬롯 재사용 시 증가. 0 = 무효
};
static_assert(sizeof(ObjectHandle) == 8);  // 경계 ABI 고정

C# 쪽에는 동일 레이아웃의 readonly struct로 대응합니다. blittable이라 마샬링 비용이 없습니다.

1.4 프로토타입 검증 결과

구현 후 17개 항목 전부 통과했습니다. 특히 Phase 1에서 고쳤던 UAF 패턴이 구조적으로 차단되는지 확인했습니다.

결과검증 항목
PASS해제된 객체의 낡은 핸들 → nullptr (12.3-② 본 팔레트 UAF 패턴 차단)
PASS슬롯 재사용 시 세대 증가 → 낡은 핸들이 새 객체를 가리키지 않음
PASS범위 밖 인덱스·세대 불일치·기본 생성 핸들 모두 안전하게 거부
PASS10,000회 생성/파괴 후 슬롯 수 1개 (프리리스트 재사용, 누수 없음)
PASS8바이트 고정 · trivially copyable
의미

Phase 1에서 사후 수정으로 잡았던 UAF를, 이 모델에서는 애초에 만들 수 없습니다. 해제된 참조에 접근하면 크래시 대신 nullptr이 돌아옵니다.

02결정 ② 소유권 단일 진실 공급원

현재 문제는 "누가 소유자인지"가 코드로 강제되지 않는다는 점입니다. DataSystem의 shared_ptr 맵이 사실상 유일 소유자인데, 사용처는 전부 원시 별칭이라 맵에서 지우는 순간 전부 댕글링이 됩니다(12.2 보충 분석).

2.1 계층 규칙

계층보유 형태규칙
DataSystemshared_ptr<T>유일한 소유자. 에셋의 생성·파괴는 여기서만 일어난다.
컴포넌트 · Modelshared_ptr<T> (공동 소유)사용하는 동안 수명을 보장받는다. 언로드가 즉시 파괴로 이어지지 않는다.
렌더 프록시shared_ptr<T> (공동 소유)렌더 스레드가 쓰는 동안 안전. 지연 파괴로 자연 처리.
경계 (C#)ObjectHandle (비소유)절대 소유하지 않는다. 유효성은 세대로 판단.
경계는 반드시 비소유여야 한다

관리 코드가 네이티브 객체를 소유하면 shared_ptr 순환과 GC 순환이 경계를 넘어 얽힙니다. 어느 쪽도 풀 수 없는 영구 누수가 되므로, 경계는 항상 비소유 참조(핸들)로 고정합니다.

2.2 UnloadUnusedAssets 활성화 조건

12.2-①에서 확인했듯 현재 이 함수는 호출되지 않는 게 아니라 호출하면 안 되는 상태입니다. 아래가 모두 갖춰진 뒤에야 켤 수 있습니다.

  1. 컴포넌트·Model·프록시가 shared_ptr 공동 소유로 전환 (2-2 ~ 2-4)
  2. 런타임 클론(Material::Instantiate)이 retain 대상에 포함 (2-5)
  3. ManagedAssetType에 UITexture/SpriteSheet 추가 (2-7)
  4. 그 후 씬 전환부에서 활성화 (2-8)

순서를 지키지 않으면 "누수 크래시"가 "UAF 크래시"로 바뀔 뿐입니다.

03결정 ③ 평면 C ABI 형태

P/Invoke는 C++ 객체를 넘길 수 없습니다. 경계는 핸들 + 자유 함수로만 구성합니다.

// 네이티브가 export 하는 엔진 API (예시)
extern "C" {
    // 조회 — 실패는 예외가 아니라 반환값으로
    int  Engine_IsAlive(ObjectHandle h);
    int  Engine_GetTransform(ObjectHandle h, Vector3* outPos, Quaternion* outRot, Vector3* outScale);

    // 변경
    int  Engine_SetPosition(ObjectHandle h, Vector3 pos);

    // 문자열은 UTF-8 바이트 + 길이 (string 직접 전달 금지)
    int  Engine_FindByName(const char* utf8, int len, ObjectHandle* out);
}

규칙

  • 반환은 오류 코드(0=성공). 예외를 경계로 넘기지 않는다.
  • 출력은 포인터 인자로. 반환값은 상태 전용.
  • 모든 인자는 blittable.
  • 함수 이름은 Engine_ 접두사로 통일.

이득 (CoreCLR과 무관하게)

  • 모듈 간 커플링이 자연히 줄어든다 (Phase 5 선취)
  • JIT/AOT 두 모드가 같은 바인딩을 공유
  • 테스트가 쉬워진다 (평면 함수라 목킹 용이)

04결정 ④ 스레드 규칙

관리 코드는 게임 스레드에서만 호출한다

CoreCLR GC는 수집 시 스레드를 정지시킵니다. 렌더 스레드나 스레드풀 워커가 관리 코드를 호출하면 프레임이 GC에 묶입니다. 현재 엔진은 프록시 커맨드 큐로 게임/렌더 스레드를 분리해 두었으므로, 그 경계를 그대로 활용합니다.

스레드관리 코드 호출비고
게임(메인) 스레드허용모든 스크립트 진입점이 여기서만 실행된다.
렌더 스레드금지프록시 커맨드 큐로만 통신. 관리 객체를 만지지 않는다.
스레드풀 워커금지에셋 로딩 등. 완료 통지는 게임 스레드에서 처리.
물리 콜백큐 경유PhysX 콜백에서 직접 부르지 않고, 큐에 모아 틱 경계에서 일괄 디스패치.

async/await를 쓰려면 커스텀 SynchronizationContext가 필수입니다. 기본 컨텍스트는 스레드풀이라 continuation이 워커로 넘어가 위 규칙을 조용히 위반합니다.

05결정 ⑤ 네이밍 정리

Managed:: 는 .NET 문맥에서 심각한 혼동을 부른다

현재 Managed::HeapObject, Managed::SharedPtr는 mimalloc 기반 커스텀 힙을 뜻합니다. 그런데 .NET에서 "managed"는 GC 힙을 의미합니다. CoreCLR이 들어오면 "이 객체는 managed인가?"라는 질문에 두 가지 답이 생깁니다.

현재제안이유
Managed::HeapObjectMem::PooledObject실제 의미(커스텀 힙 할당)를 그대로 드러낸다.
Managed::SharedPtrMem::SharedPtr동일.
ManagedHeap.dllMemoryCore.dllDLL 이름도 함께. 다만 파급이 크므로 후순위.
(신규)Clr::.NET 관련 코드는 이 네임스페이스로 모아 구분을 명확히.

네임스페이스 치환은 기계적이라 리스크가 낮지만, DLL 이름 변경은 빌드 스크립트·배포 경로에 파급이 있습니다. Phase 2 본작업과 분리해 Phase 6(코드 정리)에서 일괄 처리하길 권합니다.
