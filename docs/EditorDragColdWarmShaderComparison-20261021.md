# 실제 에디터 드롭: 빈 셰이더 캐시와 재실행 비교

2026-10-21. **Debug 실행 파일을 직접 실행한 일반 에디터 창**에서 CreatorRobot과 Aria를 콘텐츠 브라우저에서 씬으로 드래그 앤 드롭했다. 두 모델을 각각 독립된 빈 셰이더 캐시로 실행하고, 같은 캐시로 프로세스를 다시 실행했다. 수정 전후 총 8회의 드롭·모델 표시·선택·이동 기즈모 조작을 확인했다.

**1분 지연이 재현됐다.** 수정 전 빈 캐시의 CreatorRobot은 77.6초에도 화면이 비어 있었고 87.7초에 표시를 확인했다. Aria는 62.9초에도 비어 있었고 80.3초에 표시를 확인했다. 이전 보고서의 수 초짜리 자동 실행 결과는 이 조건을 대표하지 못했다.

## 원인과 수정

원본 모델 경로로 배치하는 기존 경로는 `PendingInstance::Prepare`에서 사용 재질을 하나씩 변환하고, 각 재질의 `ConfigureModelMaterialGraph`를 통해 셰이더 그래프를 준비했다. 빈 캐시에서는 **한 작업 스레드가 서로 다른 재질 그래프를 순차 컴파일**했다. Robot 4개 재질의 64개 단계, Aria 3개 재질의 48개 단계가 이 경로에서 실제 컴파일됐다. 캐시가 있으면 같은 요청이 적중해 이 시간이 크게 줄었다.

씬 적용 후에도 가시성·장면 조회 등 첫 렌더용 셰이더와 파이프라인 준비가 남는다. 두 모델 모두 드롭 후 전체 구간에서 렌더러 보조 셰이더 등을 포함한 추가 46개가 컴파일됐다. 따라서 `model.timing`의 씬 적용 완료는 화면 표시 완료와 다르다.

수정은 `EditorModelPlacement.cpp`에 제한된 재질 준비 단계를 추가했다.

- 모델 메타데이터 작업이 완료된 뒤, 실제 노드가 참조하는 메시의 재질 그래프만 수집한다.
- 컴파일 슬롯 수를 상한으로 하는 작업 묶음에서 서로 다른 그래프를 병렬 준비한다. 그래프당 기존 `GenerationStore`의 요청 병합·검증·게시 경로를 그대로 사용한다.
- 준비된 세대 owner를 요청이 보관하고, 작업 묶음 전체가 끝난 뒤 기존 재질 변환·씬 생성 작업을 진행한다. 원래 재질 인스턴스가 세대를 보관하면 임시 owner를 해제한다.
- GT는 미완료 작업을 기다리지 않고 다음 프레임에 상태를 확인한다. 작업 스레드에서 중첩 대기를 추가하지 않았다.
- 이미 준비된 재질을 가진 typed 입력은 이 추가 단계를 건너뛴다. 그래프 부재·오류는 기존 준비/복구 경로에서 처리한다. 취소·프로젝트/씬 변경·무효화 검사와 shutdown 합류를 유지한다.

셰이더 단계, 컴파일 옵션, O3 최적화, 캐시 키와 형식, 리플렉션·의존 파일 검증은 줄이거나 바꾸지 않았다. 수정 후에도 빈 캐시의 실제 컴파일 수는 Robot 110개, Aria 94개로 같았다. 수정 전후 셰이더 파일 키 집합과 SHA-256 내용 비교에서 **Robot 261개, Aria 229개 `.rsh`/`.rsv` 기록이 모두 동일**했다. 이 수에는 에디터 시작에 필요한 기록도 포함된다.

## 실제 화면 관측 결과

단위 초. `(마지막 미표시 시점, 첫 표시 확인 시점]`이다. 연속 영상의 최초 표시 타임스탬프가 아니라 **컴퓨터 조작 도구의 화면 샘플링 구간**이다. 아래 상한을 정확한 로드 시간이나 통계 평균으로 해석하면 안 된다.

| 모델 | 셰이더 캐시 조건 | 수정 전 표시 구간 | 수정 후 표시 구간 |
|---|---|---:|---:|
| CreatorRobot | 빈 캐시 첫 실행 | **(77.563, 87.676]** | **(32.786, 46.205]** |
| CreatorRobot | 같은 캐시로 재실행 | (0.720, 7.173] | (2.255, 10.522] |
| Aria | 빈 캐시 첫 실행 | **(62.923, 80.323]** | **(30.082, 48.168]** |
| Aria | 같은 캐시로 재실행 | (1.735, 9.103] | (2.805, 13.435] |

빈 캐시의 수정 전후 구간은 겹치지 않으며, 긴 지연 감소를 확인했다. 재실행의 구간은 넓고 서로 겹치므로 **화면 표시가 재실행에서도 몇 % 빨라졌다는 결론은 내리지 않는다.** 화면 확인 사이에 도구 호출·관측 해석 시간이 포함된다.

### 표시뿐 아니라 실제 조작 확인

8회 모두 계층에서 모델 루트를 선택해 Inspector와 기즈모가 나타나는 것을 확인한 뒤, 기즈모를 직접 드래그했다. Inspector의 Z 위치가 0.333에서 약 1.000 또는 1.029로 바뀌고 모델도 이동했다.

| 실행 | 선택 반영 확인 시점 | 이동 반영 확인 시점 |
|---|---:|---:|
| 수정 전 Robot / 빈 캐시 | 98.218 | 111.429 |
| 수정 전 Robot / 재실행 | 17.188 | 30.951 |
| 수정 전 Aria / 빈 캐시 | 98.557 | 112.290 |
| 수정 전 Aria / 재실행 | 22.457 | 42.783 |
| 수정 후 Robot / 빈 캐시 | 46.205 | 58.688 |
| 수정 후 Robot / 재실행 | 23.613 | 45.198 |
| 수정 후 Aria / 빈 캐시 | 72.962 | 106.061 |
| 수정 후 Aria / 재실행 | 13.435 | 26.568 |

이 표는 드롭 후 해당 시점에는 표시와 조작이 가능했음을 입증하는 **확인 시점의 상한**이다. 최초 조작 가능 시점의 정확한 측정값은 아니다. 예를 들어 수정 후 Aria는 48.168초에 표시돼 있었지만, 선택 입력은 70.649초에 보냈고 이동 입력은 103.564초에 보냈다. 그 사이의 관측자 대기를 엔진 멈춤 시간으로 계산하면 안 된다. 도구의 입력+화면 캡처 소요 시간 역시 순수한 앱 입력 지연이 아니다. 원본 시각은 각 실행의 `ui-events.json`에 보존했다.

## 셰이더 컴파일·캐시·대기

`CE_TRACE_SHADER_COMPILE=1` 진단을 추가했다. 각 요청은 자기 스레드의 결과를 기록하므로 동시에 실행되는 전역 카운터 차이를 잘못 귀속하지 않는다. 드롭 직전 로그 위치를 저장하고 그 이후 요청만 집계했다. 시작 시점부터 기록했지만 아래 표에는 드롭 이전의 에디터 시작 컴파일은 포함하지 않는다.

| 모델 / 조건 | 전→후 실제 컴파일 | 전→후 디스크 적중 | 전→후 메모리 적중 | 전→후 셰이더 요청 전체 경과 구간 |
|---|---:|---:|---:|---:|
| Robot / 빈 캐시 | 110→110 | 0→0 | 2→2 | **80.318→34.318초** |
| Robot / 재실행 | 0→0 | 110→110 | 2→2 | 4.332→3.356초 |
| Aria / 빈 캐시 | 94→94 | 0→0 | 2→2 | **62.387→32.219초** |
| Aria / 재실행 | 0→0 | 94→94 | 2→2 | 3.822→2.998초 |

마지막 열은 해당 요청들의 가장 이른 시작부터 가장 늦은 종료까지다. 화면 표시나 GPU present 완료 시각은 아니다. 컴파일 실패는 모두 0이었다.

빈 캐시 코드 생성 시간의 **작업별 합계**는 Robot 71.688→88.425초, Aria 54.409→61.466초였다. 병렬 실행의 CPU·메모리 경합으로 합계 비용은 늘었지만 겹쳐 실행돼 사용자가 기다리는 경과 시간은 줄었다. 컴파일러 자체가 같은 작업을 더 적은 CPU 시간에 처리하게 됐다는 주장은 하지 않는다.

컴파일 슬롯 획득 시간 합계는 Robot 빈 캐시 0.122→0.836초, Aria 빈 캐시 0.127→0.419초였다. 이 값은 새 Slang global session 생성도 포함한다. 수정 후 별도로 계측한 조건변수 기반 **순수 슬롯 큐 대기는 네 실행 모두 0.000ms**였다. 수정 전에는 순수 큐 대기를 별도 필드로 기록하지 않았지만, 획득 전체 시간이 약 0.1초이므로 수십 초 지연의 주원인으로 볼 수 없다.

## 캐시 보존과 조건

- 각 실행은 `Bin/x64-Debug/Editor/CreatorEditor.exe --development-project .../Dynamic_CPP`의 보이는 일반 창이다. 디버거는 붙이지 않았고, `--smoke-offscreen`도 사용하지 않았다.
- 창 캡처는 1923×1111 논리 픽셀이며 로그의 실제 씬 렌더 크기는 **1496×692**였다. SampleScene의 기본 카메라·조명과 같은 드롭 위치를 사용했다.
- 프로세스별 `LOCALAPPDATA`를 작업 디렉터리로 지정해 셰이더 캐시를 분리했다. 모델마다 수정 전·후 캐시 디렉터리를 따로 만들었고, 재실행만 직전 캐시를 재사용했다. 각 빈 캐시의 실행 전 파일 수는 0이었다. 에디터 시작에 필요한 일부 셰이더는 드롭 전에 해당 프로세스에서 먼저 준비된다.
- 기존 기본 셰이더 캐시는 이동·삭제하지 않았다. 작업 전후 **263,128개 파일의 목록·크기·수정 시각이 동일**했다. 이는 전체 파일 내용의 암호학적 보존 검사와는 구분한다.
- 모델 cooked 데이터, 프로젝트 파생 캐시, 드라이버 내부 캐시는 지우지 않았다. 따라서 여기서 ‘빈 캐시’는 **CreatorEngine 셰이더 컴파일러의 디스크 캐시가 빈 조건**이지 모든 OS·GPU 캐시가 비어 있는 조건은 아니다.
- 원본 GLB는 변경하지 않았다. 성능 드롭 중 빌드·다른 검사·대용량 프로파일 분석은 겹쳐 실행하지 않았다.

## 검증과 한계

Debug x64 Editor를 재빌드했고, 최종 4회 실제 드롭 실행은 모두 정상 종료했다. 수정 후 새 빈 캐시에서 준비 중 undo와 scene.new도 검사해 취소 2회, 실패 0, 씬 메시 누수 0으로 통과했다. 워커에서 미완료 대기를 시도하는 예외도 발생하지 않았다.

셰이더 캐시 회귀 검사는 DXIL/SPIR-V 결과 일치, 재시작 적중, 의존/우선순위 include 변경, profile/options/permutation 변경 감지, 손상 복구, 쓰기 실패와 동시 요청을 통과했다. 현재 저장소의 독립 실행 빌드에는 기존 작업용 스크립트처럼 `CE_CONTRACT_STANDALONE`을 사용했다.

첫 Robot 수정 전 실행은 화면·조작·셰이더 로그 수집을 끝낸 뒤 profiler 저장을 너무 일찍 요청해 `profile.recording`으로 거부됐고 종료 코드 3이었다. 이 실행의 `.ceprof`는 없으며, 해당 행은 실제 화면 관측·완료 로그·셰이더 trace에 근거한다. 이를 정상 종료한 프로파일 캡처라고 취급하지 않았다. 나머지 7회 실행은 정상 종료했고 프로파일 파일을 보존했다. 이번 보고서의 시간 표는 그 파일의 손실 검사나 GPU 분석 결과에 의존하지 않는다.

모든 실행에서 일시적인 `METEOR Scene requested material program is still preparing` 메시지가 있었고 UI 오류 카운터가 1로 표시됐다. 이 준비 중 메시지를 셰이더 컴파일 실패로 집계하지 않았으며, 유효성 오류가 전혀 없었다는 주장도 하지 않는다.

**남은 문제:** 빈 캐시에서는 여전히 첫 렌더용 보조 셰이더를 렌더 스레드에서 준비하는 긴 구간과 수십 초의 최초 표시 대기가 남는다. 이번 변경은 재질 그래프를 순차 준비하던 핵심 병목을 줄였으며, 모든 cold-start 멈춤을 제거한 것은 아니다. 각 조건 1회 관측이므로 통계 평균이나 항상 1분 미만이라는 보장을 제시하지 않는다. 정확한 최초 조작 가능 시각이나 입력부터 화면 출력까지 지연을 구하려면 연속 화면 기록과 입력/표시 시각을 연결하는 추가 계측이 필요하다.
