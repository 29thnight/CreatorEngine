# 렌더 준비와 모델 배치 대기 추가 최적화

실제 Debug 에디터 드롭의 빈 셰이더 캐시/재실행 재현 및 후속 수정 결과는 [실제 드롭 비교 보고서](EditorDragColdWarmShaderComparison-20261021.md)를 참고한다. 해당 측정에서 1분 지연이 재현됐으며 아래 자동 실행 수치를 대체하는 사용자 경로 증거를 별도로 기록했다.

> 측정 범위 정정: 아래 2~4초 수치는 캐시를 유지한 332×144 offscreen 자동 `model.async` 실행의 요청 생성부터 씬 적용 완료까지다. 사용자가 실제 에디터에서 드래그 앤 드롭하여 모델이 화면에 표시되고 조작 가능해질 때까지의 시간은 측정하지 않았다. 사용자가 CreatorRobot 드롭에 1분 이상 걸린다고 보고했으므로, 이 결과를 실제 에디터 로드 시간이 2~4초로 개선됐다는 증거로 사용할 수 없다. 해당 체감 지연의 원인은 아직 확인하지 못했다.

2026-10-21. CreatorRobot과 Aria를 Debug x64 Editor의 실제 DX12 씬에서 다시 배치하고 전후를 비교했다. 직전 변경의 정상 종료 표본을 기준으로, 최장 RenderThreadFrame은 Robot 우선 실행에서 **925.832 → 728.330ms**, Aria 우선 실행에서 **777.571 → 621.648ms**였다. 각각 약 **21.3%, 20.1%** 짧아졌다. 수백 ms의 준비 비용은 여전히 남아 있다.

## 추적 결과와 변경

### 셰이더 캐시가 있어도 발생하는 렌더 준비 비용

가시성 파이프라인과 장면 조회 파이프라인은 처음 사용할 때 셰이더를 확인하고 PSO를 준비한다. 캐시 적중도 무비용이 아니다. 원본과 의존 파일을 읽고, 새로 생긴 우선순위 include 후보를 확인하고, 현재 내용으로 키를 만들어 검증된 바이트코드·리플렉션 쌍을 복원한다.

추가한 `ShaderCompiler.Process`, `ShaderCache.CheckDependencies`, `ShaderCache.BuildKey`로 진단한 실행에서는 렌더 스레드의 요청 45회가 합계 277.843ms, 그 안의 의존·캐시 확인이 217.287ms였다. 키 해시 자체는 13.003ms로 주원인이 아니었다. 모두 전체 기록 합계이며 단일 프레임 시간과 합산하면 안 된다.

`RHIShaderCompiler.cpp::ReadSourceFile`은 `ostringstream << rdbuf()`로 파일을 중간 스트림에 모은 뒤 문자열을 다시 복사했다. 파일 크기에 맞춰 최종 문자열을 한 번 확보하고 일괄 읽도록 바꿨다. 파일 내용 확인, include 우선순위 확인, 캐시 키 구성, 캐시 손상 검사 및 양쪽 백엔드 검증은 유지했다. 빈 파일과 읽기 실패는 거부한다. 시간·파일 크기만으로 내용을 신뢰하는 캐시를 추가하지 않았다.

변경 후 렌더 스레드의 같은 45회 요청은 Robot 우선에서 193.161ms, Aria 우선에서 188.545ms였다. 의존·캐시 확인은 각각 160.610ms, 158.497ms였다. 이는 진단 실행과 최종 실행 간 관측값이며, 셰이더 파일 읽기 변경만 분리한 통계적 효과량은 아니다.

### 배치 대기를 늘린 루트 페이지 준비

직전 변경은 필수 루트 페이지의 인증·압축 해제·속성 검증을 렌더 스레드에서 작업 스레드로 옮겼다. 씬에 게시하기 전에 두 작업을 모두 기다리므로, 렌더 멈춤이 줄어든 대신 배치 완료 대기가 늘어날 수 있었다. 재배치에도 새 메타데이터/archive에서 다시 준비하는 비용이 관측됐다. 준비 토큰을 기다리는 조건을 풀면 이 비용이 렌더 스레드로 되돌아가므로 그대로 유지했다.

속성 검증 내부에는 압축 패킷을 다시 인코딩해 정규 형식과 정확히 같은지 확인하는 경로가 있다. 그 과정에서 채널마다 벡터를 새로 할당하고, 여러 번 확장하며, 4바이트 쓰기를 바이트별로 처리했다. 다음을 수정했다.

- little-endian 호스트의 `Put`을 범위 검사 후 비정렬 안전 `memcpy`로 처리한다. 다른 endian은 기존 조립 방식을 쓴다.
- 인코딩 채널 사이에서 values/codes 버퍼를 재사용하고 codes 용량을 미리 확보한다.
- 32비트 스트림은 이웃 비트를 보존할 필요가 없으므로 기존 워드를 읽어 OR하는 단계를 생략한다.
- 디코딩의 채널별 scale 읽기를 정점 반복문 밖으로 옮긴다.

정규 형식 재인코딩, SHA-256, 유한성·법선·접선·스킨·범위 검증을 생략하지 않았다. 저장 형식·버전도 바꾸지 않았다. archive별 기존 캐시 범위와 취소·세대·씬 검사도 그대로다.

이전 구현을 별도 namespace에 보존한 비교 도구에서 8개 정점 레이아웃 × 5개 패턴, 총 40개 입력의 인코딩 바이트가 모두 일치했고 기존 패킷의 디코딩 결과도 원본과 일치했다. 각 100회 반복 인코딩 합계는 **1,286.900 → 887.202ms**, 약 31.1% 감소했다. 빌드 중 실행한 독립 도구의 수치이므로 실제 모델 로드 개선율로 해석하지 않는다.

## 실제 재계측

기준은 [직전 보고서](RenderThreadModelLoadOptimization-20261021.md)의 `parallel-robot`, `parallel-aria`이다. 변경 후에는 `optimized-robot`, `optimized-aria`를 실행했다. 각 프로세스에서 두 모델을 처음 배치하고, 각각 새 씬에서 한 번 더 배치했다. 캐시는 지우지 않았다. 성능 실행 중 빌드·다른 검사·캡처 분석을 겹쳐 실행하지 않았다.

두 최종 프로세스 모두 종료 코드 0, 배치 4회 성공/실패 0, 무효화 재시도 0, Recovered 재질 생성 0이었다. 프로파일은 complete=true, unacked=0, 기록 손실 0이다.

## 기능 검증과 재빌드

- Debug x64 Editor 전체 재빌드와 마지막 계측 코드 반영 빌드 모두 성공했다.
- 최종 실제 캡처 8개: 332×144, finite=true, validationCount=0. CreatorRobot은 매번 4 draws / 유효 깊이 픽셀 324, Aria는 3 draws / 525로 이전과 일치했다.
- 페이지 회귀 검사: 8개 레이아웃 52개 검사, 비정렬 읽기 9개, 비정렬 쓰기 9개와 인접 바이트 보존, 범위 밖 읽기·쓰기 거부, 잘못된 페이지 13개, 잘린 페이지 416개, 의미 손상 5개, 정확한 CPU 위치·signed zero·인덱스 보존 통과.
- 셰이더 캐시: 직렬화 경계·트랜잭션, DXIL/SPIR-V 일치, 재시작 적중, transitive include/우선순위 include 변경 무효화, profile/options/permutation 변경 무효화, 손상 복구, 쓰기 실패, 동시 요청 통과. 기존 스크립트는 현재 std 모듈 설정으로 독립 빌드가 실패해 작업용 복사본에 `CE_CONTRACT_STANDALONE`을 추가해 실행했다. 저장소의 검사 스크립트는 수정하지 않았다.
- 최종 실제 Editor에서 진행 중 undo와 scene.new를 확인했다. 취소 2회, 실패 0, 씬 메시 누수 0으로 통과했다.
- 테스트가 바꾼 active.workspace는 실행 전 파일로 복원하고 이번 작업이 생성한 rejected.3만 제거했다. 기존 사용자 변경과 캐시는 유지했다.

런타임 SHA-256:

- 이전: `863E028DE2B06B125B53094E7359E86952D188ECE2BB93E303DE75DE7E0D233D`
- 최종: `C3B1D2D2953B9E7E97E9CDEB398E43BB8D87785AA430C2FF8FA0471C55B7C7C1`

원본 GLB는 변경하지 않았다. CreatorRobot SHA-256은 `58D779AFDE1A7FBD13332999C8B11890FB7E10FF2036CA6AE3645D14BEDBA402`, Aria는 `8ED22A7E3CF7E4F7087A45E83EEBF327B283F0162622F0051CF8AE45833FB0E7`이다.

## 남은 비용과 측정 한계

최종 렌더 스레드에는 compute pipeline 준비 39회 합계 Robot 우선 168.950ms / Aria 우선 163.076ms가 남았다. 최장 한 번은 32.073 / 29.207ms였다. 여기에는 캐시 조회·해시·필요한 PSO 생성이 함께 포함돼 있어 전부 드라이버 컴파일 시간이라고 단정할 수 없다.

셰이더 include 대체 후보 확인도 45회 합계 90.232 / 90.594ms가 남았다. 이를 줄이더라도 새 우선순위 include가 생기는 경우를 놓치지 않아야 한다. 명령 기록 계획의 전체 최장값은 약 169~195ms로, 이번 변경에서 일관되게 감소하지 않았다. 다음 렌더 최적화는 PSO 준비와 이 명령 계획 내부를 더 나눠 추적할 필요가 있다.

진단용 `trace-robot`은 배치·캡처·프로파일 저장을 마친 뒤 종료 시 `slang-compiler.dll`의 `0xc0000409`가 발생했다. Windows Application Error 이벤트를 보존했고, 이 실행은 원인 진단에만 사용했다. 최종 성능 두 실행과 취소 실행은 정상 종료했지만, 기존 Slang 종료 오류 자체를 고쳤다고 주장하지 않는다.

이번 표는 순서를 바꾼 전후 각 1회 실행의 관측이다. 반복 통계나 모든 씬에 대한 상한 보장은 아니다. Debug CPU 범위이며 GPU 시간, 표시 FPS, Release 성능 또는 고해상도 성능의 개선율로 해석하지 않는다.

## 증거 위치

`Build/render-ready-20261021/`에 원본 캡처, stdout/results, 실행 파일 해시, 분석 JSON, 검사 로그와 작업용 재현 스크립트를 보존했다.

- `optimized-robot/`, `optimized-aria/`: 최종 정상 종료 계측.
- `comparison.json`, `compare.py`: 이전/이후 시간·범위·캡처 검증.
- `trace-robot/`, `application-errors.json`: 진단 및 종료 오류.
- `optimized-build.log`, `markers-build.log`: 재빌드 기록.
- `page-probe.log`, `codec-compare.log`, `codec_compare.cpp`, `QuantizedGeometry.reference.h`: 코덱 검사와 이전 구현 비교.
- `shader-cache-adapted/Run-ee39220638184021be2452cd9a2bbfad/`: 셰이더 검사.
- `cancel-final/`: 실제 취소·씬 전환 검사.
