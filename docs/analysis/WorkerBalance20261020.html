§00

결론과 범위

최신 저장 계측은 워커 풀 전체의 장기 편중보다 렌더 소유자 스레드의 직렬 작업 집중과 명령 기록 대상별 작업량 차이를 보여 준다. ETW ON 구간에서 공용 워커 8개의 평균 Running 비율은 각각 7.15–8.02%이고 최대/최소 비율은 1.121배다. 같은 구간의 RenderThread는 81.28% Running이다. RenderGraphDeclare는 평균 5.097 ms 중 5.035 ms가 Running이므로, 이 단계의 대부분을 워커 대기 시간으로 해석할 수 없다.

명령 기록에는 별도의 개선 후보가 있다. 현재 캡처는 8개 공용 워커를 사용하지만 네이티브 command target은 4개다. RenderCommandRecord.Worker1이라는 기록 대상 1은 그래프당 두 작업의 합이 평균 1.723 ms이며, 그중 OS Running이 1.671 ms다. 이것은 [Worker 1]이라는 물리 작업 스레드 번호가 아니다. 다른 기록 대상과 비용 차이가 있지만, 의존 관계와 같은 대상의 순서를 유지한 채 분배해야 한다.

이 문서는 변경 전 저장 계측을 재분석한 기준선이다. 변경 후 Windows 호스트 실행, 실제 GPU 출력 검증 및 엔진 프레임 성능 재측정은 이 분석 환경에서 수행하지 않았다. 작업 분배 변경이 실제 프레임 시간을 줄였다는 주장은 하지 않는다. 정본 수치는 WorkerBalance20261020.json에 있으며, 대용량 원본을 복제하지 않고 기존 계측 파일을 참조한다.

참고 방법론은 사용자가 제시한 cpu-performance-engineering의 공식 README다. 전용 MCP는 이번 세션의 호출 가능한 도구로 노출되지 않아 README의 측정·동시성·allocator 관점을 적용했다. 이 작업에서는 저장 실측과 코드 정적 근거를 구분하고, 누적 작업 합과 의존 관계의 critical path를 따로 평가하며, 분배 장치에는 고정 크기 또는 소유자가 재사용하는 저장소를 사용한다. 외부 코드를 복제한 구현이 아니며, 실제 변경 후 측정 전에는 speedup을 주장하지 않는다.

소스 신원의 한계

source-identity.json은 캡처 전부터 존재한 Editor 프로젝트·GUI·문서 변경 등 dirty 목록을 함께 기록한다. source-verification.json의 sourceUnchanged=true는 캡처 도중 소스가 변하지 않았다는 뜻이며, 전체 작업 트리가 깨끗한 HEAD였다는 보증이 아니다.

기록된 582개 파일 SHA256을 변경 중인 작업 트리가 아닌 고정된 4eeba98 Git blob과 대조했다. 98개는 원문 바이트가 일치하고 445개는 LF를 CRLF로 변환했을 때 일치한다. 나머지 39개는 일률적인 줄바꿈·BOM 변환으로 일치하지 않아 동등성을 확정하지 않았다. 혼합 줄바꿈일 수도 있고 다른 바이트 차이일 수도 있으며, SHA만으로 둘을 구분하지 않는다. 목록과 핵심 경로의 hash는 정본 JSON의 integrity.source_identity에 보존했다. EnhancedRenderGraph.cpp, EnhancedSceneRenderer.cpp, MaterialGraphSceneHost.cpp, GpuGeometryVisibility.cpp, RHICommandTranslator.cpp, RHISubmissionThread.cpp 등 분석 경로는 원문 또는 CRLF 변환 hash로 연결된다.

저장소 verification.json은 원본 381개 파일의 hash 일치와 캡처 round trip 일치를 보고한다. 이번 독립 분석에서는 필요한 43개 파일을 내려받아 manifest의 byte 수와 SHA256을 다시 확인했으며 불일치는 0개였다. 이번 분석이 381개 전체를 다시 검증했다고 주장하지 않는다.

§2

2. 시간 축과 표본 선택

  • baseline 전체 summary는 ETW를 켜지 않은 엔진 계측 캡처다. 프레임 경계 402개, 완전한 RenderGraphDeclare/MaterialGraphScenePrepare/RenderCommandRecord scope는 각각 794개다. CPU 렌더 제출 신원이 완전한 표본은 뷰별 396개다.
  • ETW 전체 summary는 프레임 경계 376개이고, CPU 렌더 제출 표본은 뷰별 349개다. 아래 OS 상태 분석은 전체 summary와 구분하여 ON 구간에 완전히 포함된 scope만 사용한다. 경계 partial flags의 하위 두 비트가 설정된 scope는 제외한다.
  • ETW ON의 완전한 RenderCommandRecord는 678개이며, Scene/Game 각각 339개로 실제 렌더 측정 구간에 일대일 대응한다. 작업 scope 4407개 모두 부모 기록 구간에 속한다. MaterialGraphScenePrepare는 경계 위치 차이로 679개다.
  • p50은 median, p95/p99는 정렬한 실제 표본의 min(n-1, floor(n*p)) 인덱스다. 서로 다른 자식 scope의 p95를 더하지 않는다.
  • ETW의 Running은 OS가 CPU에 올린 시간으로 유용한 작업량과 동일하지 않다. Ready는 실행 가능하지만 스케줄되지 않은 시간이고, Waiting 자체는 특정 mutex·fence의 대기 원인을 알려 주지 않는다.
  • 여러 워커의 시간 합은 core-ms 또는 겹치는 scope의 합이다. 이를 wall time, 프레임 시간, 화면에 표시된 FPS로 바꾸어 쓰지 않는다.

baseline summary, ETW summary, ETW timeline metadata, scope-metrics.json이 근거다. 원본 scope와 OS 상태를 다시 교차하여 주요 네 단계의 count·mean·Running/Ready/Waiting 평균이 저장된 scope-metrics와 반올림 오차 범위에서 같음을 확인했다. ETW lost buffers/events는 모두 0이고, 캡처의 partial scope는 14개다.

§6

6. GPU와 계측 영향

baseline은 각 뷰 396개 렌더의 GPU pass 표본을 갖는다. 같은 뷰에서 pass별 시간을 합하고 렌더 수로 나눈 평균은 Scene 5.9646 ms, Game 6.1244 ms다. 이 값은 기록된 GPU pass 시간 합이며, 보정된 queue busy 합집합·GPU 전체 프레임 span 또는 p95가 아니다.

Shared.First.Cull, Shared.ShadowRecovery.Cull, CameraMeshlet.Recovery.Cull 세 종류의 합은 Scene 평균 2.5240 ms, Game 2.5395 ms로, 각 뷰의 측정 pass 합 중 42.32%, 41.46%다. CPU command target 분배는 이 GPU shader 자체의 수행량을 줄이는 변경과 구분한다.

§7

7. 변경과 수용 조건

변경의 적용 범위

이 기준선은 다음 작업의 근거다. 명령 target 상한을 실제 가용 워커 범위에 맞추되 기존 최대 8개의 계약을 지키고, contiguous partition의 최대 추정 비용을 줄이는 후보를 기존 CPU dependency·wave 수용 조건으로 평가한다. RHI 번역에서는 긴 target을 먼저 배정하고, 먼저 끝난 작업자가 아직 시작하지 않은 target을 맡을 수 있게 한다. ScenePrepare에는 독립 packet 작업의 분리와 재사용 scratch를 구현했다. 반복 상수 업로드 배칭은 이번 PR에서 수행하지 않았다.

command target 용량과 소유권의 정적 검토

WorkPartition.h의 새 분할 함수는 caller가 제공한 span과 scalar만 사용한다. 비용 합의 정수 overflow를 결과 기록 전에 거부하며, 기존 명령 순서를 보존하는 연속·비어 있지 않은 구간을 만든다. EnhancedRenderGraph.cpp의 consider가 기존 CPU dependency와 wave 수, 추정 critical work 조건으로 후보를 평가한다. 최대 target 추정 비용의 최소화만으로 후보를 무조건 채택하지 않는다.

command target 수와 raster slice 수는 다른 값이다. MaterialGraphSceneHost.cpp의 RasterRecordingSlices는 최대 4개를 반환하며, MaterialGraphSceneShadowStage.inl을 포함한 두 raster split caller가 이 값을 전달한다. 그래프는 min(pass.maxSlices, poolWorkers)를 적용하므로 command target을 8개로 늘려도 recordedGeometryRoutes[4]와 shadowRecordingStats[6][4]의 slice 인덱스는 0–3이다. DX12·Vulkan command pool의 slot/encoder는 초기화된 worker 수만큼 준비되고, DX12 제출 배열과 공통 target 검증의 최대 용량은 기존 kMaxWorkers=8이다.

정상 Editor·Player 부팅에서는 EngineBootstrap.h의 InitializeRuntime이 scheduler를 시작한 뒤 Run이 app을 생성·초기화한다. 이후 렌더 스레드의 첫 pipeline build에서 live command pool이 초기화된다. 따라서 정상 부팅에서 scheduler가 아직 시작되지 않아 command pool이 1개 fallback으로 고정되는 순서는 확인되지 않았다.

RHICommandTranslator.cpp는 고정 용량을 넘는 target count를 결과 배열 접근 전에 거부한다. 고정 크기 claim queue는 각 target을 한 작업자에게만 배정하고, 그 작업자가 해당 target의 모든 segment를 번역한다. 모든 작업을 join한 뒤 실패 선택과 최종 제출은 원래 target 순서를 사용한다. 이 정적 검토는 native driver의 병렬 실행 검증을 대신하지 않는다.

변경 후 실행에서 확인할 조건

추정 비용의 균형은 실제 비용의 균형을 보장하지 않는다. 변경 후에는 같은 코드 구성·장면·뷰·worker 수의 Windows 실행에서 다음을 확인해야 한다.

  1. 원래 GPU command 제출 순서, CPU dependency, target의 단독 기록 소유권과 실패 시 전체 drain을 유지한다.
  2. 1·4·8 worker와 빈 target·부분 사용 target·큰 비용·정수 overflow 경계를 검증한다. command target 최대 8개와 raster slice 최대 4개의 독립된 용량 계약을 유지한다.
  3. 같은 방식으로 Record/Translate/ScenePrepare의 wall·p95, target별 실제 CPU 비용과 생성된 DAG의 critical path를 측정한다. 현재 없는 per-unit timing을 사용할 경우 그 진단 비용을 별도 구분한다.
  4. 엔진 계측 OFF의 정상 실행 관측과 GPU validation을 켠 정확성 실행을 분리한다. CPU-only 회귀 통과를 실제 DX12/Vulkan 실행 통과로 표기하지 않는다.

이 문서의 렌더링 시간·사용률은 전부 변경 전 저장 계측이다. 다음 절의 CPU 회귀 검증은 코드 계약을 확인하며 Windows native 실행 완료나 성능 개선을 뜻하지 않는다.

작업 분배용 지역 저장소는 bounded array·span·scalar다. RHI translation의 새 queue는 이 검증 환경에서 128 bytes이고 cost array는 64 bytes다. 이것은 해당 구조의 크기이며 함수 전체 stack 크기나 native RHI 전체의 무할당을 보장하는 값은 아니다. ScenePrepare의 packet record vector는 owner 상태에 보관하고, 참조를 빌려 resize·덮어쓰기를 수행한다. packet마다 지역 vector와 그 Debug proxy를 다시 만드는 방식은 피한다. record는 UploadPackets에서 복사되므로 재사용 vector의 주소를 완료된 frame에 게시하지 않는다.

CPU 회귀 검증과 한계

세부 실행 결과와 실제 검증 입력의 SHA256은 WorkerBalance20261020Validation.json에 모은다. normal·sanitizer·실제 scheduler 검증을 구분하며, 아래의 native scheduler는 엔진 JobScheduler·ThreadPool·enkiTS CPU 경로를 뜻한다.

ScenePrepare packetexact Host packet admission/build/join과 UploadPackets, RenderArena 및 실제 scheduler를 실행한 308,808개 검증을 normal·ASan/UBSan에서 각각 통과했다. worker 1·2·4·8, 기록 bytes·출력 소유권·오류 순서·drain을 확인했다. 전역 pool을 시작하지 않고 주입한 scheduler만 4·8 worker로 실행한 경우도 검증한다. 작업 수 계산은 해당 scheduler가 소유한 pool의 worker 수를 조회한다.

ScenePrepare의 warm allocation 비교는 해당 packet CPU fixture에서 관측한 할당 요청이다. worker 4·8, draw 97·4096, static cache hit/miss의 8개 조건에서 각각 16회 warmup 후 17개 표본을 수집했다. cache hit의 median은 preparation당 133→64회, cache miss는 172→85회였다. 변경 후 모든 표본은 각각 64·85회다. 집계는 일반·aligned new와 arena upstream service의 할당 요청을 포함하며, RHI upload와 기존 GPU packet plan은 fixture이고 mimalloc은 malloc shim으로 대체했다. 또한 작은 admission-count adapter가 실제 preparation helper로 전달한다. 이 결과를 전체 MaterialGraphScenePrepare의 무할당, Windows 할당 횟수 또는 프레임 시간 개선으로 해석하지 않는다.

ASan/UBSan 실행에서는 sandbox의 /proc 접근 제약으로 LeakSanitizer를 비활성화했다(detect_leaks=0). 따라서 이 결과를 leak 검사 통과라고 쓰지 않는다. 강제 지연·admission 실패 fixture 일부는 join되는 std::thread를 사용하며, 전체 결과를 실제 native RHI·driver 검증으로 확장하지 않는다.

이 Linux 환경의 include-boundary gate는 FAIL이며 기존 실패가 그대로 남아 있다. 변경 전 HEAD 7ebcd2b의 Git blob을 별도 임시 트리에 복원하고 현재와 같은 sparse-checkout footprint에서 같은 검사기·allowlist로 실행한 결과, 양쪽 모두 상향 간선 27개·물리 경계 69개로 stdout까지 동일했다. 이번 수정으로 추가된 위반은 0개다. 전체 HEAD scanner 입력에는 현재 sparse checkout에 없는 ThirdParty/DxTimingCaptureLibrary/lib/DxTimingCaptureLibrary.lib.vcxproj가 하나 더 있어 물리 경계 70개가 된다. 이 footprint 차이를 수정에 의한 위반 감소로 보고하지 않는다. 검사기나 allowlist를 변경해 통과시키지 않았다.

Linux CPU 검증으로 확인한 범위는 분배·순서·수명·실패 처리와 제한된 할당 계약이다. Windows 빌드, DX12/Vulkan native GPU 실행, GPU 출력 동일성, 변경 후 CPU/GPU 시간 및 표시 FPS는 아직 검증하지 않았다. 최종 수용에는 7절의 동일 조건 재측정이 필요하다.
