기준은 master f4264beb85a4183ab4373313a2492fe5c427c739다. 이번 변경은 재현한 RG9 정확성 결함과 CPU 기록·입력 준비의 반복 비용을 수정한다. Windows native 빌드·GPU 출력·일반 프레임 성능은 이 환경에서 실행하지 않았다. 따라서 제품 성능 수용이나 PHASE 완료율을 올리지 않는다.

초기 수정 커밋은 4de854c4b7171619b942e7eba2541b6a9fdb88f9다. 아래 후속 구현과 검증은 이 커밋에서 열려 있던 recording 전체 gate, translation consumer 검증과 재질 선택의 중복 작업을 다룬다. 초기 실패를 없던 일로 처리하지 않고 원인과 해결 범위를 함께 기록한다.

§01

RG9 결함과 회귀

1 mip에서 mip 0만 쓰고 전체 texture를 읽는 선언은 유효하다. 접근 범위를 그대로 둔 채 2 mip로 바꾸면 mip 1이 초기화되지 않으므로 compile이 실패해야 한다. 원래 retained 경로는 기존 program을 재사용해 성공했고, 같은 선언의 fresh graph만 실패했다.

기존 CheckTransientMips()는 mip 수와 사용 범위를 동시에 바꿔 범위 차이만으로도 재컴파일됐다. 새 검사는 접근 범위를 고정한 1 → 2 → 1 → 1 전환, 게시 program의 직접 binding schema, cached/fresh 오류 동치와 실패 뒤 Reset 복구를 확인한다. fixture의 현 API 불일치를 먼저 복구한 뒤 원래 matcher에서 신규 검사 두 개가 실제 assertion으로 실패하는 RED를 확인했고, mip 비교를 추가한 뒤 기존 전체 suite를 그대로 통과했다.

공식 portable graph runner는 실제 graph translation unit을 빌드한다. native service와 platform allocation은 fixture이며, 사용하지 않는 worker 제출 경계는 여전히 명시적으로 거부한다. 미사용 WinRT 의존을 RHIResourceTypes.h에서 제거했고 SDK 대역 헤더를 production에 추가하지 않았다.

§02

후속 구현: 실제 재할당과 재질 선택의 중복 작업

Recording scratch

초기 전체 recording gate의 recording scratch or nested dependencies were reallocated or accumulated 실패는 실제 구현 결함이었다. ce::dynamic_array::assign(count, value)는 여유 capacity가 있어도 새 배열을 만들고 swap한다. RHIBuildRecordingTaskGraph의 이전 target 배열과 CriticalWork의 완료 작업량 배열에 이 API를 사용하여, 재사용을 의도한 경로에서 매번 저장 공간이 교체됐다.

RHIRecordingTaskGraph.h의 두 scalar 배열만 resize와 std::ranges::fill로 초기화하도록 변경했다. 기존 pointer-stability assertion을 유지했고, target 수 4 → 2 → 16 → 2 → 16, node 수 3 → 1 → 0 → 3, dependency·work 변경과 잘못된 target 수 거부를 추가로 검사했다. 전역 컨테이너 API나 scheduler 동작은 변경하지 않았다. 초기의 helper 선택 실행 761개 통과만으로 전체 gate를 통과 처리했던 것은 아니며, 후속 수정 후 기본 전체 gate 24,928개를 통과했다.

Material slot별 선택

SelectReadyInput의 기존 unique-slot 수집 결과에 이번 호출의 readiness 결정과 preview pin을 보관한다. PollPrograms 이후 현재 backend의 준비 상태를 판단하며, 첫 draw 등장 순서에서 pending·실패를 처리하고 selected draw 순서에서 revision을 게시한다. 함수가 반환하면 결정은 폐기한다. 다음 프레임이나 다른 세대의 준비 상태를 영속 cache로 재사용하지 않는다.

RequestProgram은 이전에도 slot별 한 번이었다. 새로 줄인 작업은 polling 이후 선택 단계의 중복 readiness scan과 동일 preview에 대한 Retain·Borrow·coverage 분류다. 다음 수치는 수정 전 커밋과 현재의 실제 선택 함수 본문을 같은 fixture에서 실행한 호출 수다. 축소한 RequestProgram/PollPrograms 내부의 작업, 엔진 전체 호출 수나 실행 시간은 포함하지 않는다.

scene-input 검사는 전체 mesh identity 19필드 변경, stale/범위 밖 hint, 같은 값의 다른 owner, generation 변경, 외부 draw 조작, 순서 변경·새 key collision, 1,021개 pin의 동시 append를 포함한다. 실제 SceneViewInput::Seal과 재질 경로를 쓰는 기존 native probe에도 회귀를 추가했지만, 작성된 native 검사를 실행 통과로 계산하지 않는다.

graph entry 회귀는 실제 RAII scope를 직접 활성화해 PrepareParallel과 SubmitQueues가 native 준비·plan·출력·queue 동작을 변경하기 전에 거부되고 scope 종료 후 정상 동작하는지 검사한다. 실제 helper callback 안의 중첩 호출과 예외 복구는 recording-helper suite가 검사한다. RecordParallelInternal·RecordSoftware의 조기 guard 위치는 정적 검토 범위이며 이 fixture에서 두 경로의 전체 native 기록을 실행하지 않는다.

translation fixture는 현재 profiling·provenance·backend scope API에 맞춰 복구했다. production profiling/provenance 타입과 backend TLS 구현을 사용하고, owner inline·다중 worker 실행, 정확히 한 번 replay, target 독점, 예외 뒤 owner-thread backend scope 복구와 CPU 출력 resource 수명을 검사한다. 고의 지연·admission 실패 시나리오는 fixture의 join하는 std::thread 경로이며, 실제 엔진 scheduler 실행은 worker 1/4/8 경로에서 별도로 확인한다. shipping 계약이므로 개발 빌드의 profiler context 전달·이벤트 기록은 검증하지 않는다.

Translate의 단일 job 직접 실행은 기존에도 있던 동작이다. 이번 helper 변경의 실제 consumer 검증은 software-queue suite에 추가한 IRHIQueueRecorder::RunParallel 경로가 담당한다. 실제 software recording을 열고 target 1개는 owner inline, target 4개는 worker에서 기록하며 예외 전파·callback drain·inline scope 복구·resource 해제를 확인한다. 기존 queue 검사의 제출 준비·실패 진단·CPU fence retirement 조건도 그대로 실행한다.

software-queue fixture의 오래된 std::function override를 ce::owned_func로 맞추고, mimalloc 대역의 실패는 현재 API 계약에 따라 noexcept에서 null을 반환하도록 복구했다. 실제 owning allocator가 bad_alloc을 발생시키고 storage를 반환하는 검사는 유지했다. GCC runner는 -Werror를 유지하되 reflgen:: annotation만 제외하고 nonnull·mismatched-dealloc을 경고로 출력한다. 전자는 unevaluated destructor noexcept 검사에서, 후자는 bulk_reallocate의 가상 over-aligned 경로에서 발생한다. 실제 유일 caller의 bulk_block 조건은 alignment <= malloc_alignment를 요구하므로 해당 aligned-delete 경로는 도달하지 않는다. 이 예외는 JSON 검증 결과에도 기록하며 production allocator를 변경하지 않는다.

통과로 세지 않은 항목

  • 초기 커밋의 recording 전체 gate 실패와 translation fixture 컴파일 실패는 위 후속 구현·복구로 해소했다. 이 사실을 원래 검사도 통과했다는 의미로 소급하지 않는다.
  • 초기 include-boundary gate는 sparse checkout에서 상향 include 7개·물리 경계 85건으로 실패했다. 지적한 source/project 경로 중 초기 수정 커밋에서 변경한 경로는 없고, project-parse 5건은 checkout에서 제외한 프로젝트다. 전체 master checkout의 결과나 나머지 실패 원인까지 이 관찰로 입증하지 않는다. allowlist는 변경하지 않았다.
  • scene-input·scene-selection 기본 LeakSanitizer 실행은 컨테이너의 /proc task/ptrace 제약으로 실패했다. 이후 leak detection을 끈 ASan+UBSan 결과를 누수 검사 통과로 확대하지 않는다.
  • GCC의 기존 reflection/noexcept 관련 경고가 출력된다. warning-free 빌드로 표시하지 않는다.
  • Windows/MSVC Debug·Release 및 non-unity 빌드, DX12/Vulkan native 기록·RG9 GPU·재질 수명 회귀, 픽셀·validation, 일반 프레임 CPU/GPU p50/p95는 미실행이다. 단일 target의 owner 실행에 맞춘 native self-test, inline/worker 혼합 기록의 실패 복구·진단·종료 순서도 재실행이 필요하다.

§04

보고서 정정과 잔여 범위

RG9 구현 기록의 mip program 검증 문구에 mip-only 사각지대를 명시하고, 정본 계획과 진척 원장에 현재 수정본의 native 재검증이 열려 있음을 덧붙였다. 과거 실행의 source/binary hash와 인일 원장은 보존하며, 그 기록을 이번 코드의 완료 근거로 재사용하지 않는다.

기술설명서의 자동 측정 기반 큐 배치 설명도 현재의 authored async 정책과 graphics-only primary 경로에 맞췄다. CPU worker 절감과 GPU async compute는 서로 다른 작업이다.

실제 제품 pass의 async opt-in과 전체 프레임 개선, RG7 조합, Declare 비용, 뷰 간 독립 실행, pending geometry/preview 정책, shadow cache 예산 재설계는 이 PR에서 완료한 것으로 주장하지 않는다. 이들 변경은 대표 장면의 trace와 native 수명·출력 검증을 함께 확보해야 한다.

특히 EnhancedSceneRenderer의 DX11·DX12 경로는 view loop 전에 prepareSceneGeometry() 실패를 반환하므로 geometry 준비 지연이 독립적인 material preview까지 막을 수 있다. 이 gate는 이번 slot별 선택 최적화로 해결되지 않았다. geometry pin 게시·draw-pool 구축과 view별 실패 범위를 함께 변경해야 하는 후속 구현 항목으로 남긴다.
