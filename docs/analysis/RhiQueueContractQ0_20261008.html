Q0 queue/timeline foundation — accepted 2026-10-08

Q0 accepted for the DX12 queue foundation. RG8/L4 consumers remain separate. RG7 remains closed/default OFF. Current device/submission/retirement consumers use one queue and an unqualified fence value; Q0 must provide identified queues and producer-owned timeline points before adding scheduling. The first slice added backend-neutral contracts and CPU validation. The second slice adds concrete DX12 queue/timeline primitives; GPU overlap and resource submission acceptance remain pending.

RHIQueueContract.h defines Graphics/Compute/Copy kinds, process-unique device-incarnation/queue identity, service capabilities, timeline status and a strongly retained issued point. Fence objects remain opaque; no D3D12/Vulkan native handles enter this API. Capabilities default unavailable and refer to implemented service availability, not assumed hardware concurrency. The abstract factory and queue interfaces declare creation, monotonic signal and GPU-enqueued wait; DX12DeviceResources now implements the factory using DX12QueueService. Vulkan has no provider in this slice.

Wait validation rejects null/unissued/zero/reserved points, invalid queue kinds/IDs, different device incarnations, unavailable timelines and native device-loss sentinels. Completion requires an available timeline, a finite non-sentinel completion value and the issued target reached. Common-boundary resource handoff validation requires distinct queue IDs, the actual producer timeline and both release/acquire declarations. This validates the envelope only; it does not issue resource barriers, detect dependency cycles or authorize cross-queue alias reuse. Vulkan must translate its state/layout/queue-family rules in its backend.

§01

Concrete DX12 primitives

DX12DeviceResources supplies Graphics/Compute/Copy queue creation through the common factory; actual D3D12 queue types are DIRECT/COMPUTE/COPY. Queues have distinct IDs and a process-unique DX12 service incarnation recreated on device initialization. Each owns a native fence and publishes a point only after native Signal acceptance and device-loss checks. Zero, sentinel, equal and decreasing values fail with an empty output point. Wait uses ID3D12CommandQueue::Wait directly, validates device/service provenance, and retains native producer fences before enqueue. Retention is deduplicated by producer timeline and lasts until service teardown; queue-specific resource retirement remains step 3. A native queue may fail to be created even when the primitive service is available; capabilities promise no hardware overlap.

Shutdown revokes admission under the same lock used for native enqueue, appends private final markers to cover even waits after the last public signal, and requires completion or proven device removal before releasing service-owned queues. Private markers use separate fences, so they cannot publish a public point or consume the reserved UINT64_MAX sentinel. External queue/point owners can retain native objects after shutdown, but operations reject the retired service and its timelines report unavailable. No current frame submission is routed through these queues; the existing serialized product path and RG7 default OFF remain.

The existing Editor dx12.rendergraph queue-native checks real queue creation and Graphics→Compute→Copy Signal/Wait completion, value rejection/output clearing, native provenance, foreign service incarnation, trailing wait teardown, shutdown/reinitialization and real removal of a separate WARP device. A fake timeline with a matching identity is still rejected by the native backend. This proves primitives only: it does not force a delayed payload dependency, execute resource handoff barriers, associate recordings with queues or prove queue-specific resource retirement. These stay in fixed step 3, not in RG7.

Test-window responsiveness limitation

The initial visible Debug commandlet spent 106,402ms in the existing full dx12.rendergraph regression, compared with 537ms for the new native queue test. App.cpp calls ConsoleCommandSystem::Pump() on the main/game thread, and RunOne() synchronously executes the command; the next scripted command was quit. This blocks window processing during the full regression and explains the observed window becoming responsive only at exit. Passed GPU/test output and exit status do not establish UI responsiveness. The wrapper now uses the existing --smoke-offscreen Editor mode (no separate test project); Release ran without a visible main Editor window. This avoids presenting a frozen automation window, but interactive execution of the full synchronous regression still blocks the Editor. Normal editing responsiveness is not an acceptance claim of this slice.

§02

Final submission/resource acceptance — Q0 closed

All three fixed Q0 steps are complete in the supported DX12 environment. IRHIQueueCommandBatch exposes immutable target queue and recording identity; native lists remain behind the backend. Submit is one-shot, validates recording provenance and fresh values before native execution, and executes through the existing bounded RHI submission thread. The CPU admission wait does not wait for GPU completion. Successful execution publishes that queue's timeline point and retains the batch, command allocator/list, resources and optional caller token until that same queue completes. Other queues' larger fence values cannot retire it. Collection and teardown destroy caller-owned lifetime tokens outside the admission lock.

DX12SealQueueRecording bridges existing backend-owned closed command lists through a required lifetime pin. The caller must pin their actual allocator/resource storage and must not reset it while retained; the bridge cannot infer resources from a native list. The buffer-copy adapter owns its allocator/list/resources directly and translates supported default-heap buffers through COMMON→COPY_SOURCE/COPY_DEST→COMMON. Upload/readback fixed states stay fixed. Resource-specific recording of other workloads and live graph scheduling are consumers in RG8/L4, not a new Q0 closure gate. Existing serialized product rendering is preserved.

Rejection before native execution leaves the recording reusable and retains no GPU batch. Execution followed by failed Signal publishes no point, faults the queue against further work and quarantines ownership with retire value zero. A private teardown marker must prove completion before releasing quarantine; actual device loss instead provides teardown proof and is never treated as ordinary timeline completion. External handles survive as retired objects and reject submission. Controlled failure injection here is not a claim of spontaneous hardware failure/native driver Signal failure testing.
