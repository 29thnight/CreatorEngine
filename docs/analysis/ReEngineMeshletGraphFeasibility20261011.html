메시렛 단계의 render graph 수용 경계

기준: master 493536e300e274cbf59989cdd62b20310c8ae64f의 소스 정적 조사. 이번 재작성에서 빌드·실행·성능 측정은 하지 않았다.

가능성 검토에서 실제 배선으로producer와 consumer의 선언history와 현재 depth동시 쓰기와 단계 분할후속 수용 조건

가능성 검토에서 실제 배선으로

옛 문서는 다단계 meshlet pipeline을 기존 graph에 넣을 수 있는지 제안했다. 현재 BuildPipelineDesc에는 Geometry·Cull.First·Occluder·Cull.Final·Surface가 실제로 배선되어 있다. 따라서 이 전체 연결을 여전히 미구현 제안으로 설명하지 않는다. 외부 엔진과 동일한 구현이라는 주장도 하지 않는다.

producer와 consumer의 선언

LivePipelineDesc는 먼저 publish되지 않은 slot의 read/modify, 중복 publisher, 꺼질 수 있는데 새 slot을 쓰는 node, declare 누락을 거부한다. 이후 EnhancedRenderGraph의 versioned resource usage가 실제 recording dependency를 표현한다. 이름의 순서와 resource dependency는 서로 다른 검사다.

GpuGeometryVisibility::Frame은 AddCommandInputRead와 AddVisibleIdsRead로 consumer usage를 제공한다. 이미 다른 recording에 속한 frame을 재사용하는 것은 허용되지 않는다. SceneHost admission은 ExplicitVersioned·meshIndirect·cooked meshlet을 요구한다.

history와 현재 depth

GpuGeometryOcclusion::History는 완료와 identity를 가진 이전 입력이며 ReadHistory가 현재 recording의 read로 가져온다. current pyramid는 앞선 같은 view D32Float standard-Z depth에서 선언한다. geometry consumer가 그 depth를 다시 쓰지 않는다는 조건이 중요하다.

이 helper의 존재는 모든 temporal effect의 자동 history 관리 서비스가 완성됐다는 뜻이 아니다. scene epoch·view·history revision·extent 변경, abort/rejection에서 각 owner의 invalidation이 필요하다.

동시 쓰기와 단계 분할

옛 commutative-writer 확장 제안을 현재 제품 API로 간주하지 않는다. 지금 연결은 명시적인 producer 버전과 consumer read를 통해 단계 간 순서를 표현한다. 여러 dispatch가 같은 UAV를 건드린다면 atomic 의미·범위·barrier·최종 consumer 버전을 실제 graph API로 설명해야 한다.

GPU args/visible list는 recording 소유이며 completion까지 유지한다. node를 많이 나눴다는 사실만으로 async overlap이나 순성능 개선이 생기지 않는다. queue admission과 자원 conflict는 별도 검토 대상이다.

후속 수용 조건

순서 누락, wrong graph/recording, history identity 불일치, empty/unsupported 입력, invalid cooked meshlet과 failure propagation을 negative case로 확인해야 한다. pixel parity, LOD 품질과 성능은 같은 scene·camera·material·resolution의 실제 실행이 필요하다.

일반 helper의 unsupported-null 결과를 SceneHost direct fallback으로 문서화하지 않는다. 자세한 제품 계약은 GPU 기하 배선, 단계 책임은 RenderGraph 계획을 따른다. 이번 문서는 실행 수용 결과를 추가하지 않았다.
