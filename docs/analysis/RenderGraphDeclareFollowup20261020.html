§00

결론과 현재 상태

저장된 최신 캡처에서 RenderGraphDeclare의 병목은 작은 metadata packet의 생성만으로 설명되지 않는다. ETW를 사용하지 않은 baseline의 Declare 평균은 4.405760 ms이고, 순서대로 실행되는 37개 노드 본문의 합이 **4.122460 ms, 93.57%**다. 공용 워커가 수행한 기존 packet build의 합은 Declare당 0.135630 ms다. 이 값은 겹쳐 실행될 수 있는 작업량이며, 이를 그대로 Declare에서 뺄 수 있는 시간은 아니다.

ETW ON 원본 678개 Declare를 노드·하위 scope와 다시 연결했다. 25,086개 named node와 같은 수의 본문이 모두 올바른 부모에 포함됐다. 중첩을 제거하면 평균 5.096890 ms 중 그래프 API가 1.500037 ms, SharedBuild가 0.210163 ms, 그 밖의 노드 본문이 3.003421 ms다. 따라서 이번 후속은 pass usage와 resource version 저장 방식, HZB 선언의 반복 저장·이름 생성, SSGI의 지역 컨테이너와 callback capture 복사, metadata packet의 실제 작업량에 맞춘 분배를 대상으로 한다.

기존 엔진 시간은 변경 전 저장 캡처이며, 후속 변경의 수치는 7절의 Linux CPU fixture 결과다. 구현과 해당 CPU 회귀 검증은 완료했다. 변경 후 Windows 실행·실제 GPU 출력·프레임 시간 측정 결과는 아직 없다. 정본 JSON은 원본 hash, 표본 선택, 노드별 수치, 재현 가능한 분석 스크립트 원문을 포함한다. 기존 WorkerBalance 분석과 그 검증 기록은 앞선 변경의 근거로 보존한다.

§2

2. 원본을 분해한 방법

분석 입력은 baseline summary, ETW timeline metadata, RenderThread 원본이다. 세 파일 모두 manifest의 byte 수·SHA256과 다시 일치했다.

ETW scopes는 [beginMs, durationMs, markerIndex, depth, flags, view, submission] 형식이다. duration이 양수이고 flags & 3 == 0이며 ON 구간에 완전히 포함되는 Declare만 선택했다. measurements의 렌더 구간에 포함되는지 확인하여 뷰를 대응시켰다. Scene/Game 실행 순서는 사용하지 않는다. 시간 출력의 0.0001 ms 반올림을 고려해 부모·자식 포함 관계에만 0.0002 ms 허용 오차를 사용했으며, ON 구간 선택에는 이 허용 오차를 사용하지 않았다.

각 Declare 안에는 RenderDeclare.<node>라는 실제 이름별 scope가 있다. 노드 순번으로 이름을 추측하지 않았다. 다음 조건을 678개 전체에서 확인했고 오류는 0개였다.

  • Declare마다 대응하는 렌더 측정 구간이 정확히 하나다.
  • named node가 37개이고, 각 노드에 RenderGraphDeclareNodeBody가 하나씩 있다.
  • 노드 본문끼리 겹치지 않는다.
  • 분석한 그래프 API와 SharedBuild scope가 노드 본문에 포함된다.
  • 그래프 API 구간 합집합과 SharedBuild 구간 합집합은 서로 겹치지 않는다.

그래프 API 합집합에는 ImportBuffer, ImportTexture, CreateTexture, CreateBuffer, AdvanceVersion, InitializePass, AddPass, AddRepeatedPass, AddSplitPass marker를 포함한다. InitializePass는 AddPass 등에, AddPass는 AddRepeatedPass에 중첩될 수 있어 개별 duration을 그대로 더하지 않고 시간 구간의 합집합을 계산했다. SharedBindings는 이미 SharedBuild 안에 있으므로 다시 더하지 않는다.

p50은 median이고, p95는 정렬된 실제 표본의 min(n-1, floor(n*0.95)) 값이다. 먼저 각 Declare 또는 노드 안의 구간을 계산한 뒤 표본 전체를 집계했다. 서로 다른 marker의 p95를 더하지 않는다. baseline의 전체 raw frame을 새로 내려받아 분해한 것은 아니며, baseline은 전체 summary 집계, ETW는 ON 구간 원본 분해로 명확히 구분한다.

기존 packet build의 공용 워커 scope 합은 107.690300 ms / 794 = 0.135630 ms/Declare다. owner가 실행한 packet build까지 포함하면 0.139236 ms/Declare다. PacketDispatch는 평균 2.5회로 합계 0.069031 ms/Declare, PacketJoin은 1회 0.065351 ms다. 이 값들 역시 중첩·동시성이 있어 하나의 절감 가능 시간으로 더하지 않는다.

실제 호출 구조는 EnhancedLivePipelineDesc::DeclareAll이다. owner가 NextDeclarationPacket()을 호출한 다음 각 node.declare 본문을 순서대로 실행하고, 마지막에 packet을 합류·병합한다. 따라서 metadata packet 병렬화를 노드 본문 전체의 병렬 실행으로 설명하면 안 된다.

4. ETW ON: 같은 표본에서의 실제 비용 분할

ETW를 사용한 구간의 Declare는 평균 5.096890 ms, p50 4.896900 ms, p95 6.530400 ms다. Scene 339개의 평균은 5.211236 ms, Game 339개는 4.982545 ms다. baseline 4.405760 ms와의 차이를 코드 성능 회귀로 해석하지 않는다. 서로 다른 계측 모드·표본이다.

5. 코드까지 연결되는 큰 본문 경로

5.1 이전 HZB import: 첫 MeshletDeclare보다 앞선 비용

METEOR.Scene.Cull.First는 shared first-stage 선언을 통해 camera와 최대 세 shadow view의 history pyramid를 먼저 import한다. 경로는 SceneHost::DeclareSharedFirst → Frame::DeclareFirstStageBatch → Pyramid::ImportHistory다.

Scene.Cull.First 내부 구간평균 msp95 ms
NodeBody 시작 → 첫 MeshletDeclare 시작0.2963680.449200
그 안의 ImportTexture 합집합0.0933670.126600
그 구간의 나머지 비용0.2030000.314400
첫 MeshletDeclare 자체0.3564750.525200

678개 모든 표본에서 첫 MeshletDeclare 이전에 정확히 44번의 ImportTexture가 있다. 위쪽 첫 행은 아래 두 행의 합으로 분해되지만, 첫 행과 아래 두 행을 모두 더하면 안 된다. 첫 MeshletDeclare에는 SharedBuild와 그 이후 graph metadata 작업이 포함된다.

고정 기준 코드의 ImportHistory는 mip마다 m_history->name + ".PreviousHZB"를 만들어 넘기고, recording-local Pyramid::m_levels vector에 push한다. ReadHistory가 새 Pyramid를 만들기 때문에 이 vector의 이전 recording 용량을 재사용하지 않는다. RequireImportedFinalState는 별도 marker 없이 graph의 retained final-state 목록에 추가한다. 이 코드들이 0.203000 ms 잔여 구간에 있다는 것은 확인되지만, 각각의 비용이나 allocation 횟수를 원본에서 따로 측정한 것은 아니다.

이번 HZB 변경 대상은 최대 16개 level handle의 고정 저장소와 previous-HZB 이름 재사용이다. depth/view/recording/descriptor/graph epoch 검증, history의 읽기 전용 계약, import된 final state는 유지해야 한다. ShadowFinalCull.HzbDeclare, Shadow.History 및 camera history도 같은 pyramid 선언 코드를 사용하므로 회귀 검증은 history import와 current-depth 선언을 함께 포함해야 한다.

5.2 SSGI: 선언 중 지역 vector와 capture 복사

고정 기준 EnhancedSSGIPass::Declare는 mip마다 두 usage를 채우는 지역 vector를 만들고, Trace·Resolve·Filter·Composite·StoreHistory에서도 별도 usage/SRV 목록을 만든다. 공통 declareStage는 지역 constantCopy vector를 생성한 뒤 SRV 목록과 함께 callback에 값으로 복사한다. 주요 위치는 532, 601, 705–718, 815–861, 873–886, 901–934, 958–977행이다.

ETW의 SSGI node 평균 0.398252 ms 중 NodeBody는 0.395047 ms다. API 합집합은 0.101148 ms이고 그 밖의 본문은 0.293899 ms다. 매 노드의 호출 수는 AddPass 13, InitializePass 13, AdvanceVersion 14, CreateTexture 12, ImportTexture 4다. 이 역시 0.293899 ms 전체가 vector 생성 비용이라는 증거는 아니다. 다만 크기가 제한된 입력에서 불필요한 동적 저장·복사 경로가 본문에 직접 남아 있어 좁은 변경과 byte/metadata parity 검증으로 접근할 수 있다.

새 저장 방식은 SRV 순서와 누락된 normal/motion/material 입력의 fallback을 보존해야 한다. callback은 Declare 이후에 실행되므로 지역 배열을 가리키는 span만 capture하면 안 된다. 상수와 handle은 callback 자체가 소유하거나, 제출 완료까지 살아 있는 명확한 소유자의 저장소에 있어야 한다.

같은 함수의 UploadConstants, CreateBindings, Dispatch 중 execute lambda 안의 호출은 기록·실행 단계다. 이를 Declare 개선의 측정 근거에 더하지 않는다. callback 안에 있는 임시 source vector도 선언 시간 분석에서는 별개로 구분한다.

5.3 여러 노드에 공통인 graph 저장 비용

Graph API는 pass usage, resource version, 이름 및 선언 packet metadata를 만든다. baseline만 보더라도 AdvanceVersion은 Declare당 302회, InitializePass는 142.5회다. 따라서 고정된 노드 한 개만 worker로 옮기기 전에 공통 저장 방식의 반복 비용을 줄일 이유가 있다.

이번 계획은 pass usage를 소유권이 분명한 immutable arena span으로 보관하고 trivial 복사를 사용하며, resource version은 retained storage와 실제 활성 범위를 분리하는 것이다. graph epoch, index/version identity, 순서, 실패 시 상태, packet 작업이 읽는 주소의 안정성과 완료 전에 저장소를 재사용하지 않는 조건이 검증 대상이다. Debug의 checked-container bookkeeping 감소 가능성은 있지만, 현재 캡처만으로 그 개선량을 확정하지 않는다.

§6

6. 분배 구조의 범위와 제외한 방법

이번 metadata packet 분배는 실제 사용 가능한 worker 수를 최대 8개까지 반영하고, payload 비용을 기준으로 최대 16개 범위로 나눈 다음 큰 범위부터 작업자가 동적으로 가져간다. 한 pass의 phase 저장소는 한 작업이 소유한다. 필요한 이름·descriptor·phase 변경이 없는 warm 묶음은 건너뛰고, 작은 작업은 arena batch를 만들지 않고 직접 처리한다. 최종 merge의 선언 순서와 callback/resource 수명은 유지한다.

admission은 합계 8,388,608 비용점수 이상, worker당 최소 524,288점수로 제한한다. 이름 또는 descriptor 변경에는 고정 64와 문자열 byte 수를, repeated phase에는 64와 이름·usage byte 수를 더하는 추정치다. 따라서 이 수치를 실제 memcpy byte, allocation byte 또는 측정 대역폭으로 부르지 않는다. 작은 packet을 실제 scheduler에 제출했을 때의 비용을 고려한 보수적 기준이며, 최종 CPU fixture 결과와 Windows 성능 수용은 구분한다.

이것은 모든 node.declare를 동시에 호출한다는 뜻이 아니다. 현재 node callback은 동일한 graph의 resource/pass/version 목록을 변경하고, 같은 frame/stage의 handle을 게시하며, 앞 노드가 만든 version을 다음 노드가 검사한다. 단순한 병렬 for는 이 계약을 보존하지 않는다. 독립적인 owned payload 준비를 병렬화하고 graph에 대한 게시 경계를 유지하는 편이 현재 구조에 맞는다.

작은 SharedBuild를 별도 job으로 옮기는 방식도 이번 계획에서 제외한다. 10월 19일의 별도 CPU 실험에서는 64-bin visibility 작업의 직접 실행 약 4.2 µs가 실제 scheduler를 경유하면 1/4/8-worker에서 약 41.5/46.2/48.6 µs로 늘었다. 이것은 당시 portable fixture 결과이며 이번 캡처의 0.180656 ms에 그대로 적용할 수 있는 예측식은 아니다. 실제 scheduler 비용과 입력 크기별 교차점을 확인하지 않고 작은 leaf를 더 잘게 제출하지 않는 근거로만 사용한다.

GpuVisibility.PrepareInternal, draw/material bindings 준비, HZB texture 준비 중 ScenePrepare에서 수행하는 작업은 이번 Declare 시간에 포함시키지 않는다. 이번 후속에서 ScenePrepare나 Execute의 비용을 Declare에서 제거한 것으로 보고하지 않는다.

SSGI CPU 회귀·할당 관측

verify-ssgi-declaration-cpu.py는 고정 2e08a19와 변경본의 실제 SSGI class·parameter·Declare·ResetHistory 본문 및 graph 소유권 template을 추출한다. 실제 RenderArena를 컴파일하고 graph/RHI 경계는 선언·업로드·binding·command를 기록하는 fixture로 대체한다. 정상과 fail-fast ASan+UBSan에서 각각 812개 시나리오 / 565,658 checks를 통과했다. 세 graph mode, 256개 optional-input 조합, mip 1–8, temporal/history, arena 성장, upload/binding 실패를 포함한다. LeakSanitizer는 비활성화했으며 이를 누수 검사 통과로 표시하지 않는다.

별도 warmed allocation 조건은 1186×514, mip 8, 모든 optional 입력, 16회 warmup 후 17회 표본이다. 모든 표본에서 Declare의 heap 요청이 76→5회, 93.42% 감소했고, 지연 callback의 임시 staging 요청은 11→0회였다. operator new/new[]와 실제 arena의 mi_malloc/mi_malloc_aligned malloc-shim 호출을 함께 센다. graph/trace 저장소와 arena는 warm 재사용한다. Configure/Reset을 포함한 전체 프레임 allocation, 실제 driver allocation, Windows 실행 시간 또는 GPU 시간의 결과가 아니다. Declare의 나머지 5회까지 제거했다는 주장도 하지 않는다.

정본 JSON의 verification.executed_results에 원본 보고서 hash, 비교 기준, 추출 본문 hash, compiler/sanitizer 및 결과를 수록했다. SSGI CPP의 검증 바이트 SHA256은 f2ab5f2db18863047acc7641169a305e3be7c5e818d2eba801d32be72e5be350이다. 최종 보고서 10개에 기록된 입력 hash 비교 102개가 현재 소스와 모두 일치했다. 이는 중복 입력을 포함하는 비교 수이며, 서로 다른 파일 102개를 뜻하지 않는다.

HZB CPU 회귀·할당 관측

verify-hzb-declaration-cpu.py는 고정 2e08a19와 변경본의 실제 class/layout 및 ReadHistory, ImportHistory, Declare, AddReadUsages, BindingInputs, Bindings, view/epoch 검사를 추출한다. graph/RHI 서비스, pipeline 초기화와 GPU retirement가 fixture 경계다. 일반 및 ASan+UBSan에서 각각 232 parity 시나리오 / 63,595 checks를 통과했다. 빈 history, 16단계 초과 또는 reader 생성 후 크기가 바뀐 history는 새로 명시적으로 거부하는 입력으로 따로 확인한다. 실제 native graph나 GPU shader를 실행한 검사는 아니다.

16 levels, 16회 warmup 후 17회 표본에서 ReadHistory의 heap 요청은 3→3회, ImportHistory는 21→0회, 두 구간의 합은 24→3회였다. 실제 추출 본문의 new/new[]/aligned new를 세며 graph trace 저장소는 미리 준비한다. 이전 HZB 이름을 reader에서 한 번 소유하는 준비 비용은 남아 있다. 이 16-level fixture를 실제 캡처의 네 pyramid·44 mip에서 관측한 allocation 수로 바꾸어 쓰지 않으며, 전체 프레임 무할당이나 GPU 시간 개선도 주장하지 않는다.

Graph 저장소 CPU 회귀·할당 관측

verify-render-graph-declaration-storage.py는 2e08a19와 변경본의 실제 선언·cache 본문, production 타입 및 실제 arena를 비교한다. CPU RHI/profiling/job 서비스와 mimalloc의 경계는 fixture/shim이며, 실제 native command recording 검사는 아니다. 일반 및 ASan+UBSan에서 각각 148,142 checks를 통과했다. 저장소 성장 후 span 주소, reset/epoch, cached declaration의 소유권, 이전 atomic flag 제거, 부분 실패 및 비자명 객체의 destructor 호출을 확인한다.

warm 상태의 128 passes × pass당 8 usages에서 lvalue 전달의 heap 요청은 기존과 변경본이 모두 0회다. rvalue 전달의 요청은 128→0회다. 이 둘을 합쳐 모든 호출 방식에서 할당을 줄였다고 쓰지 않는다. 변경본 arena의 usage payload 사용량은 24,576 bytes이며, 매번 그만큼을 새로 heap에 할당했다는 뜻은 아니다. rvalue 입력의 용량을 호출자에게 남겨 재사용하고, graph가 소유한 arena에 값을 복사하는 계약이다. 이 관측 역시 CPU fixture의 요청 수이며 Windows Debug STL 비용이나 프레임 시간의 실측 개선량은 아니다.

Packet 분배 CPU 결과와 검증 범위

verify-render-graph-packet-dispatch.py는 실제 packet 본문과 JobScheduler·ThreadPool·enkiTS를 실행한다. Resource/Pass는 metadata projection이며, 전체 RHI 구현은 아니다. worker 1/2/4/8, merge 순서·작은 작업·반복 처리·취소·실패 시 drain을 확인했다. 일반 및 ASan+UBSan의 공통 정확성 검사는 130,280 checks다. 일반 보고서의 145,772 checks에는 다음 timing 뒤의 출력 검증이 추가돼 있다. 두 보고서의 입력 hash 13개는 동일하다.

다음은 GCC 13.3 -O2의 **packet publish CPU fixture median(µs)**이며 전체 Declare나 프레임 시간이 아니다. 각 variant는 5회 warmup 후 19회 측정했고 baseline→변경본→강제 inline 순서로 실행했다. 교차·무작위 실행이 아니므로 작은 차이는 잡음의 영향을 받는다. 준비된 scene metadata는 측정 밖이고, publish의 begin/next/finish 및 join이 측정 안에 있다.

기존 ScenePrepare suite도 공유 RenderArena 변경 뒤 일반 및 ASan+UBSan에서 각각 308,808 checks를 통과했다. 이 재실행은 연동 회귀 확인이며, 보고서 안의 이전 ScenePrepare 할당 개선을 이번 후속의 새 성과로 계산하지 않는다. CPU 검증 결과 원문과 hash는 정본 JSON에 수록했다. ASan+UBSan의 LeakSanitizer는 비활성화했으므로 누수 검증 통과를 뜻하지 않는다.

Include 검사 결과는 기존 FAIL이다. 같은 checkout 범위에서 상향 27·물리 경계 69가 유지됐고 stdout SHA256 9955a04f95e53baf1f631328f9f46e4ce17f1f06046ed499caa16fa360fe5b76이 앞선 검사와 같다. 규칙·allowlist는 변경하지 않았다. 전체 HEAD의 물리 경계 70과의 차이는 기존 checkout에 없는 ThirdParty 프로젝트 한 개이며, 상세 비교는 JSON의 verification.include_boundary에 보존했다.

CPU-only fixture를 통과하더라도 실제 Windows/GPU 검증을 대체하지 않는다. 속도 비교에는 Declare 전체, 상위 named node, packet dispatch/join, allocation 및 raw bytes의 의미를 함께 확인해야 한다. 계측 marker의 개수나 경계를 바꿨다면 작은 scope 시간 감소를 순수 본문 speedup으로 단정하지 않는다. validation/readback을 켠 진단 실행과 일반 프레임 성능 캡처도 구분한다.

사용자가 지정한 cpu-performance-engineering의 측정·동시성·allocator 관점을 이어받았다. 전용 MCP는 호출 가능한 도구로 노출되지 않아 공식 README를 참고했으며, 외부 코드를 복제하지 않았다. 이번 문서는 누적 작업량과 critical path, 정적 개선 가능성과 실측 결과, 고정 저장소와 제출 완료 수명을 분리해 기록한다.
