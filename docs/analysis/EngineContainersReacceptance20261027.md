# 모듈 바이너리 전체 성능 재수용 — 2026-10-27

> 후속 결과: [작은 MPSC 탐색 힌트와 성능 재수용](MpscTailHintAcceptance20261027.html)에서 엔진 정본의 기존 기준 전체 통과와 최신 제품 검증을 확인할 수 있다. 아래 내용은 이전 실행의 진단·실패 기록이다.

실제 측정 결과: **일반 컨테이너 78/82, 고정 MPSC 주 수용 batch8 3/4·개별 전송 추가 검사 3/4, FAA 락 프리 큐 5/6, SPSC·기존 스핀 MPMC 처리량 8/8**. 전체 수용 판정은 **FAIL**다. 이 판정은 새 named module 바이너리와 이번 원시 표본에서 계산했다. 이전 헤더 바이너리의 통과 판정을 승계하지 않았다.

## 고정한 수용 기준

일반·확장 컨테이너와 고정 MPSC는 매 반복에서 custom/MSVC STL 또는 PPL 중앙값 비율 ≤1.10, 양쪽 각각 정렬 15표본 x[13]/x[1] ≤1.30이어야 한다. 일반 82개 조건은 각각 별도 프로세스에서 3회, 총 246개 프로세스로 실행했다. 고정 MPSC는 4개 조건을 3프로세스에서 실행했다. 모든 15표본을 보존했고 반복 2는 일반 조건 순서와 A/B 측정 순서를 반전했다.

FAA 확장 MPMC는 기존 최적화 보고서의 6개 조건을 5프로세스에서 PPL과 비교했다. 8B/128B 값, 생산자·소비자 1/1·4/1·4/4이며 생산자당 65,536개를 전송한다. 전송 시간과 소멸 포함 시간 비율이 각 프로세스에서 모두 ≤1.10이어야 한다. FAA의 원래 기준에는 표본 편차 한도가 없으므로 이번에도 이를 추가하거나 완화하지 않았으며, 양쪽 편차는 표에 공개한다.

## 환경과 구현 경계

Windows x64 MSVC 19.50.35730, MSVC STL 145, Release, iterator debug 0, C++23이다. 실제 구현은 Creator.Containers 모듈의 26개 파티션에서 가져온다. 기존 정확성/비교 소스의 ce 구현 include를 제거하고 import를 삽입해 같은 작업을 실행했다. 측정용 STL/PPL 사용은 비교 실행 파일에만 있다. FAA 비교 소비자는 기존과 같은 /Ob3을 사용한다.

일반 및 고정 MPSC는 이전 최종 수용과 같은 측정 스레드 CPU4/above-normal, 자체 SMT pause helper CPU5 조건이다. 자체 helper는 절대 시간을 늘리는 비교 환경 제어이며 라이브러리 최적화가 아니다. 다른 앱이나 OS 설정은 바꾸지 않았다. 일반 항목은 각 구현 100ms 목표로 독립 보정하고 각각 고정 1초 워밍업 후 15표본을 수집했다. 고정 MPSC는 OS yield 대기와 개별 전송 표본을 사용하며 생산자는 다른 물리 코어에 배치한다.

FAA/PPL 5프로세스는 기존 queue_acceptance 프로토콜 그대로 SMT helper 종료 후 실행했다. 해당 프로토콜은 affinity 고정 없이 A/B 순서를 표본마다 번갈아 사용한다. 일반 단일 스레드/고정 MPSC와 다른 측정 조건임을 구분한다. 측정 중 소스와 바이너리를 수정하거나 빌드하지 않았다.

## 남은 STL 사용처와 이번 전환

추적·미추적 엔진 소스를 함께 검사한 `Build/Verification/ContainerMigration/inventory-20261027-final.json`에는 **9,407개 명시적 참조, 970개 파일**이 남았다. 문자열 8,106건, unordered_map 210건, vector 62건, bitset 3건 등이 포함된다. 파일 내 참조 수이지 객체 수가 아니다. 범위는 Engine·Editor·Lattice·Player·HeadlessHost의 추적 파일과 무시되지 않은 미추적 C++ 소스이며, 서드파티·Tools·생성 빌드 산출물·컨테이너 정본은 제외한다. 매크로 확장과 외부 API의 추론 타입은 이 집계만으로 완전히 알 수 없다.

프로파일 기록의 65,536비트 스레드 슬롯 2곳을 `ce::fixed_bitset`으로, 프로파일 집계의 구조체/정수 키 로컬 맵 2곳을 `ce::node_hash_map`으로 전환했다. 맵은 조회·삽입에만 사용하고 출력 순서는 별도 배열에서 결정한다. 두 프로파일 집계 맵의 실제 워크로드 성능은 별도로 측정하지 않았다. 잠금·큐 알고리즘, 캡처 소유권 및 외부 라이브러리 경계는 바꾸지 않았다.

동적 비트셋의 64비트 블록과 RHI 8비트 집합, 렌더 버퍼 풀의 가변 크기 집합은 미수용 또는 근거 부족으로 STL을 유지했다. 엔진 내부 모듈을 새 Release 소비자에 연결해 세 프로세스에서 각 15표본을 수집한 추가 미시 실험은 다음과 같다. 100ms 배치·측별 1초 워밍업과 CPU4/CPU5 SMT 보조자를 사용했다. 이는 실제 프레임 시간 측정이 아니다.

| 시나리오 | 자체/STL 중앙값 비율 3회 | 적용 판단 |
|---|---|---|
| 64비트 생성 및 `count` | 2.541 / 2.586 / 2.557 | 기준 초과, 동적 비트셋 블록 전환 보류 |
| 8비트 `test`·`set` | 1.150 / 1.131 / 1.153 | 기준 초과, RHI 전환 보류 |
| 65,536비트 초기화·설정·조회 | 1.039 / 1.074 / 1.062 | 세 반복 1.10 이내, 프로파일 기록 2곳 유지 |

8비트 경로는 중복 인덱스를 포함하는 합성 시험이며 실제 RHI 프레임 전체 시간을 뜻하지 않는다. 렌더 버퍼 풀은 다양한 컴파일 타임 크기를 사용하므로 단일 크기 실험만으로 수용하지 않았다. 8비트 시험을 바꾼 별도 소비자 바이너리의 65,536비트 비율은 0.671 / 0.675 / 0.674였다. STL 절대 시간이 바이너리 사이에서 달라졌으므로 이 수치는 해당 PC·시험 조건으로 제한한다. 원시 표본과 각 시험 바이너리·소스 해시는 `CreatorContainers/results/20261027-bitset-consumer*`에 보존했다.

프로파일러 회귀 시험의 기존 배열 입력 타입을 현재 소유 컨테이너에 맞춰 수정했다. 예산 검사는 새 배열의 첫 확보 용량 8개를 1개로 가정하고 있었다. 실제 증가량 320바이트는 40바이트 샘플 × 8과 일치했으며, 테스트는 독립 배열의 실제 확보 용량으로 예산을 검증하도록 수정했다. 수정 후 프로파일러 본 검사 **1,396건**과 CRC 생략 결함 주입을 통과했다. 집계 전용 검사 79건과 집계 결함 주입, 소프트웨어 RHI 39개 메서드 검사도 통과했다.

최종 `Build/container-reaccept-editor-verified-bitset.log`의 Editor Debug 빌드와 `Build/Verification/ContainerMigration/ReacceptVerifiedDebug1/acceptance.json`의 실제 실행이 통과했다. 17개 명령, 두 차례 8,192개 정확히 한 번 전달, UTF-16 프로브, 렌더링 준비와 Play/Stop 후 씬 복원을 확인했다.

## 증거와 재현

독립 라이브러리 results/20261027-engine-full-reaccept1-verdict.json이 판정 정본이며, 20261027-engine-full-reaccept1-before.json과 20261027-engine-full-reaccept1-environment.json에 소스·스크립트·바이너리 SHA256을 보존한다. 종료 후 입력 124개의 해시를 다시 확인해 `20261027-engine-full-reaccept1-snapshot`에 복사했다. guard JSON과 246개 case 파일의 시간 범위를 대조하고 원시 표본에서 요약 비율과 편차를 다시 계산했다. 전체 표본 파일의 해시도 판정 JSON에 기록한다.

총 324개 조건/프로세스 결과다. 일반 246·고정 MPSC 개별 12·FAA 30개 결과는 각각 15표본, SPSC·스핀 MPMC 24개 결과는 기존 방식의 9표본으로 총 4,536쌍이다. 주 수용 MPSC 12개 결과의 180개 묶음 표본(하위 전송 1,440쌍)도 추가 보존했다. 워밍업은 이 수에 포함하지 않는다. 컴파일러 및 실제 비교한 STL/PPL 설치 파일 해시도 reference-files JSON에 남겼다.

재현은 새 Tag와 별도 GuardTag로 experiments/20261026-small-array/with-guard.ps1 안에서 run-module-acceptance.ps1을 실행한다. guard 태그는 측정 태그와 다른 접두사를 사용한다. 이어 module_queue_acceptance.exe를 guard 없이 5회 실행해 <Tag>-ppl-1.csv…5.csv, module_concurrent_tests.exe를 3회 실행해 <Tag>-concurrent-1.csv…3.csv로 보존한다. 별도 run-module-mpsc-primary.ps1 -Tag <Tag>로 주 수용 batch8을 수집하고 verify-module-acceptance.ps1 -Tag <Tag> -GuardTag <GuardTag>로 검증한다. 수집 전에 reference-files JSON과 module-concurrent-before JSON에 비교 설치 파일 및 concurrent 실행 파일 해시를 기록한다. 빌드는 수집 전에 modules/validate-msvc.ps1을 실행한 뒤 module_library_benchmark·module_mpsc_benchmark·module_queue_acceptance 타깃을 Release로 빌드한다.

모듈 정확성·ASan·Linux 실행 검증은 [모듈 구현 보고서](ContainerModules20261026.md), 이전 헤더 수용은 [이전 수용 보고서](SmallArrayVarianceAcceptance20261026.md)를 참조한다. 다른 OS의 성능 동등성이나 실제 엔진 프레임 수용을 입증한 결과는 아니다. 이번 성능 시험은 엔진 정본으로 만든 외부 모듈 소비자 바이너리의 결과이며, 엔진 프레임 성능과는 별개다.
