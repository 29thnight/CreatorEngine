# UTF-8 2KB 추가 성능 최적화와 재수용

> 후속 전체 82조건·PPL 재수용은 **미통과**다. 이 문서의 57/57 문자열 전용 결과와 다른 범위다. [후속 재수용 결과](EngineContainersReacceptance20261027.html).

동일한 모듈 바이너리 시험에서 **57/57을 통과했다.** 기존 UTF-8 2KB 추가의 미달 두 건을 해소했고, UTF-16·UTF-8 생성/추가·변환·캐시·입력 확정 전체 19항목을 3개 독립 프로세스로 다시 검사했다. 시간 비율 1.10 이하와 양쪽 편차 1.30 이하 조건을 유지했다.

MSVC 모듈 **16/16**, ASAN **16/16**, Linux TSan **13개 실행**과 헤더 방식 검증을 통과했다. 새 모듈을 포함한 네이티브 **Editor Debug 빌드와 실제 실행도 통과했다.**

## 최종 성능

`20261027-utf8-partition-accept5`는 단일 소유 버퍼를 재사용하는 원래 시험이다. 여러 주소의 평균이나 좋은 실행만 골라 수용하지 않았다. 각 측정 측의 1초 준비 실행, 100ms 배치 15개, 측별 연속 수집, 편차는 정렬한 표본의 14번째/2번째 비율, 두 번째 프로세스의 측 순서 반전, CPU4 고정·AboveNormal 우선순위·임시 CPU5 SMT 보조 프로세스를 그대로 유지했다. 측정 중 컴파일하지 않았다.

| 2KB 추가 실행 | 엔진 ns | MSVC STL ns | 엔진/STL | 엔진 편차 | STL 편차 |
|---|---:|---:|---:|---:|---:|
| 1 | 22.906 | 21.683 | 1.0564 | 1.0029 | 1.0067 |
| 2 | 22.049 | 22.706 | 0.9711 | 1.0037 | 1.0059 |
| 3 | 22.990 | 21.429 | 1.0728 | 1.0042 | 1.0044 |

전체 57조건의 최대 시간 비율은 **1.085942**, 최대 편차는 엔진 **1.054802**, STL **1.038264**다. UTF-8 2KB 생성 비율도 세 실행에서 **1.0157 / 1.0007 / 0.9891**로 통과했다. 기준이 허용하는 동급 성능이며 모든 실행에서 항상 더 빠르다는 뜻은 아니다.

측정 환경은 Intel Core i7-8700K, Windows x64, MSVC 19.50.35730, Release 모듈 소비자다. 전역 `/arch:AVX2`는 추가하지 않았다. 수집 전후 구현·시험·바이너리 등 **69개 입력 해시**가 일치했다. 원래 `tests/unicode_benchmark.cpp`의 SHA256은 `7D724524928F576F1F1F85EBACFC34DED03CAAB5DBF75858FF710EE2503C7E3D`로 이전 55/57 측정과 동일하다.

## 원인 분리 계측

복사·객체 길이 갱신·할당 정렬·주소 배치·코드 생성 영향을 각각 진단했다. 아래 수치는 진단 실행의 중앙값으로, 최종 수용 판정과 구분한다.

- 같은 주소에서 `memcpy`와 `memmove`는 약 0.97~1.00배였다. 함수 이름을 바꾸는 것으로 병목을 해소하지 못했다. `REP MOVSB`, 256바이트 역방향 블록 분할, 32바이트 머리 복사도 비교했지만 느려 채택하지 않았다.
- 객체 길이를 복사 전/후에 갱신하는 실험은 순서 변경이 개선을 만들지 않았다. 길이 저장만 원인으로 보지 않았다.
- 서로 다른 가상 메모리 영역에서 원본의 페이지 내 위치를 고정하고 목적 주소의 차이를 바꾸면 CRT 2KB 복사 비용이 약 **19.9~35.0ns**로 달라졌다. 정렬과 페이지 내 오프셋 차이가 함께 영향을 준다. CPU 성능 카운터로 특정 stall을 입증한 것은 아니므로 단일한 4KB alias 원인으로 단정하지 않는다.
- 할당 정렬만 32바이트로 바꾼 시제품은 2KB 생성 약 80.42/81.22ns였지만, 한 버퍼 추가는 41.77/22.79ns로 악화됐다. 이 할당자·저장소 변경은 적용하지 않았다.

주소를 통제한 정렬 저장 커널 비교:

| 목적 32바이트 위상 | 페이지 내 주소 차이 | 커널 ns | CRT ns |
|---|---:|---:|---:|
| 0 | 0 | 16.58 | 19.77 |
| 0 | 48 | 18.20 | 27.46 |
| 0 | 240 | 18.24 | 35.01 |
| 16 | 48 | 18.09 | 30.54 |
| 16 | 240 | 18.04 | 32.86 |
| 0 | 4048 | 29.08 | 20.73 |

커널도 불리한 주소 조합에서는 느렸다. 따라서 마지막 행 같은 조합을 전용 경로에서 제외하고 CRT를 사용한다. 이 진단의 여러 주소 결과를 원래 단일 버퍼 수용 시험 대신 쓰지 않았다.

## 적용한 구현

정본은 `Engine/Containers/modules/string.ixx`와 새 `utf8_copy.ixx` 파티션이다. 헤더는 이 정본에서 생성한다. 외부 테스트 솔루션과 네이티브 `EngineContracts`가 모두 내부 구현을 빌드한다.

- `append`의 용량 내 2KB 복사와 2KB 생성에서 별도 모듈의 복사 디스패처를 호출한다. 목적 16바이트 정렬, 서로 겹치지 않는 두 범위, `(destination - source) mod 4096 < 256`, 런타임 AVX2 지원 조건을 모두 만족할 때만 전용 커널을 사용한다.
- 본문의 목적 주소를 32바이트 경계에 맞추며 원본 2048바이트 밖은 읽지 않는다. 목적 32바이트 위상 16은 16바이트 머리/꼬리와 정렬된 본문으로 처리한다. 다른 크기·정렬·중첩·미지원 CPU는 CRT `memmove` 경로다.
- MSVC의 읽기 전용 ISA 지원 검사 또는 GNU 계열 x64의 CPU 지원 검사를 사용한다. 지원하지 않는 플랫폼은 벡터 경로를 사용하지 않는다. 자체 정적 초기화 락·할당·대기·잠금은 추가하지 않았다.
- 1~64바이트 추가는 원본의 머리·꼬리를 지역 값에 먼저 읽고 기록한다. 서로 겹치는 뷰도 원래 값으로 복사하며 범위 밖을 읽지 않는다. 짧은 복사의 CRT 호출 비용을 줄였다.
- 용량·SSO·할당자·소유권·예외 계약과 큐 알고리즘은 바꾸지 않았다. 확보 용량 내 추가는 할당하지 않는다. 동시성 큐의 진행 보장에 변경은 없다.

## 퇴행 확인과 재시도 기록

처음에는 SIMD 구현을 문자열 파티션에 함께 두었고 **45/57**로 변환·캐시 퇴행을 만들었다. 별도 파티션으로 분리한 실행은 **54/57**, 호출 단계를 줄이고 생성에도 적용한 실행은 **53/57**이었다. 최종 수정 전의 실패 결과를 보존했다.

인라인 지정만 추가한 시도는 소비자 디스어셈블리 해시가 같았고 짧은 추가도 느려 채택하지 않았다. 다음 시도의 1~7바이트 복사는 5바이트를 개선했지만 64바이트 퇴행이 남았다. 이 두 실행은 완성된 실패 샘플을 확인한 뒤 중단했고 `*-aborted.json`에 사유를 기록했다. 모든 수집 샘플을 남겼으며 완료된 57조건 실행으로 세지 않았다. 최종본은 1~64바이트 스냅샷 복사까지 적용해 3회 전체 실행을 완료했다.

분리와 경로 수정이 측정된 퇴행을 없앴다는 것은 확인했다. 명령어 캐시나 분기 예측 중 어느 하드웨어 요인이 얼마를 차지했는지는 카운터를 측정하지 않았으므로 확정하지 않는다.

## 기능 검증과 범위

새 복사 검사는 32개 원본 정렬 위상과 두 목적 위상·주소 차이 조합 **576건**, 런타임 벡터 경로와 강제 폴백, 실제 중첩, 사용자 지정 8바이트 정렬, 자체 추가 중 확장, 보호 페이지 **64건**, 용량 내 10,000회 추가의 할당 0회를 확인한다. 1~64바이트 추가의 중첩·보호 페이지 검사는 **148,288건**이다.

최종 수정본의 검증 결과:

- `20261027-utf8-final-normal`: MSVC 모듈 16/16.
- `20261027-utf8-final-asan`: ASAN 16/16.
- `20261027-utf8-final-linux`: 26개 파티션과 주 모듈, TSan 13개 실행.
- `utf8-final-headers-build.log`: 모든 공개 헤더 독립 컴파일과 Windows SDK 헤더 조합.
- `utf8-final-header-functional.log`: 헤더 방식의 같은 복사 기능 검사와 두 소스 파일 링크.
- `Build/utf8-copy-editor-debug.log`: 새 파티션을 포함한 네이티브 Editor Debug 빌드 성공.
- `Build/Verification/ContainerMigration/Utf8CopyDebug1/acceptance.json`: 17명령, 두 프로브 각 8,192개 전송, `utf16Strings=true`, GPU 렌더링 준비, Play/Stop 후 씬 복원, 정상 종료. 사용자 워크스페이스와 분리한 디렉터리에서 실행했다.

 실제 한글 IME 조합/확정은 앞선 `20261027-unicode-ime-locked` 증거를 유지한다. 이번 변경은 복사 경로이며 IME 메시지 처리·입력 확정 계약을 바꾸지 않았다. 다른 OS의 성능, 전체 82항목/PPL 재수용, 엔진의 모든 STL 문자열 사용처 전환 완료를 뜻하지 않는다.

## 증거 파일

외부 `CreatorContainers/results`:

- `20261027-utf8-partition-accept5-verdict.json`, `*-inputs.json`, `*-snapshot`, `*-1.csv`~`*-3.csv`, 측정 환경·SMT 보조 프로세스 기록.
- `20261027-utf8-diagnostics-summary.json`와 `20261027-utf8-copy-paths1`, `utf8-store-order1`, `utf8-peel1`, `utf8-alias-matrix1`, `utf8-alignment1`, `utf8-aligned-kernel1`의 CSV·실행 환경 기록.
- `20261027-utf8-copy-accept1`, `utf8-partition-accept1`, `utf8-partition-accept2` 실패 판정과 입력 스냅샷. `utf8-partition-accept3`·`accept4` 중단 사유와 원시 샘플.
- `20261027-utf8-final-kernel.disasm.txt`, `20261027-utf8-final-consumer.disasm.txt`: 최종 코드 생성 증거. ISA 지원 분기가 AVX 명령보다 앞에 있음을 확인했다.
- `20261027-utf8-partition-before-small.disasm.txt`, `20261027-utf8-partition-inline.disasm.txt`: 인라인 지정만으로 코드가 달라지지 않았던 비교 증거.
