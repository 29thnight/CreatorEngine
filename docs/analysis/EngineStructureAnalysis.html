CreatorEngine의 실행 구조와 소유 경계

기준: master 493536e300e274cbf59989cdd62b20310c8ae64f의 소스 정적 조사. 이번 재작성에서 빌드·실행·성능 측정은 하지 않았다.

제품을 조립하는 지점모듈별 책임조립과 데이터 의존프레임의 실제 렌더 연결simulation과 물리의 순서현재 관리 스크립트 경로문서와 reflection 경계작업·메모리·진단Editor의 저작과 명령Player와 표시 소유자빌드와 배포수명 문제를 판단하는 기준다음 검토의 기준

제품을 조립하는 지점

CreatorEngine은 Windows x64의 native engine과 CoreCLR 게임 스크립트, 독립 BuildTool을 결합한다. 현재 구조는 옛 D3D11·root ScriptBinder 중심 개요와 다르다. 먼저 Editor/EngineEntry/App.cpp와 Player/PlayerMain.cpp에서 어떤 정책·경로·서비스를 조립하는지 읽어야 한다.

파일 개수나 클래스 크기는 기능 연결의 증거가 아니다. 이 문서는 entrypoint, 프로젝트 참조와 실제 소비 계약을 기준으로 설명한다.

모듈별 책임

SceneRuntime은 scene·entity·component·script lifecycle·audio를 소유한다. RenderEngine은 자산 runtime과 material/geometry·RHI·render graph를 제공한다. Physics, Utility_Framework, GCCE가 공통 실행과 수명을 지원한다. Editor는 저작/UI와 그 adapter를 가지며 Player는 packaged content와 native presentation을 조립한다.

Player.vcxproj는 Editor를 직접 참조하지 않는다. 단, 실제 transitive DLL closure는 별도 실행 inventory로 확인해야 한다.

조립과 데이터 의존

host가 EngineLaunchConfig를 만들면 EngineBootstrap이 초기화 순서를 적용한다. config의 callback은 host settings와 runtime content 준비를 주입한다. compatibilityRunMode는 아직 SceneManager/TagManager의 legacy 소비 때문에 남아 있다. 따라서 모든 host 구분이 완전히 제거됐다고 말할 수 없다.

RenderEngine에서 저작 기능이 필요할 때 AssetAuthoringPort 경계를 사용한다. gameplay state는 GT가 sealed frame/proxy 입력으로 만들어 renderer에 전달한다. 포인터를 공유한다는 사실만으로 다른 thread에서 live Scene 접근이 허용되지 않는다.

프레임의 실제 렌더 연결

EnhancedSceneRenderer의 BuildPipelineDesc는 METEOR Geometry → Cull.First → Occluder → Cull.Final → Surface를 연결하고 Shadow가 Geometry를 독립 소비하도록 한다. versioned graph는 producer와 consumer의 resource version을 추적한다. SceneHost는 meshIndirect와 cooked meshlet 입력을 요구하며 일반 helper의 nullable fallback을 제품 CPU/direct fallback으로 확대할 수 없다.

GT가 packet을 만들고 RT가 소비한다. in-flight 입력 하나와 교체 가능한 pending 하나, GPU credit 뒤 최신 선택이 CPU publication 경계다. GPU queue나 화면 지연의 절대 상한과는 다르다.

simulation과 물리의 순서

RuntimeFrame은 Initialization/InputEvents, pause 처리, managed pre-physics, Physics/GameLogic과 post-physics flush를 조정한다. 구조 변경이 예정된 때에는 managed 진입을 억제하는 조건이 있다. 물리 callback의 개수와 관리 경계를 넘는 호출 수를 같은 것으로 계산하지 않는다.

simulation 완료, render recording 완료와 GPU fence 완료는 각각 다른 시계다. 구조 변경과 native collection은 owner의 안전 경계에서 수행한다.

현재 관리 스크립트 경로

Engine/SceneRuntime/ClrHost는 CoreCLR를 초기화하고 ScriptCore entrypoint를 바인딩한다. TickPrePhysics/TickPostPhysics와 등록·이벤트 flush는 GT에서 호출한다. source에 Mono 비활성 코드가 있었다는 옛 설명으로 현재 .NET10 경로를 설명할 수 없다.

BuildTool은 배포본의 Roslyn·reference assembly·ScriptCore로 GameScripts를 컴파일하고 정확한 engine identity를 검증한다. 스크립트 없는 Editor 기동 허용과 packaged game의 lifecycle verification은 다른 정책이다.

문서와 reflection 경계

Authoring::Document는 long-lived 문서를 소유하고 ParsedDocument는 한 parse의 tree를 소유한다. ReadNode는 빌린 view다. reflection serializer는 typed 값 변환을 담당하며 scene 객체 소유권을 가져가지 않는다. Player의 ParseCooked는 CEDO strict 경계로 legacy YAML fallback을 하지 않는다.

Core.Minimal이 Reflection.hpp를 자동 include하지 않으므로 사용처는 의존성을 명시한다. 모든 직렬화를 raw struct 복사로 통일하는 설계는 없다.

작업·메모리·진단

engine-owned job_scheduler는 persistent worker와 명시적 start/shutdown을 갖는다. dependency continuation은 owner-thread mutation 권한을 부여하지 않는다. worker에서 미완료 작업 blocking wait를 사용할 수 없다.

Scene/Entity/Component는 GCCE의 domain·root_ref·trace_ref·weak_ref를 사용한다. native owning handle, AssetRequest의 consumer lifetime, GPU completion lease는 별도 계약이다. Profiler와 memory snapshot은 이 층을 관찰하지만 모든 heap을 합산한 완전한 census는 아니다.

Editor의 저작과 명령

Editor command 등록은 실제 domain registrar와 direct 등록, descriptor seed의 교집합으로 읽는다. commandlet과 일반 서비스 registry, Player whitelist는 서로 다르다. GUI와 명령이 공통 operation에 위임하더라도 Undo/selection/dirty 의미는 실행으로 따로 검증해야 한다.

ProfilerViewer는 독립 child process이며 소유 Job·인증 IPC·bounded shutdown을 사용한다. 창의 존재만으로 수집이 진행 중이거나 현재 frame을 표시한다는 뜻은 아니다.

Player와 표시 소유자

Player 프로젝트는 Player.runtime.dll을 만들고 launcher가 이를 로드한다. Player presentation이 acquire·composition·pacing·resize·Present를 소유한다. DX12 shared resource와 Vulkan CPU readback/upload bridge는 서로 다른 capability다.

GetSubmittedGameFrames는 composition 제출 뒤 성공한 native Present 수이며 scanout 측정이 아니다. consumer lease는 마지막 GPU 사용까지 유지하고 완료를 증명하지 못한 slot은 재사용하지 않는다.

빌드와 배포

native 프로젝트는 x64·v145·C++23과 Windows SDK를 선언한다. BuildTool은 .NET10 win-x64 apphost다. publish-engine이 immutable 배포 identity와 payload manifest를 만들고 프로젝트는 설정별 pin으로 선택한다.

package-game은 candidate를 만들고 managed compile·cook/prebuilt·PAK·Player 검증 후 current를 갱신한다. skip-verify는 게시하지 않는다. 정식 project descriptor/Launcher/installer는 별도 미구현 의도이며 open-project는 development-project adapter다.

수명 문제를 판단하는 기준

옛 D3D11 leak 목록이나 raw pointer cache 관찰을 현재 코드의 결함 목록으로 재사용하지 않는다. 현재 조사에서는 exact generation의 backing, CPU live/retained/inflight, GPU retired/completed, cross-device consumer lease를 각각 추적한다.

RHI retirement는 논리 cache 제거와 실제 native 해제를 분리한다. completion 0은 quarantine이며 일반 collection으로 풀리지 않는다. 이러한 방어 코드의 존재는 모든 resize·device-loss 경로의 무결성 증명이 아니다.

다음 검토의 기준

기능을 확인할 때 선언 → host 등록 → 실제 consumer → 오류·취소 → shutdown 순으로 추적한다. 실행되지 않는 helper와 probe는 제품 지원으로 세지 않는다. 빌드·장치 품질·성능·패키지 clean-machine 검증은 서로 별도의 증거다.

상세 계약은 레이어 분리, 동기화, 소유권, 빌드 파이프라인에서 이어진다.
