# 모델 원본 재질 전환 및 시작 셰이더 준비 — 2026-10-21

## 결과

Debug x64를 재빌드하고 CreatorRobot과 Aria 각각 빈 엔진 셰이더·재질 캐시 첫 실행과 같은 캐시 재실행에서 콘텐츠 브라우저 → 씬으로 실제 드래그 앤 드롭했다. 원본 재질 렌더 제출은 Aria 빈 캐시 57.126 → 24.409초, CreatorRobot 빈 캐시 36.891 → 26.109초였다. CPU 재질 적용 후 원본 제출 대기는 이번 네 실행에서 0.866–1.247초였다.

**과거 Aria의 17.750초 대기는 이번 동기 경로 대조에서 그대로 재현되지 않았다.** 같은 새 실행 파일에서 최적화를 끈 Aria 빈 캐시는 2.248초였다. 따라서 17.750초 전체의 원인을 확정하거나 모든 환경에서 해결했다고 주장하지 않는다. 확인한 직렬 준비 경로를 수정했고, 이번 실제 실행에서 긴 대기가 발생하지 않았다는 결과다.

## 확인한 원인과 변경

1. CPU 원본 재질 적용은 최종 GPU 준비 완료가 아니었다. indexed PSO가 준비된 후에도 원본 프로그램마다 mesh 19종과 reconstruction 16종의 준비가 남았다. 기존 SceneHost는 네이티브 mesh PSO를 동기로 만들고 프레임마다 준비를 진전시켰다. Slang 결과 캐시 적중만으로 이 구간은 없어지지 않는다.
2. DX12 mesh PSO를 기존 작업 스케줄러에 비동기 요청하도록 변경했다. 요청은 해시로 중복 제거하고 입력 바이트코드 및 root signature 수명을 보유한다. 작업자는 네이티브 PSO만 생성하고, 렌더 소유 스레드가 완료를 확인한 후 핸들을 공개한다. 필요한 reconstruction까지 모두 준비되어야 원본으로 전환하며 그 전에는 대체 재질을 유지한다. 무효화·종료는 진행 중 작업을 회수한다.
3. 공통 셰이더 46개를 일반 에디터 시작 로딩 창에서 준비한다. 실제 소비자와 동일한 옵션·permutation·검증 캐시를 사용하며, 모델 드롭을 기다리지 않는다. 빈 캐시 시작 준비는 10.938–11.150초, 재실행은 0.499–0.507초였다. 비용을 제거한 것이 아니라 시작 로딩 단계로 옮겼다. 네 모델 드롭 모두 공통 셰이더 컴파일 0회, 메모리 적중 48회였다. 46개 고유 준비 외에 실행 중 재요청이 포함된다.
4. `[material.prepare]` indexed-ready/ready 및 `[pso.mesh]` 작업 스레드·시간 로그를 추가해 CPU 적용과 네이티브 준비를 구분했다. 진단용 `CE_SYNC_MESH_PSO=1`, `CE_SKIP_MODEL_SHADER_WARMUP=1`로 같은 실행 파일의 이전 경로를 비교했다. 일반 실행 기본값은 최적화 경로다.

동기 대조에서는 네이티브 mesh 생성 65건이 모두 작업자 밖에서 실행됐고, 합계 778.893ms, 최장 32.429ms였다. 최적화 후 Aria는 65건 모두 작업자에서 생성됐다. cold 합계 1582.114ms, 최장 79.273ms로 개별 작업 합계가 줄어든 것은 아니다. 병렬 생성 및 프레임별 직렬 진행 제거로 원본 전환 대기가 줄었다. 병렬 작업 시간 합계는 벽시계 지연과 다르다.

## 실제 드롭 비교

단위: 드롭 요청 이후 초. 변경 전은 직전 최소 대체 재질 검증 보고서의 실제 실행, 변경 후는 이번 재빌드 실행이다. 각 조건 1회로 통계적 평균은 아니다.

| 모델 / 조건 | 대체 렌더 제출 전 → 후 | 원본 렌더 제출 전 → 후 | 변경 후 CPU 적용 | 변경 후 CPU → 원본 |
|---|---:|---:|---:|---:|
| CreatorRobot 빈 캐시 | 11.474 → 2.043 | 36.891 → 26.109 | 24.861 | 1.247 |
| CreatorRobot 재실행 | 2.092 → 1.992 | 4.259 → 3.594 | 2.356 | 1.238 |
| Aria 빈 캐시 | 18.675 → 1.175 | 57.126 → 24.409 | 23.543 | 0.866 |
| Aria 재실행 | 1.292 → 1.175 | 3.576 → 2.543 | 1.354 | 1.190 |

같은 새 실행 파일의 Aria 빈 캐시 동기 대조는 대체 11.624초, CPU 적용 32.311초, 원본 34.559초였다. 공통 셰이더 46개가 드롭 중 컴파일됐고 요청 시간 합계 10.508초였다. 최적화 후에는 시작 단계에서 준비되고 드롭 중 컴파일되지 않았다. 새 동기 대조 → 최적화의 CPU 이후 대기는 2.248 → 0.866초다. 과거 57초에서의 개선 전체를 비동기 PSO 하나의 효과로 해석하지 않는다.

원본 소스 컴파일은 빈 캐시 Robot 64개, Aria 48개이며 재실행에서는 모두 0개였다. 대체 재질 런타임 컴파일은 네 조건 모두 0개이고 배포 제품 11단계를 사용했다. 원본 소스 컴파일이 남아 빈 캐시 원본 완성에는 여전히 약 24–26초가 필요하다.

## 화면과 조작 확인의 경계

모든 배치는 네이티브 UI 드래그로 수행했다. 각 실행에서 화면의 원본 재질, 계층 선택 및 기즈모 이동 후 Inspector Z 값 변경을 확인했다. GPU 제출 로그는 Present 또는 최초 픽셀 시각과 같지 않으므로 아래 화면 관측을 별도로 남긴다.

| 조건 | 실제 화면 관측 |
|---|---|
| Aria 빈 캐시 | 2.495초 체커 표시. 15.699초 체커 상태 선택 응답. 29.844초에는 원본 표시 및 이동 반영 |
| Aria 재실행 | 0.511초 미표시, 다음 14.012초 관측은 이미 원본. 30.878초 선택, 46.579초 이동 확인 |

관측 사이에는 도구 처리와 분석 공백이 있다. 특히 마지막 실행의 긴 선택 관측 시각은 자동화 작업 공백이며 로딩 지연으로 계산하지 않는다. 이 시각들은 관측 상한이며 최초 조작 가능 시각의 정밀 측정치가 아니다. 체커 상태 조작은 이번 Aria cold 선택으로 확인했고, 모든 조건에서 체커 상태 이동까지 검증한 것으로 확대하지 않는다. 원본 제출 수치가 화면에 보인 정확한 시각이라는 주장도 하지 않는다.

## 환경·증거

- 직접 실행한 Debug 실행 파일, 디버거 미부착, DX12, Debug Layer 사용, GPU validation 미사용. 보이는 에디터의 `--console`로 결과 로그와 종료만 수집했다. 성능 배치에는 commandlet 모델 배치를 사용하지 않았다.
- 빈 캐시는 조건별 별도 `LOCALAPPDATA` 및 `CE_MATERIAL_CACHE_ROOT`에 시작 파일 0개를 확인한 엔진 셰이더·재질 캐시다. OS·모델 import·GPU 드라이버 캐시는 초기화하지 않았다. 이 제한 때문에 과거 드라이버 상태와 동일한 실험은 아니다.
- 변경 후 및 동기 대조 runtime SHA256: `994563C4E671310DDDCABCB03BF8C9B43DBEA983903CB3B48C16EB15FBFCEB72`. 대체 재질 패키지도 이 실행 파일에 맞춰 다시 생성했다.
- 직전 비교 runtime: `DC13B95EB1671786D3FE66ABC1502752DA7D8E15A9314417971459B013BFE0A9`.
- 원시 증거: `Build/editor-render-warmup-20261021/{sync-aria-cold,after-aria-cold,after-aria-warm,after-robot-cold,after-robot-warm}`의 stdout/stderr, execution.json, ui-events.json, UI 캡처. `summarize.py`가 shader 로그의 드롭 직전 바이트 위치부터 집계해 각 summary.json 및 comparison.json을 생성한다.
- 이전 기준: `docs/EditorMinimalPreviewComparison-20261021.md` 및 `Build/editor-minimal-preview-20261021/comparison.json`.

## 검증

Debug 빌드: 오류 0, 경고 0. 실제 DX12 `EditorMeshPsoProbe` 통과: 중복 요청, 입력 바이트 소유, 작업자 실행과 소유 스레드 공개, 무효화 후 재요청, 잘못된 입력, 진행 중 종료 회수. 배포 제품 정상 적중 및 손상 제품의 11개 셰이더 복구 검사 통과, 패키지 원상 복원 확인.

취소·씬 전환 검사는 저장된 원본 graph 4개와 대체 graph 비직렬화, Undo 및 씬 변경 후 취소 2개/잔여 배치 0개를 확인했으나, 첫 실행은 Finalize 완료 로그 뒤 `slang-compiler.dll`의 `0xc0000409`로 종료했다. 정상 성능 실행 5개와 배포 검사 2개는 종료 코드 0이다. 이 오류를 성능 개선으로 해결했다고 표시하지 않는다. 반복 검사 결과는 아래에 기록한다.

단독 재실행 `lifecycle-commandlet-retry`는 동일 runtime으로 모든 검사 및 종료 코드 0을 통과했다. 첫 오류는 패키지 검사와 동시에 실행한 시점에 발생했지만 동시 실행이 원인이라고 확정할 증거는 없다. 오류는 숨기지 않고 첫 실행 로그와 Windows 오류 보고를 남긴다.
