PHASE 3.5머테리얼 · 셰이더 파이프라인 재설계

예상 공수: 20일 · 신설(2026-08-11) · 선행 조건: 3-1 V1~V4 + Vulkan 골격(완료) · RhiBoundaryPlan §7.2의 V5(셰이더 컴파일)·V6(파이프라인 상태 기술)를 이 페이즈가 승계(M1=V5 · M3=V6) · 설계 문서: MaterialPipelinePlan.md
목표: Material → 셰이더 메타데이터 → (Defines · Pass · RenderStates) → 셰이더 퍼뮤테이션 → HLSL 소스 → 플랫폼 컴파일러 → DXIL | SPIR-V 의 단일 파이프라인을 세운다. 실측 결론: 셰이더 컴파일 시스템이 둘인데 화면에 나오는 쪽은 애셋 파이프라인이 아니다 — Material::GetShaderPSO()의 렌더 경로 소비자 0, 실소비는 m_renderingMode와 텍스처 4장·스칼라 4개뿐이고, 셰이더는 패스에 박힌 C++ 문자열 HLSL(D3DCompile 93건)이다. 커스텀 머테리얼 셰이더(.shader 12종)는 DX12 전환에서 계승되지 않았고, 퍼뮤테이션과 렌더스테이트는 애셋에 개념 자체가 없으며(DSL Keywords는 파싱만 되고 소비 0, 상태는 패스 C++ 하드코딩), FXC SM5.0은 DXIL도 SPIR-V도 못 낸다. V5·V6에 착수하기 전에 그 인터페이스를 섬길 소비자의 모양을 먼저 정하는 것이 이 페이즈의 자리다 — 구 RHI가 죽은 이유가 "소비자 없는 추상"이었다.
페이즈 완료 기준
  • 컴파일 진입점 하나 — D3DCompile* 직접 호출 0건, FXC 은퇴 · 손 퍼뮤테이션(RHIShaderDefine 배열) 0건(D3D_SHADER_MACRO는 M1에서 이미 0)
  • 머테리얼 커스텀 셰이더가 화면에 나온다 — 검증 씬 픽셀 판정 통과, Material 프로퍼티 변경이 다음 프레임에 반영
  • 같은 메타·같은 소스에서 DXIL과 SPIR-V — vk.selftest의 SPIR-V 모듈 로드 통과 + 두 타깃 리플렉션의 바인딩 일치 단정
  • 두 번째 실행 컴파일 0건 + .hlsli 수정 시 영향받은 셰이더만 재컴파일(전체 .cso 삭제 경로 은퇴) · 머테리얼 직렬화 경로 하나
  • 자가 검증 스윕 판정 착수 전과 동일 + dx12.live status 패스 목록 문자 일치 + 회귀 세트 통과
리스크
fxc→dxc 게이트는 현재 HLSL 49개·엔트리 67개를 실측해 전량 SM6 통과 — 이중 타깃 기간 없이 진행한다. 공식 DXC 바이너리 벤더링 전까지 SDK 없는 배포는 미완이다. M6 배선이 최대 위험 — "배선만 이으면 그림이 더 나빠진다"(Forward+ 전례), 검증 씬·셰이더 프로브 선행. 핫리로드가 map 엔트리 주소 안정성 불변식에 의존 — 핸들화(M5) 전에는 개별 erase 금지 규약을 유지해야 조용한 UAF를 피한다.

PHASE 4차세대 GPU 렌더링 기능 구상

예상 공수: 구상 10일 · 선행 조건: Phase 3 기반 완료 + Phase 3.5 셰이더 계약 확정 · 구현 공수는 이 페이즈의 기술 결정 후 별도 산정
목표: 일반 개발자가 C#으로 파이프라인과 신규 Pass를 설계하되 Game→Render 비동기와 네이티브 RenderGraph/RHI 실행을 보존하는 Scriptable Render Pipeline 계약을 먼저 세운다. 그 위에서 GPU-driven rendering, Stochastic Tile-Based Lighting, DXR, DLSS를 서로 떨어진 기능 목록으로 두지 않고 공통 가시성·모션 벡터·깊이·조명·히스토리 데이터와 하나의 차세대 렌더링 로드맵으로 구상한다. 이 페이즈는 구현이 아니라 기술 선택, 지원 범위, 폴백, 성능 기준선, 의존 순서와 수직 슬라이스를 확정하는 설계 게이트다.
페이즈 완료 기준
  • C# RenderPipelineAsset·ScriptableRenderPass → 불변 native pipeline → EnhancedRenderGraph 실행 계약과 Custom Pass 범위를 확정 — Render/CommandBuild/RHI 스레드 managed callback 0
  • 일반 Pass는 C#+Shader, 특수 Pass는 소스 수준 C++ EnhancedRenderPass로 확장하며 외부 Native DLL ABI는 만들지 않는 경계를 확정
  • 네 기능의 지원 GPU·백엔드·품질 모드·래스터 폴백을 기능 행렬로 확정
  • RenderScene/RenderView → GPU 가시성 → 타일 조명 → DXR → 업스케일·프레젠트의 데이터 흐름과 프레임 히스토리 소유권을 문서화
  • 대표 씬의 GPU 캡처·프레임 시간·VRAM 기준선과 기능별 성공/실패 판정 방법을 확정
  • 기능 간 의존 그래프와 최소 수직 슬라이스, 구현 페이즈 분할 및 공수 산정 완료
범위 원칙
이 단계에서 SDK 연동이나 렌더 패스를 먼저 만들지 않는다. 공통 입력과 폴백 계약 없이 개별 기능부터 붙이면 모션 벡터·깊이·노출·히스토리와 가시성 결과가 기능마다 중복되므로, 4-6 설계 게이트를 통과한 뒤 구현 순서를 확정한다.

PHASE 9생명주기 재설계 (델리게이트 프레임 루프 은퇴)

예상 공수: 10.5일 · 선행 조건: PHASE 2 스크립트 C# 전환 완료(2-10~2-21) · 병행: PHASE 3와 병행 가능, 9-4는 브랜치 보존 확인 후 5-4와 묶어 진행 가능 · 설계 문서: LifecycleRedesignPlan.html
목표: 컴포넌트 생명주기를 CRTP + 델리게이트 구독에서 Scene 소유 단계 리스트 + 프레임 끝 단일 파괴 지점으로 옮긴다.

왜 지금인가. 스크립트가 전면 C#으로 전환되면서(2-10~2-21) Scene 생명주기 델리게이트의 잔존 구독자는 엔진 내장 컴포넌트 26종뿐이 됐다. 델리게이트는 "누가 구독할지 모르는" 상황을 위한 도구인데, 프레임 루프에 이제 모르는 구독자가 없다. 반면 위험은 그대로다 — Broadcast 복사-후-호출 UAF 창, 즉시 파괴, 재진입 불가 스핀락. 씬 중복 등록 더블 delete와 Scene::~Scene의 Clear() 종료 행이 전부 이 계열의 실사고였다.

목표 구조. Scene이 이미 렌더·물리 대상에 쓰는 Collect* 패턴을 생명주기로 확장한다: Component가 생명주기 훅을 직접 소유(CRTP 26곳 제거), "어떤 이벤트를 구현했나"는 ComponentFactory 등록 지점 1회의 LifecycleMask로 판정, pending 큐 + 단계 리스트 + 프레임 끝 파괴로 순회 중 무효화를 표현 불가능하게 만든다. 생명주기 API는 게임 스레드 전용 무락(無lock) 규약 — ClrHost와 같은 규약이다. Core::Delegate는 삭제하지 않고 시스템 이벤트(sceneLoadedEvent, OnResize 등)용으로 남긴다. 부록으로 .NET GC를 엔진 스케줄에 종속시키는 두 항목(씬 경계 Collect, HUD 계측)을 포함한다.

  • ✔ IRegistableEvent.h 삭제, Scene 생명주기 델리게이트 제거 — 프레임 루프에 델리게이트 참조 0건 — 계획의 8종보다 많은 15종이었다(물리 6종·InternalPhysicsUpdate는 이미 죽은 멤버)

PHASE 10파티클·이펙트 백지 재작성

예상 공수: 24일 · 선행 조건: 없음(구 계통 제거 완료) · 우선순위: 최후순위 — 다른 모든 페이즈 뒤
목표: 파티클·이펙트 계통을 백지에서 DX12로 쓴다. 처음부터 패키지 밖에서 쓴다.

★ 방향을 바꿨다(2026-08-08, 사용자 판단): 이식이 아니라 백지 재작성. 원래 계획은 "DX11 계통을 보면서 DX12로 옮기되 발견한 결함은 고친다"였다. 그 전제에서 구 코드는 참고본이었는데, 참고본이 있으면 그 구조를 따라가게 된다 — ping-pong 버퍼 둘, 모듈 아홉 개의 체인, 저작 JSON 스키마가 전부 DX11 즉시 컨텍스트 시절의 형태다. 옮길 기준선이 없다는 것(구버전은 legacy/pre-coreclr가 맡는다)은 처음부터 참이었으므로, 참고본을 지우는 쪽이 일관된다.

★ 구 계통을 들어냈다(2026-08-08 · 10-0 완료 · 빌드 그린). EffectSystem 프로젝트 56파일 19,639줄, 파티클 셰이더 30종, EffectComponent(C++·C#·generated), ClrHost의 스크립트 API 20항목, 엔진 배선 6파일이 사라졌다. 이제 이 페이즈의 시작점은 진짜 백지다 — EnhancedRenderPass 규약과 이미 검증된 DX12 자산(PSO 캐시·디스크립터 링·인코더) 위에서 쓴다.

★ 순서를 뒤집는다 — 패키지 경계가 먼저다(10-1). 지형(PHASE 11)에서 이미 같은 결론에 왔고, 이번에는 근거가 실측이다: EffectSystem은 엔진 안에서 다 만든 뒤 41차 슬라이스에서 54파일을 떼어내야 했고, 그러고도 패키지화가 끝나지 않은 채로 제거됐다. 나중에 자르는 것이 처음부터 밖에서 쓰는 것보다 비쌌다는 증거다.

사라진 코드에서 건져 둔 사실(재조사 불필요). 코드는 지웠어도 측정값은 남는다 — 새로 쓸 때 "무엇이 어려운가"의 답이 이미 있다.
· ★ append/consume 버퍼·CopyStructureCount·간접 드로우·DispatchIndirect가 저장소 전체에 0건이었다. 어려운 구조를 새로 뚫을 일이 없다 — 평범한 StructuredBuffer + Dispatch로 충분하다.
· 시뮬레이션은 GPU, 트레일 생성만 CPU였다(872줄). 정렬 없음, 지오메트리 셰이더 없음, 소프트 파티클 없음.
· DX11이 드라이버에 맡기던 UAV↔SRV 해저드를 DX12에서는 배리어로 명시해야 한다. 모듈 체인이 최대 9단이라 여기가 이 페이즈의 핵심 엔지니어링이고, 그것은 백지에서 써도 똑같다.
· 구 계통의 결함 둘을 기록해 둔다. 새 코드가 같은 자리를 밟지 않기 위해서다: TrailModuleCS가 그룹 수를 (capacity+255)/256으로 계산하는데 셰이더는 numthreads(1024)였다(4배 과소 디스패치). 그리고 이펙트 패스 직후 매 프레임 Flush()를 불러 GPU를 통째로 비웠다 — DX12에 대응물이 없고, 필요한 것은 그 자리의 배리어다.
· 저작 형식은 PathFinder::Relative("Effect\\") 아래 .json이었고, 그 디렉터리는 저장소에 존재하지 않았다 — 남은 저작 자산이 애초에 0이다. 새 형식을 자유롭게 정할 수 있다.
페이즈 완료 기준
  • 파티클 시뮬레이션이 DX12 컴퓨트로 돌고, 모듈마다 켬/끔 대조군이 붙은 자가 검증이 통과한다
  • 빌보드·메시·트레일 세 렌더 모듈이 DX12에서 그려진다
  • 체인의 모든 쓰기-읽기 경계에 배리어가 있고, 리드백으로 값이 단정된다("그려지긴 한다"와 구분)
  • 새 Effect 프로젝트를 솔루션에서 빼도 나머지가 빌드되고 실행된다 — 10-1 직후부터 계속 참이어야 한다

PHASE 11지형 렌더 경로 신규 작성과 패키지화

예상 공수: 20일 · 선행 조건: 없음(GPU 코드 제거 완료) · 우선순위: 최후순위 — PHASE 10과 같은 자리 · 설계 문서: EnginePackagingPlan.md §4.1
목표: 지형 렌더 경로를 백지에서 쓰고, 붙였다 뗄 수 있는 패키지로 만든다.

★ 이펙트와 다르게 잘랐다(2026-08-08, 사용자 판단). 이펙트는 계통을 통째로 지웠지만 지형은 GPU 코드만 지웠다. 이유는 두 계통의 상태가 달라서다 — 이펙트는 GPU 코드가 곧 계통 전부였지만, 지형은 편집 로직(조각·페인팅·레이어 관리 · 1,300여 줄)이 GPU와 무관하게 살아 있고 그것은 다시 쓸 이유가 없다.

★ GPU 코드를 들어냈다(2026-08-08 · 11-0 완료 · 빌드 그린). 걷어낸 것과 그 근거:
· TerrainMaterial의 DX11 일습 — 스플랫맵 텍스처 배열 + SRV, 레이어 Albedo 배열 + UAV + SRV, 상수 버퍼 둘, 레이어 배열을 굽던 DX11 컴퓨트 셰이더(TerrainTexture.cs). ★ 그 전부의 소비자가 0이었다 — GetSplatMapSRV·GetLayerSRV·GetLayerBuffer의 호출자를 전수로 세어 확인했다. 잃은 기능이 없다.
· TerrainMesh의 DX11 정점·인덱스 버퍼와 Map/memcpy 경로.
· 브러시 마스크의 DX11 텍스처·SRV(TerrainBrush::BrushMask)와 LoadRunTimeTerrain의 레이어 배열 조립.
· 셰이더 둘(TerrainTexture.cs·TerrainDebugBrush.ps), 지형·폴리지 저작 에셋.

★ 그러면서 선결 결함이 함께 풀렸다 — 자료의 진실이 CPU로 왔다. TerrainMesh::UpdateVertexBufferPatch가 DX11 버퍼만 Map/memcpy 하고 m_vertices(CPU 배열)는 그대로 두고 있었다. 즉 조각(sculpt) 결과가 CPU 자료에 남지 않았고, DX12는 CPU 배열에서 업로드하므로(DX12MeshCache의 규약) 그 결과가 화면에 반영될 길이 없었다. 게다가 그 버퍼를 읽는 코드는 이미 0이었다 — 아무도 읽지 않는 버퍼에 계속 쓰고 있었다. 이제 갱신은 전부 CPU 배열에 쓰고, m_revision으로 "올린 것이 최신인가"를 판정한다(스플랫 마스크도 같은 형태).

★ 잃은 것 하나를 명시해 둔다. 브러시 마스크 썸네일이 사라졌다(인스펙터의 마스크 선택이 이미지에서 이름 버튼이 됐다). 마스크의 진실인 CPU 배열(m_mask)은 그대로이고 브러시 동작도 그대로다 — 미리보기만 없다. 11-5에서 DX12로 복원한다.

★ 패키지 경계가 먼저다. 경계를 먼저 세우고 EnhancedTerrainPass를 그 안에서 쓰면 경계를 넘는 코드가 애초에 생기지 않는다. EffectSystem이 그 반대로 가서 치른 값이 근거다(PHASE 10 참조).

★ 파일을 옮기기 전에 의존을 역전해야 한다. 지금 옮기면 프로젝트 순환이 닫힌다 — Terrain → ScriptBinder(Terrain.cpp가 Scene.h·SceneManager.h를 include)와 ScriptBinder → Terrain(Scene.h가 std::vector<TerrainComponent*>를 멤버로 든다)이 맞물린다. 엔진이 지형을 타입으로 아는 자리 열 곳을 세어 두었다(11-1의 내용).

남은 조사 결과(2026-08-08 실측).
· RHI/DX12/ 아래 TerrainComponent 참조 0건. RenderPassData가 m_terrainQueue에 프록시를 쌓지만 읽는 코드가 없다.
· 구 DX11에서 대응 패스가 사라진 것: TerrainGizmoPass(편집 브러시 표시).
· 프록시가 나르는 지형 필드 넷: m_terrainMesh·m_terrainMaterial·m_terrainGizmoBuffer·m_terrainlayerBuffer — 소비자 0.
· 폴리지(FoliageComponent)도 같은 상태다 — 큐에 쌓이고 읽는 곳이 없다. 지형과 함께 다룬다(레이어 마스크·높이맵을 공유한다).
페이즈 완료 기준
  • 지형이 DX12에서 그려지고, 스플랫 레이어 블렌딩이 자가 검증(dx12.terrain)으로 확인된다
  • 조각·페인팅 결과가 화면에 반영된다 — CPU 자료가 진실인 것은 11-0에서 이미 참이고, 여기서는 그것을 읽는 쪽이 생긴다
