PHASE 0안전망 구축

예상 공수: 10일 · 선행 조건: 없음 · 병행 가능: 전체 작업과 병행
목표: 리팩토링 전후를 정량 비교할 수 있는 계측 체계와, 회귀를 즉시 잡아내는 빌드 검증 체계를 먼저 확보한다. 안전망 없는 대규모 리팩토링은 "고쳤는지 알 수 없는 수정"이 되므로 이 페이즈가 모든 작업의 전제다.
페이즈 완료 기준 (Exit Criteria)
  • ✔ 씬 전환마다 라이브 객체 수/타입별 증감과 VRAM이 로그에 정량 기록됨
  • 씬 전환 10회 반복 벤치마크의 VRAM/객체 수 기준선이 문서화됨 (0-3에서 수행)
  • ✔ master 푸시/PR에서 엔진 라이브러리 7종이 Debug·Release로 자동 컴파일 검증됨
  • ASan 빌드 구성으로 에디터가 기동되고 12.3-② UAF가 실제로 재현·캡처됨
  • ✔ 크래시 이후 로그 파일을 열었을 때 마지막 로그와 크래시 사유가 남아 있고, 비정상 종료가 배너로 식별됨

PHASE 1크래시 핫픽스 (소유권 변경 없이 가능한 결함)

예상 공수: 13일 · 선행 조건: Phase 0 (계측으로 수정 효과 검증) · 근거: 분석 보고서 12.1 / 12.3
목표: 소유권 모델을 건드리지 않고도 고칠 수 있는 확정 크래시·누수 결함을 전부 제거해 현재 빌드를 안정화한다. Phase 2의 대수술 전에 환자를 안정시키는 단계.
페이즈 완료 기준
  • ASan 빌드에서 "Animator 비활성화 + 스키닝 메시 유지" 시나리오 1시간 반복 무크래시
  • EffectEditor에서 프리셋 100회 변경 후 ReportLiveDeviceObjects의 BlendState/DepthStencilState 수가 증가하지 않음
  • 병렬 에셋 로딩(LoadAssetBundle) + 씬 컬링 동시 수행 스트레스에서 힙 손상 미발생
리스크
락 추가(1-2, 1-8)는 프레임 타임에 영향을 줄 수 있음 — Phase 0의 프로파일러로 전후 프레임 타임을 비교하고, 경합이 크면 맵 샤딩 또는 커맨드 버퍼링으로 완화.

PHASE 2자원 소유권 모델 재설계

예상 공수: 33일 · 선행 조건: Phase 1 완료 (안정된 기반 위에서만 수술) · 근거: 분석 보고서 12.2 + 보충 분석 + CoreCLR 전환 결정
목표: "shared_ptr 캐시 = 유일 소유, 사용처 = 원시 별칭"이라는 근본 설계 오류를 제거한다. 컴포넌트·Model·프록시가 에셋 수명에 안전하게 참여하도록 소유권을 재설계한 뒤, 비로소 UnloadUnusedAssets()를 활성화해 씬 전환 시 메모리가 회수되게 만든다. 이 프로젝트 리팩토링의 본체.
페이즈 완료 기준
  • 씬 A↔B 전환 50회 반복 후 VRAM 사용량이 평탄(±5%)하게 유지됨 — Phase 0 기준선 대비 그래프로 입증
  • 언로드 활성 상태에서 게임플레이(클론 머티리얼 사용 포함) 1시간 무크래시 (ASan)
  • ReportLiveDeviceObjects에서 씬 언로드 후 이전 씬 전용 텍스처/버퍼가 0개
리스크
접점이 가장 넓은 페이즈(컴포넌트 직렬화, 에디터 인스펙터, 프록시, 348개 게임 스크립트의 Instantiate 사용처). 2-1 설계 결정에서 기존 원시 포인터 API를 유지한 채 내부만 핸들화하는 호환층을 두는 방안을 우선 검토해 게임 코드 변경량을 최소화할 것. 핫리로드 DLL 경계에서 shared_ptr 컨트롤 블록이 언로드된 모듈 코드를 참조하지 않도록 삭제자(deleter)를 엔진 측에 고정해야 함.

PHASE 3DX12 렌더러 전환

예상 공수: 64일 · 방향 전환(2026-07-31): DX11 제자리 개선 → DX12 별도 구현 후 교체 · 병행: Phase 4와 병행 가능(RHI가 4-1 인터페이스 절단과 상승 작용)
목표: RHI 계층 위에 DX12 렌더러 EnhancedSceneRenderer를 별도로 세우고 검증 후 기존 SceneRenderer(DX11)를 교체한다. PSO 중앙 관리·디스크 캐시, RenderGraphBuilder 완성(배리어 자동 유도·리소스 수명), DXR 레이트레이싱, DLSS를 갖추고, 게임/렌더 스레드를 락스텝 배리어에서 프레임 스냅샷 프로듀서-컨슈머로 재편한다. 구 계획(3-1~3-7 DX11 개선)은 이 전략에 흡수 — 각 항목의 계승 관계를 detail에 남겼다.
페이즈 완료 기준
  • EnhancedSceneRenderer가 대표 씬 N종을 렌더하고 DX11 결과와 패스 캡처 대조 통과 — 에디터 전 기능(기즈모·씬뷰·게임뷰) 동작
  • 두 번째 실행에서 PSO 런타임 컴파일 0건(파이프라인 라이브러리 전부 히트) — 히트/미스 카운터로 확인
  • 신규 패스 추가가 그래프 선언 한 곳 수정으로 완료 — 배리어·리소스 수명은 그래프가 유도(수동 배리어 0건)
  • RT 패스 on/off 토글 즉시 동작, 미지원 GPU에서 래스터 폴백으로 동일 씬 렌더 · DLSS 품질 모드 런타임 전환 + UI 회귀(Tools/regression) 통과
  • 프레임 스냅샷 구조에서 3-0의 크래시 시나리오(재생 진입 중 씬 교체) 재실행 시 문제 부류 자체가 성립하지 않음을 확인

PHASE 4구조적 커플링 제거

예상 공수: 19일 · 선행 조건: Phase 2 완료 · 병행: Phase 3과 병행 가능 · 근거: 분석 보고서 3장 / 13장
목표: RenderEngine ↔ ScriptBinder 양방향 include를 인터페이스 계층으로 절단하고, 에디터 UI가 리소스 시스템에 박혀 있는 구조(DataSystem 내 콘텐츠 브라우저)를 분리한다. 모듈 경계가 개념(렌더 vs 게임플레이 vs 에디터)과 일치하도록 물리 구조를 재정렬한다.
페이즈 완료 기준
  • RenderEngine이 ScriptBinder 헤더를 include하지 않음 (인터페이스 헤더만 참조) — include 그래프 검사 스크립트로 CI 게이트화
  • GameBuild 구성에서 에디터 전용 코드(콘텐츠 브라우저, EffectEditor UI)가 링크되지 않음
  • Mono 관련 디렉터리/코드 제거 후 전체 솔루션 클린 빌드 통과
리스크
디렉터리 재구성(4-5)은 vcxproj·filters·include 경로·코드젠 도구(리플렉션 스캐너)의 경로 가정을 동시에 건드림 — 코드젠 도구 3종의 스캔 경로 설정을 먼저 확인하고, 한 서브폴더씩 이동 → 빌드 검증의 소단위 반복으로 진행할 것.

PHASE 5코드 정리 및 품질 상시화

예상 공수: 10일 · 선행 조건: 각 페이즈 종료 시 부분 수행, 최종 총정리는 Phase 3·4 완료 후
목표: 리팩토링 과정에서 확정된 데드 코드를 제거하고, 재발 방지 장치(정적 분석, include 게이트, 리소스 카운터 회귀 테스트)를 CI에 상시화한다. "한 번 청소"가 아니라 "더러워지지 않는 구조"가 목표.
페이즈 완료 기준
  • 미사용 심볼·주석 처리 블록·비활성 Mono 경로가 저장소에서 제거되고 빌드 통과
  • CI에 컴파일 + include 경계 검사 + (선택) clang-tidy 핵심 체크가 게이트로 동작
  • 씬 전환 메모리 평탄성 벤치마크가 자동화되어 회귀 시 CI 실패

PHASE 6UI 서브시스템 재설계

예상 공수: 12일 · 선행 조건: Phase 1 완료 권장 · 병행: Phase 2~4와 독립 · 근거: 스크립트 API 바인딩 중 실측 크래시 3건
목표: 캔버스·UI 요소의 등록처를 한 곳으로 줄이고 이름 문자열 결합을 제거한다. 스크립트 UI 바인딩 작업 중 런타임에 캔버스를 붙이는 것만으로 엔진이 즉사하는 크래시 3건이 연쇄로 드러났는데, 전부 같은 뿌리다 — 하나의 UI 요소가 Canvas.UIObjs(weak_ptr) · UIManager.Images/Texts(원시 포인터) · Scene.CanvasMap(이름 키) 세 곳에 수동 등록되고, 연결 고리가 이름 문자열이라 어긋난 순간 널 역참조나 빈 컨테이너 접근으로 이어진다. Phase 2가 자원 캐시에서 걷어낸 "수동 등록 + 원시 별칭" 문제의 UI판이다.
페이즈 완료 기준
  • 빈 씬에서 component.add로 Canvas·Text·Image를 임의 조합으로 붙이고 재생/정지를 반복해도 크래시 없음(CLI 자동화)
  • UI 요소의 등록처가 한 곳으로 줄고, 등록·해제가 생성·파괴에 자동으로 따라감(수동 Register/Unregister 호출 소멸)
  • 캔버스 이름 변경·중복 이름 시나리오에서 UI 귀속이 깨지지 않음
  • 기존 씬 파일이 수정 없이 로드되고 UiTextProbe 전체 통과 유지

PHASE 7UI 레이아웃 해상도 독립

예상 공수: 14.5일 · 선행 조건: Phase 6 완료 · 근거: RectTransformAnalysis.html (정적 분석 10건 + 런타임 재현)
목표: UI 레이아웃을 저작 해상도(1920×1080) 고정에서 해방한다. 현재는 최상위 캔버스가 레이아웃 드라이버의 사각지대라 worldRect가 로드 시점 값으로 동결되고, 그 파생값이 프리팹에 직렬화되어 저작 해상도가 파일에 구워진다. 창 크기 변경 경로에도 UI 재배치가 없다. 세 결손을 순서대로 걷어내면 화면 추종이 되고, 그 위에 CanvasScaler를 얹으면 비례 스케일이 되어 uGUI와 같은 수준에 도달한다. 앵커 수학 모델 자체는 이미 uGUI와 동형이라 기반은 그대로 살린다.
페이즈 완료 기준
  • 1280×720 / 1920×1080 / 2560×1440 / 21:9에서 동일 씬의 UI가 앵커 의도대로 배치·스케일됨
  • 실행 중 창 크기 변경 시 1프레임 내 전체 UI 리플로우
  • RectLayoutProbe 역방향 단정(H1~H3이 "반응함") 전체 통과 + 해상도 스위프 회귀 편입
  • 기존 씬·프리팹 무수정 로드, 1920×1080에서 픽셀 동일(회귀 없음)
  • worldRect가 신규 저장 파일에서 사라지고 로드 경로가 기존 값을 무시함
대시보드 갱신 방법: 이 파일 하단 <script>의 TASKS 배열에서 해당 항목의 status 값을 "todo" → "progress" → "done"(또는 "blocked")으로 바꾸면 전체/페이즈 진행률·요약 카드가 자동 재계산됩니다. note 필드에 진행 메모를 남길 수 있습니다. 갱신 시 상단 last-updated도 함께 수정하세요.
