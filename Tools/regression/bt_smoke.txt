# 행동 트리 동작 확인 시나리오 (PHASE 9-8 완료 기준 1·3)
#
# 목적: BT가 실제로 도는지를 재는 유일한 경로다.
#
# ── 왜 별도 시나리오인가 ──
#
# 회귀 세트(run-all.ps1)는 BT를 전혀 건드리지 않는다. BT 컴포넌트는 프리팹 11종에만
# 붙어 있고 회귀 시나리오가 여는 씬에는 그 프리팹이 없다. 그래서 회귀가 전부
# 통과해도 BT 코드는 한 줄도 실행되지 않은 채 통과할 수 있다 — "안 깨졌다"이지
# "동작한다"가 아니다.
#
# 게다가 트리 생성·틱은 실패할 때만 로그를 남긴다(성공은 무음). 즉 "트리가 안 서서
# AI가 가만히 있다"와 "정상"이 로그에서 같아 보인다. bt.status가 그 자리를 메운다.
#
# 실행: Academy_4Q.exe --script Tools\regression\bt_smoke.txt
# 판정: verify-bt-smoke.ps1 (수치 판정은 전부 거기에 있다)

wait 60

# 소환 전 상태를 먼저 남긴다.
#
# 이 줄이 없으면 나중 수치가 "이번에 생긴 것"인지 "원래 있던 것"인지 가를 수 없다.
# 트리 0개가 여기서 확인돼야 뒤의 증가가 이 시나리오의 결과가 된다.
bt.status

# 검증 전용 프리팹을 소환한다.
#
# 게임 프리팹(MonsterA 등)을 쓰지 않는 이유: 그쪽 트리의 잎은 아직 이식되지 않은
# 사용자 노드 43종을 참조해 트리가 서지 않는다. 게다가 게임 콘텐츠에 의존하면
# 콘텐츠가 바뀔 때마다 이 검사가 흔들린다 — 엔진 경로를 재는 검사가 콘텐츠 회귀로
# 오해되기 시작하면 아무도 믿지 않게 된다.
#
# 셋을 소환하는 이유는 배치 크기를 1보다 크게 만들기 위해서다. 트리가 하나뿐이면
# "크로싱 1회"가 배치 덕인지 트리가 하나뿐이어서인지 구분되지 않는다. 크로싱당
# 전달 틱이 1을 넘어야 배치가 실제로 증명된다.
prefab.instantiate BTProbe BTProbeA
wait 20
prefab.instantiate BTProbe BTProbeB
wait 20
prefab.instantiate BTProbe BTProbeC
wait 30

# 소환 직후 — Awake가 돌았으니 트리가 서 있어야 한다. 아직 틱은 0이다
# (재생 전에는 InternalAIUpdate가 m_isGameStart에서 막힌다).
bt.status

# 여기서부터 구간 측정. 앞의 프레임이 분모에 섞이면 비율이 흐려진다.
bt.reset
play
wait 180
bt.status
stop
wait 30

# 정지 후에도 트리는 남아 있어야 한다(파괴는 OnDestroy에서만).
bt.status

# 씬을 갈아 치우면 트리가 함께 내려가야 한다. 남으면 Running 상태가 다음 씬으로
# 새고, 노드가 스크립트 타입을 붙들어 어셈블리 언로드도 막는다.
scene.new BTProbeEmpty
wait 60
bt.status

log.flush
quit
