# Deep capture CLI and shared admission

All fixtures and acceptance scenarios below are **UNEXECUTED**. No build,
collector, Editor, test executable, installation or manual CI was run.

The source closure is `DxCaptureService.{h,cpp}`, the Diagnostics command
registration TU and `CommandDescriptorSeeds.cpp`. No new product library or
dependency is needed. Build-disabled paths do not reference the optional
DxTimingCaptureLibrary or live `process_client` implementation. The viewer
continues to compile neither the service nor the process-client implementation.

## Public surface

- `profile.deep.start`: no arguments; returns `accepted`, `sessionId`,
  `artifactPath` and the admission snapshot. The session ID is a decimal string
  so HTTP/JavaScript consumers cannot round it. The first ID in a service uses
  cryptographic randomness; later IDs increment without wrapping
- `profile.deep.status`: no arguments; reads the current session, phase,
  helper status/Win32 error, file summary, loss counters and artifact path
- `profile.deep.stop <session-id>`: exact nonzero unsigned decimal session ID;
  requests asynchronous drain. Duplicate stops on the same active or completed
  session succeed; stale, zero, malformed and overflowing IDs do not stop a
  different session

HTTP uses the existing authenticated `POST /command`, discovery/help schema,
Editor command queue and GT execution. Named Stop input is `sessionId` with a
string value. There is no new route, listener, provider, helper selector,
elevation flag or output-path parameter. `profile.stats.dxDeepCapture` exposes
the same shared service status. No extra save command is required: the engine
retains the `.cedx` artifact at `artifactPath` for later viewer Open.

`accepted` means only admission. State `in_progress` requires the real helper
to report capturing. `stopping` includes requested stop and drain/finalization.
`finalized` means a successful writer footer after normal collector termination,
and may still have `complete=false` or nonzero loss counters. `failed`,
`permission_denied` and `unavailable` retain the raw helper state and error.
A failed collection can retain a recoverable prefix or footer; an intended
`artifactPath` alone does not prove the file was written or finalized.

## Source fixtures and pending acceptance

1. `DeepCaptureCommandFixtures.cpp`: all descriptor seeds are strictly lexical,
   duplicate-free and individually resolvable by binary lookup; Diagnostics
   canonical/alias names do not collide; each deep command is registered once,
   has no alias, and advertises the exact matching HTTP parameter schema
2. `DxCaptureControlFixtures.cpp`: the real service with an isolated fake
   collector covers simultaneous callers, accepted-vs-capturing, duplicate and
   stale stop IDs, repeated sessions, successful footer publication, helper
   permission/unavailable/failure states and the SDK-disabled result
3. Concurrent CLI/GT and viewer/PT starts: exactly one admission wins; the loser
   sees busy and the winning session ID. No caller joins/waits for the worker;
   admission remains busy until all old writer/helper cleanup has returned
4. Stop during worker startup, active capture and footer drain; repeated Stop;
   old Stop after a newer capture and after an engine restart. Only the exact
   session may be affected. CLI/HTTP IDs must survive full uint64 round trips
5. SDK-disabled and Shipping builds: Start reports unavailable without spawning
   a helper. Missing helper, ordinary-token ETW denial, already-elevated Editor,
   helper crash, invalid protocol, file-open/write failure and record limits
   remain distinct from successful admission and successful finalization
6. Keep ordinary `.ceprof` capture running throughout each deep failure. Its
   generation, writer, saved artifact, command queue and HTTP authentication
   remain unaffected; no UAC, runas or inherited high-token bypass occurs
7. Compare `help profile.deep.start/status/stop`, `commands.describe`, HTTP
   discovery and command results. The three new golden rows were authored as a
   source delta, not regenerated by execution. The existing golden has unrelated
   historical drift (for example the old profile.record/pause summaries); do
   not report that full golden gate as passed without a real snapshot review
