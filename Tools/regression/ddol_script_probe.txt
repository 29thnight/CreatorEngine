# DDOL 이송 신호가 C#까지 닿는가 (트랙 L · L3 잔여)
#
# ── 이 검사가 메우는 구멍 ──
#
# 관리 측 생명주기의 드라이버가 둘이다. 네이티브 ScriptComponent는 인스턴스의
# 생성·파괴만 알리고, 그 사이 네 단계는 BehaviourRegistry가 자기 큐로 굴린다.
# 그래서 네이티브에서만 일어나는 사건 — DontDestroyOnLoad 이송 —이 스크립트에
# 전혀 닿지 않았다. 오브젝트는 살아서 씬을 건너는데 스크립트는 그 사실을 모른다.
#
# ★ 이 시나리오를 처음 돌렸을 때 두 번째 결함이 함께 나왔다:
# ClrHost::NotifySceneUnload가 ScriptObjectRegistry::Clear()를 부르는데, 그 함수가
# **살아남는 DDOL 오브젝트의 핸들까지 전부 죽였다.** 스크립트는 살아서 계속 도는데
# 자기 GameObject를 잃는다 — GameObject.Name이 빈 문자열이 되고 그 경유 API가 전부
# 무응답이 된다. SweepOrphans는 Clear보다 먼저 돌아 그 스크립트를 고아로 잡지도
# 않는다. 이 검사의 판정 4가 그것을 잡는다.
#
# ── 왜 play가 필요한가 ──
#
# 관리 측 드레인(BehaviourRegistry.AwakeNewlyCreated)은 Runtime::TickSimulationFrame의
# 돈다. 재생 중이 아니면 인스턴스는 만들어져도 훅이 한 번도 불리지 않는다 —
# 그 상태로 재면 "이송 통지가 안 왔다"와 "애초에 아무 훅도 안 왔다"를 구분할 수 없다.
#
# ── 판정 항목 (verify-ddol-script.ps1) ──
#
#   1  생성 시 Awake·AddedToScene 각 1회   — 기준선(관리 드레인이 돌았다)
#   2  이송 시 RemovingFromScene 1회 추가   — ★ detach 통지가 닿았는가
#   3  이송 시 AddedToScene 1회 추가        — ★ attach 통지가 닿았는가
#   4  이송 뒤 로그에 오브젝트 이름이 남는다 — ★ 핸들이 이송을 살아 건넜는가
#
# 판정 2·3은 "이중 발화 없음"도 함께 본다 — 각 단계가 정확히 예상 횟수여야 한다.
#
# ── 목적지 씬도 이제 저작 자산이 아니다 (2026-08-21) ──
#
# 예전 목적지는 `FT_Material`(저작 자산)이었다. 폐기(§0.05) 대상이므로 시나리오가
# 직접 만든다: 빈 씬을 하나 만들어 저장하고, 그 파일로 이송한다.
#
# ★ 검사 스크립트가 실행 **전에** 그 파일을 지운다. 안 지우면 이전 실행이 남긴
# 파일이 남아, scene.save가 실패해도 switch가 성공해 버린다 — 저장 경로가 죽은
# 채로 게이트가 통과하는 거짓 통과다. 지워 두면 저장이 실패했을 때 switch가
# 실패하고 판정 2·3이 그것을 잡는다. 저장 자체도 판정 0으로 명시한다.
#
# 경로는 검사 스크립트가 실행 직전에 채운다({{DEST_SCENE}}).

wait 60

# 판정 0 — 목적지 씬을 만들어 저장한다. 빈 씬이라 이송분과 섞일 것이 없다.
scene.new L3DdolDest
wait 30
scene.save {{DEST_SCENE}}
wait 30

scene.new L3DdolProbe
wait 30
object.create DdolScriptProbe
wait 10
script.add DdolScriptProbe LifecycleProbe
wait 10
play
# Release headless는 90프레임이 Scope.Delay(0.2s)보다 먼저 끝날 수 있다.
# 이송 순서 판정이 wall-time 운에 흔들리지 않도록 resume 여유를 둔다.
wait 300
scene.ddol DdolScriptProbe
wait 10
scene.switch {{DEST_SCENE}}
wait 150
log.flush
quit
