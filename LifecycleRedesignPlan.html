01전제 재정립 — C# 전환 이후의 지형

이 문서 이전의 위험 평가는 "사용자 스크립트가 네이티브 델리게이트에 직접 구독하는 세계"를 가정했다. 그 세계는 끝났다. master 기준 실행 주체별 디스패치 경로는 이제 이렇다.

실행 주체디스패치 경로상태
사용자 스크립트 (C#) ClrHost::TickAwake/TickFixedUpdate/TickUpdate/TickLateUpdate — 틱당 경계 통과 4회 고정, C# 내부 일괄 순회. 물리 콜백도 blittable 구조체로 라우팅 (2-20) 유지 — 이미 올바른 모델
엔진 내장 컴포넌트 26종 RegistableEvent<T> CRTP → Scene 델리게이트 8종에 AddLambda(raw 캡처) 이 문서의 대상
C++ 스크립트 (ModuleBehavior + HotLoadSystem + Dynamic_CPP) AddShared(weak_ptr) 구독 — master에는 코드가 남아 있으나 실사용 경로 아님 브랜치 보존 · master 은퇴 대상
Mono 경로 (MonoManager) AwakeEvent.AddLambda 등 — 데드 코드 (대시보드 4-4에서 제거 예정) 은퇴 대상
엔진 시스템 이벤트 (sceneLoadedEvent, OnResizeEvent, 렌더 이벤트 등) Core::Delegate — 프레임 루프 바깥, 구독자가 진짜로 동적 유지 — 델리게이트의 정당한 용도

핵심 관찰: 델리게이트는 "누가 구독할지 컴파일 타임에 모르는" 상황을 위한 도구다. 사용자 스크립트가 C#으로 떠난 지금, 프레임 루프(생명주기)에는 모르는 구독자가 없다. 구독자는 엔진이 직접 컴파일하는 26종의 고정 집합이고, 이들의 override 분포는 전수 조사 결과 다음과 같다.

생명주기네이티브 override 수 (26종 중)해당 컴포넌트
Awake21Collect/UnCollect 등록이 대부분 — 콜라이더 6종, 렌더러류, 라이트 등
OnDestroy24위의 해제 대칭
Update13Animator, Camera, Canvas, Decal, Effect, Foliage, Image, Light, PlayerInput, Sound, SpriteSheet, Text, UIButton

LateUpdate2CharacterController, Sound
FixedUpdate1CharacterController

조사 방법: 26종 헤더의 override 선언 전수 grep. ScriptComponent는 설계 의도대로 Awake/OnDestroy만 받는다 (관리 측 라이프사이클은 ClrHost가 일괄 디스패치 — ScriptComponent.h 주석 참조).

02위험 재평가 — 무엇이 소멸했고 무엇이 남았나

소멸했거나 심각도가 내려간 것

이전 평가재평가
"같은 엔진에 안전성이 정반대인 생명주기 체계가 두 벌" (CRTP raw 캡처 vs ModuleBehavior weak_ptr) 소멸 — ModuleBehavior 경로가 브랜치로 이관. master의 실경로는 하나로 수렴
CRTP final 상속 함정 — 파생 클래스의 override가 조용히 안 불림 심각도 하락 — 사용자 확장은 C#으로 갔으므로 노출면 축소. 단, 엔진 컴포넌트를 파생할 때(UIComponent → ImageComponent → 파생) 여전히 함정이므로 구조 교체 시 함께 제거
스크립트 수만큼 경계를 넘는 디스패치 비용 소멸 — ClrHost 고정 경계 4회로 이미 해결 (2-10 설계 그대로)

그대로 유효한 것 — 이제 유일한 실경로가 네이티브 26종이므로 오히려 더 선명해졌다

#위험근거실사고 이력
R1 Broadcast 복사-후-호출 UAF 창. 락 안에서 콜백 벡터를 복사하고 락 밖에서 호출 — 순회 도중 컴포넌트가 파괴되면 Remove는 원본만 지우고 로컬 사본은 죽은 this를 호출한다 Delegate.inl:86–104 본 팔레트 UAF(1-1), EffectComponent null 프록시(1-5)와 동족
R2 즉시 파괴 — 지연 파괴 부재. 순회 중 Destroy가 실제 소멸로 이어질 수 있는 구조. 유니티(프레임 경계)·언리얼(GC 경계)이 원천 차단하는 그 창구 Scene.cpp DestroyGameObjects / DestroyComponents 씬 중복 등록 더블 delete (커밋 0361b228)
R3 재진입 불가 스핀락. Clear()의 swap 우회는 증상 치료 — 콜백 실행 중 같은 델리게이트에 Add/Remove가 재진입하는 다른 조합은 여전히 열려 있다 Delegate.inl:67–83 (주석 자체가 진단서) 종료 행 — Scene::~Scene의 AwakeEvent.Clear() (커밋 c712011f)
R4 매 프레임 전체 벡터 복사. Update/LateUpdate/FixedUpdate 브로드캐스트마다 std::function 벡터 통째 복사 + 우선순위 정렬 순서라 타입이 흩어진 순회 Delegate.inl:88–92 —
R5 isStopped_ 락 밖 읽기(형식상 data race), 예외를 std::cout 한 줄로 삼킴 Delegate.inl:98, 102 —

재평가 결론: 위험의 목록은 줄지 않았다 — 위험의 주인이 바뀌었다. 이전에는 "사용자 스크립트가 밟을 지뢰"였다면, 지금은 전부 엔진 자신이 밟는 지뢰다 (씬 전환·종료·프리팹 파괴 때마다). 그리고 주인이 엔진이라는 사실이 해법을 단순하게 만든다: 동적 구독이 필요 없는 고정 집합이므로, 델리게이트를 고칠 필요 없이 프레임 루프에서 빼면 된다. C# 쪽이 이미 증명한 모델(고정 경계 + 소유 리스트 일괄 순회)을 네이티브에도 똑같이 적용하는 것이다.

03목표 구조 — Scene 소유 생명주기 레지스트리

설계 원칙은 하나다: "Scene은 이미 답을 알고 있다." CollectMeshRenderer / CollectLightComponent / CollectColliderComponent… — Scene은 렌더·물리 대상에 대해 이미 "타입별 소유 리스트 + 등록/해제" 패턴을 쓰고 있고, 이 패턴에서는 사고가 나지 않았다. 생명주기도 같은 패턴으로 옮긴다.

3.1 구성 요소

① Component가 생명주기를 직접 소유

IRegistableEvent의 가상 훅(Awake~OnDestroy)을 Component 기본 클래스로 흡수. 유니티 MonoBehaviour 메시지 모델과 동일. CRTP 상속 26곳, enable_shared_from_this 혼합 상속, 다이아몬드 우회가 전부 사라진다.

② LifecycleMask — 판정은 한 곳에서 1회

"이 타입이 Update를 구현했나"는 지금의 if constexpr(&T::Update != …) 트릭을 ComponentFactory 등록 지점 한 곳으로 옮겨 타입당 1회 계산, Meta::Type에 비트마스크로 저장. 유니티가 리플렉션으로 하는 일을 컴파일 타임에 하는 것. final 함정은 마스크 계산을 "최종 등록 타입" 기준으로 하므로 소멸.

③ Scene이 단계 리스트를 소유

m_pendingAwake / m_pendingStart 큐 + m_updateList / m_lateUpdateList / m_fixedUpdateList. 원소는 Component* (소유는 기존대로 GameObject의 shared_ptr). 등록·해제는 swap-and-pop O(1), 해제는 프레임 경계에서만 일어나므로 순회 중 무효화가 불가능.

④ 지연 파괴 일원화

Destroy는 마킹만. 프레임 끝 단일 지점에서 OnDisable → OnDestroy → 리스트 제거 → erase. R1·R2가 클래스째 소멸한다 — "순회 중인 것이 죽는" 상황 자체가 표현 불가능해진다.

3.2 프레임 시퀀스

┌ 프레임 시작 │ pendingAwake 큐 소진 → Awake() 호출, 마스크 보고 update 리스트들에 편입, pendingStart로 │ pendingStart 큐 소진 → Start() │ ClrHost.TickAwake() ← C# 신규 스크립트 (기존 유지) │ │ [고정 스텝 루프] FixedUpdate 리스트 순회 → 물리 → ClrHost.TickFixedUpdate() │ Update 리스트 순회 → ClrHost.TickUpdate() → 코루틴 │ LateUpdate 리스트 순회 → ClrHost.TickLateUpdate() │ │ 프레임 끝 — 파괴 지점(유일) │ destroyQueue: OnDisable → OnDestroy → 리스트 swap-and-pop → GameObject에서 erase └ 렌더 스냅샷 · 순회 중 AddComponent → pendingAwake에 적재, 이번 프레임 순회에 끼어들지 않음 (재진입 안전) · 순회 중 Destroy → 마킹 + destroyQueue 적재, 리스트는 건드리지 않음 (무효화 안전) · SetEnabled(bool) → 상태 전이 시 OnEnable/OnDisable 직접 호출 + update 리스트 편입/이탈 (매 프레임 브로드캐스트 스캔 폐지 — 어차피 네이티브 구현 0곳)

3.3 스레드 규약

생명주기 API(AddComponent / Destroy / 리스트 순회)는 게임 스레드 전용으로 선언하고 락을 아예 두지 않는다. ClrHost가 이미 같은 규약이다("관리 코드 호출은 게임 스레드로 한정" — ClrHost.h:24). 크로스 스레드에서 오는 요청(AI future, 로더)은 프레임 시작에 소진하는 커맨드 큐로 받는다. 스핀락·재진입·데드락 문제는 락을 잘 잡아서가 아니라 락이 필요 없는 설계로 푼다.

3.4 Core::Delegate의 거취

삭제하지 않는다. sceneLoadedEvent, OnResizeEvent, 렌더 이벤트, 에디터 이벤트처럼 구독자가 진짜로 동적인 곳에서는 올바른 도구다. 다만 프레임당 N회 도는 뜨거운 경로에서 뺀다. 남는 사용처에 대해 R5(경합 읽기, 예외 삼킴)만 소규모 수리한다.

검증 계획

  • 기능 동등성: L-0의 CLI 시나리오(로드→플레이→전환→종료)가 각 단계 후 동일하게 통과. Awake/Start 호출 순서는 로그 대시보드로 전/후 diff.
  • 수명 안전: ASan 빌드로 씬 churn 반복 — 순회 중 파괴·재진입 케이스를 CLI 명령으로 강제 재현(플레이 중 Destroy 연타, Update 안에서 AddComponent).
  • 성능: scripts/scene_churn_benchmark 기준선 대비 — 기대 효과는 프레임당 벡터 복사 3회 제거 + Update 순회의 타입 지역성.

05하지 않는 것

  • 전면 ECS 전환 — 컴포넌트 26종 고정 집합에 아키타입 스토리지는 과잉. 지금 문제는 데이터 배치가 아니라 수명 규약이다.
  • C# 디스패치 변경 — ClrHost 고정 경계 모델은 이 재설계가 따라가는 기준이지 대상이 아니다.
  • Core::Delegate 전면 재작성 — 프레임 루프에서 빼는 것으로 충분. 시스템 이벤트용으로는 현행 유지 + L-5 위생 수리만.
  • 세대(generation) 핸들 도입 — 지연 파괴 + 게임 스레드 규약이 서면 리스트의 raw 포인터는 불변식으로 안전하다. 2-6 조사("핸들화는 과잉 설계로 판단해 보류")와 같은 판단. 크로스 스레드 참조가 생기는 시점에 재검토.

07부록 — .NET GC를 엔진 스케줄에 종속시키기

CoreCLR 도입으로 힙이 두 개가 됐다. 원칙은 본문과 같다: GC에 수명을 맡기지 않는다(세대 핸들 설계 유지). 대신 GC가 도는 시점을 엔진이 쥔다. 현재 ScriptCore.runtimeconfig.json은 순정 기본값(Workstation + Background GC)이고, GC를 의도적으로 쓰는 곳은 핫리로드 ALC 언로드 검증(ScriptAssemblyLoader.cs:150) 한 곳뿐이다. 아래 두 항목을 이 계획에 편입한다 — 합쳐서 0.5일 규모, L-0(안전망)과 함께 진행하는 것이 자연스럽다.

A-1. GC 스케줄링 — 씬 경계 Collect + 플레이 모드 LatencyMode

작업내용지점
씬 전환 시 확정 수집 GC.Collect(2, Forced, blocking: true) + WaitForPendingFinalizers. 파괴된 씬의 Behaviour 인스턴스·필드가 참조하던 관리 객체를 씬 경계에서 확정 회수 — 핫리로드가 이미 쓰는 패턴을 씬 언로드로 확장하는 것. UnloadUnusedAssets(2-8)와 같은 프레임 경계에서 실행해 네이티브·관리 힙이 같은 시점에 평탄해지게 한다 ClrHost::NotifySceneUnload 흐름 (관리 측 진입점에 추가)
플레이 모드 지연 모드 플레이 진입 시 GCSettings.LatencyMode = SustainedLowLatency(gen2 블로킹 수집 억제 → 프레임 스파이크 완화), 에디터 모드 복귀 시 Interactive로 원복. Bootstrap 두 줄 ScriptCore/Bootstrap.cs (플레이 시작/정지 알림 경계)

보류 항목: TryStartNoGCRegion(컷씬·스폰 버스트용)은 예산 산정이 필요하므로 A-2 계측 이후 별도 판단. Server GC 전환은 하지 않는다 — 관리 코드가 게임 스레드 하나에서만 도는 구조에서 이득이 거의 없고 메모리만 더 쓴다.

A-2. GC 계측 — 리소스 HUD 편입 (대시보드 2-9 직결)

작업내용지점
틱당 GC 지표 수출 GC.GetGCMemoryInfo()(힙 크기·pause 시간), GC.CollectionCount(0/1/2)를 틱당 1회 blittable 구조체로 경계 너머로 뽑는다 — 경계 통과 규약(틱당 고정 횟수)에 +1 ClrHost Tick 반환값 또는 전용 폴링 함수 1개
HUD·검증 연동 리소스 카운터 HUD(0-2)에 gen0/1/2 수집 횟수와 관리 힙 크기 표시. 씬 churn 벤치(2-9 "메모리 평탄성 검증")의 판정 기준에 관리 힙 평탄성을 추가 — "씬 전환 N회 반복 후 네이티브·관리 힙 모두 기준선 복귀"가 완료 조건이 된다 EngineResourceCensus / 리소스 HUD 오버레이

편입 위치: A-1·A-2는 L-0(안전망)과 함께 선행 실행한다. L-3의 씬 전환 churn 벤치가 "델리게이트 철거 전/후 비교"를 할 때 관리 힙 지표까지 같은 그래프에서 읽을 수 있어야 재설계 효과와 GC 효과를 분리해 판정할 수 있기 때문이다.

A-3. 구현 노트 (2026-08-07 · 9-6·9-7 반영)

진입점을 Bootstrap이 아니라 새 GcControl 타입에 뒀다. 성격이 스크립트 수명이 아니라 런타임 정책이고, Bootstrap은 이미 40개가 넘는 진입점을 담고 있어 "경계의 전부"라는 그 문서의 주장이 읽기 어려워지고 있었다. 바인딩은 선택 바인딩이다 — 이 타입이 없는 구 어셈블리에서는 GC 연동만 조용히 꺼지고 엔진은 그대로 뜬다.
