RHI 계층 추출

설계 방향

Device·CommandContext·Buffer·Texture·PipelineState·DescriptorSet·Fence·SwapChain을 순수 인터페이스로 추출하고 DX11 구현을 그 뒤로 옮긴다. 이것이 '별도 구현 후 교체' 전략의 전제다 — 상위 코드(패스·프록시·이펙트)가 RHI만 보게 되면 DX12는 새 백엔드 하나를 꽂는 일이 되고, 교체는 스위치가 된다. 주의 지점 둘. ① 전역 DeviceStates(g_pDevice·g_pDeviceContext·g_Viewport 등)를 직접 만지는 코드가 렌더 패스 전반에 퍼져 있다 — 이 전역 접근을 RHI 컨텍스트 인자로 바꾸는 것이 작업량의 본체다. ② DirectXTK(SpriteBatch·SpriteFont)에 UI 렌더가 얹혀 있다 — DX12용 DirectXTK12로 짝을 맞추되 UI 프록시가 RHI 위에서 양쪽을 같은 코드로 타게 한다. 완료 기준: RenderEngine에서 d3d11.h 직접 include가 백엔드 폴더 밖에서 0건.

슬라이스별 기록

1차 슬라이스 완료 — 경계와 검증 루프를 먼저 세웠다. ① RenderEngine/RHI/에 인터페이스 4종(RHIDefinitions·RHICommandContext·RHIDevice·RHI 접근점)과 DX11 백엔드(DX11RHI). 인터페이스 표면적은 첫 이식 대상이 요구한 최소만 — 미리 크게 그리면 DX12에서 검증 안 된 서명이 쌓인다. 리소스는 전환기 임시 핸들(RHINative*)로 나르고 저장 금지 규약을 명시했다. ② DX11 백엔드는 기존 DirectX11:: 자유 함수에 위임 — 드로우콜 카운트 등 부수 동작이 갈라지지 않게. ③ BlitPass를 첫 이식: 커맨드 기록이 전역 호출 대신 RHI 컨텍스트를 탄다. ④ 타이틀바의 하드코딩 '<Dx11>'을 RHI::Device().GetName()으로 교체 — 교체 스위치(3-9)의 확인 수단이 된다. 검증 도구 신설: Tools/regression/capture-window.ps1 — PrintWindow(PW_RENDERFULLCONTENT)로 구동 중인 엔진 창을 PNG로 캡처한다(엔진 내부 캡처가 게임 스레드에서 죽는 문제의 우회). 검증: 이식 전후 스크린샷을 타이틀바 제외 124,800 샘플 픽셀 대조해 차이 0(0.000%), 에디터 풀 렌더(씬 뷰 그리드·하이어라키·게임 뷰) 확인, 회귀 세트 전체 통과. 2차 슬라이스 — deferred 래핑 + 첫 deferred 패스 2종. ① DX11CommandContext가 네이티브 deferred 컨텍스트를 감싸도록 확장(널이면 immediate) — 모든 호출이 if(m_native) 분기로 deferred/immediate 자유 함수 오버로드에 위임. ② RHIDevice::WrapNativeDeferred 추가(전환기 임시 통로 — 커맨드 빌드 시스템이 RHICommandContext를 직접 넘기게 되면 제거). ③ 인터페이스에 상수 버퍼(VS/PS)·DepthStencilState·BlendState 추가 — 두 패스가 요구한 만큼만. 상태 두 호출은 DX12에서 PSO에 흡수되므로(3-4) 이식 후 제거될 후보임을 명시. ④ UIPass·SpritePass의 커맨드 기록을 RHI 경유로 이식. SpritePass는 자유 함수와 deferredPtr-> 직접 호출이 섞여 있었는데(직접 호출은 드로우콜 카운트를 우회) RHI로 통일하며 그 우회도 제거. 검증: 기준선 대비 픽셀 차이 0(124,800 샘플) · 회귀 세트 전체 통과 — ui_regression의 캔버스+텍스트+이미지+재생 4회가 UIPass의 이식된 기록 경로를 실행한다. 한계를 명시: 폰트(.spritefont)·UI 텍스처가 저장소에 없어 가시 픽셀 검증은 실게임 에셋 환경 몫이고, SpritePass는 스프라이트시트 에셋 부재로 실행 경로가 노출되지 않았다(위임이 1:1 기계 변환임을 근거로 수용). 3차 슬라이스 — 컴퓨트 표면 + 포스트 패스 2종. ① 인터페이스에 컴퓨트 계열(셰이더·샘플러·SRV/UAV·상수 버퍼·Dispatch)과 UpdateBuffer·ClearRenderTarget 추가. UpdateBuffer는 ' 프레임 안에서 유효한 일회성 갱신'만 계약으로 삼는다고 명시 — DX12에서 업로드 링버퍼 복사가 되기 때문. CopyResource는 이번 배치가 안 써서 미룸(원칙 유지). ② BitMaskPass 이식 — 순수 컴퓨트 패스라 새 표면 전체를 지나간다. ③ SSAOPass 이식 — SceneRenderer의 커맨드 빌드가 이 패스를 매 프레임 무조건 부르므로(1024행) 에디터 씬 렌더 자체가 이식 경로의 실행 증명이고, 스크린샷 대조가 곧 기능 검증이 된다. 검증: 기준선 대비 픽셀 차이 0(124,800 샘플) · 회귀 세트 전체 통과. 4차 슬라이스 — CopyResource 표면 + 포스트체인 3종(SSGI·SSR·SubsurfaceScattering) 이식. SSGI가 이 배치의 본체다(컴퓨트 6디스패치·듀얼 필터링 2단). SSR의 히스토리 텍스처 복사 2건이 CopyResource의 첫 사용처 — 렌더그래프(3-5)에서 복사 노드가 될 지점이라고 주석에 표시했다. 함정 하나를 밟았다: 변수명을 cbuffer로 지었더니 BaseTypeDef.h의 '#define cbuffer struct alignas(16)'(HLSL 스타일 상수 버퍼 선언용 매크로)가 확장돼 구문 오류가 났다 — 이 매크로가 렌더 코드 전역에 살아 있으므로 RHI 이식 중 변수명으로 cbuffer·row_major 같은 HLSL 예약어를 쓰면 안 된다. 검증: 기준선 대비 픽셀 차이 0(124,800 샘플) · 회귀 세트 전체 통과. SSGI·SSAO는 매 프레임 실행 경로라 스크린샷 대조가 기능 검증이고, SSR·SSS는 isOn 게이트가 있어 기본 씬에서 미노출(기계 변환 + 컴파일 검증만). 5차 슬라이스 — 본체 패스 4종(GBuffer·Deferred·ShadowMap 캐스케이드/일반·Forward) 이식. 표면 추가 3종: SetVertexShaderResources · ClearDepthStencil(플래그 대신 bool 두 개 — API 상수를 인터페이스에 노출하지 않는다) · UpdateBufferRange(인스턴스 행렬의 바이트 구간 갱신, DX11 box UpdateSubresource ↔ DX12 업로드 복사). 함께 단일 슬롯 편의 오버로드 8종(비가상)을 얹었다 — 배열 인자는 T* const* → void* const* 변환이 안 돼 호출부마다 임시 핸들 변수가 필요했는데, 단일 슬롯은 값 전달이라 그대로 들어간다. 머티리얼 텍스처 바인딩(한 슬롯씩 5장)이 GBuffer·Forward에 수십 곳이라 이것 없이는 이식 소음이 심했다. GBuffer·Forward는 패턴이 균일해 스크립트 치환으로 이식(치환 후 잔여 호출을 grep으로 전수 확인 — 배열 케이스만 수동). 검증: ① 캔버스 씬 기준선 대비 픽셀 차이 0(124,800 샘플) ② 모델 씬 신설 — Gunner 모델을 배치해 스킨드 메시가 이식된 GBuffer 애니메이티드 경로(본 버퍼·머티리얼 5텍스처)→Deferred 라이팅→Blit 체인으로 정상 렌더됨을 스크린샷으로 확인(텍스처·노멀·림 라이트까지 눈으로 검증) ③ 회귀 세트 전체 통과 — ui_regression이 같은 모델을 배치하고 재생 4회를 돌므로 섀도·GBuffer 기록 경로가 플레이 모드에서도 크래시 없이 돈다. 함정 하나: CLI wait는 초가 아니라 프레임 단위다(±140fps) — 캡처 타이밍을 잡을 때 wait 3000 ≈ 21초로 계산해야 한다. 6차 슬라이스 — 잔여 deferred 패스 5종(SkyBox·Decal·VolumetricFog·LightMap·TerrainGizmo) 이식으로 deferred 커맨드 기록 경로의 이식이 완료됐다. 표면 추가: 입력 조립 3종(SetVertexBuffer·SetIndexBuffer·SetPrimitiveTopology — DecalPass의 데칼 박스 메시가 첫 사용처). 인덱스 포맷은 DXGI 상수 대신 use32BitIndices 하나로, 토폴로지는 D3D11/12 공통 부분집합 enum으로 받아 API 상수 비노출 규약을 유지했다. 5개 파일을 축적된 패턴 라이브러리(치환 규칙 20여 개)로 일괄 변환 후 잔여를 grep 전수 확인 — 이번 슬라이스는 수동 수정이 배열 캐스트 몇 곳뿐일 만큼 패턴이 안정됐다. 의도적으로 DX11에 남긴 것: PSO Apply(3-4에서 흡수) · FinishCommandList(커맨드 리스트 모델 자체가 DX12에서 다름) · 프록시 드로우 내부(Mesh::Draw) · RenderDebugManager 캡처. 검증: 캔버스 씬 픽셀 차이 0 · 모델 씬 5차 캡처 대비 차이 3/124,800(0.002% — 애니메이션 포즈 시차로 인한 노이즈) · 회귀 세트 전체 통과. 7차 슬라이스(구조 전환) — CreateRenderCommandList 서명을 ID3D11DeviceContext*에서 RHICommandContext&로 교체했다. 이제 패스는 그래픽 API를 직접 받지 않는다: SceneRenderer의 커맨드 빌드 람다 12곳과 LightController(섀도 경로)가 DX11CommandContext를 스택 생성해 넘기고, 패스별로 흩어져 있던 WrapNativeDeferred 임시 통로 17곳은 헤더에 약속한 대로 함수째 제거됐다(프레임당 힙 할당 17건도 함께 소멸). 아직 네이티브가 필요한 잔존 경로(PSO Apply·FinishCommandList·프록시 드로우 내부·카메라 버퍼 갱신)는 context.GetNativeHandle() 탈출구로 얻는다 — 이 호출부 수(현재 19곳)가 곧 남은 이식량이며 0이 되는 날 탈출구도 제거된다는 계약을 헤더에 명시했다. 프레임 스냅샷 기반 게임/렌더 스레드 동기화

설계 방향

현재 구조는 게임 스레드 + CB(커맨드 빌드) + CE(커맨드 실행) 스레드가 renderBarrier 2-랑데뷰로 락스텝 동기화된다(Dx11Main::Update). 같은 프레임 데이터를 세 스레드가 공유하므로 씬 구조 변경 같은 작업은 배리어 사이 구간에만 안전하고(3-0에서 실증), 리사이즈는 플래그 폴링으로 우회한다. 이를 프레임 스냅샷(더블 버퍼) 프로듀서-컨슈머로 바꾼다: 게임 스레드가 프레임 N의 렌더 입력(트랜스폼·가시성·머티리얼 파라미터)을 스냅샷으로 밀봉해 넘기고, 렌더 스레드는 N-1 스냅샷을 소비한다. 락스텝이 풀리므로 게임 로직과 렌더가 겹쳐 돌고, 씬 구조 변경은 '다음 스냅샷부터 반영'으로 자연 해결된다. 이 모델은 DX12의 인플라이트 프레임(2~3개) 구조와 정합해 3-3의 전제가 된다. 기존 ProxyCommand가 이미 절반쯤 스냅샷 역할을 하므로 이를 공식화하는 방향으로 간다. 카메라 수명·패스별 커맨드 큐 정리(구 3-3)는 스냅샷 수명에 흡수된다.

슬라이스별 기록

1차 슬라이스 완료 — 렌더 스레드가 게임 소유 Camera를 쓰던 경로 제거. 발견: ShadowMapPass가 매 프레임 camera.m_cascadeEnd를 clear()+push_back()으로 갈아엎고 camera.m_cascadeinfo[i]에 결과를 썼다. 공유 객체의 std::vector를 렌더 스레드가 재할당하는 구조라 게임 스레드가 같은 카메라를 만지는 순간과 겹치면 그대로 힙 손상이고, 두 경로(캐스케이드/일반)가 같은 벡터를 갈아엎기까지 했다. PHASE 3-2 직전에 잡은 종료 구간 힙 손상과 같은 부류다. 한 일: ① 캐스케이드 스크래치(m_cascadeEnd·m_cascadeInfo)를 RenderPassData로 이관하고 Initalize에서 크기를 미리 잡아 매 프레임 재할당이 없게 했다. ② DevideCascadeEnd/DevideShadowInfo가 RenderPassData 참조를 받고 카메라에서는 읽기만 한다. ③ 프러스텀·역뷰 계산이 살아있는 카메라 재계산 대신 프레임 밀봉된 m_frameCalculatedProjection/View를 쓴다 — 스냅샷 방향의 첫 걸음이다. ④ VolumetricFogPass도 렌더 측 캐스케이드를 읽는다. ⑤ 게임 카메라에서 m_cascadeEnd 제거. 검증 방법을 바꿔야 했다: 스크린샷 대조는 같은 빌드로 두 번 찍어도 8.8%가 어긋나(에디터 창의 FPS·프로파일러·로그 패널) 신호 6.4%보다 노이즈가 컸다. 대신 render.shadowinfo CLI를 만들어 계산값을 직접 대조했다 — 카메라 2대 x 캐스케이드 3단의 분할값·eye·look·near·far·폭·높이와 광원 뷰프로젝션 16성분 전부, 토큰 231개 중 229개가 완전 일치했고 두 실행 재현성도 확인했다. 다른 2개는 버그 수정이다: 일반 그림자 경로가 상수를 camera.m_shadowMapConstant에 썼는데 셰이더에 올라가는 것은 렌더 소유 m_shadowCamera 쪽이라 죽은 쓰기였고, 그 결과 useCasCade가 초기화되지 않은 0xCDCDCDCD(-842150451) 상태로 GPU에 올라가고 있었다. 캐스케이드 경로와 같은 곳에 쓰도록 맞춰 1이 된다. 기본값이 켜짐이라 화면에는 드러나지 않았지만, 캐스케이드를 끄면 셰이더가 여전히 0이 아닌 값을 봤다. 회귀 세트 전체 통과. 남은 것: 렌더 스레드의 살아있는 카메라 읽기 43곳을 스냅샷으로 돌리는 일, 그 다음이 락스텝 해제다. 3차 슬라이스 완료 — 카메라 소유 D3D 상수 버퍼 이관. 렌더링 대상 카메라의 뷰·투영 상수 버퍼(Camera::m_ViewBuffer·m_ProjBuffer)를 열일곱 곳이 각자의 deferred 컨텍스트에서 갱신하고 있었다. 게임 소유 객체의 GPU 리소스를 렌더 스레드가 만지는 구조였고, 값이 같아서 드러나지 않았을 뿐 소유자가 없는 상태였다. RenderPassData가 Initalize에서 만들어 두고 쓰지 않던 같은 이름의 버퍼로 옮기고, BindFrameCameraBuffers(RHICommandContext&) 하나로 통일했다 — 값은 프레임 밀봉 스냅샷에서 온다. deferred 14곳은 패스가 이미 들고 있는 RHI 컨텍스트를, 아직 RHI 이식 전인 즉시 경로 3곳(ColorGrading·Vignette·WireFrame)은 RHI::Immediate()를 쓴다. Camera::DeferredUpdateBuffer는 호출부가 0이 되어 제거했다 — 게임 소유 카메라의 GPU 버퍼를 렌더 스레드가 갱신하던 유일한 통로였다. GizmoLinePass의 ConvertScreenToWorld도 스냅샷 역행렬을 쓰도록 RenderPassData로 옮겼다(Camera 쪽은 역행렬을 그 자리에서 다시 구한다). 검증: 이 변경은 '어느 버퍼에 쓰느냐'를 바꾸므로 누락이 있으면 화면이 무너진다 — 3-2 착수 전 기준선 스크린샷과 나란히 놓고 확인했고 구도·음영·그리드까지 동일했다(타이틀바 FPS만 다름). live-vs-snapshot 대조 delta 0 유지, 회귀 세트 전체 통과. 이제 렌더 스레드가 게임 카메라에서 읽는 것은 m_cameraIndex(21)·m_avoidRenderPass(9)·m_cascadeDevideRatios(1)뿐이고, 셋 다 프레임 중 바뀌지 않는 식별자·저작 값이다. 쓰기는 0건. 다음이 락스텝(배리어 2-랑데뷰) 해제다. 4차 슬라이스 — 락스텝 비용 측정. 배리어를 걷어내는 일은 크고 위험해서 '얼마나 손해인가'를 먼저 쟀다. Barrier에 도달/실제대기/대기시간 계측을 넣고 render.syncstats로 뽑는다. 실측(600프레임 구간, Debug 빌드): 도달 3612회 중 66.7%가 실제로 대기(랑데뷰마다 3스레드 중 2개가 기다린다는 뜻), 세 스레드 합산 6.13ms/프레임. 프레임이 약 6.7ms이므로 기다리는 스레드는 프레임의 약 46%를 배리어에서 보낸다. 곁가지로 대기 방식을 A/B 했다: 512회 스핀 후 std::this_thread::yield()로 양보하는 방식은 더 나빴다 — 같은 600프레임 구간에서 벽시계 17.99s→19.02s(+5.7%), 대기 6.13→7.46ms/프레임(+22%). 재스케줄 지연이 절약한 코어 시간보다 컸다. 되돌리고 순수 스핀을 유지하되, 판단 근거를 주석에 남겼다. 해체가 한 단계로 끝나지 않는 이유: 배리어는 두 가지 일을 겸한다 — (a) 렌더가 게임 상태를 중간에 읽지 않게 하는 일관성, (b) 게임이 앞서 나가지 못하게 하는 페이싱. 1~3차 슬라이스가 (a)를 카메라에 대해 걷어냈지만, 배타 구간(랑데뷰 1~2 사이)에 남은 ApplyPendingSceneStructureChange는 여전히 배타성이 필요하고(PHASE 3-0에서 실증), EndOfFrame의 스냅샷 쓰기는 아직 제자리 갱신이라 CB가 동시에 읽으면 경합이다. 남은 순서: ① 스냅샷 이중 버퍼 + 게시(제자리 갱신 제거) ② 배타 구간을 씬 구조 변경이 있는 프레임에만 조건부로 ③ 프레임 인플라이트 상한으로 페이싱 대체 후 배리어 제거. 5차 슬라이스 — 스냅샷 이중 버퍼(①) 완료, 배타 구간 조건부화(②)는 측정 결과 보류. ①: FrameCameraSnapshot 구조체를 신설하고 RenderPassData가 두 벌을 들도록 했다. 게임 스레드가 뒷면을 채우고 release로 게시하면, 커맨드 빌드 스레드가 프레임 시작에 acquire로 한 번 래치해(LatchFrameSnapshot) 그 프레임 내내 같은 면만 읽는다. 매 읽기마다 게시 인덱스를 다시 보면 같은 프레임 안에서도 패스마다 다른 카메라를 볼 수 있어서 래치를 한 곳으로 모았다. 호출부 21개 파일을 GetFrameSnapshot() 경유로 전환. 검증: live-vs-snapshot delta 0 유지, 캐스케이드 16항목 동일, 회귀 전체 통과. ②는 하지 않았다 — 랑데뷰별로 갈라 재 보니 근거가 무너졌다. 배타 구간(랑데뷰2) 대기는 0.586~0.650 ms/프레임으로 전체 대기의 9.9%뿐이고, 90%는 랑데뷰1(가장 느린 스레드 대기)이다. ②는 EndOfFrame의 프레임 인덱스 게시·DisableOrEnable까지 동시성 안전하게 만들어야 하는 큰 변경인데 회수 가능한 몫이 10%다. 역할별로 더 갈라 보니 원인이 분명해졌다: 커맨드 실행(CE) 스레드가 95% 프레임에서 마지막 도착자이고 자신은 0.054 ms/프레임만 기다린다. 게임(2.59ms)과 커맨드 빌드(2.90ms)가 CE를 기다리는 구조다. Present1(0, ...)이라 VSync는 꺼져 있으므로 CE 자신의 작업(커맨드 실행 + Present)이 프레임을 정한다. 세 스레드는 이미 파이프라인으로 도는데 처리량은 가장 느린 단계로 정해지므로, 배리어를 걷어내도 처리량은 그 5.5ms를 회수하지 못한다 — 그 시간은 병목이 아닌 단계의 여유(slack)다. 결론: 락스텝 해제의 이득은 CPU가 병목일 때 나타난다. 지금은 CE가 병목이므로 순서를 바꾼다 — 3-3(DX12 인플라이트 2~3프레임)과 CE 단계의 작업 분해가 먼저이고, 배리어 제거는 그 뒤에 재측정해 판단한다. ①은 그때 필요한 전제라 남는 값어치가 있다. 계측 수단(render.syncstats: 랑데뷰별·역할별 대기와 마지막 도착자)은 그대로 두어 재판단에 쓴다. 확정: 배리어 제거는 3-9(렌더러 교체) 이후로 미룬다. 지금 걷어내도 처리량은 CE 단계에 묶여 있고, DX12로 CE 단계가 열린 뒤라야 게임·커맨드빌드의 여유가 실제 이득으로 바뀐다. 그 시점에 render.syncstats를 다시 재서 랑데뷰1 대기가 여전히 크면 그때 걷어낸다. 참고로 컬 데이터 버퍼(m_findProxyVec 등)는 이미 3중 버퍼에 프레임 인덱스로 N-2를 소비하고 있어 ③의 형태가 부분적으로 존재한다. 2차 슬라이스 완료 — 렌더 스레드의 살아있는 카메라 '값 읽기' 42곳을 스냅샷으로 돌렸다. 스냅샷에 역뷰·역투영·eye·forward·right·up·fov·near·far·직교여부를 추가하고 UpdateData가 게임 스레드에서 한 번에 채운다. 역행렬을 미리 담은 이유는 여러 패스가 같은 XMMatrixInverse를 매 프레임 다시 구하고 있었기 때문이다(CalculateInverseView는 정의상 CalculateView의 역행렬이라 값이 같다). 전환한 곳: GizmoLine·Gizmo·Grid·SSAO·WireFrame·SkyBox·SubsurfaceScattering·LightMap·SSR·VolumetricFog·Sprite·ParticleSystem·Mesh(LOD 판정)·RenderScene(ShadowStage)·ShadowMapPass. GetGizmoScale은 Camera 대신 RenderPassData를 받도록 서명을 바꿨다. 검증: render.shadowinfo에 live-vs-snapshot 대조를 넣어 스냅샷이 살아있는 카메라와 같은 값인지 직접 쟀다 — 행렬·eye·fov·near·far 전부 delta 0.000000000(카메라 2대). 캐스케이드 출력 16개 항목도 1차 결과와 완전 일치. 회귀 세트 전체 통과. 남은 것은 '값 읽기'가 아닌 다른 부류다: ① DeferredUpdateBuffer/UpdateBuffer 17곳이 카메라 소유 D3D 상수 버퍼(m_ViewBuffer·m_ProjBuffer)에 렌더 스레드에서 쓴다 — RenderPassData에 이미 같은 이름의 버퍼가 준비돼 있어 그쪽으로 옮기는 것이 다음 슬라이스다. ② m_cameraIndex 21곳·m_avoidRenderPass 9곳은 프레임 중 바뀌지 않는 식별자·저작 플래그다. 그 다음이 락스텝(배리어 2-랑데뷰) 해제다.

DX12 디바이스 브링업 (EnhancedSceneRenderer 골격)

설계 방향

DeviceResources12: 디바이스·커맨드 큐·스왑체인·디스크립터 힙(CBV/SRV/UAV·RTV·DSV·샘플러)·프레임 펜스·업로드 링버퍼. 인플라이트 프레임 2~3개와 프레임당 커맨드 얼로케이터 회전. 렌더러 클래스는 EnhancedSceneRenderer로 신설한다 — 기존 SceneRenderer를 건드리지 않고 병존하며, 상위(Dx11Main)는 두 렌더러를 같은 인터페이스로 부른다. DX11이 암묵으로 해 주던 것들(리소스 상태 추적, 수명 관리, 바인딩 슬롯)이 전부 명시 책임이 되는 지점이라, 여기서 얇게라도 규약을 세워야 이후 패스 이식이 흔들리지 않는다. 완료 기준: 기존 에디터 창 안에서 EnhancedSceneRenderer가 DX12 삼각형 + 텍스처 블릿을 프레임 펜스 검증(GPU 검증 계층 클린)과 함께 그린다. 구 3-4(DX11 GPU 동기화의 ID3D11Query 구현)는 펜스 모델이 대체하므로 하지 않는다.

슬라이스별 기록

1차 슬라이스 완료 — DX12 코어가 실제로 돈다. RenderEngine/RHI/DX12/에 DX12DeviceResources(디바이스·큐·얼로케이터 3개·펜스·RTV 힙·오프스크린 타깃·리드백 버퍼)와 EnhancedSceneRenderer 골격을 신설했다. 스왑체인은 만들지 않았다 — 창은 DX11이 점유 중이고 병존 기간의 출력 경로는 3-9에서 결정한다. 대신 오프스크린 + 리드백으로 렌더 결과를 파일로 꺼낸다: 픽셀이 곧 증거다. 검증 수단은 dx12.selftest CLI — 자체 디바이스로 돌므로 DX11 렌더 스레드와 충돌하지 않는다. 통과 조건 4단계: ①디바이스·큐·펜스·타깃 생성 ②루트 시그니처·PSO 생성(D3DCompile 인라인 셰이더, SV_VertexID 삼각형) ③6프레임 제출·완료(얼로케이터 3개 × 2회전 — BeginFrame의 펜스 대기가 인플라이트 회전을 증명) ④리드백 픽셀 검증(삼각형 내부 ≠ 배경, 구석 = 클리어 기대값) + PNG 저장 + 검증 레이어 메시지 0건. 최종 실행: 4단계 전부 통과, PNG에서 RGB 보간 삼각형 확인, DX11 회귀 세트 무영향. 검증 과정에서 잡은 것 3건이 이 슬라이스의 실질 수확이다: ① 내 픽셀 단정이 틀렸던 오탐('파랑 우세' 느슨한 가정 → 기대값 비교로 교체. 렌더는 맞는데 검사가 틀리는 부류) ② 검증 레이어의 클리어 값 규칙 실측 — 힌트와 다른 값도, 힌트 없음도 경고를 쌓는다. 클리어 색을 kClearColor 상수 하나로 고정해 해결. 실전 타깃(3-5 transient)도 같은 규칙을 따라야 한다 ③ near/far가 windef.h 매크로라 식별자로 못 쓴다(cbuffer에 이어 두 번째 매크로 함정). 2차 슬라이스 — 텍스처 블릿 완료로 완료 기준의 렌더 부분(삼각형 + 텍스처 블릿 + 펜스 검증 + 검증 레이어 클린)이 충족됐다. 추가된 것: SRV 디스크립터 힙(셰이더 가시), 정적 샘플러 루트 시그니처(샘플러 힙 없이 블릿을 증명 — 실전 샘플러 힙 설계는 3-4 몫), 업로드 힙 → CopyTextureRegion → PIXEL_SHADER_RESOURCE 전이의 전용 업로드 사이클(렌더 프레임과 분리해 실패 지점을 격리), 4x4 체커보드(64px, 행 256바이트 = 업로드 정렬과 정확히 일치하는 크기 선택)를 쿼드로 그려 셀 2점의 픽셀을 기대색과 대조. 최종 PNG: 삼각형 + 체커 쿼드 동시 렌더 확인. 부수 수확: 회귀 검사기의 구멍을 막았다 — ui_regression에서 프로브가 전부 통과하고도 종료 시점 힙 손상(0xC0000374)으로 죽은 실행이 '전체 통과'로 지나갔다(간헐, 3회 재실행 무재현 — 기존 종료 크래시 부류로 별건 작업에 이관돼 있음). run-all.ps1이 이제 종료 코드도 판정에 넣는다: 간헐 크래시는 검사를 흔들리게 만들지만 숨겨지는 것보다 낫다. 남은 것: 에디터 창 내 출력 경로(3-9의 병존 출력 결정과 연동), 업로드 링버퍼(현재는 단발 업로드 버퍼 — 씬 이식 시 필요). 3차 슬라이스 — 업로드 링버퍼 완료. 브링업에서는 텍스처마다 CreateCommittedResource로 업로드 버퍼를 만들고 GPU가 다 읽을 때까지 살려 뒀는데, 씬을 이식하면 프레임당 수십~수백 건이 되어 생성 비용과 수명 관리가 양쪽으로 무너진다. DX12UploadRing 신설: 큰 버퍼 하나를 인플라이트 프레임 수만큼의 고정 구간으로 나누고 프레임 i는 구간 i만 쓴다. 반납을 펜스 추적이 아니라 구조로 보장하는 것이 요점 — DX12DeviceResources::BeginFrame이 이미 그 슬롯의 펜스를 기다린 뒤 진입하므로, 구간 i에 다시 손대는 시점에는 GPU가 다 읽은 것이 보장된다. 그래서 링을 DeviceResources 안에 두고 BeginFrame이 되감게 묶었다(따로 들고 다니면 그 계약이 호출부 규율이 되고 한 곳만 어겨도 GPU가 읽는 중인 데이터를 덮는다). 정렬은 호출부가 용도에 맞춰 넘긴다 — 상수 버퍼 256, 텍스처 배치 512. 기본값 하나로 두면 둘 중 하나가 조용히 틀린다. 구간이 모자라면 무효를 돌려주고 세어 둔다 (조용히 다음 구간을 침범하면 '다음 프레임에 가끔 이상한 것이 보인다'로만 드러나 추적이 어렵다). 자가 검증 dx12.uploadring 신설 — 링의 계약은 눈에 보이지 않아서 직접 단정해야 한다: ①정렬(어긋난 크기를 섞어 요청해도 오프셋·GPU 주소가 정렬) ②프레임 구간 분리(할당이 자기 구간을 벗어나지 않음) ③되감기(6프레임을 돌려도 사용량이 누적되지 않음: 4096B → 4096B) ④넘침 거절(구간보다 큰 요청은 무효, 거절 뒤에도 정상 할당은 성공) ⑤GPU 도달(링 → CopyBufferRegion → 리드백, 1024바이트 불일치 0). 앞의 넷은 CPU 계산이라 ⑤가 없으면 '계산은 맞는데 GPU에는 안 닿는' 경우를 못 잡는다. 체커보드 텍스처 업로드를 링 경유로 바꿨고 dx12.selftest도 그대로 통과. 부수 수확: 검증 레이어가 내 테스트 코드의 실수를 잡았다 — 버퍼는 초기 상태 지정이 무시되고 항상 COMMON으로 만들어지는데 COPY_DEST를 넘기고 있었다. 같은 실수가 DX12DeviceResources의 리드백 버퍼에도 있어 함께 고쳤다. 동작은 같지만(첫 사용 시 암묵 승격) 경고가 쌓이면 진짜 문제가 묻힌다. 회귀 세트 전체 통과. 남은 것: 에디터 창 내 출력 경로 — 3-9의 병존 출력 결정, 그리고 당시 별도 에디터 셸 계획에서 다루던 렌더 표면 계약과 같은 문제다. 에디터 셸이 Qt로 가면 뷰포트 위젯마다 스왑체인이 필요하고 자체 UI로 가면 스왑체인 하나에 UI까지 합성하게 되므로, 셋을 따로 정하면 반드시 되돌리게 된다. 셋을 함께 결정한다. ★ 출력 경로 결정(3-3 미결 해소, 3-9 공동). 코드를 읽어 보니 전제가 달랐다 — 에디터의 씬 뷰·게임 뷰는 스왑체인에 직접 그리지 않는다. RenderPassData::m_renderTarget의 SRV를 ImGui::Image로 표시한다(SceneViewWindow.cpp:194, GameViewWindow.cpp:53). 백버퍼에 직접 그리는 것은 최종 BlitPass와 게임 빌드 경로뿐이다. 따라서 병존 기간에 DX12는 스왑체인이 필요 없고, 필요한 것은 '＇DX12가 그린 텍스처를 DX11이 SRV로 여는 것'＇ 하나다. 결정: 공유 텍스처(D3D12_HEAP_FLAG_SHARED → CreateSharedHandle → ID3D11Device1::OpenSharedResource1 → SRV). 이 계약의 좋은 점은 셸 선택과 무관하다는 것이다 — 렌더러는 '＇텍스처를 만들어 내놓는다'＇로 고정되고, 그것을 ImGui가 합성하든 Qt 위젯이 표시하든 자체 UI가 그리든 상관없다. 렌더 표면 계약의 답이 여기서 나온다. 실증 dx12.sharedtexture 신설 — 4단계 전부 통과: ①어댑터 LUID 일치 ②DX12가 공유 텍스처에 기록 ③DX11이 SRV로 열기 ④DX11로 되읽어 픽셀 대조(4096픽셀 불일치 0). 검증 중 잡은 것: DX11은 기본 어댑터(D3D11CreateDevice에 nullptr)를, DX12는 고성능 우선을 고르고 있었다. 공유는 같은 물리 어댑터에서만 성립하므로 iGPU+dGPU 장비에서는 이 불일치만으로 경로가 깨진다 — DX12DeviceResources::Initialize가 LUID를 받아 맞추도록 고쳤다(정책을 맞추는 것으로는 부족하고 같은 어댑터임을 확인해야 한다). 소멸 시점도 함께 정했다: 이 경로는 병존 전용이다. 지금 공유가 필요한 이유는 창과 ImGui가 DX11에 묶여 있어서고, 교체(3-9) 후에는 DX12가 스왑체인을 갖고 에디터 셸 전환 여부와 무관하게 공유할 이유가 없어진다. GetNativeHandle()과 같은 부류의 전환기 장치이며, 3-9에서 RunSharedTextureTest와 공유 경로를 함께 제거하는 것이 계약이다. 남은 것: 실전 동기화 — 지금은 WaitForGpu로 완전 대기하지만 프레임을 겹치려면 공유 펜스(D3D12_FENCE_FLAG_SHARED + ID3D11Fence + ID3D11DeviceContext4::Wait)가 필요하고, 그 설계는 패스 이식(3-6)에서 붙인다.

PSO 중앙 관리 + 캐시

설계 방향

PSOManager 신설: (셰이더 조합 + 래스터/블렌드/뎁스 상태 + RT 포맷 + 루트 시그니처) 해시 → ID3D12PipelineState. 현재 ShaderSystem의 ShaderPSO/VisualShaderPSO는 이름만 PSO인 DX11 셰이더 묶음이라 상태 객체 개념이 없다 — 이름 충돌부터 정리하고 셰이더 리로드(기존 핫리로드 경로)와 연결한다. 캐시 2층: 메모리(해시맵) + 디스크(ID3D12PipelineLibrary, 드라이버·셰이더 해시 무효화 포함). 프레임 중 미스는 비동기 컴파일로 돌리고 완성 전 프레임은 폴백 PSO 또는 스킵 — 컴파일 스톨을 프레임에서 격리하는 것이 목적이다. 완료 기준: 두 번째 실행에서 PSO 컴파일 0건(전부 라이브러리 히트), 히트/미스 카운터 노출.

슬라이스별 기록

1차 슬라이스 완료 — 완료 기준('두 번째 실행에서 PSO 컴파일 0건')을 실측으로 충족했다. DX12PSOManager 신설: 해시 키(FNV-1a 64 — 셰이더 바이트코드 내용 + 래스터/블렌드/뎁스 + RT 포맷 + 루트 시그니처 식별자) → PSO. 셰이더를 내용으로 해시하므로 핫리로드 시 자동으로 다른 키가 된다 — 캐시 무효화와 리로드가 같은 메커니즘이다. 캐시 2층: 메모리(해시맵, 같은 실행 내 중복 제거) + 디스크(ID3D12PipelineLibrary). 드라이버·어댑터 변경 시 CreatePipelineLibrary가 실패하고 빈 라이브러리로 시작한다 — 무효화 판정을 런타임에 맡기는 쪽이 직접 버전을 추적하는 것보다 정확하다. 라이브러리 이름은 해시에서 유도해 실행 간 안정적으로 만들었다(포인터는 쓸 수 없다). 비동기 경로: Request()가 미스면 std::async로 컴파일을 걸고 Pending을 돌려준다 — 그 사이 프레임은 폴백 PSO를 쓰거나 드로우를 건너뛴다. 목적은 컴파일 스톨을 프레임에서 격리하는 것. Shutdown이 진행 중인 future를 전부 회수한 뒤 해제한다. dx12.psocache CLI로 3층 전부 검증: ①상태만 다른 변형 3종의 해시가 서로 달라 상태 차이를 실제로 구분 ②1회차 컴파일 3 → 캐시 저장 → 2회차 컴파일 0 · 라이브러리 히트 3 · 메모리 히트 3 ③비동기 Pending → Ready. 나아가 selftest도 매니저 경유로 바꿔 프로세스 재실행에서 측정: 1회차 컴파일 2 · 라이브러리 히트 0 → 2회차 컴파일 0 · 라이브러리 히트 2. 같은 프로세스 안이 아니라 실제 재실행에서 확인한 값이다. 검증 인프라 수확: 검증 레이어 판정을 두 번 고쳤다. 처음엔 메시지를 전부 세다가 '라이브러리에 그 이름이 없음'(=캐시 미스, 설계된 정상 경로)이 실패로 둔갑했다. 심각도 필터를 넣었더니 이 메시지가 WARNING이라 여전히 걸렸고, 결국 D3D12_MESSAGE_ID_LOADPIPELINE_NAMENOTFOUND 하나만 StorageFilter로 억제했다 — 심각도를 통째로 낮추면 진짜 문제까지 숨는다. 억제 목록이 길어지는 것 자체가 신호이므로 항목마다 '왜 정상인지'를 코드에 남기는 규약을 세웠다. 2차 슬라이스 — 잔여 3종 완료. ① 컴퓨트 PSO: 그래픽과 같은 캐시 2층을 공유하되 해시 시드에 태그를 섞어 종류가 섞이지 않게 했다(같은 바이트 배열이 우연히 나와도 안전). 검증: 1회차 컴파일 1 → 2회차 컴파일 0 · 라이브러리 히트 1. ② 폴백 정책: SetFallback + Resolve()가 '비동기 컴파일 중인 프레임에 무엇을 그릴지'에 답한다 — 폴백이 있으면 UseFallback, 없으면 Skip. 어느 쪽이든 프레임이 컴파일을 기다리지 않는 것이 핵심이며, fallbackDraws/skippedDraws 카운터로 관측 가능하게 했다(폴백이 계속 늘면 캐시가 놀고 있다는 신호). 검증: 컴파일 중 폴백 1회 → 완료 후 요청 PSO로 전환 · 스킵 0. ③ 셰이더 리로드 연결: OnShaderReloaded()가 진행 중인 컴파일을 회수한 뒤 메모리 캐시를 비운다 — 리로드된 셰이더는 해시부터 다르므로 '잘못된 PSO를 쓸' 위험은 없고, 문제는 옛 PSO가 메모리만 먹는 것이다. 디스크 라이브러리는 건드리지 않는다(키가 다르니 공존해도 무해하고 되돌릴 때 다시 히트). 회수를 먼저 하는 이유는 옛 바이트코드를 참조하는 백그라운드 작업이 해제된 블롭을 읽을 수 있어서다. 의도적으로 하지 않은 것: 기존 ShaderPSO(이름만 PSO인 DX11 셰이더 묶음)의 개명. 수십 파일을 흔들면서 3-10 원칙('DX11에 새 구조를 만들지 않는다')과 충돌하고, DX11 은퇴와 함께 자연 소멸할 이름이다. 검증 중 관측: run-all이 ui_regression 종료 코드 0xC0000374(힙 손상)로 한 번 실패했으나 단독 4회 재실행과 이어진 run-all 재실행 모두 정상 — DX12 코드는 이 경로에서 실행되지 않으므로 이번 변경과 무관한 기존 종료 크래시 부류이며, 3-3에서 넣은 종료 코드 판정이 그것을 드러내고 있다(별건 작업 이관됨). 4차 슬라이스 — 루트 시그니처 중앙 관리로 PSO 캐시의 구멍을 막았다. PSO 해시에는 루트 시그니처를 포인터로 넣을 수 없어(주소가 실행마다 달라 디스크 캐시의 키가 못 된다) 호출부가 안정된 식별자를 주기로 했는데, 그 값이 손으로 박혀 있었다(자가 검증 코드에 1, 2, 10). 두 패스가 같은 번호를 서로 다른 레이아웃에 붙이면 PSO 캐시가 엉뚱한 파이프라인을 돌려준다 — 증상은 화면이 틀리거나 죽는 것인데 원인이 '캐시 히트'라 재현도 추적도 어렵다. 번호를 사람이 정하는 한 언젠가 반드시 일어난다. DX12RootSignatureCache 신설: 설명(desc)을 해시해 식별자를 유도하므로 같은 레이아웃이면 같은 id, 다른 레이아웃이면 다른 id를 구조가 보장한다. 덤으로 같은 레이아웃을 여러 패스가 쓸 때 객체도 하나로 준다. 해시는 반드시 내용으로 해야 한다 — D3D12_ROOT_SIGNATURE_DESC는 파라미터·정적 샘플러를 포인터로 들고 있어서 구조체를 통째로 바이트 해시하면 주소를 해시하는 꼴이 되고, 같은 레이아웃이 매번 다른 키가 되어 캐시가 통째로 논다(증상은 '왜인지 매번 컴파일한다'로만 보인다). 그래서 파라미터 타입별로 union 안까지 따라 들어가 해시한다. 검증 3종을 PSO 캐시 테스트에 넣었다: ①같은 레이아웃 재요청 → 같은 객체·같은 id ②다른 레이아웃 → 다른 id ③같은 내용을 다른 주소에 담아도 같은 id(내용 해시 확인 — 이게 없으면 포인터 해시 실수를 못 잡는다). 실측: 생성 2 · 히트 2 · 보관 2. 자가 검증 코드의 손번호를 전부 유도값으로 교체했고, id가 바뀌면서 기존 디스크 캐시 키가 무효화됐으나 2회차 실행에서 컴파일 0 · 라이브러리 히트 2로 복귀함을 확인했다(캐시 무효화가 설계대로 동작). 회귀 세트 전체 통과. 남은 것: 디스크립터 힙 관리(샘플러 힙 포함) — 지금은 자가 검증이 정적 샘플러와 단발 SRV 힙으로 때우고 있고, 패스 이식(3-6) 전에 프레임 단위 디스크립터 할당자가 필요하다. 업로드 링(3-3)과 같은 '프레임 구간 + BeginFrame 되감기' 패턴을 그대로 쓸 수 있다. 5차 슬라이스 — 디스크립터 힙 관리 완료로 3-4의 완료 기준 충족. DX11은 SRV·샘플러를 슬롯에 그냥 꽂았지만 DX12는 힙에 디스크립터를 만들어 테이블로 넘기고, 제약이 둘이다: 셰이더 가시 힙은 종류별로 한 번에 하나만 바인딩되고(패스마다 힙을 만들면 경계마다 교체가 일어나 비싸다), GPU가 다 읽기 전에 덮으면 안 된다. 두 문제의 성격이 달라 자료구조를 둘로 나눴다. ① DX12DescriptorRing — 프레임마다 바뀌는 CBV/SRV/UAV. 큰 힙 하나를 프레임 구간으로 자르고 BeginFrame이 되감는다(업로드 링과 같은 패턴이라 반납도 구조가 보장한다). 디스크립터 테이블은 연속이어야 하므로 낱개가 아니라 구간 단위로 준다. ② DX12SamplerHeap — 샘플러는 종류가 적고 프레임마다 바뀌지 않으므로 링이 아니라 해시 캐시다. 링으로 돌리면 같은 샘플러를 매 프레임 다시 만드는 꼴이고, 하드웨어 상한이 2048이라 링과 맞지도 않는다. 자가 검증에서 단발 SRV 힙과 정적 샘플러를 실제 링·샘플러 힙으로 교체했다 — 그 결과 쿼드 루트 시그니처가 테이블 2개(SRV·샘플러)로 바뀌었고, 루트 시그니처 캐시가 레이아웃 변화를 id에 반영해 PSO 캐시도 자동으로 새 키를 썼다(4차 슬라이스가 실제로 작동함을 부수적으로 증명). 검증 dx12.descriptorheap 신설: ①핸들 연속성(구간 안 i번째가 increment 간격으로 정확히 떨어지고 다음 할당이 바로 뒤에 붙는가 — 어긋나면 테이블 둘째 원소부터 엉뚱한 리소스를 가리키는데 화면에는 '텍스처 하나만 틀리게' 나온다) ②프레임 구간 분리 ③되감기 ④넘침 거절 ⑤샘플러 중복 제거(같은 설정 → 같은 핸들, 다른 설정 → 다른 핸들). 실측 전부 통과, 샘플러 생성 2 · 히트 1. GPU 도달은 따로 재지 않았다 — RunSelfTest의 픽셀 검증이 이미 링에서 자른 SRV와 샘플러 힙을 거쳐 체커보드 색을 대조하므로 그것이 종단 증명이고, 링 교체 후에도 통과했다. 자가 검증 4종(selftest·psocache·uploadring·descriptorheap) 전부 통과, 회귀 세트 전체 통과.

EnhancedRenderPass 신규 작성 (성능 목표)

설계 방향

★ 방향 정정(2026-08-01): 기존 DX11 패스를 재활용·이식하지 않는다. EnhancedRenderPass를 새로 쓰되, 기존 패스보다 빠른 것을 목표로 삼는다. 기존 패스는 코드의 출처가 아니라 결과의 기준선이다 — 같은 씬에서 같은 그림이 나오는지 대조하는 정답지로만 쓴다. <br><br>재활용하지 않는 이유: DX11 패스는 드라이버가 대신 해 주던 것(리소스 상태 추적, 바인딩 검증, 드로우 병합)을 전제로 짜여 있다. 그걸 그대로 옮기면 DX12에서는 배리어와 디스크립터를 손으로 붙인 DX11 코드가 되고, DX12로 옮긴 이유였던 이득이 사라진다. 실제로 3-2 실측이 그 이득이 어디 있는지 알려 준다 — 커맨드 실행(CE) 단계가 95% 프레임의 마지막 도착자이고 게임·커맨드빌드는 그 뒤에서 논다. 병목은 CE 하나다. <br><br>그래서 EnhancedRenderPass의 설계 기준은 CE 단계를 줄이는 것이다: ① 커맨드 기록 병렬화 — 패스별 커맨드 리스트를 워커가 동시에 기록하고 제출만 CE가 한다 ② 배리어를 그래프가 유도해 일괄 삽입 — 호출마다 붙이는 배리어는 파이프라인을 끊는다 ③ 상태 변경 최소화 — PSO·루트 시그니처·디스크립터 힙 교체를 정렬로 묶는다(3-4의 캐시들이 그 재료다) ④ 드로우 병합·인스턴싱 — DX11 패스는 프록시마다 드로우를 낸다 ⑤ transient 리소스 힙 앨리어싱(3-5) — 메모리와 캐시 지역성 ⑥ 컬링·라이트 분류를 컴퓨트로 — CPU에서 하던 것을 GPU로 옮겨 CE의 CPU 부담을 던다. <br><br>작성 순서는 의존성을 따른다: GBuffer → Deferred(라이팅) → Shadow → Forward → SSAO/SSGI → 포스트체인 → UI/스프라이트 → Gizmo(에디터). 각 패스는 그래프 노드 선언 + RHI 커맨드 기록으로 쓰고 전역 DeviceStates 접근을 만들지 않는다. 파티클/이펙트 컴퓨트(구 3-7 EffectManager 동시성 문제 포함)도 여기서 스냅샷 모델로 새로 쓴다. <br><br>검증은 둘을 함께 본다. ⓐ 정확성 — 같은 씬을 DX11/DX12로 렌더해 패스 출력을 픽셀 대조한다. DX12 결과를 DX11 SRV로 열어 되읽는 경로가 3-3에서 이미 뚫렸으므로(dx12.sharedtexture) 그것을 그대로 쓴다. ⓑ 성능 — 패스마다 GPU 타임스탬프와 CE 단계 시간을 재고, DX11 대비 개선이 없으면 그 패스는 다시 설계한다. "일단 돌게 만들고 나중에 최적화"로 가면 나중은 오지 않는다 — 패스 단위로 판정한다. 중간 체크포인트: GBuffer+Deferred가 도는 시점, 포스트체인까지 도는 시점. <br><br>⑦ 비동기 컴퓨트(async compute) — 언리얼 RDG가 하는 것을 참고해 넣는다. RDG는 패스를 재정렬하지 않지만 AsyncCompute로 표시된 패스는 의존성을 보고 fork/join 지점을 계산해 별도 큐로 보낸다. 선형 순서를 뒤집는 것이 아니라 겹치는 것이다. 3-2 실측이 이것을 가리킨다 — 병목이 커맨드 실행(CE) 단계 하나이므로, 그래픽 큐가 붐빌 때 그림자 준비·SSAO·라이트 컬링 같은 것을 컴퓨트 큐로 넘겨 겹치면 그 단계가 직접 짧아진다. 필요한 것: 별도 컴퓨트 큐와 큐 간 펜스, 그래프의 패스 플래그(Graphics/AsyncCompute)와 fork/join 유도, 큐를 넘나드는 리소스의 상태 전이 규칙(COMMON 경유). 주의: 겹치기가 항상 이득은 아니다 — 두 큐가 같은 SM을 나눠 쓰므로 그래픽이 이미 GPU를 채우고 있으면 오히려 느려진다. 패스별로 재서 판정한다(3-6의 성능 판정 기준을 그대로 적용). 구현 순서는 뒤쪽이다: 패스가 몇 개 돌아 GPU 타임라인이 보이기 시작해야 어느 것을 겹칠지 판단할 수 있다.
