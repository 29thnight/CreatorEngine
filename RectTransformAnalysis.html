RectTransform 구조 분석 & uGUI 수준 도달 계획

작성 기준: kApiVersion 17 · 검증 도구: RectLayoutProbe(C#) + CLI 무인 실행 · 관련: RefactoringPlanDashboard PHASE 6(UI 소유권) 후속
결론: 의심이 맞다 — 현재 UI 레이아웃은 저작 시점 해상도(1920×1080)에 고정되어 있다.
세 겹의 증거가 겹친다. ① 최상위 캔버스는 프레임 레이아웃 드라이버가 구조적으로 건너뛰어 worldRect가 영영 재계산되지 않고, ② 파생값인 m_worldRect가 프리팹/씬에 직렬화되어 저작 해상도가 파일에 구워지며, ③ 창 크기 변경 경로(OnResize)에 UI 재배치가 존재하지 않는다. 셋 다 정적 분석으로 짚고 런타임 테스트로 재현했다. 1920×1080이 아닌 어떤 해상도에서도 UI는 저작 당시 픽셀 좌표에 그대로 남는다.

2정적 분석 발견 사항

#발견위치심각도
F-1최상위 캔버스 리레이아웃 부재. 프레임 드라이버(UpdateModelRecursive/UpdateUIRecursive의 UI 분기)는 부모의 RectTransform을 요구하고 없으면 return한다. 캔버스의 부모는 씬 루트(RectTransform 없음)이므로 캔버스의 UpdateLayout은 어떤 경로로도 불리지 않는다. worldRect는 로드 시점 값으로 동결.Scene.cpp:1680-1692, 1748-1762P0
F-2파생값 직렬화. m_worldRect가 [[Property]]로 파일에 저장된다. 저작 해상도가 데이터에 구워지고, F-1 때문에 로드 후 교정 기회도 없다. 원점 규약마저 파일마다 다르다(중심 원점 -960,-540 vs 좌상단 0,0 — 실제 프리팹에서 두 형태 공존 확인).RectTransformComponent.h:76-77, 프리팹 10여 개P0
F-3해상도 변경 대응 부재. OnResize 경로는 스왑체인·카메라만 재구성하고 UI는 건드리지 않는다. MakeCanvas는 생성 순간의 DirectX11::GetWidth/Height로 크기를 박제한다. g_ClientRect 폴백은 Get/Set 좌표 변환에만 쓰여 드라이버와 기준이 불일치한다.Dx11Main.cpp:249-, UIManager.cpp:33-39, RectTransformComponent.cpp:70-73P0
F-4CanvasScaler 부재. 기준 해상도·스케일 정책(ScaleWithScreenSize/ConstantPixel/match 계수)이라는 개념 자체가 없다. F-1~3을 고쳐 "현재 화면 크기 추종"이 되어도, 1920×1080 기준으로 저작된 픽셀 값들은 다른 화면비에서 비례 축소되지 않는다.(해당 구조 없음)P1
F-5좌표 규약 혼선. 헤더 주석은 피벗 (0,0)=좌측 하단(y-up)이라 하는데, AnchorPreset은 Top이 y=0(y-down·화면 좌표)이다. 프리팹 데이터의 원점도 두 규약이 공존한다(F-2). 코드·주석·데이터 삼자가 서로 다른 규약을 말한다.RectTransformComponent.h:71-73 vs .cpp:167-183P1
F-6Stretch 프리셋 복붙 버그. StretchLeft/Center/Right가 전부 동일한 앵커를 설정하고(주석에도 "Middle과 동일"), StretchTop/Middle/Bottom도 마찬가지다. 9종 스트레치 중 실질 3종만 존재한다.RectTransformComponent.cpp:186-196P2
F-7레이아웃 크기가 텍스처 픽셀에 종속. ImageComponent::Awake가 rect->SetSizeDelta(uiinfo.size)로 저작된 크기를 텍스처 픽셀 크기로 덮어쓴다. 텍스처가 없으면 0×0이 된다 — 런타임 테스트에서 QuestBg의 worldRect가 (172, 101, 0, 0)으로 실증. uGUI의 SetNativeSize(명시적 호출)에 해당하는 동작이 암묵 기본값이 된 형태.ImageComponent.cpp:96-112P1
F-8렌더 위치 계산식 의심. pos = worldRect.x + width * 2 * pivot.x — ×2 계수의 근거가 불명. 피벗 0.5일 때 x+width(우측 끝)가 나온다. origin(텍스처 중심)과 상쇄되는 보정일 가능성이 있으나, 상쇄에 의존한 식은 worldRect 의미를 바꾸는 순간 깨진다.ImageComponent.cpp:101-105P2
F-9레이아웃 순회 삼중화. 같은 UI 갱신 로직이 UpdateModelRecursive와 UpdateUIRecursive에 복제돼 있고, UpdateLayout 내부에도 자식 재귀가 또 있다(thread_local visited 가드로 순환만 막음). 순회 소유권이 불명확해 갱신 순서·횟수를 추론하기 어렵다.Scene.cpp:1661-/1734-, RectTransformComponent.cpp:141-160P2
F-10dirty 전파 불완전. 자식의 재계산은 "부모의 UpdateLayout이 돌 때" 전파되는 구조인데, F-1로 최상위가 돌지 않으니 화면 크기 기반의 전파 사슬 전체가 시동조차 걸리지 않는다. 부모 rect만 변한 경우(자식 dirty 아님) 자식이 낡은 값을 유지하는 설계이기도 하다.RectTransformComponent.cpp:115-160P1

3런타임 검증 (RectLayoutProbe)

실제 게임 프리팹 Canvas.prefab을 소환하고 C# 바인딩(RectTransform.WorldRect, 이번 분석을 위해 추가)으로 계산 결과를 직접 읽었다. 무인 CLI 실행, 종료 코드 0.

[RectLayoutProbe] 30프레임 후 캔버스 worldRect (-960, -540, 1920, 1080)
[RectLayoutProbe] H2 — 캔버스 worldRect 재계산: 안 됨 (드라이버가 최상위를 건너뜀)

H1 확정 — 캔버스 worldRect가 파일에 저장된 값 그대로다(중심 원점 −960,−540). 현재 화면과 대조·재계산되지 않는다. (F-1+F-2)
H2 확정 — SizeDelta를 960×540으로 바꿔도 30프레임 뒤 worldRect는 1920×1080 그대로. 최상위는 드라이버 사각지대다. (F-1)
H3 확정 — 자식도 전혀 반응하지 않는다. 화면 크기→캔버스→자식으로 내려가는 전파 사슬이 존재하지 않는다. (F-10)
보너스 — QuestBg의 크기 0×0: 텍스처 미로드 상태에서 Awake가 SizeDelta를 0으로 덮어쓴 결과. (F-7 실증)

5uGUI 수준 도달 계획 (PHASE 7 제안 · 총 14.5일)

전략: "해상도에서 자유로워지는 것"이 목표의 전부다. 순서가 중요하다 — 파생값 직렬화(F-2)를 끊고 루트 리핏(F-1·F-3)을 만들면 화면 추종이 되고, 그 위에 CanvasScaler(F-4)를 얹으면 비례 스케일이 된다. 기존 콘텐츠는 기준 해상도를 1920×1080으로 선언하는 것만으로 무수정 호환된다(현재 데이터가 이미 그 기준으로 저작돼 있으므로). 레이아웃 그룹 같은 확장은 이 기반이 선 뒤의 별개 단계다.
ID작업내용우선공수
7-1캔버스 루트 리핏최상위 캔버스의 worldRect를 화면 rect(g_ClientRect)로 매 프레임 갱신하는 루트 드라이버 추가 — F-1의 사각지대 제거. 화면 크기가 변하면 캔버스 dirty → 기존 전파 사슬(F-10)이 자동 시동. OnResize 이벤트에서 전체 dirty 마킹. Get/Set 변환(ResolveParentRect)과 드라이버의 기준 통일.P02일
7-2파생값 직렬화 제거m_worldRect를 저장 대상에서 제외하고 로드 시 항상 재계산. 기존 파일의 worldRect 필드는 로드 때 무시(하위 호환 — 파일 수정 불필요). 원점 규약을 좌상단·y-down으로 확정하고 헤더 주석·프리셋·문서 일치화(F-5), Stretch 프리셋 9종 복원(F-6).P02일
7-3CanvasScalerCanvas에 기준 해상도(기본 1920×1080)와 모드(ConstantPixel / ScaleWithScreenSize+match) 추가. 루트 리핏이 화면 rect 대신 "기준 해상도 rect × 스케일"을 공급하는 구조라 7-1 위에 얇게 얹힌다. 폰트 크기·보더에도 동일 스케일 적용. 기존 씬은 기본값으로 현행 유지.P13일
7-4SizeDelta-텍스처 분리ImageComponent::Awake의 SizeDelta 덮어쓰기 제거(F-7). 명시적 SetNativeSize()로 대체하고 C# 바인딩 추가. 텍스처 미로드 시 0×0 붕괴 소멸. 기존 씬에서 "텍스처 크기에 의존하던 이미지"는 로드 시 1회 보정 옵션 제공.P11일
7-5레이아웃 순회 일원화UpdateModelRecursive/UpdateUIRecursive의 중복 UI 분기를 단일 캔버스-루트 패스로 통합(F-9). UpdateLayout 내부 자식 재귀와 thread_local visited 가드 제거 — 순회는 드라이버가, 계산은 컴포넌트가. dirty 규칙 명문화: 부모 rect 변경 시 자식 dirty(F-10).P12일
7-6렌더 좌표식 정리pos의 ×2 계수(F-8)를 worldRect 의미 기준으로 재유도하고 프록시 3종(Image/Text/Sprite)과 버튼 히트 테스트의 좌표 규약을 하나로. 7-1~3 이후 실제 화면에서 픽셀 검증.P21.5일
7-7검증 자동화CLI에 window.resize <w> <h> 추가. RectLayoutProbe를 역방향 단정으로 전환(H1~H3이 이번엔 "반응함"이어야 통과)하고 1280×720/2560×1440/21:9 스위프를 회귀 세트에 편입.P11일
7-8(확장) 레이아웃 그룹Horizontal/Vertical/Grid 레이아웃 그룹 + ContentSizeFitter. 자동 배치가 필요해질 때(인벤토리·목록 UI) 착수 — 기반(7-1~5) 완성이 선행 조건.P22일+

완료 기준

  • 1280×720 / 1920×1080 / 2560×1440 / 21:9에서 동일 씬의 UI가 앵커 의도대로 배치·스케일됨 (스크린샷 대조)
  • 실행 중 창 크기 변경 시 1프레임 내 전체 UI 리플로우
  • RectLayoutProbe 역방향 단정 전체 통과 + 해상도 스위프 회귀 편입
  • 기존 씬·프리팹 무수정 로드, 1920×1080에서 픽셀 동일(회귀 없음)
  • worldRect가 파일에서 사라지고(신규 저장 기준) 로드 경로가 이를 무시함

리스크

  • F-8 상쇄 의존 — 렌더 좌표식이 worldRect의 현재(잘못된) 의미에 맞춰져 있을 수 있어, 7-1 적용 순간 기존 화면이 틀어질 수 있다. 7-6을 7-1과 같은 브랜치에서 함께 검증할 것.
  • 중심 원점 프리팹 — 원점 규약 확정(7-2) 시 −960,−540형 데이터는 로드 무시로 자연 해소되지만, anchoredPosition에 원점 가정이 스며든 콘텐츠가 있는지 대표 프리팹 4종(HPCanvas·UI_CanvasesIngame·SettingCanvas·SceneTransitionCanvas)으로 선검증.
  • 에디터 game view — 백버퍼와 game view 크기가 다른 에디터 환경에서 입력 스케일(CheckClick)과 렌더 스케일의 일치를 7-7 스위프에 포함.
