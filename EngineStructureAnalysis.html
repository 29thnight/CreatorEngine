01프로젝트 개요

CreatorEngine은 게임 "Kori: The Spritail" 개발을 위해 제작된 인하우스 게임 엔진으로, Windows(WinAPI) 위에서 DirectX 11(feature level 11.1/11.3) 렌더러와 C++20 모듈형 런타임을 기반으로 실시간 에디터, 런타임 게임 빌드 파이프라인, 그리고 C++ 스크립트 핫리로드를 제공합니다.

전체 구조는 Unity의 개념 모델(GameObject–Component, MonoBehaviour 라이프사이클, Assembly-CSharp, .meta 파일, ShaderLab 유사 DSL)을 네이티브 C++로 재해석한 형태이며, 코드 생성 도구(Unreal Header Tool 유사)를 통한 리플렉션 자동화가 아키텍처의 핵심 축을 이룹니다.

02솔루션 및 모듈 구성

솔루션은 두 개로 나뉘며, 동일한 엔진 모듈 집합 위에서 에디터 실행 파일과 게임 배포 실행 파일이 갈라지는 구조입니다.

  • CreatorEngine.sln — 에디터 빌드. 시작 프로젝트는 Academy_4Q("Creator Editor" 창 타이틀).
  • GameBuild.sln — 게임 배포 빌드. 시작 프로젝트는 TrainAsis("Kori: the Spritail"). GameBuild|x64 전용 구성 보유.
주목할 점: EngineEntry / EngineGUIWindow는 별도 프로젝트가 아님

EngineEntry(진입점·부트스트랩)와 EngineGUIWindow(에디터 윈도우) 폴더의 소스는 독립 vcxproj 없이 Academy_4Q.vcxproj에 직접 포함됩니다. 즉 Academy_4Q가 곧 "에디터 = EngineEntry + EngineGUIWindow + 엔진 라이브러리 링크"의 실체입니다.

03모듈 의존 그래프

모듈 의존 그래프 — 실선: 정적 링크/프로젝트 참조, 점선: 빌드 산출물(.lib) 직접 링크 후 런타임 DLL 핫로드
구조적 특이점: RenderEngine ↔ ScriptBinder 양방향 커플링

RenderEngine은 ScriptBinder를 프로젝트 참조하고(렌더 프록시가 GameObject.h 등을 include), ScriptBinder는 반대로 RenderEngine 헤더를 include 경로로 사용합니다. 링크는 단방향이지만 include 수준에서는 상호 의존이며, 모듈 경계가 개념(렌더 vs 게임플레이)만큼 물리적으로 분리되어 있지는 않습니다.

04렌더링 엔진 (RenderEngine)

246개 파일, 약 51,000줄 규모의 DirectX 11 디퍼드+포워드 하이브리드 렌더러입니다. DX12 심볼은 존재하지 않으며, D3D11의 지연 컨텍스트(deferred context)와 ID3D11CommandList를 활용한 멀티스레드 커맨드 리스트 생성이 핵심 설계입니다.

4.1 프레임 파이프라인

오케스트레이터는 SceneRenderer이며, 모든 패스는 추상 클래스 IRenderPass를 상속합니다. 각 패스는 카메라별(최대 10) × 프레임별(트리플 버퍼링, 3) 커맨드 리스트 큐를 보유하고, 스레드풀에서 병렬 기록 후 메인 스레드에서 실행합니다. 카메라마다 실행되는 실제 패스 순서:

ShadowMapPass GBufferPass LightMapPass DecalPass SSAOPass DeferredPass SSGIPass TerrainGizmoPass SkyBoxPass ForwardPass EffectPass (파티클) SubsurfaceScatteringPass ScreenSpaceReflectionPass VolumetricFogPass PostProcessingPass (Bloom) BitMaskPass AAPass ToneMapPass VignettePass ColorGradingPass SpritePass UIPass BlitPass

이 밖에 에디터 전용 GizmoPass/GridPass/WireFramePass/PositionMapPass 등을 포함해 IRenderPass 파생 구체 클래스는 약 28개입니다.

RenderGraphBuilder — 개발 중, 미사용

RenderGraphBuilder.h에 텍스처/패스 의존성 그래프 기반 자동 관리 시스템의 골격(RGTextureHandle, PassBuilder)이 존재하지만, 실제 프레임 루프는 위와 같이 하드코딩된 순차 호출 방식입니다. 렌더 그래프 전환을 시도 중인 단계로 보입니다.

4.2 게임 스레드 ↔ 렌더 스레드 분리: 프록시 아키텍처

GameObject/Component/Scene은 RenderEngine이 아닌 ScriptBinder에 정의되어 있고, RenderEngine은 그로부터 파생된 렌더 프록시(스냅샷)만 소비합니다.

  • RenderScene — 씬의 렌더 상태 스냅샷. ProxyMap, UIProxyMap, AnimatorMap, 카메라별 RenderDataMap 보유.
  • MeshRenderer·TerrainComponent·SpriteRenderer·DecalComponent 등 게임 스레드 컴포넌트가 ProxyCommand(Register/Update/Unregister)를 ProxyCommandQueue에 큐잉 → 렌더 스레드가 소비하는 커맨드 패턴.
  • 프록시 종류: PrimitiveRenderProxy(메시/폴리지/터레인/데칼/스프라이트), UIRenderProxy, EffectRenderProxy.

4.3 셰이더 시스템

  • ShaderResourceSystem — VS/HS/DS/GS/PS/CS 6종 캐싱, HLSL include 변경 감지 리로드(HLSLIncludeReloadShaders).
  • PipelineStateObject(PSO.h) — D3D11에 없는 PSO 개념을 소프트웨어로 묶은 래퍼 (셰이더 6단계 + 상태 객체 + 토폴로지 → Apply()).
  • ShaderDSL — Unity ShaderLab 유사 커스텀 텍스트 DSL 파서. Shader "Name" { VS/PS…, keywords, queueTag } 형태를 ShaderAssetDesc로 파싱.
  • VisualShaderDSL/VisualShaderPSO — 노드 기반 비주얼 셰이더 트랙 별도 존재.
  • Material은 CBuffer 리플렉션 메타데이터(CBEntry/VariableDesc)를 통해 TrySetFloat/Vector… 등 이름 기반 파라미터 조작 지원.

4.4 에셋 / 리소스 관리

  • DataSystem(싱글턴) — Models/Materials/Textures/SpriteSheets/Fonts를 FileGuid 기반으로 로딩·캐싱. ImGui 콘텐츠 브라우저 내장(에디터 강결합).
  • AssetBundle/AssetEntry — retain 집합 기반 번들 로딩·언로드(UnloadUnusedAssets). 단, 언로드 함수는 실제로 호출되지 않음 — 12장 참조.
  • AssetLoadJob + 자체 ThreadPool — 비동기 에셋 로딩.
  • AssetMetaRegistry + efsw 파일 감시 — Unity 스타일 .meta(YAML) 자동 생성/관리.
  • Mesh는 LOD 시스템(GenerateLODs/SelectLOD) 내장, meshoptimizer로 최적화. Model은 Assimp 임포트.

4.5 애니메이션 & 파티클

스켈레탈 애니메이션

  • Skeleton/Bone 계층 트리, BoneRegion 분류, Socket 부착, MAX_BONES=512
  • Animation — 본별 키프레임 + KeyFrameEvent(스크립트 콜백 연동)
  • AnimationJob — 멀티스레드 본 업데이트/블렌딩, GPU 스키닝용 본 팔레트 관리
  • Animator 컴포넌트·상태머신(FSM)은 ScriptBinder 측 AnimationController에 위치

GPU 파티클 / 이펙트

  • ParticleSystem — 컴퓨트 셰이더 + 더블 버퍼링(UAV/SRV)
  • 모듈 체인: Spawn/Movement/Color/Size/Life/Trail *ModuleCS (인트루시브 링크드리스트)
  • 렌더 모듈: BillboardModuleGPU, MeshModuleGPU, Trail Generate/Render
  • EffectManager(IRenderPass) + EffectEditor(에디터 내장 이펙트 편집기)

05물리 엔진 (Physics)

NVIDIA PhysX 5.5.0(vcpkg) 기반이며, GPU 가속을 적극 사용합니다 (PxCudaContextManager 생성 시도 후 실패 시 CPU 폴백, eENABLE_GPU_DYNAMICS + GPU 브로드페이즈). 디버그 빌드에서는 PhysX Visual Debugger(PVD)에 자동 연결됩니다.

5.1 3계층 래퍼 구조

계층위치역할
① SDK 코어 래퍼Physics/Physx.h — PhysicX 싱글턴Foundation/Physics/Scene/ControllerManager 직접 소유. 강체·CCT·래그돌 생성/제거, Raycast/Sweep/Overlap 저수준 API
② ECS 브리지ScriptBinder/PhysicsManagerGameObject↔PxScene 트랜스폼 동기화(SetPhysicData/GetPhysicData), 32×32 충돌 매트릭스, 콜백·지연 변경 큐
③ 컴포넌트RigidBodyComponent, *ColliderComponent, CharacterControllerComponent, RagdollComponent에디터/스크립트에서 다루는 실제 컴포넌트. 리플렉션 매크로로 자동 직렬화·인스펙터 노출

5.2 시뮬레이션 틱 흐름 (PhysicX::Update)

Update(fixedDeltaTime)
 ├ 1. RemoveActors / RemoveControllers   — 대기 중 제거 처리 (simulate 이전이라 안전)
 ├ 2. RigidBody 갱신                     — 신규 액터 PxScene 등록
 ├ 3. CCT 갱신                           — 기존 컨트롤러 Update, 대기 리스트에서 신규 캡슐 컨트롤러 생성
 ├ 4. CollisionData 정리 / Ragdoll 갱신
 ├ 5. m_scene->simulate(fixedDeltaTime)  — 물리 스텝
 ├ 6. m_scene->fetchResults(true)        — 블로킹 대기
 └ 7. m_eventCallback->StartTrigger()    — 트리거 오버랩 이벤트 디스패치

5.3 이벤트 전파 체인

PhysicsEventCallback(PxSimulationEventCallback 구현)이 onContact/onTrigger를 수신하고, std::function 델리게이트 → PhysicsManager::CallbackEvent → 컴포넌트의 OnTriggerEnter/Stay/Exit·OnCollisionEnter/Stay/Exit(ICollider 인터페이스)로 전달되는 구조입니다. 주요 클래스: StaticRigidBody/DynamicRigidBody, CharacterController(넉백 이징 커브 지원), RagdollPhysics(PxArticulationReducedCoordinate 기반), Convex/Triangle/HeightField 쿠킹 리소스.

06스크립팅 및 핫리로드

현재 활성 방식: C++ 스크립트 DLL 핫리로드

Unity처럼 C#을 쓰는 대신, C++로 작성한 스크립트를 별도 DLL(Dynamic_CPP)로 MSBuild 재컴파일 후 LoadLibrary로 즉시 교체하는 네이티브 핫리로드 방식을 사용합니다.

6.1 HotLoadSystem (ScriptBinder 최대 규모 파일, 2,129줄)

  • 파일 타임스탬프 비교(IsScriptUpToDate)로 변경 감지 → 백그라운드 스레드에서 MSBuild 커맨드라인으로 Dynamic_CPP 재빌드.
  • 빌드된 DLL을 LoadLibraryA로 로드, GetProcAddress로 팩토리 함수 바인딩: CreateModuleBehavior(스크립트), CreateBTActionNode·CreateBTConditionNode(비헤이비어 트리), CreateAniBehavior(애니메이션 FSM 행동).
  • ReplaceScriptComponent() — 리로드 후 씬에 존재하는 스크립트 컴포넌트 인스턴스를 새 DLL 클래스로 일괄 교체.
  • 스크립트 베이스는 ModuleBehavior — Unity MonoBehaviour와 동일한 라이프사이클: Awake → OnEnable → Start → FixedUpdate → OnTrigger*/OnCollision* → Update → LateUpdate → OnDisable → OnDestroy.

6.2 Mono/C# 경로 — 설계 완료, 전면 비활성화

Unity 유사 Mono 임베딩 구조(MonoManager, CSharpScriptComponent, icall 바인딩, Assembly-CSharp API 스텁, MonoBleedingEdge 런타임 바이너리)가 전부 존재하지만, EngineEntry/framework.h와 각 헤더의 #define UNUSE_MONO_LIB 매크로로 컴파일에서 완전히 제외되어 있습니다 (README에서도 취소선으로 폐기 명시).

  • 바인딩 설계는 Unity와 동일한 mono_add_internal_call icall 패턴 — "CreatorEngine.GameObject::ICall_Find" 등.
  • C# 측은 [MethodImpl(MethodImplOptions.InternalCall)] extern 선언 (GameObject.cs 등).
  • 루트의 bindings.txt는 C#과 무관한 HLSL 셰이더 리소스 바인딩 표입니다.

07리플렉션 / 코드 생성 파이프라인

Unreal Header Tool과 유사한 빌드 전(pre-build) 오프라인 코드 생성기 2종이 리플렉션·직렬화·인스펙터 노출·팩토리 등록을 자동화합니다.

도구대상산출물
AutoRegisterCreateReflection 엔진 전체 헤더 — [[Serializable(Inheritance:X)]], [[Property]], [[Method]] 어노테이션이 붙은 클래스 클래스별 <Class>.generated.h (Reflect 매크로 블록) + ScriptBinder/RegisterReflect.def (AUTO_REGISTER_CLASS 팩토리 일괄 등록)

08코어 인프라 (Utility_Framework 외)

8.1 동시성 프리미티브 (최근 개선 영역)

최근 커밋 1afe6687("CountingSemaphore 및 ThreadPool 동기화 개선")에서 다듬어진 핵심 구조:

  • ThreadPool<TaskType> — MS PPL concurrent_queue 기반. 워커 수는 GetActiveProcessorCount로 결정, 스레드 어피니티/우선순위/초기화·종료 콜백 지원.
  • CountingSemaphore — acquire()는 32회 스핀 후 커널 세마포어(WaitForSingleObject) 폴백, release(n)은 실제 대기 스레드 수만큼만 ReleaseSemaphore 호출하는 하이브리드 방식.
  • WaitAll 패턴: 태스크 카운트 0→1 전이 시 수동 리셋 이벤트를 리셋, 잔여 0이 되면 SetEvent → NotifyAllAndWait()가 블로킹 대기.
  • 기타: Core.Barrier/Core.Fence/SpinLock/Core.Coroutine(코루틴) 등.

8.2 DLL 경계 싱글턴 — SingletonManager

DLLCore::Singleton<T, shareDLL=true> CRTP 템플릿. typeid(T).hash_code()를 키로 SingletonManager.dll이 export하는 전역 맵에서 인스턴스를 관리해, 엔진 모듈과 핫리로드되는 게임 DLL이 동일한 싱글턴 인스턴스를 공유합니다 (double-checked locking + std::atomic acquire/release). 엔진 전역의 SceneManagers, EngineSettingInstance, Sound 등이 모두 이 위에 구축되어 있습니다 — 핫리로드 아키텍처의 필수 기반입니다.

12렌더링 자원 누수 / 크래시 분석

"렌더링 자원 관리에서 누수로 인한 크래시가 의심된다"는 증상을 전제로, D3D11 COM 수명 관리 · 리소스 캐시/에셋 시스템 · 프록시/이펙트/애니메이션 계층 세 방향에서 코드 레벨 정밀 조사를 수행했습니다. 아래 발견 중 핵심 3건(12.1-①, 12.2-①, 12.3-②)은 소스에서 직접 재검증한 확정 결함이며, 나머지는 조사 에이전트가 파일:라인 근거와 함께 보고한 항목입니다. "가능성" 표기는 코드 결함은 확인됐으나 실제 트리거 경로가 미확정인 경우입니다.

종합 진단: 크래시의 유력한 근본 원인 3가지

① VRAM/RAM 무한 누적 — 씬 전환 시 리소스 언로드 경로(UnloadUnusedAssets)가 어디서도 호출되지 않아 모든 에셋 캐시가 증가만 합니다. 장시간 플레이/씬 반복 전환 → 메모리 고갈 크래시의 전형적 패턴입니다.
② 유즈애프터프리(UAF) — Animator 제거 시 free()된 본 팔레트 버퍼를 스키닝 메시 프록시가 계속 참조하여 렌더 패스가 해제된 메모리를 읽습니다. 릴리스 빌드에서 간헐적·비결정적 크래시로 나타납니다.
③ 무동기화 컨테이너 동시 접근 — 프록시 맵과 에셋 캐시 맵에 대해 락이 일부 경로에만 적용되어 있어, 병렬 로딩/컬링 중 unordered_map 리해시 경합으로 힙 손상 크래시가 발생할 수 있습니다.

12.4 권장 수정 우선순위

  1. [즉시] 12.3-② 본 팔레트 UAF — 재현 조건(Animator 비활성화 + 스키닝 메시 유지)이 게임플레이 중 흔하고 증상이 "간헐적 크래시"와 정확히 일치. UnregisterAnimator 시 해당 애니메이터를 참조하는 프록시들의 m_finalTransforms를 무효화하거나, malloc/원시 포인터 대신 shared_ptr 버퍼 소유권 모델로 교체.
  2. [중기 — 설계 변경 선행 필수] 12.2-① 에셋 소유권 재설계 후 언로드 복구 — 보충 분석에서 확정했듯 현재 구조에서 UnloadUnusedAssets() 호출을 추가하는 것만으로는 사용 중 에셋 파괴(UAF)를 유발함. 올바른 순서: (1) 컴포넌트·Model·프록시의 에셋 참조를 shared_ptr(또는 세대 핸들)로 전환해 "캐시 맵 erase = 참조 해제"가 되도록 소유권 분리 → (2) 런타임 클론(Material::Instantiate)을 retain 대상에 포함하거나 씬 수명에 바인딩 → (3) ManagedAssetType에 UITexture/SpriteSheet 추가 → (4) 그 후에 씬 전환부에서 UnloadUnusedAssets() 활성화. 단기 완화책으로는 소유권 변경 없이 씬 전환 횟수 대비 메모리 상한 모니터링과 명시적 재시작 유도가 현실적.
  3. [즉시] 12.1-①② 상태 객체 Release — RenderModules 6곳 재생성 전 Release 추가(또는 ComPtr 전환), PipelineStateObject의 소유/비소유 포인터 분리.
  4. [단기] 락 일원화 — ProxyCommand 생성자·Register/UnregisterAnimator에 RenderScene과 동일한 SpinLock 적용, DataSystem 캐시 맵별 뮤텍스 규약 통일(특히 LoadSharedTexture/LoadMaterial/SFonts).
  5. [단기] 카메라 수명 정리 — 예측 인덱스 제거(등록을 RegisterContainer 이후로 이동), AddCamera 만석 시 명시적 실패 처리, 카메라 삭제 시 패스별 커맨드 큐 flush.
  6. [중기] 진단 인프라 — 디버그 빌드에 ID3D11Debug::ReportLiveDeviceObjects 주기 리포트와 D3D11_CREATE_DEVICE_DEBUG 브레이크를 추가해 위 수정들의 효과를 정량 검증. Address Sanitizer(MSVC /fsanitize=address)로 UAF 재현 확인.

강점

1. 일관된 자동화 파이프라인 (어노테이션 → 코드젠 → 직렬화/에디터/팩토리)

C++ 속성 어노테이션 하나로 YAML 직렬화, ImGui 인스펙터, 팩토리 등록이 모두 파생되는 체인은 UHT 스타일의 성숙한 설계이며, 엔진 컴포넌트와 게임 스크립트 양쪽에 동일 패턴이 적용되어 일관성이 높습니다.

2. 실용적인 네이티브 핫리로드

Mono/C# 경로를 폐기하는 대신 "MSBuild 재빌드 + DLL 교체 + 인스턴스 마이그레이션 + DLL 경계 싱글턴 공유"라는 현실적 조합으로 C++ 스크립트의 반복 개발 속도 문제를 해결했습니다. BT 노드·애니메이션 FSM까지 동일 메커니즘으로 핫리로드되는 점이 완성도 있습니다.

3. 멀티스레드 렌더링 구조

게임/렌더 스레드 분리(프록시 커맨드 큐), 트리플 버퍼링, 지연 컨텍스트 병렬 커맨드 리스트 기록, 배포 빌드의 빌드/실행 스레드 분리까지 D3D11에서 가능한 멀티스레딩 패턴을 폭넓게 활용하고 있습니다.

리스크 및 개선 여지

0. 렌더링 자원 수명 관리 결함 (크래시 유발)

씬 전환 시 에셋 언로드 미동작(언바운드 VRAM 누적), 본 팔레트 UAF, 프록시 맵 무동기화 접근, D3D11 상태 객체 누수 등 CRITICAL 등급 결함 다수가 확인되었습니다. 상세 근거와 수정 우선순위는 12장 참조.

1. 모듈 간 커플링

RenderEngine ↔ ScriptBinder의 include 수준 양방향 의존, DataSystem에 내장된 콘텐츠 브라우저(리소스 관리 + 에디터 UI 혼재) 등 개념적 경계와 물리적 경계가 어긋난 지점이 있습니다. 렌더 프록시 계층이 이미 존재하므로 인터페이스 분리로 정리할 여지가 큽니다.

2. 빌드/테스트 CI 부재

CI는 버전 파일 갱신뿐이며 컴파일 검증·테스트가 없습니다. 핫리로드가 MSBuild에 의존하는 구조 특성상, 엔진 헤더 변경이 Dynamic_CPP 빌드를 깨뜨리는 회귀를 자동으로 잡을 수단이 없습니다.

3. 데드 코드 및 과도기 상태

Mono 스크립팅 전체(Managed/MonoBleedingEdge/Assembly-CSharp/바인딩 코드)가 비활성 상태로 저장소에 남아 있고, RenderGraphBuilder는 미완·미사용입니다. 방향이 확정되었다면 Mono 관련 자산 제거로 저장소·빌드 표면을 줄일 수 있습니다.

4. 단일 평면 디렉터리 구조

RenderEngine(246파일)·ScriptBinder(235파일)가 하위 폴더 없는 평면 구조라 탐색성이 떨어집니다. 패스/리소스/애니메이션/파티클 등 이미 뚜렷한 서브도메인별 폴더 분리가 유효합니다.
